## Proposed clauses (not semantic proofs)

- selfhost.revision [proposed]: A snapshot is identified by exact book, requirements, protobuf, implementation, and repository revisions. Changes invalidate affected checks and derived artifacts; stale requests fail without overwriting current state.
- selfhost.gates [implemented]: Review and acceptance are git commits made by the user; LeanFM records no approvals and never blocks an edit, source write or launch on one. Code generation requires the current snapshot's requirements and implementation mapping to pass their canonical checks. Project status reports whether each is checked and committed.
- selfhost.project.implementations [implemented]: A project may carry several implementations of one specification, so the same requirements can be implemented in different languages and the implementations compared. manifest.json lists them as implementations: [{name, implementation, source}] with default_implementation naming one of them; a project without that list has one implementation, default, in spec/Implementation.lean with the manifest's source directory, exactly as before. Always: the specification check (scripts/chatui_specification.py, make spec-check in a project) validates the requirements once and derives spec/tasks.json from them alone, then compiles each implementation in the same sandbox and validates it against the same RequirementSpec in a driver of its own (so implementations may share a namespace), the default first; each listed implementation's outputDirectory must be its manifest source; reports/specification-check/validation.json records default_implementation and, per implementation, its file, source, module, target, status (validated, invalid or does_not_compile) and errors, and the digests of every implementation file; the default implementation failing fails the check and promotes nothing, while another implementation failing is recorded and the check still succeeds, so a port in progress never blocks the specification or its views. Never: a name that is not [a-z][a-z0-9_]* (at most 32 characters), more than 8 implementations, two implementations sharing a name or a file, an implementation path or source outside the project root, through a symlink, or whose path components are not Lean identifiers; a default_implementation that is not listed; an implementation compiled outside the sandbox the requirements use; an implementation's text changing spec/tasks.json.
- selfhost.pr [proposed]: PR delivery requires an actual patch, requirement-to-code/test mappings, reproducible check results, base revision, and remaining limitations. The PR may be delivered as a local reviewable bundle; remote publication requires explicit authority. Failed checks cannot be labeled completed.
- selfhost.checker [proposed]: Check results distinguish proved, disproved, unknown, unsupported, and resource-limit reached. Identify model revision, formula, assumptions, bounds, terminal-path convention, fairness, and witness or counterexample. Schema validation is not a semantic proof.
- selfhost.formulas [proposed]: Requirements must support typed nested CTL state formulas and separately typed path conditions. AF AG p is eventual permanent safety; AG AF p is universal recurrence. Preserve existential counterexample duals without claiming CTL covers all LTL.
- selfhost.modal [proposed]: Knowledge quantifies over legal histories with identical declared actor observations. Obligation and permission quantify over all and some nonempty named ideal policy futures. Never conflate legal, observable, ideal, and probabilistic alternatives. Belief and morality are outside this extension.
- selfhost.lazy [proposed]: Retain modality-specific indexes only while current formulas reference the corresponding actor or policy relation. Rebuild them from retained source evidence; release unreferenced indexes. Index lifetimes must not alter truth. Isolate caches by project and model revision.
- selfhost.probability [proposed]: Probabilities are optional and distinct from existence. Identify declared model probability versus observed frequency versus unknown. Specify normalization, conditioning, scheduler or min/max policy, horizon, threshold comparison, and sample boundary. Do not infer independence or treat unknown as zero.
- selfhost.history [proposed]: Immutable events carry predecessor links; derived successor indexes preserve event identity and partial order. State whether a past monitor uses causal ancestry or a declared linearization. Strictly prior facts exclude the current event.
- selfhost.coverage [proposed]: Every normative book claim is linked to an accepted requirement, an explicitly pending proposal, or a deferred/illustrative classification. Every accepted requirement maps to implementation decisions and evidence; unmapped claims prevent a claim of complete one-shot readiness.
- selfhost.handoff [proposed]: A new session starts from book/main.pdf, book/main-dark.pdf, canonical requirements/protobuf/implementation, component registry, current repository, and generated review report. Application goals also retain spec/ProjectMemory.md, spec/runtime.json, revision-bound actual-launch evidence, failure remedies and PR/base-revision context. Conversation history is not required input.
- selfhost.bounds [proposed]: Declare finite exploration and resource bounds. Exhaustion yields resource-limit or unknown, never proved. Compaction must preserve the declared observation and monitor semantics.
- selfhost.session.syntax [implemented]: A protocol is written in Lean with the protocol notation of LeanFM.Session and elaborates to a value of Global R for any role type R, so it can be instantiated with another protocol's roles. Statements: a message (optional name, label, sender, receiver, optional cause naming an earlier message, optional route naming the operation a request invokes such as POST /orders, optional status a response carries such as 402, optional where clause); an event at one role; choice with or-branches; parallel with and-branches; join k of branches; loop with continue in tail position; sessions; include of another protocol. Always: a label is a Lean type (one no structure declares is a structure that carries nothing, as the text reading treats it, so a misspelt label shows as a message of its own in every view, and a condition reading its fields is an error), and a where clause is a condition over the payloads of the messages named so far, type-checked as a Lean proposition when the protocol is written and run over the logged fields by LeanFM's interpreter when a trace is checked (selfhost.session.lean-syntax). Never: repetition other than continue at the end of a branch (the state space stays finite); a route or status changing any check's verdict (they are for people and generated views).
- selfhost.session.choice [implemented]: A choice names no decider. Always: the decider is the one role that starts every branch, by sending its first message or by an event at that role alone; an empty branch is that role choosing to do nothing. Never: a choice whose branches are started by different roles accepted (it is reported as a race naming who starts what); two branches that start with the same event; a choice none of whose branches does anything.
- selfhost.session.causes [implemented]: A message's cause names an earlier message it answers. Never: a cause that its sender has neither sent nor received (a role decides only from its own history); it is reported.
- selfhost.session.projection [implemented]: Projection gives each role its local type: the protocol with every message the role neither sends nor receives erased, its own choices as select and other roles' choices as offer; a role that takes part only in nested sessions blocks is a service (a text-message gateway, a mailer) whose local type serves those sessions, sessions { ... }, without being projected through the enclosing session's choices, and a service of several kinds of session tells them apart by their first messages (as an offer) or is reported; a join k of as join k of over the role's own branches (parallel when it takes part in no more than k of them), resolved by what arrives. Always: a role that does not decide a choice can tell its branches apart when the first messages it can receive in them differ, looking inside parallel; a role whose part of the session has not started (its first message has not reached it) may be absent from a branch that never contacts it, and the body of sessions is projected as not started. Never: a role that has already taken part left out of a branch, or unable to tell branches apart; projection fails with the reason (Role cannot tell which branch Decider chose).
- selfhost.session.composition [implemented]: Protocols compose. Always: include runs another protocol with the given roles and the rest continues where it finishes, each protocol written as if it were the whole; parallel runs branches interleaved, each keeping its order; join k of continues after any k branches, recording which ones; sessions runs any number of independent copies of its body. Never: an unselected join branch canceled implicitly (cancellation is an explicit message).
- selfhost.session.http [implemented]: The HTTP call discipline is optional and applies to channels declared HTTP (session_check: every channel once mayCall is given, except those between the roles of a notHttp pair). Always: every message on an HTTP channel is a request to a role the sender may call, or the response to the nearest pending request in its cause chain, sent back to the role that asked; a streaming response may answer more than once; every request gets a response before a run reaches the end of the protocol (a run that goes round a loop again has not ended). Never: a response sent to a role other than the caller, a request to a role the sender may not call, or a request left without any response accepted; each is reported as a cut naming the message.
- selfhost.session.physics [implemented]: Channel physics is declared beside the protocol. Always: a channel has a capacity, a full policy (block, reject, drop newest or drop oldest), sequencing, sharding, loss and duplication; presets (reliable, udp, stream, http, kafka) name common channels and a declaration states only what differs; every channel defaults to reliable; a spec states which surfaced conditions each channel's protocol handles, its properties and its assumptions. Never: a condition a used channel surfaces (timeout, duplicate, reject, loss, reorder, per-key order, partition, hostile, readable, close) left unhandled without being reported.
- selfhost.session.topology [implemented]: A deployment tree places actors in islands, datacenters, machines and replicated or sharded groups, and gives them interfaces with a scope and a kind. Always: an interface is named by its path (island, actor, scope, interface); ingress is reachable from anyone, peering from any island, internal from the same island, local from the same machine; placement adds conditions to a channel (partition across islands, hostile from outside, reject into a replicated group, per-key order into a shard); a library adds an interface kind by refining an existing one. Never: a channel to an internal or local interface reported reachable from outside its scope.
- selfhost.session.deployment [implemented]: The deployment tree of selfhost.session.topology is written as text, after the protocol it places: deployment Name of P { ... } holds outside and island groups, which hold datacenter, machine, replicated and sharded groups and roles; a role is written Role; or Role { scope name : kind; ... } with scope ingress, peering, internal or local and kind call, queue, stream, http, api, ingressHttp, ingressHttps, datagram or one declared earlier in the block by kind Name refines Kind [adds "condition", ...] [removes "condition", ...];. Neither deployment nor kind is a reserved word in a Lean module that imports the library. In a Lean file the block is a Lean command that checks it against P and defines nothing; session_deployment reads the same block with the same grammar and answers placed or refused, each role's place and interfaces, each link (a distinct sender and receiver of P's messages, includes inlined) with its labels, the interface it uses, whether that interface is reachable from the sender and the conditions the interface and placement add, and an SVG view of the tree with the links. A deployment adds no step to P: P's messages, their order and its nesting (choice, parallel, include, sessions) are unchanged, a replicated group does not replace the messages of a replication protocol, and the conditions are reported for the implementation to handle. Always: every role of P is placed exactly once; a link whose messages are all replies (each one's cause chain, at most 64 links, reaches a message its receiver sent to its sender, as the diagram dots replies) travels back over the interface of the link it answers, with its conditions and its verdict; any other link to a role with interfaces uses the first of them, in the block's order, that the sender can reach; any other link to a role with no interfaces is unrestricted, as in the topology; the view draws every placed role inside its groups and every link, a refused link dashed, and its answer carries the question, event source, reducer, unit and boundary. Never: a deployment accepted (elaborated without error, or answered placed) with a role of P unplaced or placed twice, a placed name that is not a role of P, a group inside a role or an outside or island group below the top, an unknown kind or a kind declared twice, two interfaces of one role with one name, or a link whose receiver has interfaces of which the sender can reach none; each is a Lean error at the offending role or declaration, and session_deployment answers refused with every such issue. Never: a deployment of more than 256 groups, roles and interfaces in all read.
- selfhost.session.diagram [implemented]: Interaction diagrams are generated from the global type, in standard sequence-diagram notation, never drawn separately. Always: Global.diagram draws one lifeline per listed role and one arrow per message, labelled with its id, label, route and status, with its where clause under it; a message whose cause chain reaches a call (a message that was not itself a reply) from its receiver to its sender is a reply, drawn dotted (round dots) while every other message, a request, is drawn solid, and the dividers of choice and parallel frames stay dashed, so a reply is never mistaken for a frame's line; so a response that follows other calls is drawn as the answer to the call that asked for it and a new call made after a reply is not; an event is an action box on its role; choice is an alt frame captioned with the role that decides (the one that sends the first message of every branch); parallel is a parallel frame; join k of n is a parallel frame captioned any k of n; loop is a loop frame and continue is drawn inside it; sessions is a loop frame around one instance; include is a ref frame named after the included protocol; a choice with no single decider is drawn and captioned as a race; every request that is answered is an activation bar on the callee from the request to its response, inset when the callee is still busy with another call, and a response in another branch of a choice gets its own bar from where that branch begins, so no bar runs through a branch its call is not in; the diagram is a list of shapes (rect, line, path, text) with colours named by role (fg, arrow, frame, muted, line, bg, actFill), written as SVG text in a theme or handed to a view as data. Lifelines are spaced so the widest message label fits between neighbours (180 to 420 pixels); Messages are drawn thicker than frames, dividers and lifelines, with arrowheads of a fixed size, a frame or divider opens below the arrow before it, and text outside a box has a halo in the background colour so no line runs through its letters. Repeated replies to one request within a branch extend its existing activation bar. Never: an activation bar starting before its request or overlapping an actor header; a construct of the protocol omitted from its diagram; an arrow that is not a message of the protocol; a frame's edge or a divider drawn along an arrow; protocol text (labels, ids, guards, role names) placed in the drawing unescaped.
- selfhost.session.calls [implemented]: cause packages interactions into calls, and LeanFM derives the calls and each role's typestate API from the global type. Always: a message whose cause chain reaches a request from its receiver to its sender is a response to that request, and every other message is a request; a call is a request with its responses (with their statuses) and its detail, which is every message the request causes directly or through others except its responses and what they cause; Global.calls lists calls as a tree, a request in another call's detail nested under the nearest such call, a request with no response listed as having no reply; Local.typestate reads a role's projection as states: the role starts in S0, a send, an event or a continue is a method that consumes its state and returns the next, a select is several methods on one state, an offer is one receive returning a sum of label and next state, a loop's continue returns to the loop's state, a parallel the role takes part in on one side only is that side followed by what comes after, and End has no methods. Never: a response listed as a call of its own; a message placed in the detail of a call one of whose responses caused it; a typestate method for a message the role neither sends nor receives.
- selfhost.session.generative [implemented]: Inline generative annotations in MCP protocol text elaborate to metadata beside an unchanged Global grammar: clock c = time(id) or max(time(id), time(id)); obligation Name on Role { trigger clock; require Label or Label within N days; on breach record Label; }; choice at Role using declared(name) with probability n/d per branch; and message at clock or time(id), optionally plus a duration or finite sample of duration:probability entries. Fixed units ms, seconds, minutes, hours and days convert to milliseconds. Always: erasure preserves all branches including zero-probability and late paths and the same CTL/projection/conformance semantics. session_check and session_diagram return a resolved generative layer. An external overlay with named choice weights and message timing expressions may supply or explicitly replace those annotations without changing the core text; the effective layer and provenance are returned. Never: malformed, negative, zero-denominator, greater-than-one, non-normalized, partial or duplicate distributions; unknown or forward clock/message references; mismatched deciders; duplicate clocks, obligation names or ambiguous event ids in one path accepted; metadata executed as Lean or host code; annotated concurrency, recursion, includes or nested sessions silently assigned timed scheduling semantics. Structural tools retain the grammar; generative execution reports unsupported constructs. Input and enumeration bounds fail explicitly rather than truncate.
- selfhost.session.generative.execution [implemented]: For finite sequential protocols with choices, session_simulate uses the resolved probability/time layer to produce deterministic seeded timed event envelopes and per-session deadline reports. Always: event time is monotonic milliseconds within each session; a missing explicit time uses the preceding event time (initially zero); a requested absolute time before its causal prefix is an error, never clamped. Unweighted multiway choices require weights in generative mode, never silently uniform. Finite path enumeration is bounded; unsupported or inconsistent paths, including zero-mass paths, are validated. Samples carry conditional weights and an explicit declared or external overlay origin; generated events conform to the erased grammar and preserve event causes, predecessors and answers. Obligations start at their declared clock, fulfill on a matching message sent by the named actor from trigger through the inclusive deadline, and are pending until the observation horizon passes the deadline if unmet. A late fulfillment remains violated. Breach records are monitor output, never fabricated sends. Never: a late or zero-probability trace removed from protocol conformance; a complete protocol treated as evidence that an unmet deadline already passed; probability claims inferred from a seed; one session's clocks, message ids, causes or obligations reused in another; incomplete generation returned as complete after an event limit.
- selfhost.session.generative.monitor [implemented]: session_conform keeps structural verdicts independent of normative deadline reports. For annotated sequential protocols, timestamped observed traces are replayed against the erased paths with actual event times; report obligations as fulfilled, pending, violated or not-triggered. Observations outside a generation distribution remain structurally admissible. Optional observation horizon is per-session-relative milliseconds, at least the last event time; otherwise use the last event. A protocol whose layer only the chain can run (loop, accrue, after on an event, a periodic gate) has no finite paths to replay: session_conform gives its structural verdict with no deadline reports, and the layer's executionUnsupported note says that generation and expectations run on the chain (session_simulate, session_dataset, session_mdp) while deadline monitoring does not; for any other unsupported construct the note is the generator's own reason. Never: a conformance check that fails because deadline monitoring cannot run; a note saying a protocol cannot be generated when the chain generates it; missing or decreasing timestamps silently accepted for timed monitoring; a label from the wrong actor fulfilling an obligation; a future delivery inferred from a prefix; a sidecar overlay silently discarded or partial distributions silently renormalized.
- selfhost.session.mdp [implemented]: session_mdp renders a finite sequential session with its resolved inline or external probability layer as a decision tree: protocol states, explicit action selections with policy weights, probabilistic timing outcomes and deterministic transitions. Always: generated shapes and escaped SVG describe the same checked graph, with exact terminal masses summing to one, including zero-mass terminals. Return terminal message/time/obligation outcomes and the exact probability of at least one violation, counting each terminal once. Pending obligations are not violations or fulfillment. Terminal probability is reaching that complete path, not probability on an outgoing terminal edge. Preserve prefix history, clock times and branch identity; never merge states merely because labels match. The view is an unfolded process under the supplied policy, not an optimal-policy solver. Unknown weights, invalid protocols, unsupported scheduling, path/node/output limits and non-unit terminal mass fail explicitly; never normalize or truncate a complete-looking graph. No evaluation, external IO, HTML injection or secret access from model input. Return prompt, question, source, reducer, units and finite-session boundary with each view. The MCP Apps view displays the graph and terminal distribution directly and retains overlays when redrawing.
- selfhost.session.amounts [implemented]: A message may carry an amount, moving a quantity of one named unit from its sender to its receiver: amount 1000 USD, or amount sample { 1000 USD : 9/10; 700 USD : 1/10; } for an uncertain quantity. An obligation may name a penalty its actor pays when it is violated: on breach record Label pays 2000 USD to Role. Always: quantities are whole numbers of at most 12 digits; erasure leaves the Global grammar, projection, conformance and CTL unchanged; session_mdp shows each amount on its message state and an amount sample as transition outcomes whose exact probabilities multiply into the terminal masses; each terminal reports every role's net balance per unit (received minus sent, plus penalties received minus penalties paid), and the result reports each role's exact expected net balance per unit (the sum of terminal probability times balance, signed) together with the expected penalty paid; for every terminal and unit the roles' balances sum to zero, since value is moved, not created. Never: an amount on an event or outside a message; a negative, fractional or oversized quantity; an amount sample with mixed units, duplicate quantities, more than 16 entries or probabilities that do not sum to 1; a penalty payee that is not a role or is the payer; a pending or fulfilled obligation's penalty counted; an expected balance rounded, normalized or computed from a seed.
- selfhost.session.mdp.loops [implemented]: session_mdp also analyses a sequential session with loops (loop and continue) as an absorbing Markov chain under the supplied policy, and does so for any session when asked for view chain. One state per protocol point; one edge per message, event, choice action or loop entry, each with its exact probability and the mean of its amount. Always: expected visits per state solve v = start + vQ over the transient states with exact rationals; an edge's expected traversals are its source's expected visits times its probability; each role's expected net balance per unit is the sum over edges of traversals times the edge's mean amount, minus for the sender and plus for the receiver; the expected number of messages is the sum of message-edge traversals; amounts are drawn on edges, in this view and in the tree view, and every state shows its expected visits (in the tree, its probability of being reached); on a loop-free session without obligations the chain's expected balances equal the tree's; the result carries prompt, question, source, reducer, units and boundary. Never: a session that some reachable state can never leave reported with finite expectations (the linear system is singular, and the tool says the session can loop forever); obligations evaluated in a looped session (deadlines depend on history, and the tool points to the tree view); message times silently used (the view says it does not use them); parallel, join, sessions, include or an unweighted choice accepted; more than 96 states; a probability or expectation rounded.
- selfhost.session.mdp.rewards [implemented]: The chain view of session_mdp is a multi-reward process: amounts per traversal on edges, time per edge, and amounts that accrue per unit of time while a rate is in force. A message or event may come after a delay relative to the step before it (on 1 week, or after sample { 1 days : 1/2; 3 days : 1/2; }); weeks join the time units. A statement accrue N UNIT per PERIOD from A to B sets the rate at which A pays B from that point until the next accrue for the same payer, payee and unit (accrue 0 ends it, as a grace period). Always: an edge's expected time is its traversals times its mean delay; a state's expected residence is the sum of the expected times of the edges that leave it; the session's expected duration is the sum over edges; each accrual adds, for every edge, traversals times mean delay times the rate in force at the edge's source; the session ends in one end state per distinct last step, each with its exact probability (their sum is 1) and the expected balances and duration given that outcome (joint expectation divided by the outcome's probability, using absorption probabilities from every state); a rate period is exact milliseconds and rates are exact rationals per millisecond; the drawing's legend and the result's breakdown give, per role and unit, the expected balance with each source's share (a message's label, or the rate that accrued) and, when a role trades exactly two units against each other, the effective price of one in the other; the legend's decimals are rounded to the nearest hundredth and the exact values stay in the result. Never: a state whose rate in force differs between paths that reach it accepted (the tool names the state and asks for the rate to be declared after the paths meet); an absolute time (at clock or at time(id)) used as a delay in the chain or mixed with accruals; an accrual in the tree view silently ignored (the tool points to the chain view); a conditional expectation for an outcome of probability 0 reported as a number; a negative rate, a zero or oversized period, or a rate between a role and itself.
- selfhost.session.mdp.walk [implemented]: session_mdp with walk computes the rewards of one specific walk through the chain instead of their expectations: the same weights (trade vectors on edges, rates in force times time) applied to the walk's actual traversal counts and times. A walk comes from an event stream: events in session_conform's format (label, from, to, session, and timeMs or time in session-relative milliseconds), grouped by session in order of first appearance, each step's delay being the time since the previous event of its session (the first since zero); a hand-written walk is a list of steps (label, optional from, to and afterMs), a step without a time taking its edge's mean delay. With several sessions the result gives each session's walk and their totals. Always: from the current state the walk follows choice, loop and rate edges to the one message or event edge that matches the step, multiplying the probabilities of the choices it takes; the result gives each edge's count, each state's visits and time, the walk's duration, each role's balance per unit as a map keyed by unit, the walk's probability under the policy, and whether it reached an end. Never: a step that no edge reachable from the current state matches, or that two do, accepted (the tool names the step and what could come next); a time that goes backwards within a session, or a stream mixing timed and untimed events; more than 512 steps in one session or 5000 events in a stream; a walk's result presented as an expectation.
- selfhost.session.mdp.horizon [implemented]: A step may wait for a periodic gate: at next 1 week (on a message, or on an event after its role) happens at the next whole period since the session began. session_mdp with horizon (such as 52 weeks) analyses a session with exactly one gate over that many whole periods, whether or not it ever ends: the gate splits time into periods, each ending with one passage of the gate, so the graph is the same for every horizon and only the count of periods changes. Always: the tree view times a gated step at the next multiple of its period after the previous step; with a horizon of N periods, the initial segment (start to the gate) and the cycle (gate back to the gate) are solved as absorbing chains, q0 and q being the probabilities that each reaches the gate; the gate passes q0 (1 + q + ... + q^(N-1)) times in expectation and the cycle runs q0 (1 + ... + q^(N-2)) times; the expected wait at the gate is the period times its passages minus the expected work time on the paths that reach it; every reward is then traversals times trade vectors plus rates in force times time, so a weekly trade that always continues passes exactly N times and a rate in force throughout accrues for exactly N periods; the result gives the number of periods, the probability that the session is still running at the horizon, totals per role and unit as maps keyed by unit, and the same drawing with horizon totals; a partial period after the last whole one is not counted, and the result says so. Never: a horizon without exactly one gate, or a gate without a horizon in the chain view (the tool says which is missing); a loop that does not pass the gate; work before a gate that can take longer than its period (the longest path, with each delay at its largest, is checked); a horizon shorter than one period or over 10000 periods.
- selfhost.session.generate.chain [implemented]: session_simulate generates event streams from the chain for sessions the timed generator cannot run (loop, accrue, after on an event, a periodic gate): each session walks from the start, drawing each choice's branch, each delay and each amount by their exact probabilities with the seeded integer-ticket sampler, a gate waiting for the next whole period. Events carry session, id, label, src, dst, prior, session-relative time in milliseconds, the amounts actually moved, the message's own id, and the cause the protocol names for it: the latest event in the session with that id (a loop rebinds an id on every pass), so a generated stream conforms. Always: the same seed gives the same stream; every generated session is a walk of the chain, so session_mdp with the stream as events accepts it and computes each session's realized rewards from the amounts actually drawn (a walk step may carry amounts, which must match the edge's sender, receiver and unit); a session that reaches an end is marked ended; over many sessions the mean realized balance approaches the expected one. Never: more than the instance limit of sessions or 512 events in one session (a longer session is cut and marked not ended, never extended); an amount on an event that its edge cannot move accepted by a walk; a generated time that goes backwards; a generated event without the cause its message names.

- selfhost.session.buffers [implemented]: A protocol says the order its messages should happen in; a deployment can only enforce some of it. Each actor has an inbox, a FIFO buffer that loses nothing, whose size is written where the actor is named, protocol Shop (Client, Api[8], Bank[2]); an actor without a size has an inbox of size 0, a rendezvous. Tool session_realizable explores what a deployment can do: each role runs its own projection, a send puts the message at the back of the receiver's inbox when it has room, a send to a full inbox waits until the receiver takes one out (with size 0, until the receiver takes this one: sending and delivery are one step), and a role takes the message at the front of its inbox only when its projection lets it receive that message there, waiting otherwise; every wait ends when its step becomes possible. It answers realizable when every order of deliveries the deployment can produce is one the protocol allows and no deployment state is stuck; otherwise it answers the first problem with the deliveries that lead to it: an order the protocol does not allow (unrelated roles cannot be held to the protocol's order between their messages), or a deadlock, with each role's inbox and what each role waits for (a role that needs two messages to send one, gets one, and is owed the other only after it sends, deadlocks this way). Always: the protocol's own text stays the specification, so session_check, session_ctl, the faithful rules, conformance and every other answer are unchanged by inbox sizes; the answer lists the inbox sizes it used and the guarantees it assumed (in order, lossless, each inbox at most its size); sending and taking are separate steps only for an inbox larger than 0. Never: a message taken out of order or lost; a message put into a full inbox; a size that is not a whole number from 0 to 64, or a size on a name that is not a role; a protocol whose roles run parallel branches or serve sessions explored as if they did not (it is refused, naming the role, until those are supported); the state bound exceeded silently.

- selfhost.session.bits [implemented]: A protocol's hidden state is measured in bits per message. - selfhost.session.keywords [implemented]: A keyword of the protocol language is the word it is explained with: branches that run interleaved are parallel { ... } and { ... }, and a named loop is loop Name { ... continue Name; } (bounded: loop Name at most N { ... } otherwise { ... }); the JSON protocol form names its steps parallel and loop the same way. - selfhost.session.rec.bounded [implemented]: A loop may be bounded: loop Name at most N { body } otherwise { stmts } runs the body at most N times and, where an Nth pass would continue again, runs the otherwise block instead (an empty block when it is left out). - selfhost.session.mdp.distribution [implemented]: session_mdp gives the full distribution of each role's balance per unit, not only its mean, wherever it is finite: in the tree view, the terminals grouped by balance; with a horizon behind one gate, the periods convolved exactly: each period's paths (finite, since every loop passes the gate) are enumerated with their exact probabilities, delay and amount outcomes, trade vectors, accruals and the wait at the gate, and sessions are carried period by period, merging equal outcomes. - selfhost.session.mdp.optimize [implemented]: session_mdp with optimize (role, unit and goal max or min; unit time for the expected duration) treats each choice without probabilities as an open action of the role that sends its branches' first messages and finds the stationary policy that optimizes the objective, over the same chain, rewards and residencies: choices with probabilities stay as given. Always: the policy is found by exact policy iteration (evaluate with exact rationals, switch a choice only when another branch is strictly better), starting from a policy under which every state can still reach an end; each open choice reports the chosen branch, named by its first message, and every branch's exact value from that choice; the optimal value from the start equals the objective's expected value under the chosen policy, and the whole chain answer (visits, outcomes, balances, legend, drawing) is given under it; a policy is optimal for the stated role only, and the result says whose objective it is. - selfhost.session.sla [implemented]: A protocol states what it requires as well as what it assumes. The probabilities written on choices (choice at Role using declared(name) { probability p: ... }) are assumptions: the distribution of a peer's hidden internal choice as seen from outside, which generation samples and the system never promises. Requirements follow the protocol as require per q { clauses } blocks, where q is the id of a message of the main protocol and every occurrence of q is one entry, one independent trial: every q reaches A, B [within d] is a hard deadline (each entry must reach one of the targets, within d when given, and one entry that does not is a counterexample); at least p of q reach A, B [within d] over W and at most p of q reach ... over W are probability bounds that are only checkable over an observation window W (a duration or a number of entries), with a confidence (default 95/100) and optionally the expected traffic (expecting N per unit). session_sla checks every requirement against the assumptions before any implementation exists: over the chain view, from each entry it enumerates the continuations with their exact probabilities and delay outcomes until a target is reached (a hit), the deadline passes, the session ends or the next entry comes first (a miss), and gives the per-entry probability as an exact interval [hits, hits + unresolved]; the verdict is met, violated or undecided from that interval and the bound, for the worst entry; a violated requirement comes with the most probable path that breaks it and the stated choices it passes through, each written [choice name -> first message of the branch taken: probability] so that it names the outcome as well as the question (the name belongs to the whole choice, so the same choice reads differently on each branch), and a late step says when it arrived and which deadline it passed, so the conflict between an assumption and a requirement is visible; and it says how many entries a window must hold to decide each probability bound (ln(1/(1 - confidence)) / margin, the rule of three at 95/100) and, with expecting, whether the window will hold them. Always: q must be a message id and every target a message or event of the protocol; every takes no window and a probability bound needs one; the analysis uses exact rationals. Never: a probability bound accepted without an observation window; a verdict claimed beyond what the interval decides (undecided is said when the enumeration stops at 20000 continuations); a requirement checked over a choice without stated probabilities (an assumption is missing, and it says which choice); a protocol with a periodic gate (at next d) analysed (its waits depend on absolute time; it says so).
- selfhost.session.execution [implemented]: State lives in the protocol execution, not in the actors: an execution is its event stream. Each event has a unique timestamp, which is its identity, and may name an earlier event as prev and one as cause, so the stream is a causal DAG keyed by timestamp; rewards are a sparse map from timestamp to the whole reward vector per role and unit, and a new reward vector is recorded only at an event where it changes. An actor's state is only its view: the events it sent, received or performed, with their causal past; the reward vector at an event is found by walking its prev links backwards to the first event that has one (none on the way back is the zero vector), never by scanning smaller timestamps. session_sla checks the requirements on an observed stream: an entry (an event with q's label) reaches its target when an event with a target label is in its causal future within the deadline; entries whose deadline has not passed by the end of the stream are pending, not failures; a hard deadline is violated by any entry that misses it, with that entry and its causal future as the counterexample; a probability bound is decided per tumbling window (of time or of entries), and only once the window's observation period is over (a time window when the stream has passed its end plus the deadline, an entry window when it holds its N decided entries; before that it is open whatever it has seen, so no early miss breaks an agreement), by an exact one-sided binomial test at the requirement's confidence: met when the observed hits would be improbable if the bound were only just met, violated when the misses would be, undecided otherwise. Always: the answer gives each window's entries, hits, verdict and the probability behind it, each role's view size and total reward, and for a given timestamp its causal past, view and reward. Never: two events with the same timestamp, a prev or cause naming a missing or later event, or more than 20000 events accepted; a reward vector recorded where it does not change (equal to the one inherited through prev), or two for one timestamp; a reward taken from an event that is not on the prev chain; a pending entry counted as a miss; a window judged met or violated before its observation period is over (one miss among the first entries is open, not a violation).

- selfhost.session.where [implemented]: A where condition on a message is run: conformance evaluates it over the logged payloads, so a run whose data breaks it does not conform. - selfhost.session.actor-conformance [implemented]: A log of many instances interleaves, and the interleaving carries no information: what matters is the order in which each actor processed its messages. - selfhost.session.timelines [implemented]: Time is measured only as differences between two readings of one clock, so clock skew between machines cannot affect a duration. A call is a request and the first reply that names it as cause, from the callee back to the caller. It has two views: the caller's (reply received minus request sent, on the caller's clock) and the callee's own (reply sent minus request received, on the callee's clock); the caller's is at least the callee's, and the difference is network and queueing time for both directions together, which cannot be split without synchronized clocks and is not split. A call tree is laid on its root caller's timeline: a callee's clock is offset so that it received the request at the moment the request was sent, and its sub-calls are placed the same way, recursively. session_spans answers every call with both views, its network time, its sub-calls and each tree's timeline. Always: every position on a timeline and every duration is computed from same-clock differences; a call without the readings it needs is listed without durations. Never: two actors' clocks compared or subtracted; a callee's own duration longer than its caller's wait accepted (it is reported with both numbers as inconsistent: a mis-attributed event, a missing cause or a clock that jumped); the network time of one direction reported as if measured.
- selfhost.session.critical-path [implemented]: A call is at least the critical path of its sub-calls. Along a chain the durations add; across concurrent sub-calls the longest counts (parallel gives the longest branch; join k of n replies once k are back, and the replies after the parent's reply are not awaited). Always: session_spans names, for every call, its critical path: the chain of awaited sub-calls whose caller views add to the most, with that total; the sub-calls' own durations along the heaviest chain are a lower bound the call's own duration must meet. Never: concurrent sub-calls summed as if sequential; a call whose own duration is below the bound accepted silently (reported with the chain and both numbers); a not-awaited reply counted toward the call's time.

Always: the answer gives the verdict (holds or fails) at that first checked sample; the margin, how far the claim is from failing (a reading minus the bound for above, the bound minus the reading for below, the least margin of the parts for and, always and throughout, the greatest for or, within and possibly, the negation for not, unbounded either way for on), written unbounded when it is infinite; for a claim that is always or never, the first sample where it fails, with its time and readings; how many moments had a window cut short by the end of the run, counted and never hidden; and, for drawing, each field the claim reads and the claim's inner margin as series over time, at most 2000 points each with the rest counted; and, given theme light or dark, an SVG chart drawn from the same numbers: one panel per field the claim reads, its line over time, a dashed line at each bound the claim sets on it, the samples where the claim fails marked in red, and a tick at each sample with a label the claim names. The check takes time proportional to the claim's size times the number of samples: each window is a sliding minimum or maximum, never a rescan. The answer's steps counts the elementary steps the check took and stepBound is 10 times the claim's nodes times the samples checked; a change that makes the check grow faster than that complains loudly: a check over its bound is refused as an internal error naming both numbers, never answered quietly, and the tests fail, saying how much the steps grew, when doubling the samples more than doubles the steps. Never: a claim about a field the run never reads (refused, naming the field); a claim whose branches would start at different samples without from (refused before anything is evaluated, naming the branch that starts latest and one that starts earlier, and saying to give from or check the branches separately), where a branch starts at the first sample at which every field it reads has had a reading, or at the first sample when it reads none, as (on M) does, since starting the whole claim later would judge such a branch over fewer samples than it is judged alone; a from before a field's first reading (refused, naming the field); samples out of time order (refused, naming the first); a word other than these, a bound or window that is not a number, a negative window, or a claim of more than 256 words (refused); a file read or any text evaluated; more than 100000 samples (refused); a margin that is not a number written into the answer's JSON; a field name or label written into the chart as anything but escaped text; a log read by a path a client gives, or by serverLog where server_logs is not served; a client-sent log over 64 KiB accepted.
- selfhost.mcp.logic.reassembly [implemented]: Tool check_reassembly takes a signature of 1 to 4 characters, the overlap policy of a defender scanning the stream and of the host behind it (first: old bytes win an overlap; last: new bytes win), whether the defender blocks (resets the stream on a match) or only alerts, and optionally a formula over the claims alerted(signature) and delivered(signature). Always: the attacker may send any segment of the stream, at any offset and length, with each byte the signature's or another, any number of times; the defender and the host each apply every segment with their own policy, except that nothing reaches the host after a blocking defender has matched; the search covers every such segmentation, and an evasion is answered with the segments that make it, in order. - selfhost.requirements.list [implemented]: A project has an actual list of requirements and a similar list for each implementation, and both are lists of things that convert to CTL. The rule: an entry is an object of a kind that has a transform into CTL (RequirementCtl), and a kind is admitted only with its transform; sorry is the entry that does not convert yet, reported as uses sorry, never met and never refuted, and a hint converts to true because it claims no behaviour. - selfhost.requirements.map [implemented]: Every requirements file ends in a map from requirement names to pointers, so a project's requirements are found in its files, not kept elsewhere. - selfhost.implementations.map [implemented]: An implementation is a map too, written against the requirements it implements, and a project may have any number of them. Syntax, after the protocols of an implementation file: implementation Go of Orders.Requirements { refines PlaceOrder by ShopImpl; "Orders must be placed" => conform "logs/orders.jsonl"; "Card numbers are never logged" => test "PayTests.noCardInLogs"; "Refunds within 30 days" => sorry; "Writes before acknowledging" => ShopImpl ⊨ (AG (implies (on Ack) (on DbWritten))); hint "Implement the code as Go"; }. An entry keyed by an imported requirement is evidence: conform "log" (a log inside the project root, checked by session_conform against the requirement's protocol: met when it conforms; it carries the requirement's AG properties to that run, not its AF or EF ones, which also need covering guards), test "name" (a named test the project's checks run: counted as tested, not as CTL), or sorry. An entry with a new name is the implementation's own CTL, a pointer as in a requirements map, decided the same way. refines P by Q: every formula requirement over P is decided again over Q (same message labels; Q may add messages), so the implementation adds behaviour but may not break what was required. hint "text" is a marker for the LLM that writes the code (such as the language); it claims no behaviour, its transform into CTL is true, it never warns, and project_view lists the hints with the implementation for code generation.
