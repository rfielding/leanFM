## Proposed clauses (not semantic proofs)

- selfhost.revision [proposed]: A snapshot is identified by exact book, requirements, protobuf, implementation, and repository revisions. Changes invalidate affected checks and derived artifacts; stale requests fail without overwriting current state.
- selfhost.gates [implemented]: Review and acceptance are git commits made by the user; LeanFM records no approvals and never blocks an edit, source write or launch on one. Code generation requires the current snapshot's requirements and implementation mapping to pass their canonical checks. Project status reports whether each is checked and committed.
- selfhost.pr [proposed]: PR delivery requires an actual patch, requirement-to-code/test mappings, reproducible check results, base revision, and remaining limitations. The PR may be delivered as a local reviewable bundle; remote publication requires explicit authority. Failed checks cannot be labeled completed.
- selfhost.checker [proposed]: Check results distinguish proved, disproved, unknown, unsupported, and resource-limit reached. Identify model revision, formula, assumptions, bounds, terminal-path convention, fairness, and witness or counterexample. Schema validation is not a semantic proof.
- selfhost.formulas [proposed]: Requirements must support typed nested CTL state formulas and separately typed path conditions. AF AG p is eventual permanent safety; AG AF p is universal recurrence. Preserve existential counterexample duals without claiming CTL covers all LTL.
- selfhost.modal [proposed]: Knowledge quantifies over legal histories with identical declared actor observations. Obligation and permission quantify over all and some nonempty named ideal policy futures. Never conflate legal, observable, ideal, and probabilistic alternatives. Belief and morality are outside this extension.
- selfhost.lazy [proposed]: Retain modality-specific indexes only while current formulas reference the corresponding actor or policy relation. Rebuild them from retained source evidence; release unreferenced indexes. Index lifetimes must not alter truth. Isolate caches by project and model revision.
- selfhost.probability [proposed]: Probabilities are optional and distinct from existence. Identify declared model probability versus observed frequency versus unknown. Specify normalization, conditioning, scheduler or min/max policy, horizon, threshold comparison, and sample boundary. Do not infer independence or treat unknown as zero.
- selfhost.history [proposed]: Immutable events carry predecessor links; derived successor indexes preserve event identity and partial order. State whether a past monitor uses causal ancestry or a declared linearization. Strictly prior facts exclude the current event.
- selfhost.coverage [proposed]: Every normative book claim is linked to an accepted requirement, an explicitly pending proposal, or a deferred/illustrative classification. Every accepted requirement maps to implementation decisions and evidence; unmapped claims prevent a claim of complete one-shot readiness.
- selfhost.handoff [proposed]: A new session starts from book/main.pdf, book/main-dark.pdf, canonical requirements/protobuf/implementation, component registry, current repository, and generated review report. Application goals also retain spec/ProjectMemory.md, spec/runtime.json, revision-bound actual-launch evidence, failure remedies and PR/base-revision context. Conversation history is not required input.
- selfhost.bounds [proposed]: Declare finite exploration and resource bounds. Exhaustion yields resource-limit or unknown, never proved. Compaction must preserve the declared observation and monitor semantics.
- selfhost.session.syntax [implemented]: A protocol is written in Lean with the protocol notation of LeanFM.Session and elaborates to a value of Global R for any role type R, so it can be instantiated with another protocol's roles. Statements: a message (optional name, label, sender, receiver, optional cause naming an earlier message, optional route naming the operation a request invokes such as POST /orders, optional status a response carries such as 402, optional where clause); an event at one role; choice with or-branches; par with and-branches; join k of branches; rec with continue in tail position; sessions; include of another protocol. Always: a label is a Lean type, so a misspelt label is a compile error, and a where clause is a Lean Bool over the payloads of the messages named so far, type-checked when the protocol is written and evaluated over decoded payloads when a trace is checked. Never: repetition other than continue at the end of a branch (the state space stays finite); a route or status changing any check's verdict (they are for people and generated views).
- selfhost.session.choice [implemented]: A choice names no decider. Always: the decider is the one role that starts every branch, by sending its first message or by an event at that role alone; an empty branch is that role choosing to do nothing. Never: a choice whose branches are started by different roles accepted (it is reported as a race naming who starts what); two branches that start with the same event; a choice none of whose branches does anything.
- selfhost.session.causes [implemented]: A message's cause names an earlier message it answers. Never: a cause that its sender has neither sent nor received (a role decides only from its own history); it is reported.
- selfhost.session.projection [implemented]: Projection gives each role its local type: the protocol with every message the role neither sends nor receives erased, its own choices as select and other roles' choices as offer; a role that takes part only in nested sessions blocks is a service (a text-message gateway, a mailer) whose local type serves those sessions, sessions { ... }, without being projected through the enclosing session's choices, and a service of several kinds of session tells them apart by their first messages (as an offer) or is reported; a join k of as join k of over the role's own branches (par when it takes part in no more than k of them), resolved by what arrives. Always: a role that does not decide a choice can tell its branches apart when the first messages it can receive in them differ, looking inside par; a role whose part of the session has not started (its first message has not reached it) may be absent from a branch that never contacts it, and the body of sessions is projected as not started. Never: a role that has already taken part left out of a branch, or unable to tell branches apart; projection fails with the reason (Role cannot tell which branch Decider chose).
- selfhost.session.composition [implemented]: Protocols compose. Always: include runs another protocol with the given roles and the rest continues where it finishes, each protocol written as if it were the whole; par runs branches interleaved, each keeping its order; join k of continues after any k branches, recording which ones; sessions runs any number of independent copies of its body. Never: an unselected join branch canceled implicitly (cancellation is an explicit message).
- selfhost.session.http [implemented]: The HTTP call discipline is optional and applies to channels declared HTTP (session_check: every channel once mayCall is given, except those between the roles of a notHttp pair). Always: every message on an HTTP channel is a request to a role the sender may call, or the response to the nearest pending request in its cause chain, sent back to the role that asked; a streaming response may answer more than once; every request gets a response before a run reaches the end of the protocol (a run that goes round a loop again has not ended). Never: a response sent to a role other than the caller, a request to a role the sender may not call, or a request left without any response accepted; each is reported as a cut naming the message.
- selfhost.session.physics [implemented]: Channel physics is declared beside the protocol. Always: a channel has a capacity, a full policy (block, reject, drop newest or drop oldest), sequencing, sharding, loss and duplication; presets (reliable, udp, stream, http, kafka) name common channels and a declaration states only what differs; every channel defaults to reliable; a spec states which surfaced conditions each channel's protocol handles, its properties and its assumptions. Never: a condition a used channel surfaces (timeout, duplicate, reject, loss, reorder, per-key order, partition, hostile, readable, close) left unhandled without being reported.
- selfhost.session.topology [implemented]: A deployment tree places actors in islands, datacenters, machines and replicated or sharded groups, and gives them interfaces with a scope and a kind. Always: an interface is named by its path (island, actor, scope, interface); ingress is reachable from anyone, peering from any island, internal from the same island, local from the same machine; placement adds conditions to a channel (partition across islands, hostile from outside, reject into a replicated group, per-key order into a shard); a library adds an interface kind by refining an existing one. Never: a channel to an internal or local interface reported reachable from outside its scope.
- selfhost.session.diagram [implemented]: Interaction diagrams are generated from the global type, in standard sequence-diagram notation, never drawn separately. Always: Global.diagram draws one lifeline per listed role and one arrow per message, labelled with its id, label, route and status, with its where clause under it; a message whose cause chain reaches a call (a message that was not itself a reply) from its receiver to its sender is a dashed reply, so a response that follows other calls is drawn as the answer to the call that asked for it and a new call made after a reply is not; an event is an action box on its role; choice is an alt frame captioned with the role that decides (the one that sends the first message of every branch); par is a par frame; join k of n is a par frame captioned any k of n; rec is a loop frame and continue is drawn inside it; sessions is a loop frame around one instance; include is a ref frame named after the included protocol; a choice with no single decider is drawn and captioned as a race; every request that is answered is an activation bar on the callee from the request to its response, inset when the callee is still busy with another call, and a response in another branch of a choice gets its own bar from where that branch begins, so no bar runs through a branch its call is not in; the diagram is a list of shapes (rect, line, path, text) with colours named by role (fg, arrow, frame, muted, line, bg, actFill), written as SVG text in a theme or handed to a view as data. Lifelines are spaced so the widest message label fits between neighbours (180 to 420 pixels); Messages are drawn thicker than frames, dividers and lifelines, with arrowheads of a fixed size, a frame or divider opens below the arrow before it, and text outside a box has a halo in the background colour so no line runs through its letters. Repeated replies to one request within a branch extend its existing activation bar. Never: an activation bar starting before its request or overlapping an actor header; a construct of the protocol omitted from its diagram; an arrow that is not a message of the protocol; a frame's edge or a divider drawn along an arrow; protocol text (labels, ids, guards, role names) placed in the drawing unescaped.
- selfhost.session.calls [implemented]: cause packages interactions into calls, and LeanFM derives the calls and each role's typestate API from the global type. Always: a message whose cause chain reaches a request from its receiver to its sender is a response to that request, and every other message is a request; a call is a request with its responses (with their statuses) and its detail, which is every message the request causes directly or through others except its responses and what they cause; Global.calls lists calls as a tree, a request in another call's detail nested under the nearest such call, a request with no response listed as having no reply; Local.typestate reads a role's projection as states: the role starts in S0, a send, an event or a continue is a method that consumes its state and returns the next, a select is several methods on one state, an offer is one receive returning a sum of label and next state, a loop's continue returns to the loop's state, a par the role takes part in on one side only is that side followed by what comes after, and End has no methods. Never: a response listed as a call of its own; a message placed in the detail of a call one of whose responses caused it; a typestate method for a message the role neither sends nor receives.
- selfhost.session.generative [implemented]: Inline generative annotations in MCP protocol text elaborate to metadata beside an unchanged Global grammar: clock c = time(id) or max(time(id), time(id)); obligation Name on Role { trigger clock; require Label or Label within N days; on breach record Label; }; choice at Role using declared(name) with probability n/d per branch; and message at clock or time(id), optionally plus a duration or finite sample of duration:probability entries. Fixed units ms, seconds, minutes, hours and days convert to milliseconds. Always: erasure preserves all branches including zero-probability and late paths and the same CTL/projection/conformance semantics. session_check and session_diagram return a resolved generative layer. An external overlay with named choice weights and message timing expressions may supply or explicitly replace those annotations without changing the core text; the effective layer and provenance are returned. Never: malformed, negative, zero-denominator, greater-than-one, non-normalized, partial or duplicate distributions; unknown or forward clock/message references; mismatched deciders; duplicate clocks, obligation names or ambiguous event ids in one path accepted; metadata executed as Lean or host code; annotated concurrency, recursion, includes or nested sessions silently assigned timed scheduling semantics. Structural tools retain the grammar; generative execution reports unsupported constructs. Input and enumeration bounds fail explicitly rather than truncate.
- selfhost.session.generative.execution [implemented]: For finite sequential protocols with choices, session_simulate uses the resolved probability/time layer to produce deterministic seeded timed event envelopes and per-session deadline reports. Always: event time is monotonic milliseconds within each session; a missing explicit time uses the preceding event time (initially zero); a requested absolute time before its causal prefix is an error, never clamped. Unweighted multiway choices require weights in generative mode, never silently uniform. Finite path enumeration is bounded; unsupported or inconsistent paths, including zero-mass paths, are validated. Samples carry conditional weights and an explicit declared or external overlay origin; generated events conform to the erased grammar and preserve event causes, predecessors and answers. Obligations start at their declared clock, fulfill on a matching message sent by the named actor from trigger through the inclusive deadline, and are pending until the observation horizon passes the deadline if unmet. A late fulfillment remains violated. Breach records are monitor output, never fabricated sends. Never: a late or zero-probability trace removed from protocol conformance; a complete protocol treated as evidence that an unmet deadline already passed; probability claims inferred from a seed; one session's clocks, message ids, causes or obligations reused in another; incomplete generation returned as complete after an event limit.
- selfhost.session.generative.monitor [implemented]: session_conform keeps structural verdicts independent of normative deadline reports. For annotated sequential protocols, timestamped observed traces are replayed against the erased paths with actual event times; report obligations as fulfilled, pending, violated or not-triggered. Observations outside a generation distribution remain structurally admissible. Optional observation horizon is per-session-relative milliseconds, at least the last event time; otherwise use the last event. Never: missing or decreasing timestamps silently accepted for timed monitoring; a label from the wrong actor fulfilling an obligation; a future delivery inferred from a prefix; a sidecar overlay silently discarded or partial distributions silently renormalized.
- selfhost.session.mdp [implemented]: session_mdp renders a finite sequential session with its resolved inline or external probability layer as a decision tree: protocol states, explicit action selections with policy weights, probabilistic timing outcomes and deterministic transitions. Always: generated shapes and escaped SVG describe the same checked graph, with exact terminal masses summing to one, including zero-mass terminals. Return terminal message/time/obligation outcomes and the exact probability of at least one violation, counting each terminal once. Pending obligations are not violations or fulfillment. Terminal probability is reaching that complete path, not probability on an outgoing terminal edge. Preserve prefix history, clock times and branch identity; never merge states merely because labels match. The view is an unfolded process under the supplied policy, not an optimal-policy solver. Unknown weights, invalid protocols, unsupported scheduling, path/node/output limits and non-unit terminal mass fail explicitly; never normalize or truncate a complete-looking graph. No evaluation, external IO, HTML injection or secret access from model input. Return prompt, question, source, reducer, units and finite-session boundary with each view. The MCP Apps view displays the graph and terminal distribution directly and retains overlays when redrawing.
- selfhost.session.amounts [implemented]: A message may carry an amount, moving a quantity of one named unit from its sender to its receiver: amount 1000 USD, or amount sample { 1000 USD : 9/10; 700 USD : 1/10; } for an uncertain quantity. An obligation may name a penalty its actor pays when it is violated: on breach record Label pays 2000 USD to Role. Always: quantities are whole numbers of at most 12 digits; erasure leaves the Global grammar, projection, conformance and CTL unchanged; session_mdp shows each amount on its message state and an amount sample as transition outcomes whose exact probabilities multiply into the terminal masses; each terminal reports every role's net balance per unit (received minus sent, plus penalties received minus penalties paid), and the result reports each role's exact expected net balance per unit (the sum of terminal probability times balance, signed) together with the expected penalty paid; for every terminal and unit the roles' balances sum to zero, since value is moved, not created. Never: an amount on an event or outside a message; a negative, fractional or oversized quantity; an amount sample with mixed units, duplicate quantities, more than 16 entries or probabilities that do not sum to 1; a penalty payee that is not a role or is the payer; a pending or fulfilled obligation's penalty counted; an expected balance rounded, normalized or computed from a seed.
- selfhost.session.mdp.loops [implemented]: session_mdp also analyses a sequential session with loops (rec and continue) as an absorbing Markov chain under the supplied policy, and does so for any session when asked for view chain. One state per protocol point; one edge per message, event, choice action or loop entry, each with its exact probability and the mean of its amount. Always: expected visits per state solve v = start + vQ over the transient states with exact rationals; an edge's expected traversals are its source's expected visits times its probability; each role's expected net balance per unit is the sum over edges of traversals times the edge's mean amount, minus for the sender and plus for the receiver; the expected number of messages is the sum of message-edge traversals; amounts are drawn on edges, in this view and in the tree view, and every state shows its expected visits (in the tree, its probability of being reached); on a loop-free session without obligations the chain's expected balances equal the tree's; the result carries prompt, question, source, reducer, units and boundary. Never: a session that some reachable state can never leave reported with finite expectations (the linear system is singular, and the tool says the session can loop forever); obligations evaluated in a looped session (deadlines depend on history, and the tool points to the tree view); message times silently used (the view says it does not use them); par, join, sessions, include or an unweighted choice accepted; more than 96 states; a probability or expectation rounded.
- selfhost.session.mdp.rewards [implemented]: The chain view of session_mdp is a multi-reward process: amounts per traversal on edges, time per edge, and amounts that accrue per unit of time while a rate is in force. A message or event may come after a delay relative to the step before it (after 1 week, or after sample { 1 days : 1/2; 3 days : 1/2; }); weeks join the time units. A statement accrue N UNIT per PERIOD from A to B sets the rate at which A pays B from that point until the next accrue for the same payer, payee and unit (accrue 0 ends it, as a grace period). Always: an edge's expected time is its traversals times its mean delay; a state's expected residence is the sum of the expected times of the edges that leave it; the session's expected duration is the sum over edges; each accrual adds, for every edge, traversals times mean delay times the rate in force at the edge's source; the session ends in one end state per distinct last step, each with its exact probability (their sum is 1) and the expected balances and duration given that outcome (joint expectation divided by the outcome's probability, using absorption probabilities from every state); a rate period is exact milliseconds and rates are exact rationals per millisecond; the drawing's legend and the result's breakdown give, per role and unit, the expected balance with each source's share (a message's label, or the rate that accrued) and, when a role trades exactly two units against each other, the effective price of one in the other; the legend's decimals are rounded to the nearest hundredth and the exact values stay in the result. Never: a state whose rate in force differs between paths that reach it accepted (the tool names the state and asks for the rate to be declared after the paths meet); an absolute time (at clock or at time(id)) used as a delay in the chain or mixed with accruals; an accrual in the tree view silently ignored (the tool points to the chain view); a conditional expectation for an outcome of probability 0 reported as a number; a negative rate, a zero or oversized period, or a rate between a role and itself.
- selfhost.session.mdp.walk [implemented]: session_mdp with walk computes the rewards of one specific walk through the chain instead of their expectations: the same weights (trade vectors on edges, rates in force times time) applied to the walk's actual traversal counts and times. A walk comes from an event stream: events in session_conform's format (label, from, to, session, and timeMs or time in session-relative milliseconds), grouped by session in order of first appearance, each step's delay being the time since the previous event of its session (the first since zero); a hand-written walk is a list of steps (label, optional from, to and afterMs), a step without a time taking its edge's mean delay. With several sessions the result gives each session's walk and their totals. Always: from the current state the walk follows choice, loop and rate edges to the one message or event edge that matches the step, multiplying the probabilities of the choices it takes; the result gives each edge's count, each state's visits and time, the walk's duration, each role's balance per unit as a map keyed by unit, the walk's probability under the policy, and whether it reached an end. Never: a step that no edge reachable from the current state matches, or that two do, accepted (the tool names the step and what could come next); a time that goes backwards within a session, or a stream mixing timed and untimed events; more than 512 steps in one session or 5000 events in a stream; a walk's result presented as an expectation.
- selfhost.session.mdp.horizon [implemented]: A step may wait for a periodic gate: at next 1 week (on a message, or on an event after its role) happens at the next whole period since the session began. session_mdp with horizon (such as 52 weeks) analyses a session with exactly one gate over that many whole periods, whether or not it ever ends: the gate splits time into periods, each ending with one passage of the gate, so the graph is the same for every horizon and only the count of periods changes. Always: the tree view times a gated step at the next multiple of its period after the previous step; with a horizon of N periods, the initial segment (start to the gate) and the cycle (gate back to the gate) are solved as absorbing chains, q0 and q being the probabilities that each reaches the gate; the gate passes q0 (1 + q + ... + q^(N-1)) times in expectation and the cycle runs q0 (1 + ... + q^(N-2)) times; the expected wait at the gate is the period times its passages minus the expected work time on the paths that reach it; every reward is then traversals times trade vectors plus rates in force times time, so a weekly trade that always continues passes exactly N times and a rate in force throughout accrues for exactly N periods; the result gives the number of periods, the probability that the session is still running at the horizon, totals per role and unit as maps keyed by unit, and the same drawing with horizon totals; a partial period after the last whole one is not counted, and the result says so. Never: a horizon without exactly one gate, or a gate without a horizon in the chain view (the tool says which is missing); a loop that does not pass the gate; work before a gate that can take longer than its period (the longest path, with each delay at its largest, is checked); a horizon shorter than one period or over 10000 periods.
- selfhost.session.generate.chain [implemented]: session_simulate generates event streams from the chain for sessions the timed generator cannot run (rec, accrue, after on an event, a periodic gate): each session walks from the start, drawing each choice's branch, each delay and each amount by their exact probabilities with the seeded integer-ticket sampler, a gate waiting for the next whole period. Events carry session, id, label, src, dst, prior, session-relative time in milliseconds, and the amounts actually moved. Always: the same seed gives the same stream; every generated session is a walk of the chain, so session_mdp with the stream as events accepts it and computes each session's realized rewards from the amounts actually drawn (a walk step may carry amounts, which must match the edge's sender, receiver and unit); a session that reaches an end is marked ended; over many sessions the mean realized balance approaches the expected one. Never: more than the instance limit of sessions or 512 events in one session (a longer session is cut and marked not ended, never extended); an amount on an event that its edge cannot move accepted by a walk; a generated time that goes backwards.
- selfhost.session.diagram.annotations [implemented]: The sequence diagram (session_diagram and every tool's diagram panel) shows a protocol's generative annotations under each arrow and event: its branch's probability on the branch's first step (p 4/5), its amounts (15 USD, or each outcome with its probability), its time (after 10 seconds, at next week) and, when the session's chain can be solved without a horizon, its expected count per session (x5/4); a legend under the lifelines gives each role's expected balance per unit with its sources and the expected duration. Always: each copy of a step that the global type repeats in several branches carries that step's own annotation, because annotations are matched by the step's position in the protocol, not by its label; a protocol without annotations draws exactly as before. Never: the position tag used for matching appears in the drawing, its text or the legend; an annotation drawn under a step it does not belong to.
- selfhost.session.rec.bounded [implemented]: A loop may be bounded: rec Name at most N { body } otherwise { stmts } runs the body at most N times and, where an Nth pass would continue again, runs the otherwise block instead (an empty block when it is left out). It is expanded when the text is parsed into N explicit copies, so bounded history is observable protocol state: each pass is its own state, the choice probabilities hold per pass, and every tool sees a finite protocol (the tree view, deadlines, the timed generator, CTL). Always: copy k (from 2) renames the ids the body declares to id_k, together with every cause and time reference to them inside that copy, so causes stay unambiguous, and its named choices to name_k, so names stay unique (an overlay addresses each pass by that name); continue to an outer loop is left as it is; N is between 1 and 32; the expansion is checked like any other text. Never: a bound outside 1..32; an expansion beyond the protocol size limits (the text is refused, not truncated).
- selfhost.session.mdp.distribution [implemented]: session_mdp gives the full distribution of each role's balance per unit, not only its mean, wherever it is finite: in the tree view, the terminals grouped by balance; with a horizon behind one gate, the periods convolved exactly: each period's paths (finite, since every loop passes the gate) are enumerated with their exact probabilities, delay and amount outcomes, trade vectors, accruals and the wait at the gate, and sessions are carried period by period, merging equal outcomes. The result also gives the distribution of gate passages. Always: probabilities are exact and sum to 1; each distribution's mean equals the expected balance computed from residencies; values are sorted; the drawing shows each role and unit as a histogram with the mean marked. Never: more than 4096 distinct outcomes or 20000 paths in one period (the tool refuses and says so, never samples); a distribution claimed for a chain with loops and no horizon (its support is infinite; the tool says so and gives expectations).
- selfhost.session.mdp.optimize [implemented]: session_mdp with optimize (role, unit and goal max or min; unit time for the expected duration) treats each choice without probabilities as an open action of the role that sends its branches' first messages and finds the stationary policy that optimizes the objective, over the same chain, rewards and residencies: choices with probabilities stay as given. Always: the policy is found by exact policy iteration (evaluate with exact rationals, switch a choice only when another branch is strictly better), starting from a policy under which every state can still reach an end; each open choice reports the chosen branch, named by its first message, and every branch's exact value from that choice; the optimal value from the start equals the objective's expected value under the chosen policy, and the whole chain answer (visits, outcomes, balances, legend, drawing) is given under it; a policy is optimal for the stated role only, and the result says whose objective it is. Never: a policy under which the session can loop forever chosen (such switches are skipped and the result says when one would score better); an open choice silently given probabilities; a protocol where no policy ends accepted; more than 100 improvement rounds; an open choice outside the optimize request (without optimize, open choices are refused as before).
- selfhost.session.sla [implemented]: A protocol states what it requires as well as what it assumes. The probabilities written on choices (choice at Role using declared(name) { probability p: ... }) are assumptions: the distribution of a peer's hidden internal choice as seen from outside, which generation samples and the system never promises. Requirements follow the protocol as require per q { clauses } blocks, where q is the id of a message of the main protocol and every occurrence of q is one entry, one independent trial: every q reaches A, B [within d] is a hard deadline (each entry must reach one of the targets, within d when given, and one entry that does not is a counterexample); at least p of q reach A, B [within d] over W and at most p of q reach ... over W are probability bounds that are only checkable over an observation window W (a duration or a number of entries), with a confidence (default 95/100) and optionally the expected traffic (expecting N per unit). session_sla checks every requirement against the assumptions before any implementation exists: over the chain view, from each entry it enumerates the continuations with their exact probabilities and delay outcomes until a target is reached (a hit), the deadline passes, the session ends or the next entry comes first (a miss), and gives the per-entry probability as an exact interval [hits, hits + unresolved]; the verdict is met, violated or undecided from that interval and the bound, for the worst entry; a violated requirement comes with the most probable path that breaks it and the stated choices it passes through, each written [choice name -> first message of the branch taken: probability] so that it names the outcome as well as the question (the name belongs to the whole choice, so the same choice reads differently on each branch), and a late step says when it arrived and which deadline it passed, so the conflict between an assumption and a requirement is visible; and it says how many entries a window must hold to decide each probability bound (ln(1/(1 - confidence)) / margin, the rule of three at 95/100) and, with expecting, whether the window will hold them. Always: q must be a message id and every target a message or event of the protocol; every takes no window and a probability bound needs one; the analysis uses exact rationals. Never: a probability bound accepted without an observation window; a verdict claimed beyond what the interval decides (undecided is said when the enumeration stops at 20000 continuations); a requirement checked over a choice without stated probabilities (an assumption is missing, and it says which choice); a protocol with a periodic gate (at next d) analysed (its waits depend on absolute time; it says so).
- selfhost.session.execution [implemented]: State lives in the protocol execution, not in the actors: an execution is its event stream. Each event has a unique timestamp, which is its identity, and may name an earlier event as prev and one as cause, so the stream is a causal DAG keyed by timestamp; rewards are a sparse map from timestamp to the whole reward vector per role and unit, and a new reward vector is recorded only at an event where it changes. An actor's state is only its view: the events it sent, received or performed, with their causal past; the reward vector at an event is found by walking its prev links backwards to the first event that has one (none on the way back is the zero vector), never by scanning smaller timestamps. session_sla checks the requirements on an observed stream: an entry (an event with q's label) reaches its target when an event with a target label is in its causal future within the deadline; entries whose deadline has not passed by the end of the stream are pending, not failures; a hard deadline is violated by any entry that misses it, with that entry and its causal future as the counterexample; a probability bound is decided per tumbling window (of time or of entries), and only once the window's observation period is over (a time window when the stream has passed its end plus the deadline, an entry window when it holds its N decided entries; before that it is open whatever it has seen, so no early miss breaks an agreement), by an exact one-sided binomial test at the requirement's confidence: met when the observed hits would be improbable if the bound were only just met, violated when the misses would be, undecided otherwise. Always: the answer gives each window's entries, hits, verdict and the probability behind it, each role's view size and total reward, and for a given timestamp its causal past, view and reward. Never: two events with the same timestamp, a prev or cause naming a missing or later event, or more than 20000 events accepted; a reward vector recorded where it does not change (equal to the one inherited through prev), or two for one timestamp; a reward taken from an event that is not on the prev chain; a pending entry counted as a miss; a window judged met or violated before its observation period is over (one miss among the first entries is open, not a violation).

- selfhost.session.conform [implemented]: A log of a running implementation can be checked against its protocol, so code built from a session type is held to it. - selfhost.session.where [implemented]: A where condition on a message is run: conformance evaluates it over the logged payloads, so a run whose data breaks it does not conform. A condition is an expression over message ids in scope (the message itself and earlier named messages of its session) and their fields: field paths (q.price, p.card.last4), numbers (exact rationals), strings, true and false, = != < <= > >=, + - * /, and, or, not, and parentheses. A logged event may carry fields, an object whose nested objects are read by dotted paths. Always: when an event matches a message whose condition evaluates to false, that message is not matched (a guard selects among branches as a label does), and if nothing else matches, the problem names the condition and the values it read (where p.amount = q.price is false: p.amount = 12, q.price = 10); a condition that cannot be decided (a field missing from the log, a message not yet in the session, or division by zero) is reported as unchecked with the reason, per session and in the reading, and the event is matched; a condition outside the language, or one that does not type-check against the message types (selfhost.session.types), is refused when the text is read; generated Python and TypeScript code logs, with each event, exactly the fields of its body that some condition of the protocol reads, and nothing else of the body. Because a condition selects a branch, the sequence diagram draws the condition of a branch's first message as that alt operand's guard, [o.total >= 100] at the top of the operand, rather than under its arrow. The condition is interpreted by LeanFM, never compiled or executed, so protocol text from any client cannot run code in the server. Never: an undecidable condition counted as satisfied without being reported unchecked; a condition that is false accepted; a message body logged beyond the fields conditions read; a condition run as Lean or as any other code; more than 64 fields per event, or a field path or string over 200 characters, accepted.
- selfhost.session.types [implemented]: Every message has a type. Protocol text declares message types as Lean structures before the protocols that use them (structure Pay where amount : Nat; x y : Nat declares two fields; deriving clauses are accepted and ignored; a doc comment before a structure documents it). A message carries the structure its label names, or nothing when no structure has that name, and an event carries nothing. Field types are Nat, Int, String, Bool, a declared structure, or List T or Option T of one of those; fields are numbered in the order written, which is their protobuf number. The JSON form declares the same types as types: [{name, fields: ["amount : Nat"]}]. Always: every where condition is parsed and typed against the message types when the text is read, before anything runs: each field path names a declared single field of the message its id labels (through nested structures, not a list or a whole structure), comparisons and arithmetic take operands of matching types, and the condition is true or false, otherwise the text is refused with the reason; session_conform refuses a log whose event carries a field its message does not declare, a value of another type, or any field on an event, naming the event; session_types writes the types as a proto3 file, as Lean structures deriving ToJson and FromJson (each after the structures it uses), and as JSON schemas; session_openapi gives each body its message type's schema with only its declared fields; session_skeleton writes each message type as a Python dataclass and a TypeScript interface and types each send method's body with it. Never: a type naming no structure, a structure that contains itself, two structures or two fields with one name, a field name that is a keyword of Lean, Python, TypeScript or protobuf, a List or Option of a List or Option, a default value, a structure after a protocol, or more than 64 structures or 64 fields in one, accepted; a condition that reads a field whose name ends in _secr accepted, because the fields conditions read are logged; a logged event carrying a _secr field accepted; a message type with the name of a class the generated module defines; JSON-form type names or fields carrying anything but identifiers, colons and spaces into the protocol text.
- selfhost.session.envelope [implemented]: Every event that crosses a tool boundary has a declared shape: JSON is only how a protobuf message travels (the protobuf JSON mapping), never a shape of its own. The event envelope is a declared type, Event: ts (a Nat, nanoseconds, unique in its stream and its identity), session (the session key), from, to, label, cause and prev (the ts of earlier events), and the payload, one of the protocol's message types; session_types writes it as a protobuf message whose payload is a oneof over the message types. Integers (Nat, Int and timestamps) travel as decimal strings, so 64-bit values survive languages whose JSON numbers are doubles. A sessions block may name its key, sessions by b.member { ... }, a Nat or String field of a message of the block with an id; conformance then requires every event of a session to carry that field's value, as logged with the message, as its session. Generated Python and TypeScript encode each sent body into its wire form and decode each received body into its message type before role code sees it (TypeScript holds Nat and Int as bigint). session_simulate gives every event a ts in nanoseconds, unique in the stream and later than the events it happened after; session_sla reads ts in nanoseconds. Always: a decimal string is accepted wherever an integer is declared, and the value is exact; every generated stream's events have distinct ts in causal order. Never: a JSON number beyond 2^53 - 1 in magnitude, or one with a fraction, accepted as an integer; two events of a generated stream with one ts, or an event whose ts is not later than its cause; a session whose events name a session other than its key's value accepted by conformance; a received body that does not fit its message type handed to role code; a sent body that does not fit its message type put on the wire; a reward naming a unit the protocol never uses, or an observed event whose label is not a message or event of the protocol, accepted by session_sla; a session key that is not a Nat or String field, or names no message of its block.
- selfhost.session.proto [implemented]: The session type is the source of its message types: from it LeanFM writes the .proto, the Lean module and the OpenAPI document, as an OpenAPI file is written for an HTTP interface, and implementations use those directly. - selfhost.session.lean [implemented]: For one global session type with its message types, session_types writes the session as one Lean module: the payload structures, the roles as an inductive type, the payload as an inductive type with one constructor per message and per event, the event envelope (ts, session, src, dst, cause, prev, payload), and for each role its states as an inductive type with start, step : State -> Event -> Option State, final, involves and accepts. - selfhost.mcp.logic.ctl [implemented]: Tool check_ctl takes a task, either a canonical task id or an inline draft with states, initial state and message-labelled transitions, plus one JSON CTL formula over that task's observable atoms (at state, after message, terminal, claimed(claim) for a claim some transition of a draft makes, holding once a transition on the path has made it, and knows(actor, term) for an actor whose knowledge the draft declares: initial terms, and whether it sees every channel, with transitions carrying terms). knows(actor, term) holds at a state when the actor can derive the term, by the rules of the knows tool, from the terms it sent, received or (seeing every channel) observed on the path to that state; two paths that reach one state with different knowledge are different states of the model. It returns one of proved, disproved, unknown, unsupported or resource-limit, the reading, the declared bounds and terminal convention, and evidence: a witness path for an existential or possibly claim that holds, a counterexample path for a universal or never claim that fails, each as states and messages.
- selfhost.mcp.logic.trace [implemented]: Tool check_trace takes event envelopes (id, prevIds, causeIds, task, src, dst, message). It reports duplicate or dangling ids, cycles, causes that do not precede their effects, src/dst that contradict a message schema, which events are concurrent, and for each task whether its events are accepted by that task's grammar or the first event that is not. It returns the interaction diagram and causal graph derived from the events, so agents design sequence diagrams by writing events rather than drawing them.
- selfhost.mcp.logic.observability [implemented]: Tool classify_requirement takes a formula or a predicate text and classifies every atom as observable (a message, a field of a message, a task state reachable from messages), derived (knowledge from the causal past, a policy permission or obligation, a where_ predicate over message fields) or implementation-only (internal state with no observable consequence). For derived atoms it names the declaration that must exist; for implementation-only atoms it says the claim belongs in Implementation.lean or must be restated through observable events, and proposes the events that would make it testable. It never reports a hidden predicate as observable.
- selfhost.mcp.logic.knows [implemented]: Tool knows takes event envelopes {id, prevIds, causeIds, src, dst, term}, an actor, an event id at, the actor's initial terms and optionally a query term. Terms are JSON data built from atom, key, pk, sk, pair, tuple, enc {key, body} and hash. Always: knows considers only the events in the causal past of at (at itself, and every event reachable backwards from it through prevIds and causeIds) that the actor sent or received, or every event in that past for an actor declared to see all channels; it takes them apart by the declared rules (both parts of a pair; the body of a ciphertext whose opening key the actor can build: the private key for a public-key ciphertext, the public key for a signature, the key itself otherwise) until nothing new appears, and returns every piece the actor then holds with the event that first gave it. For a query it answers proved, with the derivation (which held pieces, combined by pairing, encryption or hashing), or disproved. Never: an event outside the causal past contributes; a value is reported derivable without a derivation; a rule recovers an atom, a key or a hash input the actor does not hold. Inputs are bounded and handled as data like every logic tool; an unknown or duplicate event id, a dangling reference or a malformed term is rejected.
- selfhost.logic.overlay [implemented]: Branch probabilities and delivery delays live in overlays separate from the task core; a declared and a measured overlay share one shape and every answer names its overlay. An overlay annotates every transition and nothing else, and the probabilities leaving each state sum to exactly 1 as exact fractions; it is never normalized silently and never changes a CTL verdict. From the core and an overlay LeanFM generates complete runs with exact probability and duration, the most likely witness or counterexample run, P(F target), P(F<=deadline target), the completion-time distribution and the expected duration; a task that revisits a state is reported rather than truncated.
- selfhost.mcp.logic.protocol [implemented]: Tool check_protocol takes honest roles as scripts of steps over message patterns (choose a variable from values; make a value fresh to this session; send a pattern to an intended recipient; receive a pattern, binding its unbound variables; make a claim with arguments), an attacker with a name and initial terms, finite domains for received variables, an optional number of concurrent sessions for each role, an optional defender in front of named roles (its keys, drop patterns and rewrite rules), and one formula. Always: a message delivered to a role the defender protects passes the defender first, which drops it when a drop pattern matches any part it can see, rewrites it when a rewrite rule matches, and otherwise forwards it; the defender sees inside a ciphertext only when it can build the opening key from its own knowledge; every session is a separate run of its role with its own bindings, named so the evidence tells sessions apart, and a fresh value differs between sessions and is unknown to the attacker until a message reveals it; every channel belongs to the attacker: each honest send adds its message to the attacker's knowledge, and an honest receive happens for exactly the messages matching its pattern that the attacker can build; the state space is generated from the declaration and decided by check_ctl, with claimed and knows atoms available, and the answer carries check_ctl's verdict and evidence plus the messages that crossed the wire on the returned path, each named as its evidence event names it: an honest send with its sender, its addressee and the attacker it went through; a delivery with the attacker and the receiving role. Never: a wire entry whose sender or addressee differs from the evidence event it reports. Never: a verdict of proved over a model cut off at the state bound (that is resource-limit); a send or claim using a variable that no earlier choose or receive of its role binds (that is an input error); an attacker that is also an honest role; two sessions sharing a fresh value; more sessions than the declared bound; a defender matching inside a ciphertext it cannot open, or protecting a role that is not declared; the defender's link to a protected role counted as the attacker's; any input run as code. The model is bounded: each session runs once, with the declared number of sessions, and variables bind values from the declared domains, never whole ciphertexts; the answer says so.
- selfhost.mcp.logic.secrets [implemented]: A check_protocol declaration marks what must stay secret, and marking a secret is asking a question: the attacker never derives it, on any path of the bounded model. A secret is marked in one of two ways: by name, any atom or symmetric key whose name ends in _secr (passwd_secr; a fresh variable so named makes a secret value in every session, passwd_secr#2 included); or by marker, a term listed in the secrets argument, which may be compound (the hash of a password, {hash: {atom: passwd_secr}}). A hash hides its input, so the hash of a secret is not itself secret unless it is marked: a hash that a server accepts in place of the password must be marked, and then its replay is reported. Always: every marked secret gets its own verdict (kept, leaked or resource-limit) decided by check_ctl as AG not knows(attacker, secret) over the same model as the formula, a leak with its evidence path and the messages that crossed the wire; with secrets marked, the formula is optional, and without one the answer's verdict is disproved when any secret leaks, resource-limit when the model was cut off, and proved otherwise; the answer names, for each secret, the terms that protect it: the opening key of every ciphertext some role sends with the secret inside (a public key's private key, a symmetric key itself), with the role and step that sends it, so it is visible that leaking that key leaks the secret; the answer lists, as warnings, names that look secret (containing passw, secret, token, priv or cred, in any case) but are neither named _secr nor listed, so a forgotten marker is reported rather than silently unchecked. Never: a listed secret none of whose atoms occurs in the protocol accepted (its check would pass vacuously; it is an input error naming the term); a secret reported kept over a model cut off at the state bound; more than 16 secrets; a secret checked only conditionally (secrecy that depends on whom a role talks to is a formula, such as never (claimed commit(B, A) and knows(Ivo, nb)), not a mark); a secret's name or term in a metric label.
- selfhost.mcp.logic.reassembly [implemented]: Tool check_reassembly takes a signature of 1 to 4 characters, the overlap policy of a defender scanning the stream and of the host behind it (first: old bytes win an overlap; last: new bytes win), whether the defender blocks (resets the stream on a match) or only alerts, and optionally a formula over the claims alerted(signature) and delivered(signature). Always: the attacker may send any segment of the stream, at any offset and length, with each byte the signature's or another, any number of times; the defender and the host each apply every segment with their own policy, except that nothing reaches the host after a blocking defender has matched; the search covers every such segmentation, and an evasion is answered with the segments that make it, in order. Never: proved over a model cut off at the state bound; an evasion reported for a defender and host with the same policy; a segment the defender did not see reaching the host; any input run as code.
- selfhost.mcp.logic.view [implemented]: The logic tools check_protocol, check_ctl, check_reassembly and knows declare an MCP Apps view (extension io.modelcontextprotocol/ui, protocol 2026-01-26): each tool definition carries _meta.ui.resourceUri ui://leanfm/logic-view, and resources/list and resources/read offer that resource as one static HTML document with mimeType text/html;profile=mcp-app. Always: a host that renders the view shows, from the tool result alone, the verdict, the reading, the evidence path one step at a time, and for check_protocol a sequence diagram of the messages on the wire with the attacker's knowledge and the claims made at each step; a host without the extension receives exactly the text and structuredContent results it received before. Never: tool data inserted into the document as HTML or script (it is placed only as text and as SVG geometry); a network request or an external script, style, font or image (the resource declares no CSP domains); a project path, credential or session value in the resource; an unbounded drawing (at most 64 path steps and 256 knowledge items are drawn, and the rest are counted); a ui:// URI other than the declared one answered.
- selfhost.mcp.logic.safety [implemented]: Logic tools treat formulas, tasks and traces strictly as JSON data: never compiled, evaluated or executed as Lean, shell or any other code. Inputs are bounded (formula nodes, task states and transitions, trace events, string lengths); exceeding a bound yields resource-limit or an input error, never proved. Tools are deterministic, stateless and read no paths.
