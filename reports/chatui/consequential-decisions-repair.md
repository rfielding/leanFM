# Assistant decisions and native approvals

The stakeholder delegates routine formal-language and reversible engineering
choices to the assistant. Interruptions should identify a major consequence
that is hard to reverse and has no authorized reasonable default. The two
human acceptance gates remain explicit, expressed in plain language about the
project's behavior and material consequences.

Positive invariant: the assistant chooses, records and validates routine
decisions within durable requirements and existing authorization; a user can
record each required approval directly in Chat with the same protected
controller used by Project memory.

The shared provider policy now explicitly owns Lean types, protobuf names,
channel records, transports, libraries, file layout, reversible prototype
storage and resource defaults. The live interrogation reference identifies its
checklist as internal completeness work rather than questions for the user.
Unknown measurements remain unknown; defaults cannot manufacture observations.
This refines the existing `consequential-decisions-only` implementation decision
and the `reversible_defaults_prevent_interrogation_loops` contract.

The pending checked gate appears above Chat as a native approval control. It
uses the current project/revision endpoint, never a model-authored option value.
A successful click refreshes Project memory and hides the completed gate. It
makes no provider request and does not generate source. Existing Project memory
controls remain available. A stale revision still fails in the controller;
current checked requirements acceptance remains necessary before implementation
acceptance and both remain necessary before source writes.

Investigation also found an existing explicit implementation-approval answer
that the model's question form had failed to record. That unchanged checked
revision was reconciled through the existing acceptance controller. The answer
and revision evidence remain below the owning project root. This is an operator
repair of an actual human approval, not a new model capability to accept gates
or a general interpretation of ordinary chat as approval.

| Forbidden behavior | Control | Evidence |
| --- | --- | --- |
| Turn routine syntax/engineering choices or an internal checklist into a stakeholder quiz | Shared policy owns the choices and defines the high interruption threshold; live reference marks its checklist internal | Both-provider default/readiness fixtures verify the complete policy, actual durable defaults and zero routine questions |
| Suppress a real consequential ambiguity or override a requirement | Existing authorization and durable constraints remain authoritative; genuine hard-to-reverse conflicts retain structured questions | Privacy-boundary question fixture remains available on both providers |
| Invent human acceptance from a model answer or accepted-looking text | Native button invokes the protected revision-bound controller; no model parser accepts a gate | Production browser clicks both native Chat approvals; source/gate negative tests remain in the full suite |
| Bill a provider or generate source merely by clicking approval | Approval invokes only the existing acceptance API | Browser asserts the chat-request count does not change at either approval |
| Accept a stale or cross-project design or race an active writer | Per-project request scope and aborted stale fetches; captured revision and existing server validation/writer controls | Existing stale-revision, caller-isolation and shared-writer tests |
| Include private account/project content in this change | No credentials or private evidence enter source, book or committed reports; only disposable fixture evidence is regenerated | Explicit staged-path/content review; existing plaintext-key and outside-project tests |

Verification uses local deterministic providers, not live inference. It
establishes the policy delivered to the model, real approval orchestration and
server controls, not a guarantee of every live model's judgment.
