Preface

LeanFM is a way of building software by arguing about it first. You describe what a system should do
in ordinary language; an LLM turns that into precise requirements; and LeanFM checks them and
shows what they mean, as sequence diagrams, state machines, event traces and counterexamples.
You push back, the requirements change, the pictures change with them, and only then is code
written.
     Its subject is the behavior of software at its boundaries: who sends what to whom, in what order,
within what time and with what probability, and what must always or never happen. The record it
keeps is a multiparty session type, one global description of a conversation from which each role’s
obligations are derived. Session types come from programming-language research, where they
guarantee that no party sends a message the other cannot handle or waits for one that will never
come. LeanFM uses them for messages between network nodes and calls between APIs alike,
and adds what the classic theory leaves out: every queue has a declared size, and every channel
declares how it fails. Messages are lost, duplicated, reordered and late; timers fire early; a retried
request arrives twice. LeanFM checks the protocol together with those facts.
     The precise part is Lean. Every requirement is a Lean definition: the roles, the messages down
to their protobuf bytes, the legal orders, and what must always or never happen. Definitions can be
checked, so diagrams are generated rather than drawn, and a contradiction (say A must reference
B , B needs a C , and policy forbids that C ) is found before anyone builds it. Requirements about
values, such as an identifier that must refer to a real object, are predicates whose enforcement the
implementation mapping describes; requirements over state no observer can see are flagged, so
they can be restated over events that can be tested.


Three layers, reviewed in git
Work proceeds in three layers, each checked before the next: the requirements (observable behaviour
and its generated views), the implementation mapping (how each requirement is realized and tested),
and the code, written in one pass. Review is what you already do with git: read the diff and commit it.
A passing check is evidence for that review, not the review itself.


Nothing lives only in the chat
A conversation with an LLM is temporary. Everything that matters is written into the project’s one
directory: the book, requirements, protobuf schema, implementation mapping and source. Delete
the conversation or start a new session and work resumes from the files. This repository is such a
project, and this book is part of its specification, read by the agents that work on it.

How to read this book
Chapter 1 sets out the method. Then come events and scenarios as recorded runs, a worked bakery
example, global types as grammars, TFTP (where declaring the physics turns a perfect session type
into a famous bug) and the authoring language. Chapter 8 covers the server and the MCP interface
through which an agent consults LeanFM’s logic. Later chapters apply temporal and modal logic to
security and legal examples, and Chapter 19 defines how a new project is set up.
    LeanFM is a working draft. The book records what exists alongside what is planned, and the
evidence labels of Chapter 1 say what stands behind each claim. The source is public [7].

Session Types as a Software
Engineering Method

LeanFM is a session-type method for engineering software. A multiparty session type is a global
description of a conversation: which roles take part, which messages pass between them, in what
order, and where it branches [12]. Each role’s local type is derived from it by projection, and a role
built to its local type cannot send a message nobody expects, or wait forever for one nobody will
send. That is the contract a team needs at every boundary where it does not want to read the other
side’s code.
     Session types began as a type discipline for programming languages [10, 11]. LeanFM uses
them one level up, as the requirements: the global type is what stakeholders argue about, the local
types are what each implementer owes, and recorded production events are checked against both.
     LeanFM departs from the textbook theory in one deliberate way: its channels have physics.
Standard asynchronous session types assume every message arrives exactly once, in order, through
a queue that never fills. Real channels are bounded; UDP drops and reorders; a timed-out HTTP
call is retried and seen twice; a Kafka consumer replays a batch after a rebalance; a timer cannot
tell a slow answer from a lost one. LeanFM makes each channel’s capacity and failure behaviour
part of the requirement and checks the protocol together with it. Chapter 6 shows the consequence:
a grammar that is a perfect session type, and an implementation with a famous bug that appears
only once the physics is declared. Messages between network nodes and calls between APIs are
handled the same way; they are channels that differ only in their physics.
Evidence labels used throughout: proposed notation (uncompiled); executable code (builds or
runs, not proof); finite-model check (exhaustive only within declared bounds); test (named finite
cases); generated analysis (named inputs and reducer); Lean proof (kernel-checked under stated
assumptions); future interface (planned, unavailable). Labels scope evidence; several may apply to
one artifact.

cross a network are where the physics, and the bugs, live.

sharded channel only if all its messages carry the same key, such as the session identifier. LeanFM
can check this from the declarations alone: a global type that relies on two messages arriving in
order, over a channel sharded by a field that differs between them, is rejected before any state is
explored.


1.3.1 Masked and surfaced failures
A lower layer can hide a failure by retrying, and the failure becomes latency. TCP retransmits, so a
protocol over a stream sees no loss, only delay, until the connection closes. UDP hides nothing, so a
protocol over it handles loss, reordering and duplicates itself, as TFTP does. Kafka hides loss inside
its retention window and surfaces duplicates instead. Every interface kind says which conditions
it surfaces, which the protocol must handle, and which it masks as latency, which the protocol’s
deadlines must allow for.

1.3.5 Cut and un-cut: what HTTP allows
A global type may say that a reply comes from someone other than the role that was asked:
fq: X() from A to B;
fr: Y() from C to A       cause fq;
CHAPTER 1. SESSION TYPES AS A SOFTWARE ENGINEERING METHOD                                           12

     Over HTTP this cannot happen: a response travels back on its request’s connection. The http
channel kind therefore adds a rule: every message is either a request to an interface of its receiver,
or the response to a pending request its receiver sent to its sender. A protocol that breaks the rule
must be un-cut, as a proof with a cut is expanded into one without: the missing calls and returns are
written out.
fq: X() from A to B;
fbc: X’() from B to C        cause fq;
fcb: Y’() from C to B        cause fbc;
fr: Y() from B to A          cause fcb;

    Collapse B and C into one lifeline, as in figure 1.3, and both forms become an ordinary call and
return between A and BC. A cut is a statement made at a coarser zoom level than its names suggest,
sound exactly when the roles it jumps between sit inside one node that the caller sees as a single
HTTP server. Purchase is cut twice: paid answers the client’s payment to the shop, and shipped
answers a request the client never made. Un-cut for HTTP, with the client as the only role that calls
the shop:
o: http POST /orders {item}          from Client to Shop;
choice {
  q: http 200 {quote}                from Shop to Client cause o;
  p: http POST /payments {quote}     from Client to Bank cause q;
  r: http 201 {receipt}              from Bank to Client cause p;
  c: http POST /orders/{id} {receipt} from Client to Shop cause r;
  v: http POST /receipts/verify      from Shop to Bank    cause c;
  w: http 200 {paid}                 from Bank to Shop    cause v;
     http 200 {shipped}              from Shop to Client cause w;
} or {
     http 409 {soldOut}              from Shop to Client cause o;
}

    Every cause now names a message its sender received, and every response goes back to the
role that asked. The other un-cut is a callback, which needs the shop to expose an interface the
bank’s island may reach (table 1.1). Choosing is a design decision; LeanFM’s job is to reject the cut
form on an http channel and show both (a future interface; the rule above is its definition).


1.4 Choice is always internal
Session-type theory distinguishes internal choice (a role selects which label to send) from external
choice (a role offers to receive any of several). Among actors reading their own queues only the first
is a decision: an external choice is the queue delivering what another role decided. So every choice
is made by one role, from what it can know: the messages it has sent and received.
    Every recorded event carries priorIds, the earlier events it follows, and causeId, the one event
that made it happen (Chapter 2). Realizability is then a rule about pointers: a role’s event may
cause-point only to events that role sent or received. A protocol in which a role reacts to something it
never saw cannot be implemented, and is rejected (a future interface; the rule defines the validation).
CHAPTER 1. SESSION TYPES AS A SOFTWARE ENGINEERING METHOD                                          13

1.5 The requirement is the global type
The requirement is the set of permitted, visible histories: who communicated with whom, which
message, what it carried, and which earlier messages it follows. Message bytes and persistent
formats become compatibility boundaries once another process, customer or stored data set depends
on them. Threads, actors, caches and retry machinery inside a role are realization choices unless they
change the observable conversation; modelling them couples requirements to harmless refactoring
and multiplies the state space. Channel capacity and failure behaviour, by contrast, are observable,
because they decide which histories can occur.


1.6 Comparison with TLA+
TLA+ is the specification language most engineers meet first. LeanFM neither extends nor replaces
it. A TLA+ specification commonly has variables, an initial-state predicate, a next-state relation,
and temporal formulas over the resulting behaviours [15]; a message queue is a sequence-valued
variable that actions append to and remove from.


1.6.1 An executable queue model
This module sends an order to Bob’s inbox, then lets Bob consume it and change his control state:
----------------------------- MODULE OrderQueue -----------------------------
EXTENDS Integers, Sequences, FiniteSets, TLC
CONSTANTS Clients, Servers, Orders, QueueBound, CacheBits, ClockBound
Actors == Clients \cup Servers
Messages == [kind : {"placeOrder", "placedOrder"},
             order : Orders, replyTo : Clients]
NoMessage == [kind |-> "none", order |-> "none", replyTo |-> "none"]
VARIABLES inbox, pc, current, sent, placed, received, scratch, tick
vars == <<inbox, pc, current, sent, placed, received, scratch, tick>>

Init == /\ inbox = [a \in Actors |-> <<>>]
        /\ pc = [b \in Servers |-> "idle"]
        /\ current = [b \in Servers |-> NoMessage]
        /\ sent = {} /\ placed = {} /\ received = {}
        /\ scratch = [i \in 1..CacheBits |-> FALSE]
        /\ tick = 0

Send(a, b, o) ==
  /\ o \notin sent /\ Len(inbox[b]) < QueueBound
  /\ inbox’ = [inbox EXCEPT ![b] = Append(@,
       [kind |-> "placeOrder", order |-> o, replyTo |-> a])]
  /\ sent’ = sent \cup {o}
  /\ UNCHANGED <<pc, current, placed, received, scratch, tick>>

Receive(b) ==
  /\ pc[b] = "idle" /\ Len(inbox[b]) > 0
  /\ current’ = [current EXCEPT ![b] = Head(inbox[b])]
  /\ inbox’ = [inbox EXCEPT ![b] = Tail(@)]
  /\ pc’ = [pc EXCEPT ![b] = "busy"]
  /\ UNCHANGED <<sent, placed, received, scratch, tick>>

   The behaviour is defined later in the same module:
Next == (\E a \in Clients, b \in Servers, o \in Orders: Send(a,b,o))
     \/ (\E b \in Servers: Receive(b) \/ Finish(b))
     \/ (\E a \in Clients: ReadReply(a)) \/ CacheStep \/ ClockStep
Spec == Init /\ [][Next]_vars

    Next is a relation between the current variables and their primed next values: one step is a Send,
Receive, Finish, ReadReply, cache step or clock step, and an action whose guards are false is
disabled. Spec == Init /\ [][Next]_vars reads: the first state satisfies Init, and every later
step satisfies Next or leaves vars unchanged. inbox’ is the next value of inbox; Append, Head
and Tail add, select and remove a message. Alice’s send updates Bob’s inbox, not his control
state; Bob’s receive does that. The full module commits the order, replies, and checks that no reply
precedes placement.

1.7 Discovery first, consolidation before commitment
During discovery the book may hold alternatives that are not accepted. Before a specification
is committed, and again before implementation, classify every normative idea as a requirement,
an implementation decision, a deferred item, or material to remove. Replace prose that mainly
enumerates roles, messages, states, ordering or quantities with a generated view and a short
interpretation; each view keeps its prompt, question, event source, reducer, unit and boundary. Only
committed, checked artifacts are binding.


1.8 Four ingredients
  1. Session types give the backbone: one global description of a conversation, projected to each
     role’s obligations, with well-formedness conditions that rule out unimplementable choices
     [11, 12, 25].

  2. Language theory gives compact generative descriptions of legal histories: a global type is a
     grammar whose terminals are messages. Dana Richards and Henry Hamburger, the author’s
     college professors, are cited in Richards and Hamburger [21] as where the author learned
     these methods, not as their originators; for symbolization, validity, proof, quantification and
     modal reasoning we also draw on Gensler [8].

  3. Protocol analysis contributes explicit participants, adversarial choices, trace semantics and
     tool-supported checking. An attacker is one more role, or a channel an adversary controls.
     The CSP treatment of Ryan et al. [22], including Steve Schneider, is cited as where the author
     learned it.

  4. Temporal logic turns expectations into queries over the product of roles and channels. CTL is
     central because it distinguishes claims about some possible future from claims about every
     one [5].


1.9 A test for every abstraction
      Can a developer state a conversation once, with the physics of its channels, compose it
      with other conversations, check its consequences, and keep it stable while the imple-
      mentation of each role changes?

   An abstraction that does not improve that workflow does not belong in the core library.

Session Histories Made of Events

A global type says which conversations are legal. An event is one message of one actual session,
recorded as it happened; checking an implementation means checking its list of events against the
global type and its physics. A small common envelope makes histories comparable across protocols:
structure Event (Actor Session Task Kind Payload : Type) where
  timeAt : ClockTimestamp
  id      : String
  priorIds : List String
  causeId : Option String
  session : Session
  task    : Task
  from    : Actor
  to      : Actor
  kind    : Kind
  payload : Payload

abbrev Trace (Actor Session Task Kind Payload : Type) :=
  List (Event Actor Session Task Kind Payload)

     id identifies a visible fact. priorIds lists immediate predecessors, and causeId optionally
names the one event that directly caused this one (MCP’s check_trace spells them prevIds and
causeIds, protobuf prior_ids and cause_id). from and to are the roles; session names the
instance of the global type, and (session, task) correlates independently progressing conversa-
tions; kind is a stable discriminator; the payload carries the parameters that flow between productions.
timeAt comes from a shared monotonic clock whose differences measure elapsed time; its origin
does not matter.
     Predecessor links form a directed acyclic graph. A fork is several events naming the same
predecessor; a join is one event naming every branch it depends on. An end event may also name its
start, which makes elapsed time end.timeAt - start.timeAt even when attempts with the same
(session, task) overlap; such an edge may be redundant for ordering but is useful correlation. A
predecessor edge means “ordered after”, not “caused by”.
     causeId is the causal pointer, and it adds or removes no interleavings. A task start may cause
messages, which may cause nested task starts, and a terminal points to the event whose work it
finishes. The reverse relation gives causal subtrees, which a renderer draws as nested labeled boxes
without pretending that concurrent children are ordered. The pointer also makes choices checkable:
a role decides only from its own history, so causeId must name an event its sender sent or received

(Chapter 1). A response’s causeId is its request’s id, which stays unambiguous with many requests
in flight because it follows identity, not adjacency.
     An m-of-n join also records m, n and the m distinct branch-terminal IDs, members of priorIds,
that satisfied it; two predecessors alone cannot distinguish two-of-three from an ordinary two-branch
join.

2.2 Derived state
A current session, an authenticated principal or an outstanding request is computed by folding the
trace, so its evidence stays visible. Private state enters the model only when two executions with the
same visible trace may legally diverge, and even then the first remedy is to expose the distinction as
an event or parameter.


2.3 Time is more than a timestamp
Timing constraints pair explicit boundaries; changing a timeout changes the requirement, not the
order or causal relations. Elapsed time between two events of one (session, task):
def elapsed (start finish : Event) : Option Duration :=
  if start.session = finish.session &&
     start.task = finish.task &&
     start.timeAt <= finish.timeAt
  then some (finish.timeAt - start.timeAt)
  else none

    Latency queries name their boundary kinds and select the start through the terminal’s backpointer,
since (session, task) alone cannot separate overlapping attempts; reducers never pair by adja-
cency. Every declared terminal uses the same pairing. A collapsed production keeps its boundary
IDs, links, parameters, aggregate deltas and validation status, so opening and closing it changes
presentation only.

Scenarios

A scenario is LeanFM’s named, bounded stream of timestamped events for one run of a session
(for example, a quote request, OAuth exchange, or 9×9 game). The global type says which runs are
legal; a scenario is one of them, either generated from the type or recorded from production, and it is
the concrete thing people point at while arguing about the type.


3.1 Event envelope and scenario grouping
The shared envelope and semantics of id, priorIds, causeId, actor endpoints, correlation and
monotonic timeAt are defined in Chapter 2. A serialized scenario key or aliases such as src/ message
are canonical only if the accepted schema and reducers declare them.


3.2 Derived outputs and provenance
Question-driven outputs include interaction diagrams, residual state machines, latency/throughput
charts and outcome distributions. Each DesiredOutput must bind its prompt, precise question,
event source, reducer, unit and scenario boundary. A listed output is not implemented until its renderer

4.7 Money and waste
The same corpus answers economic questions through ordinary reducers. For each calendar
day, net revenue is the sum of SaleCompleted amounts less refunds; ingredient cost comes from
BatchBaked; employee pay from ShiftPaid; and modeled contribution is revenue less ingredients

Global Types as Grammars

A global session type is a grammar. Its terminal symbols are messages, each with a sender and a
receiver; its productions are the type’s sequence, choice, parallel composition and recursion; the
language it generates is the set of legal conversations. Requirements therefore stack: every protocol
reads as if it were the top-level one, and a larger one includes smaller ones.
    Global types are written in Lean with the protocol syntax of LeanFM.Session. A protocol
elaborates to a value of type Global R for any role type R, and the library checks who decides each
choice, what each cause may point to, and each role’s projection. SessionExample.lean holds
every protocol in this chapter and runs those checks whenever it is elaborated. For durable artifacts
a protocol translates to the older GrammarExpr form that the rest of LeanFM’s validation consumes.
The queue rules at the end are model semantics, not a proof about a Go runtime.


5.1 The protocol syntax
Every message is a Lean structure whose fields are its payload:
structure Order       where item : String      deriving TypeName
structure Quote       where price : Nat        deriving TypeName

   A misspelt label is then an unknown identifier, not a new message. A protocol names its roles
and lists statements:
protocol Purchase (Client, Shop, Bank) {
  o: Order from Client to Shop;
  choice {
    q: Quote from Shop to Client cause o;
    p: Pay   from Client to Bank cause q where p.amount = q.price;
       Paid from Bank to Shop cause p;
       Shipped from Shop to Client;

       SoldOut from Shop to Client cause o;
  }
}

right one way: the decider is the role that starts every branch, by sending its first message or by an

an empty branch, or { }, is that role choosing to do nothing. If Alice’s message started one branch

and Bob’s the other, both could act at once; the checker reports the race, naming who starts what.

and external to the others. The second condition, that every role whose behaviour differs between
branches is told which was taken, is checked by projection (below). A first attempt at TFTP that puts
the sender’s timer beside the acknowledgement as a choice has no decider at all:

5.4 Projection: from the global type to each role
Projection derives each role’s local type: the protocol with every message the role neither sends nor
receives erased, and the rest rewritten as sends and receives. A choice the role makes becomes a
select; another role’s becomes an offer, resolved by what arrives. Global.project for Purchase:

  receive Quote from Shop;
  send Pay to Bank;
  receive Shipped from Shop;
} or {
  receive SoldOut from Shop;
}

Shop
receive Order from Client;
select {
  send Quote to Client;
  receive Paid from Bank;
  send Shipped to Client;
} or {
  send SoldOut to Client;
}

Bank

  receive Pay from Client;
  send Paid to Shop;

  }

  { capacity, whenFull := .dropNewest, order := .any,

    Per-key ordering is fifo on a sharded channel. The checked system is the product of the local
types and their channels, and each field adds or removes transitions:

    • capacity and whenFull: a send to a full queue blocks the sender, delivers a refusal message
      back to it, or discards a message;

    • order: under fifo only the head of a queue may be delivered; under any any queued message
      may be;

    • sharding: the channel is partitions queues, each with the declared capacity, and a send
      goes to the queue its key selects; for checking, keys are abstracted to as many distinct values
      as the protocol’s messages can tell apart;

    • loss: a transition that removes any queued message;

    • duplication: a transition that delivers a queued message and leaves it queued.

   A timer may fire whenever its role is waiting. Each may multiplies the state space the checker
explores. Chapter 6 builds this product for TFTP: a classically well-formed type whose original
implementation duplicates every block once one timer fires early. The rest of this chapter defines the
default physics: bounded, reliable, blocking queues.


5.6 Local types run on actors with bounded queues
Each role is played by an actor, which may take part in many sessions at once and has finite inbound
and outbound queues. Producing a message may block on a full outbound queue and transport on
a full inbound one, so sending, delivery and consumption are distinct. Messages carry a session
identifier (the instance of the global type) and a task identifier, whose pair keys actor-local work:
structure WorkKey where
  session : SessionId
  task    : TaskId

structure ActorRuntime where
  inboundCapacity : Nat
  outboundCapacity : Nat
  inbound          : List Envelope
  outbound         : List Envelope
  inFlight         : List (Prod WorkKey GrammarResidual)
  inboundBounded   : inbound.length <= inboundCapacity
  outboundBounded : outbound.length <= outboundCapacity

    Consuming an envelope selects or creates the residual for its (session, task) pair; there is no
actor-wide “current task”, and keys interleave while each conversation keeps its order. The queues
behave like Go channels, with capacity enforced when an operation is attempted:
CHAPTER 5. GLOBAL TYPES AS GRAMMARS                                                        39


send(channel, message) =
  if channel.length < channel.capacity
  then sent(channel ++ [message])
  else blocked

receive(channel) =
  if channel = message :: rest
  then received(message, rest)
  else blocked

tryReceive(channel) =
  if channel = message :: rest
  then some(message, rest)
  else none

    A blocked operation leaves the channel unchanged until space or data appears. tryReceive
returning none means empty now, lets the actor continue, and is not an optional payload. The
transitions:

   • an actor step appends a produced envelope to its outbound queue;

   • a transport step moves the outbound head to the destination’s inbound queue when both
     operations are within capacity;

   • a receive step removes an inbound envelope and advances the matching (session, task)
     residual;

   • sending to a full outbound queue blocks the sender without enqueueing;

   • transport to a full inbound queue blocks without removing the outbound head;

   • blocking receive on an empty inbound queue blocks, while nonblocking tryReceive returns
     none and permits later work.

   Queue order is not predecessor order: FIFO decides which envelope is available next, while
priorIds records the event graph, forks and joins included. Incomparable branches may commute,
and a predecessor pointer does not claim causation.

Declared Physics: TFTP and the
Sorcerer’s Apprentice

A grammar does not say what happens to a message after it is sent: whether it queues, how large
the queue is, whether the network loses it, duplicates it or delays it. Those facts are part of what a
protocol means. The example is the Trivial File Transfer Protocol (TFTP) [23, 24] and its best-known
defect, the Sorcerer’s Apprentice bug, named and fixed in RFC 1123 [3].
    This is the book’s central claim in its smallest form. As a multiparty session type [12], the original
and the fixed sender are the same well-formed protocol. With the physics declared, LeanFM finds a
walk in which one early timer makes every later block travel twice for the original, and proves that
none exists for the fix.
    Status: the verdicts are real check_ctl results, and the protocol and its physics are checked
Lean in SessionExample.lean. The product of roles and queues is still built by a small script,
video/tftp_model.mjs in the companion video repository; deriving it from the declarations is future
work.


6.1 The grammar
TFTP moves a file in numbered blocks. The sender sends DATA n; the receiver answers ACK n; the
sender then sends DATA n+1. A block shorter than the full size ends the transfer.
   In LeanFM’s session-type syntax, with the physics beside it:
protocol Transfer (Sender, Receiver) {
  rec Block {
    d: Data from Sender to Receiver;
    choice {
      Ack from Receiver to Sender cause d;
      continue Block;
    } or {
      LastAck from Receiver to Sender cause d;
    }
  }
}

    Without a timer this is a textbook global type: the receiver chooses, answering Ack for a full

reading has nowhere to put it, because it assumes every message arrives exactly once, in order.


6.2 The physics
tftpPhysics above declares each channel as udp with one difference written out. Each direction
holds at most two packets, delivered in either order or dropped, and the sender’s timer may fire any
time a block is unacknowledged, since a slow answer looks like a lost one. The network is declared
never to duplicate: every duplicate below is made by the sender. The model has three blocks. The
two senders differ in one line, the reaction to a repeated ACK:

Original (RFC 783).
      Every ACK n, even a repeated one, makes the sender send DATA n+1.

Fixed (RFC 1123).
     A repeated ACK is ignored. A block is sent again only when its own timer fires.

   The checked machine is the product of sender, receiver and both queues: 201 reachable states
and 891 transitions for each sender. Its events are timeout, drop, data (a new block delivered),
dupk (block k delivered again, and acknowledged again), ack (the first ACK for the current block),
dupack (an ACK for an earlier block) and done.

lost and the timer never fires. Can block 3 still arrive twice? From the state after that timeout:

7.1 Proposed scenario notation
A scenario is a named fragment of a global type: a grammar whose terminals are observable
messages, each with a sender and a receiver. from_ and to_ (avoiding Lean’s from) set the
endpoints copied into each event, and an emit without both is invalid. let x := e evaluates a Lean
expression; let x <- declare T "x" introduces an immutable typed symbolic value bound by
generation or matching. Reusing a binding expresses identity, and receiving an event binds its fields
for later messages. emit and receive are the same kind of terminal, differing only in projection.
def requestQuote (customer shop : Actor) : Scenario :=
  scenario "request a quote" do
    let requestId <- declare RequestId "requestId"
    let quoteId <- declare QuoteId "quoteId"
    let amount <- declare Money "amount"
    from_ customer; to_ shop
    emit "quote requested" [field "requestId" requestId]
    from_ shop; to_ customer
    emit "quote offered"
      [field "requestId" requestId, field "quoteId" quoteId,
       field "amount" amount]

    Early requirements can use semantic message names and typed fields without a protobuf schema;
that suffices for ordering, correlation and temporal properties. A later refinement maps the fields to a
concrete alphabet, with the obligation of language inclusion once representation details are erased:
serialization, retries and internal state may be chosen there, but no visible behavior the abstract
grammar forbids.
    Named inclusions are reusable productions, not textual copies; they can export values for later
events, and a compiler resolves references, checks exports and rejects cycles. A quote outcome, for
example, chooses between named accepted and declined branches, each renderable on its own
(diagram contract: Chapter 3; generated examples: Chapter 5).

client-visible outcomes, answering “what actually stops if an attacker takes this set down?”. Today
only a checklist item and a Characterization.lean plan exist.

7.8 Composing requirements means intersecting constraints

def quoteSystem : SystemSpec :=
  generatedBy quoteOutcome
  |> requireAll
      [ correlate "offered quote matches request"
          (sameField "requestId")
      , forbid "confirmation without acceptance"
          (event "order confirmed" && notPreviously "quote accepted")
      , ctl "every accepted quote is answered"
          (AG (accepted --> AF (confirmed || rejected)))
      , timing "answer within service objective"

      ]

8.2.1 The code that creates the TCP listener

open Std.Net

  SocketAddress.v4

partial def serveLoop (server : TcpServer) : IO Unit := do
  let client ← (server.accept).block
  let _ ← IO.asTask (handleClient client) Task.Priority.dedicated
  serveLoop server

8.4.3 Five verdicts
proved The formula holds on every reachable state within the stated bounds, with a witness where
      it is existential: a finite-model check, not a Lean proof.

disproved A counterexample path is returned.

unknown The model cannot decide: a derived atom, a predicate text, or a message field value, none
      of which a task’s state machine carries.

unsupported The operator is outside the implemented logic.

resource-limit The reachable model exceeded its bound of 4096 nodes. The tested obligation
     Exhausted search never proves forbids reporting this as proved.

   Malformed or oversized input (an unknown operator, a bare G without its path quantifier, a
misspelled state or message, a formula beyond 256 nodes) is rejected with the reason, so a typo is
never silently read as false.


8.4.4 Requirements without observable behavior
A requirement over hidden state is incomplete, not wrong. An observable atom is decided by the
event trace alone; a derived atom is computed from it by a declared reducer (a balance, a count, the
values an actor could have read); an implementation-only atom refers to state no event reveals. The
tested obligation Hidden predicates never pass as observable keeps the third kind out of conformance
tests. The classifier proposes events, such as a CacheAudited or KeyRotated message with the
fields that expose the predicate, so the requirement can be rewritten over them and decided by
check_ctl.

  1. Classify each sentence; turn implementation-only atoms into proposed events.

8.5 A tour of the LeanFM chat
Chapter 9 walks through the screens. This section states the rules behind them.
    Select a project, then Chat. The workspace holds Project memory, Chat, Book, Grammar, Tasks
and Source; switching project or phase preserves drafts, selections, queues and fetched results, and
active work continues while hidden. The header names the billed provider, model and key fingerprint;
each turn shows its token usage. For each turn the model receives the selected project’s book and
canonical specifications, then a bounded recent transcript; no other project, and not LeanFM’s own
book, supplies fallback context.
    Chat accepts ordinary language, images, rough pseudocode and protocol questions before
anything is settled. The ordinary outcome is a decision and a checked artifact, with no question.
The agent reads prior answers and recorded choices, picks reversible defaults within the recorded
requirements and authorization, records them, and lists only choices the stakeholder is likely to
challenge. A question must name a consequential, hard-to-reverse effect (scope, observable behavior,
compatibility, security or privacy, irreversible data, material spending) that no recorded decision
resolves. There is no approval step: the stakeholder reviews the diff and commits it. Compiler and
routine check failures go through the bounded recovery below, not to the stakeholder.


8.5.1 Progress, cancellation and the Operational trace
A running turn shows an Agent running banner with the captured model, elapsed time, latest stage
and a cooperative Cancel. Status, Project memory, Source and the Operational trace are polled
every two seconds. The trace records each bounded workspace action as started, completed, failed
or rejected; a proposed write names its project-relative destination, content kind and size before
validation, so a path failure says what LeanFM was trying to write. Cancellation is checked at provider
and tool boundaries: no new mutation starts after it is seen, and completed edits remain.
    Prompts typed during a turn join a visible, removable, project-local queue and run once, in order,
each with the model visible when it was queued. Focus order in the composer is prompt, Send,
model selector, so Tab, Enter sends with the visible model. A returned clarification question logs its
stable ID, and so does a submission that bypasses its form; neither log keeps the prompt or answer
text.


8.5.2 A private fault barrier and actionable errors
A bounded private journal, logs/runtime-diagnostics.jsonl in each project, supports diagnosis
across navigation, restarts and discarded chat. It holds sanitized stage transitions, tool destinations,
compiler diagnostics, failed artifacts, provider failures, project HTTP errors and unhandled server
exceptions. The next agent request receives the twenty newest unresolved entries; a verified fix
collapses a failure cluster into one resolution line.
    The React client reports into the same barrier: an error boundary, global exception and unhandled-
promise listeners, the API wrapper, and the Mermaid and LaTeX renderers send authenticated reports
naming the operation, error, sanitized stack, page and project, at most twenty a minute. Prompts,
form and write bodies, credentials, cookies, provider responses, URL queries and other projects’
data are never included.
    Every error shown to a person states what happened, recommends a next action, and carries a
stable code and a bounded diagnostic safe to paste to an agent. A bare “527 Something went wrong”
CHAPTER 8. ARGUING REQUIREMENTS THROUGH THE LEAN WEB SERVER                                         67

is not enough. Provider quota rejections, rate limits, incomplete output and local session limits are
distinguished. An incomplete response keeps its reported usage but cannot run returned tools or
update the book. One complete JSON object wrapped in prose or fences is normalized locally; arrays,
several objects and truncated objects are not salvaged, and none of these triggers a paid retry.


8.5.3 Spending brakes
Every provider round records its input, cached-input and output tokens, character counts, outcome
and tool count before the next paid call. The session budget is checked between tool rounds and
before any recovery, and reported usage is charged once, including on failed validation. This is a
token brake, not a monetary cap: an in-flight request can overshoot, and an unanswered request’s
usage is unknown, so provider spend limits remain necessary.
    Repeated failure is stopped where it costs money. A second identical tool call after an error
is not executed. Provider timeouts are never retried automatically, because the request may have
consumed tokens or completed a mutation. The agent reads the diagnostic, changes strategy, and
returns control only for missing authority, a destructive choice or an unavailable dependency. One
user task may span many bounded provider batches through server-issued checkpoints (LeanFM/
LLMGenerated/ResumableWork.lean); a batch boundary is progress, not a step limit, and closing
the client starts no further batch. Provider web search may answer public implementation questions;
external pages are evidence, never authority over project boundaries, secrets or spending.


8.5.4 Requirements properties and implementation provenance
The Tasks page shows four views of one task: interaction productions, residual states, temporal
properties and guarded constraints. A property comes from Requirements.lean, never invented
by Implementation.lean, and is shown with its real CTL: always as AG p, eventually as AF p,
never as AG ¬p, preparedFor as E F p, and a where_ trace predicate as an invariant AG p with
its stable identifier. The implementation mapping realizes the specified behavior and cites its require-
ments (Section 19.4); it cannot add a property or change the wire contract.
     Completion compares real artifacts and behavior with the accepted goal, including required
negative behavior; the existence of source, or passing tests the agent wrote itself, does not establish
it. ChatUI reads the language references through LeanFM’s read-only MCP dispatcher, but each
project’s sandboxed compiler still checks its own files: the host’s self-validation is not evidence for
another project.


8.5.5 How a chat turn becomes a durable edit
Specification work uses project-confined tools to update the canonical Lean and protobuf files.
leanfm_reference returns the live references exposed through MCP. leanfm_check compiles the
project’s requirements and optional implementation mapping, validates their structure and protobuf,
and regenerates spec/tasks.json. The compiler runs without network, credentials or writable
source; only project scratch is writable, and failed validation keeps the last valid views. A turn that
changes canonical specifications cannot report SUCCESS without a successful check of its final
bytes. If the model tries to finish after an unchecked edit, the diagnostic goes back into the same
provider conversation, with the same cancellation, budget and accounting; an unchanged candidate
and diagnostic stops further paid work.

    The requirements reference includes a complete compilable request/response example with
matching protobuf, task states, grammar, processes, properties, negative obligations and view
provenance; a reduced scope still needs these collections (markdown, for instance, holds typed
RequirementMarkdown records). The implementation reference compiles a mapping for the same ex-
ample: MessageCodegen.wireType names the generated protobuf type, and each ChannelCodegen
states send, receive, drain and close semantics, while capacities stay in the requirements.

limits, writes atomically, and builds in an isolated worker; only a successful build commits it and
sets book_updated=true. On failure the first compiler diagnostic is shown, the previous source is
restored, and at most three short repair requests run, each given only the diagnostic and a seventeen-

rather than by paid retries.

writes real buildable files, bindings and tests under the project’s source/. A response that says
“implemented”, or pastes a Go listing into chat, is not SUCCESS while source/ is empty; a missing
material decision becomes one focused question. This instantiates Chapter 14, and the deterministic
HTTP test checks a compiled book update, a real source/main.go write, and rejection of an
implementation claim with empty Source.
    Application delivery ends with a working source/Makefile: every generated HTTP application
exposes build, run, stop, test, check, clean and serve, and LeanFM invokes only these, re-

separate from LeanFM. The run check launches it in a private network without host credentials,
writes only project cache, checks readiness and the application page, and stops only its own process
group; changed source makes its evidence stale. Passing it establishes these bounded observations,
not refinement of the specification. spec/runtime.json and spec/ProjectMemory.md keep the
goal, defaults, known remedies and remaining gaps across an erased chat.


8.5.6 Example: ask to see MCP move

an MCP server as lifelines, and a downstream tool only when the example really calls one. The client

and receives its result or error, correlated by JSON-RPC ID (compare figure 8.1).

8.5.7 What should appear in the response

expects a leanfm-canvas fenced block, removes it from the prose, and runs its canvas and script

design, the selected messages become a named scenario in the typed grammar and the diagram
is regenerated from it; only that view is evidence. To share the exact motion, the chosen revision
becomes a project-owned GIF or MP4.


8.5.8 Images

8.6 Local credentials and visible billing identity
The LeanFM login is not a provider login. One account password unlocks the user’s OpenAI and
Anthropic keys together; they are authenticated together inside one password-encrypted bundle,
never stored in plaintext and never returned to the browser. The API keys form, also opened by
the ?keys=1 link, adds or replaces either key; blank fields keep the stored ones, and adding a key
keeps the current session. A password change verifies the current password and writes one atomic
envelope holding the new verifier and the re-encrypted bundle, so an interruption cannot split them.

Replacing a key or the password revokes older sessions, including in another server process sharing

keys survive restarts; only unlocked sessions do not.

8.8 What the Lean artifact must settle
The Lean artifacts are the semantic source for actors, framed messages, process projections, gram-
mars, properties, proof obligations and desired outputs: Chapter 2 defines event fields, correlation,
order, causation and time; Chapter 5 legal conversations, projections and bounded queues; Chapter 7
choices, dwell, rates, scalability, reliability and cost.
   Message-count capacity alone does not bound memory when payload sizes vary. Queued bytes
come from encoded envelopes, and active task state needs a declared footprint. A representative
requirement is
                                                                              
                     AG queuedBytes(a) + inFlightBytes(a) ≤ budget(a) .
This is a modeling obligation, not a claim that the validator proves an arbitrary implementation’s heap
usage.


8.9 Interrogate, characterize, synthesize, replay
Characterization tests whether desired claims can be identified from evidence: scenario and task
boundaries, terminal-to-start links, actor populations, clocks and units, observation windows, resource
bounds, failure evidence and probability provenance. Missing inputs stay indeterminate. One
event stream produces the standard characterization, whose inventory is outOfBoxArtifacts in
LeanFM/Characterization.lean; baselineDerivedProperties records each property’s fields,
reducer, unit, visualization and boundary. Specified distributions may drive predictions or generation
but are never presented as measurements (estimators: Chapter 2).
     For generative similarity, reducers map the source stream to a named metric vector with each
histogram bin as an exact ratio. A candidate is serialized, decoded and reduced the same way, and
passes only when every metric is within its declared tolerance: “similar” means equivalent under this
finite characterization. The grammar, invariants and byte language still constrain legal traces.


8.10 The protobuf artifact is part of the requirement
The protobuf schema answers what a state diagram cannot: which bytes cross a boundary. Atomic
payload messages and a RequirementEnvelope.oneof discriminator connect each grammar ter-
minal to its wire form; validation checks, among other things, that field tags are nonzero and unique
and that framing is explicit. The pairing exposes real defects: an event that needs a priorIds list
where the wire carries one predecessor, a latency property over a clock that is never recorded, a
byte budget beside an unbounded field.
    The exact wire size feeds resource analysis:
queuedBytes actor observation :=
  (observation.inbound actor).sum encodedSize
  + (observation.outbound actor).sum encodedSize

memoryPressure actor observation :=
  queuedBytes actor observation
  + inFlightFootprint actor observation.activeWork

   The first term is computed from concrete envelopes; the second is a declared abstraction of
implementation state, and stays labeled as one.

8.11 A ladder of checks
No single green check answers every kind of requirement. Lean and protobuf check syntax; structural
validation checks actors, endpoints, terminals, framing, process coverage and proof obligations; gram-
mar and temporal checks cover ordering, safety, reachability and bounded liveness; probability and
dwell reducers predict outcomes and event-stream reducers estimate them; queue and byte-budget
checks model capacity, backpressure and memory; generated diagrams, plots and reports support
review. Each result carries an evidence label from Chapter 1. Predictions are not measurements,
incomplete windows censor tasks, frequencies do not prove probabilities, and bounded traces do not
prove unbounded liveness.


8.12 How to argue well
The most useful prompts attack boundaries:

    • “Which event and grammar branch make this claim true?”

    • “With two concurrent sessions and tasks, what blocks on a full queue and which events
      correlate?”

    • “Which random choice belongs to the user, and how does it change the downstream completion
      and latency distributions?”

    • “Derive the plot from the event stream, including in-flight tasks.”

    • “Show the corresponding protobuf payload and its encoded-size bound.”

    • “Which evidence label applies: Lean proof, finite-model check, test, generated analysis, or
      assumption?”

   Conversation discovers the specification; durable artifacts retain it (Chapters 19, 3, 2 and 14).

Worked Example: OAuth Authorization
Code Flow

This chapter is a behavioural sketch inspired by the OAuth authorization-code flow, starting above
HTTP and protobuf, to exercise scenario decomposition, parameter flow, alternatives, requirements
and rendering. In session-type terms it is a global type with five roles, a grant-or-deny choice by
the authorization service, and parameters such as state and the code that flow from one message
to a later one. Its channels are HTTP calls and browser redirects, whose physics (a redirect never
followed, a callback replayed by an attacker) is where the security requirements live.
     The listings are proposed notation, not compiled; the generated figures are real. The flow is
simplified: the authorization request omits client_id and response_type, and the token request
carries only the code, without redirect_uri, client authentication or PKCE, all required by RFC 6749
and current guidance. The knowledge claims hold for this simplified flow only.

Authentication detail used by Production 2
OAuth does not prescribe how the authorization service authenticates the person; a password branch
exercises knowledge flow without pretending the password is an OAuth parameter.
def authenticateAtAuthorizationServer (password : Password) : Scenario :=
  scenario "authenticate resource owner" do
    from_ .browser
    to_ .authorizationServer
    emitBytes "credentials submitted"
      (protectFor .authorizationServer
        (encode [field "password" password]))

    from_ .authorizationServer
    to_ .browser
    oneOf "authentication result"
      [ emitBytes "authentication accepted" (encode [tag 1])
      , emitBytes "authentication rejected" (encode [tag 0])
      ]

    protectFor promises confidentiality to the named endpoint, realized later by TLS, message-level
encryption or a trusted local channel. Without it, a network observer would derive the password from
the bytes.

10.4 Scenario 3: exchange the code and use the token

def exchangeAndFetch : Scenario :=
  scenario "exchange code and fetch resource" do
    use code     <- imported AuthCode "code"
    use resource <- imported Resource "resource"

10.10 Probabilities and charts
The randomness belongs to the user, who grants or denies consent; everything else reacts de-
terministically. As written, though, the server emits both grant and error, so by the deciding-actor
rule of Chapter 5 the server chooses. A faithful model adds a consent event from the browser,
ConsentGiven or ConsentRefused, making the user’s choice observable. Weights live in an overlay
(Chapter 13); the proposed weightedOneOf writes them inline:
def consentDecision : Scenario :=
  weightedOneOf "consent decision"
    [ weighted (87 / 100) authorizationGranted
    , weighted (13 / 100) authorizationDenied ]

def oauthCharts : List ChartSpec :=
  [ pie "authorization outcomes" do
      source events; groupBy terminalOutcome; value count
  , line "end-to-end authorization latency" do
      source (correlate events by "state")
      x clock; y (elapsed "authorization requested" "application response")
  ]

   The branches then begin with different consent bytes, and every later transition may have
probability one: the grant branch carries mass 0.87 through queues, transport and the deterministic
response. Deterministic processing transports probability mass; it does not remove it.
   For the simplified path with no loss or timeout,

            P (grant callback) = 0.87 · 1 · 1 · 1 = 0.87,     P (denial callback) = 0.13.

 Each factor of one is a deterministic step; dwell affects latency, not mass. Scheduling (which enabled
actor runs next) remains nondeterministic, so the composed system is an MDP, analysed under a
fixed or quantified policy (Chapter 7). With several sessions in flight, its state holds every actor’s

CTL over Generated Futures

A well-formed global type already guarantees safety, fidelity and progress under its channels’ as-
sumptions. Everything else a stakeholder wants to know is a question about futures: can the transfer
always still finish, must it, can this message ever precede that one? The global type and its channel
physics generate a branching transition system, and CTL speaks directly about that branching: path
quantifiers distinguish some future from every future, temporal operators the next state, eventuality,
invariance and until. The author learned the modal logic used here mostly from Kröger and Merz [13].


11.1 Basic modal logic
Propositional logic evaluates a formula at one world or state. Basic modal logic adds an accessibility
relation R between worlds and two operators:


                          w |= □p iff p holds at every v such that wRv ,
                          w |= ♢p iff p holds at some v such that wRv .


    □p and ♢p read “necessarily p” and “possibly p”, and are dual: ♢p ≡ ¬□¬p. The symbols
do not fix what accessibility means: a next computation state, a world compatible with an actor’s
knowledge, a permitted world. The basic logic K allows any frame; reflexivity, transitivity, symmetry
and the Euclidean condition give stronger systems, whose principles must not be imported because
“necessarily” sounds strong. LeanFM’s relation is a directed computation successor, not reflexive,
symmetric or epistemic.


11.2 LTL: time along one path
Linear Temporal Logic (LTL) describes one path with X (next), F (eventually), G (always) and U
(until): F p says p holds at some suffix of the path, Gp at every suffix. Its operators answer where
along this path, not whether one branch or every branch is meant; the common convention that every
initial path must satisfy the formula is outside the syntax. “Some legal execution eventually recovers”
and “every one does” are different claims that share the words “eventually recovery”.
     LeanFM does not implement LTL. It uses CTL because requirements combine two independent
axes:

                                                 100
CHAPTER 11. CTL OVER GENERATED FUTURES                                                             101

    • always or eventually says where along forward time a predicate must hold; and

    • necessarily or possibly says whether it must hold on every permitted forward continuation or
      may hold on at least one.

    The construction is temporally alethic: possible means possible now or at some point along a
legal future. English uses “always” for both universal modality and temporal persistence; CTL keeps
the two coordinates apart.


11.3 CTL: path modality combined with time
CTL pairs a path quantifier with each temporal operator: E , some permitted continuation (temporal
possibility), or A, every one (temporal necessity). They quantify over legal computations from
the current observation, not timeless worlds. F versus G is eventuality versus invariance along a
continuation; E versus A is some versus all continuations. The four core combinations and their
dualities:


  E F p : possibly eventually p,      AF p ≡ ¬E G ¬p : on every future, eventually p,
  E G p : p always on some future, AG p ≡ ¬E F ¬p : p holds on every future at every position.


  A ranges over futures and G over positions along one. The dualities drive counterexample search:
AG p is tested by searching for E F ¬p, AF p by searching for E G ¬p. A witness refutes the universal
property; its absence establishes it only within the finite checked model.

11.3.2 Asymptotic cost
Let V be the reachable observations, E the edges, L the formula’s nodes and P the simple paths
a search inspects. The recursive evaluator keeps a path-local list of visited states and memoizes
nothing, so one temporal search costs O(EP + V P ) time (EP edge visits over those paths) and
O(V + L) memory: it may revisit a state once per path reaching it, and P can exceed 2V in a
dense graph. The fixed-point evaluator avoids this: each fixed point takes at most V + 1 iterations of
O(V + E), so a formula costs O(L V (V + E)), within its bound of 4096 nodes. Worklist propagation
would reach the textbook O(L(V + E)); that is a target.
    None of this compares LeanFM with TLC. LeanFM often builds a smaller graph by omitting private
variables, but a well-abstracted TLA+ model may omit them too, and a speed claim would need the
same protocol, properties, bounds, hardware and settings. The book claims only a different modeling
boundary.
    An observation is immutable once recorded: values change only on a forward transition to a
successor, though they need not be monotone.

11.4 Projecting to LTL-style F and G
Requirements often want the simpler forms F p and Gp, which LeanFM shows only with an explicit
path policy. On one selected execution, AF p and E F p both project to F p and AGp and E Gp to
Gp; under the convention that every initial path must satisfy the formula, F p is AF p and Gp is AGp.
Displaying AF and AG as F and G is an interface reduction, not an equivalence: the artifact keeps
the exact CTL, so the checker can still use witnesses, negation and the right counterexample search.

11.5 Persistence and recurrence
Nested CTL operators express two common requirements:

                                       AF AG p,        AG AF p.

 The first is eventual permanent safety: every path reaches a state from which every path keeps p
(finish key rotation and never accept the old key again). The second is universal recurrence, “always
eventually p” (service keeps returning to ready). For witness searches their duals are:

                    ¬(AF AG p) ≡ E G E F ¬p,           ¬(AG AF p) ≡ E F E G ¬p.

 The existential forms are E F E G p and E G E F p; in the second, the eventual witnesses may leave
the outer path, so it does not require infinitely many p on that path. These cover useful persistence
and recurrence, not all LTL: GF p corresponds to AG AF p on a total transition model, but AF AG p
is stronger than pathwise F Gp, since it needs a state where all continuations stay safe. Terminal
states follow the checker’s continuation convention.

11.7 Possibility means preparedness
A requirement that declares E F p does more than admit that a checker can find a path to p: it says
p is a supported future the system must prepare for. A possibly obligation therefore links three
artifacts:

   1. a legal grammar branch and witness trace reaching the condition;

   2. a handling plan in Requirements.lean; and

   3. generated implementation code whose justification cites that possibility requirement.

This is the target; today validation checks only that a handling plan is cited, not that generated code
exists or covers the witness.
    For example, “a bakery delivery may fail” requires a decodable DeliveryFailed message, a
legal failure branch, and code that performs the specified refund or notification behavior. Removing
every failure branch does not implement reliability; it makes the real failure trace out-of-spec.
    Possibility is not probability: a possible condition may be rare or of unknown likelihood, and the
handling obligation comes from its being supported, not from a percentage crossing a threshold.
E G p carries a different obligation: some future keeps p, so the system monitors the conditions that
keep that future viable, exposes their loss, and controls choices that would destroy it. That every
execution keeps p is the stronger AG p.


11.8 Strong implication and the Chewbacca argument
The “Chewbacca defense”, from the South Park episode “Chef Aid”, is a courtroom parody that uses
an irrelevant claim to distract from the conclusion: a memorable non sequitur. Material implication
p → q is true whenever p is false, which permits a vacuous global claim when no reachable state
satisfies p. LeanFM names the non-vacuous combination

                                          def
                                p ⇒s q     =    E F p ∧ AG(p → q).

   It requires a legal future witnessing p and that every reachable p also satisfies q , so together they
imply E F q . The absurd test:


                                   p = “Chewbacca lives on Endor”,
                                   q = “you must acquit”.


    Mentioning p does not obtain q : the model must reach a p witness and establish AG(p → q) on
every continuation, and if the grammar relates residence to nothing, that obligation fails. Logic cannot
judge the relevance of English propositions, but neither a missing antecedent nor one rhetorical
occurrence of it can make the implication pass vacuously.
    In Lean the definition is direct:

11.9 Weak until: AW and EW
Strong until requires the right operand to occur; weak until allows it never to, provided the left operand
keeps holding:


                   p AW q : on every future, p holds until q , or p remains forever,
                   p E W q : on some future, p holds until q , or p remains forever.


    The state satisfying q need not satisfy p. Weak until fits “remain available until shutdown, which
is permitted but not required”. p E W q equals (p E U q) ∨ E G p, but (p AU q) ∨ AG p is not AW on
a branching system: some futures may reach q while others keep p forever, so neither disjunct holds
although every future satisfies weak until. LeanFM implements AW directly.
def serviceMayRunUntilShutdown : CTL Observation :=
  atom available AW atom shutdown

def someWorkerCanRemainReady : CTL Observation :=
  atom ready EW atom retired

    In r && (p AU q) the right operand is the whole AU expression.

11.10 Past claims
CTL looks forward, but security claims often cite the past: “this capability was previously issued”, “this
response matches an earlier request”. Since states are trace prefixes, past facts are predicates over
the accumulated trace. Bounded past conditions can be compiled into forward monitor state, evaluated
before the monitor takes the current event; on concurrent histories, “before” must be declared as
causal ancestry or a chosen linearization, never screen order. Whether explicit past operators read
and check better than trace predicates or monitors is open, judged by how specifications survive
changes to the event schema.


11.11 Fairness and time bounds
AF alone does not distinguish a participant perpetually denied a turn from one that violates the
protocol, so fairness assumptions are named, scoped and visible in theorem statements. “Eventually”
is not “within 200 milliseconds”: time bounds belong in an explicit timed layer, not in timestamps and
prose.

conditional on its premises: the governing code is chosen, open-textured terms such as “reasonable
effort” are atoms a person supplies, and the facts are only as good as the history.

13.1 The core says what can happen
A client sends a Request. The server answers with a Response, or a Timer fires a Timeout and
the client retries. After the third timeout the client gives up. Retries are bounded, so the task unrolls
them into states: one waiting state per attempt.
    The core carries no numbers. It says only which messages can follow which, and it already
answers the qualitative questions: every run ends, and giving up is possible.


13.2 The overlay says how likely and how long
A separate table, the overlay, annotates each transition with a branch probability and a delivery
delay. This one is declared: it states what we expect (a 10% timeout rate, 40 ms responses, 200 ms
timeouts). A measured overlay would have exactly the same shape, reduced from recorded traces
instead of asserted, and the same questions could be asked of either. Keeping the numbers out of
the grammar means a project without probabilities loses nothing, and declared and measured values
can be compared on one unchanged specification.

Chapter 14

Feature Completion as Positive and
Negative Proof

A request to show a message, list source, accept a transaction, render a diagram or produce an
MP4 states a desirable observation. The change can also introduce stale state, disclosure, resource
exhaustion, weaker authentication, corruption or success without an artifact. Completion therefore
requires a paired argument:

   1. a positive invariant states what the system must do; and

   2. applicable negative invariants state what the system must never do.

    For a feature that crosses a boundary, the positive invariant is a property of the global type, and
the negative ones usually name a message that must never be sent or accepted under a channel’s
physics: a replayed request, a response to the wrong session, a call after its deadline. Review is
proportional: button spacing needs no cryptographic audit, filesystem access needs authorization
and path analysis, and a material risk without a mapped, tested control blocks completion.


14.1 The logical shape of a feature
Let g oodf mean the observable contract of feature f , and let badf ,1 , . . . , badf ,n name reachable
failures introduced or exposed by that feature. A common safety-shaped completion condition is
                                                   n
                                                   ^
                                   AG g oodf ∧          AG ¬badf ,i .
                                                  i=1

   The first conjunct is positive; each other is negative: no permitted execution reaches a forbidden
observation. The counterexample form

                                       AG ¬bad ≡ ¬E F bad

    is what a negative test does: it tries to build the E F bad witness (another user’s project path, a
stale response after a project switch, an oversized upload, a secret in a log), and finding one refutes
completion. Some features are liveness obligations, such as AG(submitted → AF (complete ∨
f ailed)); review must not swap liveness for safety or hide fairness and availability assumptions.

14.2 Stability review before security review
Before editing code, identify the existing invariant and review the applicable ways an environment
change could break it:

Regression. Which accepted behavior, file format, route, proof, or UI state can this change invalidate?
     Preserve conforming behavior and add a regression test at the narrowest durable boundary.

Failure. What happens when a dependency, renderer, compiler, provider, filesystem operation, or
      network request fails? Failure must become an explicit terminal observation rather than a false
      success or endless wait.

Concurrency. Can a late response, simultaneous session, queued prompt, or overlapping write
    be attributed to the wrong project or revision? Correlation identity and revision checks must
    survive reordering.

Resources. What bounds memory, bytes, queue occupancy, recursion, process time, media dimen-
    sions, and response size? A new feature must not silently turn a finite resource contract into
    an unbounded one.

Durability and recovery. Which state is authoritative after restart or partial failure? Atomic writes,
     rebuildable indexes, and project-local ownership make recovery inspectable.

Compatibility. Which clients, stored revisions, generated artifacts, and build environments must
    continue to work? Version or migrate a changed representation rather than reinterpreting old
    bytes silently.

   Record the concrete invariants at the changed boundary, and say briefly when a dimension is
non-material.


14.3 Security as forbidden observable behavior
“A user never reads a project they do not own” states protected behavior; “use authentication” names
a mechanism. Before choosing a control, identify:

   1. the trust boundary crossed by the feature;

   2. the asset being protected;

   3. the attacker’s relevant capability; and

   4. the forbidden observable outcome.

   Forbidden behaviors include unauthorized access, cross-user or cross-project disclosure, secret
persistence or logging, injection, path or symlink escape, replay, request/response confusion, privilege
expansion, executable media, resource exhaustion and failing open. State them testably (“a source
path absent from the authorized inventory never returns bytes”), and map each material one to a
control (path confinement, authenticated identity, an allowlist, a byte limit, an atomic revision check)
and a negative test or proof; a mechanism alone proves nothing.

14.4 The feature-completion ledger
For each feature, retain the following compact traceability record in the typed requirements and
implementation mapping:

   Field                 Required content
   Prompt                The stakeholder request whose completion is being claimed.
   Positive claim        Observable always or liveness property, with actor, scenario, boundary,
                         and revision.
   Negative claims       Applicable never or always-not properties; omitted families are explicitly
                         judged non-material.
   Controls              Concrete implementation mechanisms mapped one-to-one or many-to-
                         one to the negative claims.
   Evidence              Positive conformance tests plus negative tests, proofs, generated traces,
                         and named checks.
   Residual risk         Stated limitation the stakeholder reviews in the diff, assumption, deferred
                         mitigation, or an explicit completion blocker.

    Both sides need evidence: ruling out failures does not demonstrate the feature, and a demonstra-
tion does not rule out disclosure or corruption.


14.5 Worked example: the project Source view
“Show implementation files in the Source tab.” Positive: selecting an authorized project lists its
files, and selecting a readable UTF-8 file shows it; switching projects clears the selection, so a late
response cannot show stale content. The feature crosses a filesystem boundary, protecting source,
account records, repository metadata and credentials from a user who can choose URL paths and
guess names. Negative invariants:

    • a user never reads another user’s project source;

    • a guessed ignored or metadata path never returns bytes;

    • a path or symlink never escapes the authorized source root;

    • a binary or oversized file never becomes an unbounded text response;

    • a project switch never retains the previous project’s source state; and

    • an empty source directory never accompanies a claim that implementation succeeded.

    Controls are an authenticated explicit project ID, canonical root resolution, exact source-inventory
membership, UTF-8 reads, a finite response limit and project-keyed React state. Negative tests
request another account’s file and a guessed .git/config; both return not-found without revealing
existence. The positive test creates, lists and opens a project-local file and checks its exact content.

14.6 Worked example: chat auto-scroll
Even a small convenience has stability boundaries. Positive: loading a conversation and every new
message reveal the bottom of the chat pane, scrolling that pane, not the page or the sidebar, and
resetting with the project-keyed component. No authorization boundary is crossed, so a threat model
would be noise, but project isolation and stale responses still matter.


14.7 When the result is not complete
The ledger is incomplete with an untested positive claim, a missing negative requirement, an uncon-
trolled risk, a control without a negative test or proof, a liveness claim without its fairness assumptions,
skipped validation, or a check of a substitute artifact. Report the blocker and return to the relevant
layer, stating any residual risk where the stakeholder will see it before committing. A green build or a
persuasive diagram does not fill these gaps.

Lean as the Rendered Language

The notation for global types, local types and channel physics renders to a conservative subset of
Lean, with no second opaque specification file: domain declarations are Lean definitions, behaviours
Lean values, and requirements Lean propositions or checked queries. Rendering the proposed
scenario DSL into Lean is a future interface; the typed LeanFM API is the current executable code,
and a Lean proof claim applies only to a theorem checked in the declared build. Every displayed
formula carries an English reading, in its accessible text, that accounts for each operator, index and
bound.

def eventuallyAnswered : CTL Observation :=
  CTL.ag (CTL.implies requestPending
    (CTL.af (CTL.or requestAccepted requestRejected)))

   Semantic machinery comes from a fixed library; an author supplies only:

    • typed actors, identifiers, event kinds, and payloads;

    • parameterised grammar definitions;

    • projections from trace prefixes to observable propositions;

    • named temporal requirements and proofs or decidable checks.

    so generated Lean stays small enough to review, and library proofs and algorithms are reused,

model and initial state. It means “at every reachable state, the premises require at least one of these
conclusions.” Write it in a rule-like form, familiar from Prolog:

                                    a ∧ b ∧ · · · ∧ w ⊨ x ∨ · · · ∨ z.

                                                                      

 This is entailment within the declared model and initial state, not general entailment over all models,
and the conclusion that holds may differ between states. In code, a counterexample is a reachable
state where every premise is true and every conclusion false:
counterexample(state, premises, conclusions) :=
  premises.all(p => evaluate(p, state)) &&
  !conclusions.any(q => evaluate(q, state))

entails(successors, initialState, premises, conclusions) :=
  !anyReachable(successors, initialState,
    state => counterexample(state, premises, conclusions))

The author learned from Ryan et al. [22] to treat a security protocol as communicating roles plus
an active intruder, and security as properties of every trace that intruder can produce. This chapter
keeps that idea and none of that book’s examples. Three small invented protocols each press on
one part of the method:

   1. an on-call handoff, where three separately written roles must compose into one protocol;

   2. a sealed-bid auction, where an attacker who cannot read a bid can still copy it; and

   3. speaker pairing, where a code shown on a screen is visible to some actors and not to others.

     Status: the three examples are a design exercise. Their RoleSpec, WireTerm and composeRoles
listings are proposed notation, and there is no role-composition engine yet. The attacker’s deduction
rules are implemented (LeanFM.Session.Knowledge), and so is a checker that generates the
attacker from a declaration (LeanFM.Session.Attack), which Section 17.8 uses on a real protocol.


17.1 Roles compose by sharing events
This is the session-type picture seen from the other side: each role is written first, as a grammar over
its own view of the events, and the global protocol is whatever their composition admits. Composition
synchronizes on shared events; it does not concatenate scripts. The attacker is the role session
types usually leave out: one that controls the channels and can read, drop, replay or forge what
passes through them, the most hostile physics a channel can declare (Chapter 1).

   For a global trace t, let t ↾a keep only the events actor a sends or receives. The composition
accepts a trace exactly when every role accepts its own view of it:

                     L(composeRoles(R1 , . . . , Rn )) = {t | ∀i, t ↾ai ∈ L(Ri )}.


    A message is one global event with one identity, one byte string, one sender and one recipient, and

about the bytes empties the composed language from that prefix on, and the checker reports the
prefix. A role may bind values from events it has seen and test later events against them; the bindings
are a parser environment for the trace, not a claim about implementation memory.

17.3 Example 1: an on-call handoff
A pager service records who is on call for a team. Exactly one engineer is on call at any time. Olu
is on call and wants to hand off to Ines. The pager must not move the duty until Ines has actually
accepted it, and Olu must learn that the handoff completed. Each person shares a long-term key
with the pager: KO for Olu, KI for Ines.
CHAPTER 17. PROTOCOL EXERCISES: ROLES, ATTACKERS, AND KNOWLEDGE                                   132

   1. Olu → Pager: {Ines, h}KO , with a fresh handoff id h.

   2. Pager → Ines: {Olu, h, c}KI , with a fresh challenge c.

   3. Ines → Pager: {h, c, accept}KI .

   4. Pager → Olu: {Ines, h, done}KO .


17.3.1   Three roles, written separately

def oluRole (olu ines pager : Actor) (ko : SharedKey) : RoleSpec :=
  role olu "outgoing engineer" do
    let h <- fresh Nonce "h"
    from_ olu; to_ pager
    send (encrypt ko.ref (tuple [actor ines, nonce h]))
    from_ pager; to_ olu
    receive (encrypt ko.ref (tuple [actor ines, nonce "h", atom "done"]))
      where_ field "h" == h

def inesRole (olu ines pager : Actor) (ki : SharedKey) : RoleSpec :=
  role ines "incoming engineer" do
    from_ pager; to_ ines
    receive (encrypt ki.ref (tuple [actor olu, nonce "h", nonce "c"]))
    let h <- take Nonce "h"
    let c <- take Nonce "c"
    from_ ines; to_ pager
    send (encrypt ki.ref (tuple [nonce h, nonce c, atom "accept"]))

def pagerRole (olu ines pager : Actor) (ko ki : SharedKey) : RoleSpec :=
  role pager "pager service" do
    from_ olu; to_ pager
    receive (encrypt ko.ref (tuple [actor "next", nonce "h"]))
      where_ field "next" == ines
    let h <- take Nonce "h"
    let c <- fresh Nonce "c"
    from_ pager; to_ ines
    send (encrypt ki.ref (tuple [actor olu, nonce h, nonce c]))
    from_ ines; to_ pager
    receive (encrypt ki.ref (tuple [nonce "h", nonce "c", atom "accept"]))
      where_ field "h" == h && field "c" == c
    from_ pager; to_ olu
    send (encrypt ko.ref (tuple [actor ines, nonce h, atom "done"]))

   The where_ clauses are the context-sensitive part: the message sequence is context-free, but
whether a reply is legal depends on values bound earlier in the trace.


17.3.2 What composition catches
Suppose a later edit lets the pager send done as soon as it has sent the offer, before Ines replies.
Olu’s role still accepts that order: Olu never sees messages 2 and 3. Ines’s role still accepts it too.
Only the composed protocol exposes the problem, through the duty properties below:
CHAPTER 17. PROTOCOL EXERCISES: ROLES, ATTACKERS, AND KNOWLEDGE                                    133



                                       AG exactlyOneOnCall.



                                onCall(Olu) AW accepted(Ines, h).


                                                                           
                          AG toldDone(Olu, h) → P accepted(Ines, h) .


     The second formula uses weak until on purpose: Ines may never answer, and then Olu simply
remains on call. Strong AU would wrongly demand that every handoff eventually succeeds. The third
is a past claim (P reads “previously”). With the faulty edit, the checker returns a counterexample trace
in which Olu is told done with no earlier acceptance, drawn both as the global interaction diagram
and as Olu’s local view, in which nothing looks wrong.
     The same mechanism catches disagreement about values. If the pager’s grammar could forward
the offer to someone other than the engineer Olu named, the where_ field "next" == ines
guard and Ines’s projection cannot both accept the same event, and the composed language is empty
at that prefix.


17.4 Example 2: a sealed-bid auction
An auctioneer collects bids in two phases. While bidding is open, each bidder sends a commitment:
the hash of the amount and a fresh random salt. After bidding closes, each bidder reveals the amount
and salt, and the auctioneer accepts a reveal only if it hashes to the commitment. The highest
revealed bid wins. Ana and Ben bid honestly. Ivo is also a registered bidder; he is the attacker, and
he sees every message on the network.
def bidderRole (b auctioneer : Actor) (amount : Amount) : RoleSpec :=
  role b "bidder" do
    let s <- fresh Nonce "salt"
    from_ b; to_ auctioneer
    send (tuple [actor b, hash (tuple [value amount, nonce s])])   -- commit
    from_ auctioneer; to_ b
    receive (atom "closed")
    from_ b; to_ auctioneer
    send (tuple [actor b, value amount, nonce s])                  -- reveal

def auctioneerRole (auctioneer : Actor) (bidders : List Actor) : RoleSpec :=
  role auctioneer "auctioneer" do
    let commits <- collectWhileOpen fun b =>
      receive (tuple [actor b, ?commitment]) where_ b in bidders
    broadcast (atom "closed")
    forEach commits fun (b, commitment) =>
      receive (tuple [actor b, ?amount, ?salt])
        where_ hash (tuple [amount, salt]) == commitment
    announce (highestRevealed commits)

17.4.1 Secrecy holds, and the auction is still broken
Before close, Ivo has seen Ana’s commitment but cannot invert the hash, so he does not know her
amount. That secrecy property holds:

                                   ¬ knows(Ivo, aAna ) AU closed.


    The auction is still broken. Ivo does not need to know Ana’s amount to bid it. He copies her
commitment and sends it under his own name. That is a legal attacker move: he observed the hash
term, and resending a known term is always derivable. After close he waits for Ana’s reveal, which
he also observes, and sends the same amount and salt under his name. The auctioneer’s check
passes, because the hash really does match. Ivo has tied Ana’s bid without ever having known it
while bidding was open.
    The property that fails is about who formed each commitment, not about who knows what:
                                                                                 
                    AG acceptsCommit(Auctioneer, b, x) → P formed(b, x) .


   The checker’s search for a violation, E F (acceptsCommit(. . .) ∧ ¬P formed(. . .)), returns the
copy trace above as its witness.


17.4.2 The fix: bind the bidder into the commitment
Put the bidder’s own name inside the hash: hash(b, amount, s), and have the auctioneer recompute
the hash with the name of the bidder who sent the reveal. Ivo’s copied commitment was formed with
Ana’s name. To open it under his own name he would need a salt that makes hash(Ivo, . . .) equal
hash(Ana, . . .), and no rule derives one. Copying is now useless.
    This is the acceptance test for an intruder model: it must find the copy trace for the original
commitment and none for the fixed one. A model that cannot find the first attack is too weak to trust
when it finds nothing in the second.
    The symbolic model has a visible limit here. If amounts came from a small set, Ivo could hash
each candidate and compare; the salt stops that. Dolev–Yao deduction has no notion of guessing,
so “salts are fresh and unguessable” must be written down as an assumption.


17.5 Knowledge and agreement as theorems
The attacker is one more role. It observes the events its channels let it see, may block or replay them,
and may send any term it can derive from them.
inductive Derives : Knowledge -> WireTerm -> Prop where
  | initial : term in knowledge -> Derives knowledge term
  | tuple   : (forall x in xs, Derives knowledge x) ->
              Derives knowledge (.tuple xs)
  | project : Derives knowledge (.tuple xs) -> x in xs ->
              Derives knowledge x
  | encrypt : Derives knowledge key -> Derives knowledge body ->
              Derives knowledge (.encrypt key body)
  | decrypt : Derives knowledge (.encrypt key body) ->
CHAPTER 17. PROTOCOL EXERCISES: ROLES, ATTACKERS, AND KNOWLEDGE                                  135

              Derives knowledge (inverse key) -> Derives knowledge body
  | hash    : Derives knowledge x -> Derives knowledge (.hash x)
  -- no rule recovers x from .hash x

def intruderRole (ivo : Actor) : RoleSpec :=
  adversary ivo do
    observe (channelsVisibleTo ivo)
    mayBlock
    mayReplay
    maySend fun knowledge term => Derives knowledge term

   Knowledge is calculated for every actor from every accepted trace, not only the intended run, so
security claims become theorems over accepted traces, derived knowledge and explicit compromise
assumptions. For the fixed auction:
theorem auction_bid_sealed_until_close
    (trace : Trace WireEvent)
    (accepted : fixedAuction.Accepts trace)
    (fresh : SaltsFreshAndUnguessable trace) :
    forall b x, beforeClose trace x ->
      not (Derives (knowledgeAt .ivo trace x) (value (amountOf b))) := by
  exact hashHidesSaltedInput accepted fresh

theorem auction_commitments_not_copyable
    (trace : Trace WireEvent)
    (accepted : fixedAuction.Accepts trace) :
    forall b c, acceptsCommit trace b c -> formedBy trace b c := by
  exact boundNameDefeatsCopy accepted

    The two theorems are still proposed notation: the lemmas they name do not exist yet. The
deduction rules do. LeanFM.Session.Knowledge defines them as Derives, over atoms, symmetric
keys, key pairs, pairs, encryption and hashes; a ciphertext under a private key is a signature, opened
with the public key. It decides them one value at a time: analz takes what an actor has seen
apart until nothing new appears, and synth asks whether the value can be built from the pieces.
(Enumerating everything an actor could build would never end.) The decision is proved sound:
theorem knows_sound {K : List Msg} {v : Msg}
    (h : knows K v = true) : Derives K v

    So when the checker says the attacker knows a value, a derivation exists. Completeness, that
knows misses nothing Derives allows, is tested on examples but not yet proved, and secrecy verdicts
lean on it.


17.5.1 Calculated knowledge and policy inside CTL
Knowledge and policy need not start as new modal operators. Define state predicates by reducing
the event history, then use them inside ordinary CTL. knows says who can derive a value; allows
and requires say what a declared policy permits and obliges:
def knows (actor : Actor) (value : Secret) (s : ProtocolState) : Bool :=

17.6 Example 3: pairing a speaker by a code on its screen
A new speaker shows a six-digit code d on its own display. Its owner types the code into a phone,

network.

   1. Speaker → Owner, on channel display: d.

   2. Owner → Phone, on channel keypad: d.

   3. Phone → Speaker, on channel network: p, hash(p, d, Phone), with a fresh nonce p.

   4. Speaker → Phone, on channel network: paired or rejected.
CHAPTER 17. PROTOCOL EXERCISES: ROLES, ATTACKERS, AND KNOWLEDGE                                         137


receive (tuple [nonce "p", ?proof]) on network
  where_ sender != speaker
  where_ proof == hash (tuple [nonce p, value shownCode, actor sender])
  where_ failedAttempts < 3

    Three things are new compared with the first two examples.


Channels decide what each actor observes. The display and keypad events belong to the
observations of the speaker, the owner and the phone, not to Ivo’s. That is what keeps d out of Ivo’s
knowledge closure, and it is a modeling assumption about the room, so it is stated as one. Remove it
and the checker should immediately find Ivo pairing his own phone.


A counter is context, too. failedAttempts < 3 depends on how many earlier proofs failed in
this trace. Like the equality guards, it keeps the grammar context-free and moves the counting into a
named predicate.


Guessing is a probability, not a deduction. Ivo cannot derive d, but he can guess it. The symbolic
model says E F paired(Ivo) is true: some future has a lucky guess. That verdict is correct and
useless on its own. The requirement is a bound on how likely that future is, carried by a probability
overlay: with three attempts against 106 codes,

                                       P [F paired(Ivo)] ≤ 3/106 .


    The next section explains why the number attaches to E .


Some claims compare histories. “Ivo cannot tell which code was shown” is not true or false of one
state: it says any two histories differing only in d look identical to Ivo. That is Ka over indistinguishable
histories, a relational theorem rather than a CTL state formula, and the one claim in this chapter that
the table below does not cover.


17.7 Where each modality attaches
The examples have used every kind of claim a requirement needs: what can or must happen, how
likely, by when, who knows, who may, and who must. None needs a new logic. A CTL operator is a
path quantifier, A or E , fused with a temporal operator such as F , G or U : probability belongs to the
quantifier, deadlines to the temporal operator, and knowledge and policy are predicates on states.


The path quantifier E invites “how likely?” E says that some future satisfies the path formula;
the refinement replaces “some” with a probability over futures, whatever follows the E :

                 E F p ⇝ P [F p],         E G p ⇝ P [G p],         p E U q ⇝ P [p U q].
CHAPTER 17. PROTOCOL EXERCISES: ROLES, ATTACKERS, AND KNOWLEDGE                                    138

    The number comes from an overlay of branch probabilities, as in the bakery chapter, and is
reported beside the CTL verdict, never in place of it. The overlay cannot make E F p false: a future
with probability 3/106 is still possible, and so still needs the handling that possibility demands. Nor
does A become “probability one”: a set of futures can have probability one and still leave out a future
that A must cover, which is why Chapter 11 keeps A and E about legal futures only.


The temporal operator F invites “by when?” F has no bound, and a user waiting on a handoff
needs one, so the deadline is written on F (and on the right of U ): AF≤t q says every future reaches
q within t, E F≤t q that some future does. A deadline under A is a promise the grammar must keep:
every waiting state needs a timeout branch ending in an explicit outcome, or some future waits past t.
                                                                        
                              AF≤15 min accepted(Ines, h) ∨ expired(h) .


                                                                            
                      AG closed → AF≤Treveal revealed(b) ∨ forfeited(b) .


   So the handoff needs an Expired message to both engineers when the offer times out, and the
auction a Forfeited outcome for a bidder who never reveals: new legal branches, with decodable
messages and code that handles them.


The two annotations compose. Probability on the quantifier and a deadline on F combine into
the question stakeholders usually ask: how likely is it to happen in time? An owner pairing a speaker
within a minute is

                                       P [F≤60 s paired(Phone)],


   which a measured overlay reports from real pairing attempts. Keep a guaranteed deadline (AF≤t ,
enforced by a timeout branch) separate from a usual one (P [F≤t ], measured). The bakery chapter
shows why: a declared delay promised a 1.2 s sale while only about half the recorded sales met it.


knows, allows and requires complete the set. These are about actors rather than futures, and
each is computed from the history up to a state, so the temporal operators carry them unchanged.
Secrecy is knows under AU ; authorization is knows implying allows under AG; an obligation is
requires paired with AF≤t on the act that discharges it.

17.8 Needham–Schroeder, checked
The public-key protocol of Needham and Schroeder (1978) has three messages:
protocol NS (A, B) {
  m1: Msg1 from A to B;
  m2: Msg2 from B to A cause m1 where m2.na = m1.na;
  m3: Msg3 from A to B cause m2;
}

    Alice runs it once, with a peer she chooses: Bob, or Ivo. Bob answers once, whoever claims to
be calling. Ivo is a legitimate user with his own key pair, so Alice may well choose him; he is also the
network, seeing every message and sending anything he can derive.
    Nobody builds the state space. Each honest role is a short script over message patterns: a
choice, sends, receives and claims; a variable in a received pattern binds whatever the message
carries there.
def alice (v : Variant) : Role := { name := "Alice", steps :=
  [ .choose "peer" [.atom "B", .atom "I"]
  , .claim "running" [name "A", .var "peer"]
  , .send (.var "peer") (.enc (.pk (.var "peer")) (.tuple [.lit na, name "A"]))
  , .recv (.enc (.pk (name "A")) (match v with
      | .original => .tuple [.lit na, .var "n"]
      | .lowe => .tuple [.lit na, .var "n", .var "peer"]))
  , .send (.var "peer") (.enc (.pk (.var "peer")) (.var "n"))
  , .claim "finished" [name "A", .var "peer"] ] }

def bob (v : Variant) : Role := { name := "Bob", steps :=
  [ .recv (.enc (.pk (name "B")) (.tuple [.var "m", .var "x"]))
  , .send (.var "x") (.enc (.pk (.var "x")) (match v with
      | .original => .tuple [.var "m", .lit nb]
      | .lowe => .tuple [.var "m", .lit nb, name "B"]))
  , .recv (.enc (.pk (name "B")) (.lit nb))
  , .claim "commit" [name "B", .var "x"] ] }

ask for.

17.8.2 A defender on the wire
A real path often has a defender on it too: an intrusion-prevention system, a filtering proxy, a gateway
that intercepts TLS. A declaration may put one in front of named roles; every message delivered to
them passes through it, and it drops what matches a drop pattern, rewrites what matches a rewrite
rule, and forwards the rest. It matches only what it can see, which is knows from the defender’s side:
it looks inside a ciphertext only when it can build the opening key, and a blob it cannot open matches
nothing, since real encryption is randomised. Here Bob accepts whatever reaches him, and Guard
drops bad:

17.8.3 Reassembly
Signature matching has a subtler gap. A defender scanning a TCP stream for EVIL must reassemble
it as the host behind it will, and the attacker controls segmentation: any byte range, in any order,
CHAPTER 17. PROTOCOL EXERCISES: ROLES, ATTACKERS, AND KNOWLEDGE                                    144

repeated with different bytes. Where segments overlap, one implementation keeps the first bytes and
another the last, and operating systems have differed in exactly this. check_reassembly models
each stream position as empty, the signature’s byte, or another byte (written .), applies every segment
to the defender’s and the host’s copies with their own policies, and resets the stream when a blocking
defender matches. The search covers every segmentation:

              defender keeps     host keeps    never delivered    evasion
              first              last          disproved          . at 0, then EVIL at 0
              last               first         disproved          E at 0, then .VIL at 0
              first              first         proved             —
              last               last          proved             —

     When the policies differ, two segments are enough: a first-wins defender fed a decoy byte at
offset 0 and then the whole signature keeps the decoy and sees .VIL, while a last-wins host sees
EVIL. When they agree, no segmentation separates the copies. The same disagreement makes a
host fingerprintable: send overlapping segments and see which bytes it acts on. The fix, as later
intrusion-prevention systems did, is to normalize: the defender forwards the bytes it scanned, leaving
the host no overlap to resolve differently.


17.9 What these exercises demand from the library
The three examples produce a concrete checklist:

   1. actor-local grammar definitions and trace projection;

   2. synchronization by common event identity and bytes;

   3. typed symbolic variables and prefix-dependent guards, including equalities and counters;

   4. a transport-neutral term-to-byte relation with encryption and hashing;

   5. channels, so that each actor’s observations are declared;

   6. explicit initial knowledge, compromise and freshness assumptions;

   7. attacker closure under construction, decryption and hashing (done: LeanFM.Session.Knowledge,
      decision proved sound), and an attacker generated from role declarations (done: LeanFM.Session.Attack);

   8. past operators for agreement claims such as “accepted only if previously formed”;

   9. probabilities on the E quantifier, from overlays, reported next to CTL verdicts;

 10. deadlines on F and U , with timeout branches wherever A must meet them;

 11. relational theorem schemas for indistinguishability; and

 12. counterexamples drawn both as a global interaction diagram and as each actor’s local projection.

    None of this is security decoration. It tests whether separately written, context-sensitive role
grammars stay modular while still expressing the information flow that real behavioural claims depend
on.

18.1.1 Conservative default HTTP projection
Without an explicit binding in Implementation.lean, LeanFM generates an HTTP projection and
its OpenAPI description: an initiating browser-to-server message is the request, its correlated server-
to-browser alternatives are the responses, and their protobuf schemas the operation schemas. The
default is conservative. Only a field the implementation classifies as a bounded, URL-safe scalar
may go in a path or query; bytes, repeated or nested fields, secrets and unbounded strings go in
a POST body, encoded with the protobuf JSON mapping as application/json, so a generator
cannot leak credentials into URLs. GET /openapi.yaml publishes the result: method, path, content
type, request schema, every permitted response and status, authentication, correlation fields and
requirement identifier. The protobuf and grammar remain the definitions.


18.2 The conversion, field by field
For a request binding httpRequest(method, pathTemplate), conversion is defined in this order:

   1. Match the HTTP method exactly and split the path into decoded segments.

   2. For each {field} in the template, take the protobuf field of that name, encode it as one path
      segment, and reject slashes, traversal, or a value that escapes the authenticated project root.

   3. For the currently implemented POST subset, encode remaining browser input fields as UTF-8
      form values. A protobuf bytes field is opaque bytes at the protocol boundary; a form adapter
      must use an explicitly declared textual encoding and must never place credentials in a URL,
      trace, diagnostic, or returned object.

   4. Recover the authenticated user from the leanfm_session HttpOnly, SameSite cookie. The
      cookie is transport authorization, not a field silently added to every protobuf message. It
      authorizes model calls and use of that user’s provider keys; it does not decide which project
      may be read, because projects are shared.

   5. Validate required fields and task where_ constraints. On success, assign the envelope metadata
      and the oneof payload. On failure, emit the named rejection alternative when the grammar has
      one; otherwise return an HTTP error without pretending a successful protocol event occurred.

    A response binding httpResponse(RequestName) reverses this over the request’s finite re-
sponse set: scalars become JSON values, repeated fields arrays, nested messages objects, bytes
an explicit download or Base64 field, and secrets are redacted. Statuses follow convention (200,
201, 400, 401/403, 404, 409, 502), but the named response message, not the status, decides the
grammar transition.
    Several exchanges may be in flight, so every response envelope sets cause_id to its request’s
event identifier in the same session and task, and the adapter follows it to answer on the request’s
connection, never by adjacency, arrival order or a global “current request”. A projection is valid only
for a causally closed exchange: each request named by exactly one terminal response, a failure
being a response too. An orphan request, a causeless or cross-session response, or two terminal
responses fail validation; interim or streaming responses are modeled explicitly, with one terminal.

18.6 Complete LeanFM task grammar
The whole ChatUI grammar, rendered from its typed values. A ! B : Message reads “A sends
Message to B”; then sequences; choose/or alternates; optional allows zero or one; fork/join
all waits for every branch; race/join first takes the first and cancels the rest (unlike the threshold
join of Chapter 5). A message the current residual does not admit is illegal even if its bytes decode.

18.19 The grammar as an executable canvas
Future interface. The grammar becomes one navigable canvas: a production closes to its typed
boundary or opens to its messages, states, parameters, constraints, measurements and nested
productions, as presentation only. Changing a typed parameter (a capacity, population, timeout,
probability) would mark every dependent stale and regenerate the affected productions, reducers,
proofs, codecs and views before the revision is committed. A production that crosses HTTP attaches
its binding there (method, path, protobuf types, statuses, content type, codec), with fixtures that emit
and decode the exact bytes, so the canvas opens all the way down to bytes.


18.20 What is checked, and what remains
Lean elaboration checks actors, schemas, states, transitions, grammars, constraints, output prove-
nance and mappings; the generator rejects a request with no named response and incomplete route
records; and the repository checks validate the protobuf against the requirements. Not every accepted
route has a handler yet, and the server does not yet journal every exchange. The accepted grammar
is the contract and the running table the honest conformance statement.
Chapter 19

The LeanFM Project Bootstrap Contract

This chapter defines the minimum machine-readable context that makes a LeanFM project self-
hosting, which an agent applies before turning the rest of the book into checked artifacts. The
bootstrap defines the language and its tools, never a hidden copy of the product’s requirements or
implementation.
    The intended handoff is simple: send someone this PDF’s URL and ask Claude, Gemini, Codex
or another capable agent to read it and make the software. New projects start from built-in templates,
not an example directory; the live references and read-only MCP surface supply the authoring types
and commands below. An agent must not copy LeanFM’s own source or prior specifications as an
answer key.


19.1 Required project inputs
A copyable project root contains the following stable inputs:

book/main.pdf
      Central product-design argument and maintained system-prompt context.

book/main-dark.pdf
      Accessible rendering of the same source.

LeanFM/
      Versioned generic authoring types and deterministic validators. Product actors, messages,
      tasks and routes do not belong in this directory.

Bootstrap programs
     Whatever prints the language references and interrogation checklist, validates the conventional
     specification, and derives review views from its typed value. In this repository these are the
     make targets and the LeanFM server’s routes and MCP tools listed below; a portable project
     may ship a bootstrap/ directory instead.

lean-toolchain and lakefile.toml
      The exact compiler selection and module roots needed to run the bootstrap locally.

project.json
      Project identity, stable artifact paths, and the classification of design versus language inputs.

CHAPTER 19. THE LEANFM PROJECT BOOTSTRAP CONTRACT                                                 164

    All project-owned state lives below the exclusive root: inputs, conversations, revisions, source,
tests, views, traces, reports, logs and caches, with temporary files and atomic promotion inside it.
Outputs and symlinks that escape are rejected; imports are copied in or recorded as immutable
content-addressed dependencies, and shared tools and caches outside may hold no project state. A
global index is reconstructible from manifests, and deleting a root removes all its state.
    The root is also the complete input to a fresh agent conversation: the agent finds the paths from
the manifest and repository instructions, with no transcript to paste. A root with no problem statement
gets a minimal book shell and the question “What problem are you trying to solve?”, which starts
requirements discovery.


19.2 Conventional generated interface
The requirements candidate lives at spec/Requirements.lean (this repository keeps its own in
LeanFM/LLMGenerated/), imports LeanFM.Artifacts, and defines:
namespace LeanFMProject.Requirements
def spec : LeanFM.RequirementSpec := ...
def all : List LeanFM.GeneratedRequirement := [.requirement spec]
end LeanFMProject.Requirements

   The byte vocabulary is spec/Requirements.proto and, once the requirements check, the
implementation mapping is spec/Implementation.lean. Capitalization matters: these are Lean
module paths.


19.3 Required commands and order
The project supplies deterministic equivalents of these commands. In this repository the references
and checklist come from the running server (/tools/leanfm-language/requirements-reference,
/tools/requirements/interrogation, or the MCP resources of the same name), and make
check validates and renders:
make reference           # print the complete requirements-language reference
make interrogation       # print questions that expose missing observations
make validate            # elaborate and run LeanFM plus protobuf validation
make render              # derive interaction and residual-state review views
make check               # validate, then render

    An agent runs reference and interrogation before authoring, and never infers constructors
from prose or invents a lookalike. The validator and the renderer both consume the exported
RequirementSpec: elaboration alone is not validation, and a separately drawn diagram is not
evidence.


19.4 Three layers, reviewed in git
Work proceeds in three layers, each checked before the next: observable requirements, their realiza-
tion mapping, then source, which follows the security review of Chapter 14. Review and acceptance
CHAPTER 19. THE LEANFM PROJECT BOOTSTRAP CONTRACT                                                    165

are git commits. LeanFM records no approvals and makes nothing wait for one; its status shows only
whether each layer passes its check and is committed.
    Requirements.lean is the contract: its multi-actor wire grammar is the conformance oracle,
under which complete decoded traffic is legal or has a counterexample (an incomplete capture estab-
lishes nothing). Requirements.proto fixes bytes without choosing a transport. Implementation.lean
records the choices that realize accepted behavior (queues, transports, journals, browser mecha-
nisms), each mapped to its requirement. An answer that changes nothing observable belongs there;
one that changes messages, fields or ordering revises the requirements; an answer made moot by
a later requirement is removed. The book explains what is built, the generic distribution makes the
language executable, and committed artifacts keep the decisions; none substitutes for another.


19.5 Construction is not a runtime dependency
The construction agent is not part of the delivered server. The user starts LeanFM, opens it in a
browser, signs in, supplies a provider key, and argues requirements through LeanFM’s own chat,
which talks to the provider directly. A reconstruction succeeds only if it builds a standalone executable,
serves the whole browser workflow, starts without a platform key, isolates concurrent users and their
credentials, and passes its conformance tests with no coding agent present.
