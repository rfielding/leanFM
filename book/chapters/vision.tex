\chapter{Formal Methods as the Default Path}
\label{ch:vision}

\index{formal methods}
Formal methods are usually presented as an extra stage: first build a system, then
translate a simplified version into a model, and finally ask a specialist tool a
few questions. That workflow taxes correctness. The model drifts, the difficult
translation is postponed, and proofs concern yesterday's architecture.

Our aim is the reverse. The shortest path to a running service should pass through
an executable behavioural specification. Writing the specification should remove
work: it supplies message types, scenario tests, model-checking input,
documentation, and the skeleton of the service itself. Going without it should be
the inconvenient choice.

\noindent\textbf{Evidence labels used throughout:} proposed notation (uncompiled);
executable code (builds or runs, not proof); finite-model check (exhaustive only
within declared bounds); test (named finite cases); generated analysis (named
inputs and reducer); Lean proof (kernel-checked under stated assumptions); future
interface (planned, unavailable). Labels scope evidence, not rank it; several may
apply to one artifact.

\section{Behaviour before machinery}

The primary object is a set of permitted, visible histories. An implementation may
use threads, actors, queues, databases, caches, or continuations. Those decisions
matter operationally, but they are not automatically part of the contract.
Promoting all internal state into the model creates a product state space whose
size grows exponentially with independently varying components. Worse, it makes
the specification brittle under harmless refactoring.

Protocols and persistent disk formats tend to live forever. Once another
process, customer, or stored data set depends on their bytes and ordering, they
become compatibility boundaries that must survive many implementations. The
internal structure of software is more chaotic: data structures, control flow,
threads, caches, and retry machinery are routinely replaced while the external
contract remains. Modeling every such choice would couple the specification to
short-lived machinery and introduce many more independently varying states to
explore. Concentrating first on the durable external boundary therefore both
protects what is hardest to change and keeps the tractable state space focused
on behavior that implementations must continue to preserve.

We therefore begin with \emph{behaviour}: who communicated with whom, what kind of
event occurred, what information it carried, and which predecessor order it extends.
Internal state enters only when it changes an observable promise.

\section{Comparison with TLA+}

LeanFM is not an extension of TLA+ and does not try to replace it. TLA+ commonly
describes a system with variables, an initial-state predicate, a next-state
relation, and temporal formulas over the resulting state behaviors
\citep{lamport2002specifying}. A message queue can be represented as a sequence-
valued variable, and an action can append to or remove from that sequence. This
is expressive and makes internal state transitions available to invariants and
model checking.

TLA+ does not call \texttt{Send} or \texttt{Receive} like procedures.
\texttt{Next} is a relation between the current variables and their primed next
values.  Its disjunction says that one step may be a \texttt{Send} for some
client, server and order; a \texttt{Receive} or \texttt{Finish} for some server;
a \texttt{ReadReply} for some client; a cache step; or a clock step.  A candidate
action whose guards are false is disabled.  TLC explores every enabled choice.

Read \verb|Spec == Init /\ [][Next]_vars| as: ``the first state satisfies
\texttt{Init}; thereafter, every state transition satisfies \texttt{Next} or
leaves every variable in \texttt{vars} unchanged.''  The configuration closes
the final loop with \texttt{SPECIFICATION Spec}; it tells TLC which temporal
formula to explore.

Read \texttt{inbox'} as ``the next value of inbox,'' \texttt{@} as ``the old
value at this selected entry,'' and \texttt{UNCHANGED} as ``these variables
retain their values.'' \texttt{Append} adds a message; \texttt{Head} selects the
first message; \texttt{Tail} removes it. Alice's send updates Bob's inbox, not
Bob's private control state. Bob's receive performs the latter transition.
The configuration instantiates \texttt{Clients = \{"alice"\}} and
\texttt{Servers = \{"bob"\}}; functions indexed by those sets hold instance state.
The full module commits the order, sends a reply, and checks that no reply
precedes placement. No eventual-reply property is checked.

bytes-per-state or timing law. TLA+ supports abstraction, hiding and refinement.
The lesson is to omit irrelevant state, not to blame the language for its inclusion.

\subsection{Proposed message-first notation}

This is invented TLA+-inspired syntax, not standard TLA+ or a compiled LeanFM feature:

\lstinputlisting[language={},basicstyle=\ttfamily\footnotesize]{examples/tla/MessageFirst.proposed}

Read \texttt{alice:bob ! placeOrder} as ``Alice sends placeOrder to Bob,'' and
\texttt{bob ? placeOrder} as ``Bob receives placeOrder.'' Bob consumes the
request \texttt{placeOrder}; Alice consumes the reply \texttt{placedOrder}.
A send changes the destination's inbox, a first-class queue owned by its actor
instance, not an arbitrary private variable. Receive consumes the message;
the receiver updates its own protocol state. Full queues block send without
mutation; empty queues block receive. The handler's commit precondition is an
observable obligation, not a database algorithm.

Actor classes describe behavior; instances have distinct identities, queues and
local state. WebServer instances share a class, not an inbox. DocumentStore
shards partition ownership by key; replicas protect each shard, and a quorum
controls write acknowledgment. These deployment roles are placeholders, not
classes implemented by the order module. First-class syntax still needs capacity,
routing, failure and scheduling rules; it does not eliminate their state space.

\subsection{Requirements at the message boundary}

LeanFM chooses a different primary boundary. The object available to us is often
an event stream scraped from a running system. We can decode its messages,
correlate them, follow predecessor backpointers, and classify the resulting sequence
as in-spec or out-of-spec. We generally cannot observe the implementation's
private variables at every step, so \texttt{Requirements.lean} does not pretend
to maintain them. Its grammar is intended to recognize legal traces and generate them;
state machines are projections of visible histories rather than declarations of
every variable stored by the program.

The distinction is methodological, not a claim that TLA+ is unable to express
queues or traces. This project began with an attempt to extend a TLA+-style model
with the desired message queues and MDP probabilities. The practical difficulty
was upstream: explaining an ordinary real scenario required choosing and
maintaining a small internal-state model before the observed behavior could even
be recorded. The abstraction work could exceed the apparently trivial example.
LeanFM instead asks first for the messages that would be visible in production.

The trade is deliberate:

\toprule

This boundary also separates the two durable Lean files.
\texttt{Requirements.lean} contains specified observable behavior: accepted
messages, legal ordering, probabilities, timing and reliability constraints,
and properties measurable from events. \texttt{Implementation.lean} contains
the additional decisions needed to generate software: target language, files,
transports, runtime APIs, and bindings. Existing source code may be supplied when
revising an implementation, but it does not redefine the requirement.

The durable handoff is the project-root artifact set. The bootstrap contract
(Chapter~\ref{ch:bootstrap-contract}) specifies how a fresh session resumes
without transcript-dependent intent.

\section{Discovery first, consolidation before commitment}

The working book is deliberately allowed to begin as a vibecoded stream of
consciousness. Stakeholders can introduce examples, possible abstractions,
warnings, abandoned alternatives, and future work without pretending that every
sentence is already an accepted requirement. That freedom is useful during
discovery, but an unedited transcript is not a finished design.

LeanFM therefore has a distinct cleanup phase before acceptance and again before
one-shot implementation. Each normative idea is classified as an observable
requirement, an implementation decision, deferred work, or material to remove.
The edit preserves definitions, constraints, formula readings, and necessary
qualifications while removing repetition, throat-clearing, and defensive
restatement. An idea mentioned in the book does not become an implementation
obligation merely by surviving an early draft; the accepted Lean artifacts say
which ideas bind the software.

Wordy prose is also evidence that a missing view may already be latent in the
requirements. Paragraphs that mainly enumerate actors, messages, state changes,
ordering, dependency gates, or measured quantities should normally collapse
into a generated interaction diagram, state machine, order graph, dependency
view, or chart followed by a short interpretation. The view must be reduced from
the current typed requirements and retain its prompt, question, event source,
reducer, units, and boundary. Drawing a persuasive picture independently would
only create another specification that can drift.

\section{Three ingredients}

The method combines three traditions.

\begin{enumerate}[label=\arabic*.]
  \item Language theory gives compact generative descriptions of legal histories.
        Regular and context-free grammars provide the approachable starting point.
        Dana Richards and Henry Hamburger, the author's college professors, are
        cited in \citet{richards2017logic} as the source from which the author
        learned these methods, not as their originators. For the underlying habits of
        symbolization, validity, proof, quantification, and modal reasoning, we also
        draw on the accessible progression of \citet{gensler2017introduction}.
  \item Protocol analysis contributes explicit participants, adversarial choices,
        trace semantics, and tool-supported checking. The CSP treatment of
        \citet{ryan2001modelling}, including Steve Schneider, is cited as the source
        from which the author learned this treatment.
  \item Temporal logic turns expectations into queries over the generated
        transition system. CTL is central because it distinguishes claims about
        some possible future from claims about every possible future
        \citep{clarke1986automatic}.
\end{enumerate}

\section{A test for every abstraction}

Each abstraction in this book should answer a practical question:

\begin{quote}
Can a developer state a meaningful behaviour once, compose it with other
behaviours, check its consequences, and keep it stable while implementation details
change?
\end{quote}

If an abstraction does not improve that workflow, it does not belong in the core
library.
