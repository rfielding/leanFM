\chapter{Lean as the Rendered Language}
\label{ch:lean}

\index{Lean}
The notation for global types, local types and channel physics renders to a
conservative subset of Lean, with no second opaque specification file: domain
declarations are Lean definitions, behaviours Lean values, and requirements Lean
propositions or checked queries. Rendering the proposed scenario DSL into Lean is a
\textbf{future interface}; the typed LeanFM API is the current
\textbf{executable code}, and a \textbf{Lean proof} claim applies only to a theorem
checked in the declared build. Every displayed formula carries an English reading,
in its accessible text, that accounts for each operator, index and bound.

\begin{lstlisting}
def checkout : Grammar CheckoutEvent :=
  request >>> (accepted <||> rejected)

def eventuallyAnswered : CTL Observation :=
  CTL.ag (CTL.implies requestPending
    (CTL.af (CTL.or requestAccepted requestRejected)))
\end{lstlisting}

Semantic machinery comes from a fixed library; an author supplies only:

\begin{itemize}
  \item typed actors, identifiers, event kinds, and payloads;
  \item parameterised grammar definitions;
  \item projections from trace prefixes to observable propositions;
  \item named temporal requirements and proofs or decidable checks.
\end{itemize}

so generated Lean stays small enough to review, and library proofs and algorithms
are reused, not regenerated.

\section{An unchecked exploratory fixture}

\texttt{book/logic.lean}, below, is an unchecked side experiment, not part of the
method. It explores a regularized assignment for $1+2+3+\cdots$: for each cutoff
$n$, the triangular prefix $n(n+1)/2$ plus a defined correction
\texttt{Tail\_S}(n) equals $-1/12$, which asserts nothing about convergence of the
partial sums. It needs Mathlib, which this build lacks, so it claims no checked
proof.

For a LeanFM runtime judgment, define the double turnstile $\vDash$ relative
to the declared transition model and initial state. It means ``at every reachable
state, the premises require at least one of these conclusions.'' Write it in a
rule-like form, familiar from Prolog:
\AccessibleEquation{a and b and so on through w semantically entail x or the remaining alternatives through z.}{\[
  a\land b\land\cdots\land w\;\vDash\;x\lor\cdots\lor z.
\]}
Its executable definition is that the following CTL formula holds at the
declared initial state:
\AccessibleEquation{A G of: if a and b and so on through w then x or the remaining alternatives through z. In words: at every reachable observation all the premises imply at least one conclusion.}{\[
 AG\bigl((a\land b\land\cdots\land w)
       \to(x\lor\cdots\lor z)\bigr).
\]}
This is entailment within the declared model and initial state, not general
entailment over all models, and the conclusion that holds may differ between
states. In code, a counterexample is a reachable state where every premise is true
and every conclusion false:
\begin{lstlisting}
counterexample(state, premises, conclusions) :=
  premises.all(p => evaluate(p, state)) &&
  !conclusions.any(q => evaluate(q, state))

entails(successors, initialState, premises, conclusions) :=
  !anyReachable(successors, initialState,
    state => counterexample(state, premises, conclusions))
\end{lstlisting}
A sampled trace checks only that sample. Symbolically:
\AccessibleEquation{Not E F of a and b and so on through w and not x and the remaining negated conclusions through not z. In words: there is no reachable counterexample where every premise holds and every conclusion fails.}{\[
 \neg EF(a\land b\land\cdots\land w\land\neg x\land\cdots\land\neg z).
\]}
which is the $AG$ implication by $AG\,p=\neg EF\,\neg p$. With one conclusion it is
the Prolog rule \texttt{x :- a, b, ..., w}, without Prolog's search order.
$\Gamma\vDash p$ collects the premises into $\Gamma$; $\Gamma\vdash p$, by
contrast, asserts a derivation.

For the proof-theoretic background behind derivations, natural deduction,
sequent calculus, normalization, and cut elimination, see Mancosu, Galvan, and
Zach's \emph{An Introduction to Proof Theory} \citep{mancosu2021proof}.

\section{From specification to service}

Lean hosts executable code, including LeanFM's own web server, so the formal
artifact is part of the running project. The target is for typed definitions to
drive validation endpoints, trace generation, schemas, views and runtime monitors;
coverage is partial (Chapter~\ref{ch:web-protocol}), and a checked behavioural
model stays distinct from unverified infrastructure.
