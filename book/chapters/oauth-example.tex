\chapter{Worked Example: Signing In over HTTP}
\label{ch:oauth-example}

\index{OAuth}
Signing in with an identity provider is the OAuth 2.0 authorization code flow
with PKCE, and in practice it is plain HTTP: three parties, a handful of routes,
redirects that the browser follows, and a few values that must come back
unchanged. This chapter writes it as a session type with typed messages, in
\texttt{examples/oauth}, and shows what LeanFM checks and generates from it.

\section{The session type}

\index{session key}
\texttt{SessionType.leanfm} declares the messages as structures, then the
protocol. Every message is an HTTP request with its route or a response with its
status. One sign-in is one session, keyed by OAuth's \texttt{state}: the app's
start and its callback are two separate HTTP requests, and \texttt{state} is what
ties them together, so it is the session's key.

The conditions say which values must come back. The browser's authorization
request carries the app's \texttt{state}, \texttt{redirect\_uri} and PKCE
challenge; the callback carries the same \texttt{state} and the code the provider
issued; the app exchanges exactly that code. The password, the PKCE verifier and
the access token end in \texttt{\_secr}: they are secrets, so no condition reads
them and no log carries them. The callback route takes either message, the code
or the error, as one HTTP endpoint whose request takes two shapes.

\section{A forged callback}

\index{CSRF}
A callback whose \texttt{state} is not the one the app sent is forged or replayed,
the cross-site request forgery that \texttt{state} exists to stop. Logged by the

\section{What is not a requirement}

\index{Implementation.lean}
Some choices belong to an implementation rather than to the protocol: that every
route is HTTPS, that the token request is form-encoded, how the app keeps pending
sign-ins by \texttt{state}, and how the PKCE challenge is computed.
\texttt{Implementation.lean}, written by hand beside the session type, records
them with their reasons:

The PKCE check itself, that the verifier hashes to the challenge, is a computation
on secrets that no \texttt{where} condition can state; it is a question for the
protocol checker of Chapter~\ref{ch:questions}, which asks whether an attacker can
ever learn a marked secret, rather than for conformance.
