\chapter{Worked Example: OAuth Authorization Code Flow}
\label{ch:oauth-example}

\index{OAuth}
This chapter is a behavioural sketch inspired by the OAuth authorization-code
flow. It is not a replacement for the OAuth specification and deliberately begins
above HTTP and protobuf. Its purpose is to exercise scenario decomposition,
parameter flow, visible evidence, alternatives, requirements, and rendering.

\section{Actors, values, and observable events}

The example has four participants: a person using a browser, an application, an
authorization service, and a resource service. The browser is modelled separately
from the person because redirects are observable messages between software
participants.

\begin{lstlisting}
inductive Actor where
  | user | browser | app | authorizationServer | resourceServer

opaque State       : Type
opaque AuthCode    : Type
opaque AccessToken : Type
opaque Resource    : Type
opaque Profile     : Type
opaque Password    : Type
opaque Bytes       : Type
\end{lstlisting}

Every terminal elaborates to the common event envelope. For example, the vague
message ``authorization redirected'' becomes conceptually:

\begin{lstlisting}
{ clock := t2, id := e2, priorIds := [e1]
, session := browserSession, task := oauthAuthorizationTask
, from := Actor.app, to := Actor.browser
, kind := "authorization redirected"
, fields := [field "state" state, field "redirectUri" callback]
}
\end{lstlisting}

\subsection*{Authentication detail used by Production 2}

Before the redirect returns, the authorization service may authenticate the person.
OAuth does not prescribe the authentication mechanism; we include a password branch
to exercise knowledge flow without pretending that the password is an OAuth protocol
parameter.

\begin{lstlisting}
def authenticateAtAuthorizationServer (password : Password) : Scenario :=
  scenario "authenticate resource owner" do
    from_ .browser
    to_ .authorizationServer
    emitBytes "credentials submitted"
      (protectFor .authorizationServer
        (encode [field "password" password]))

    from_ .authorizationServer
    to_ .browser
    oneOf "authentication result"
      [ emitBytes "authentication accepted" (encode [tag 1])
      , emitBytes "authentication rejected" (encode [tag 0])
      ]
\end{lstlisting}

The wire bytes are specified even though the transport is not. The abstract
\texttt{protectFor} constructor promises confidentiality to the named endpoint. A
later refinement may realize that promise with TLS, message-level encryption, or a
local trusted channel. Merely placing the password inside a field would not support
the intended knowledge set: without protection, a network observer would also
derive the password from the bytes.

\section{Production 1: application request and redirect}

\begin{lstlisting}
def applicationRequestAndRedirect (resource : Resource) : Scenario :=
  scenario "application request and redirect" do
    let state <- declare State "state"
    let callback := Uri.https "app.example" "/oauth/callback"

    from_ .browser
    to_ .app
    emit "application request" [field "resource" resource]

    from_ .app
    to_ .browser
    emit "authorization redirected"
      [field "state" state, field "redirectUri" callback]

    export "state" state
    export "redirectUri" callback
    export "resource" resource
\end{lstlisting}

This production treats the application request and its redirect as one named
unit. It establishes the correlation value \texttt{state} and exports it to the
next production. Nothing here says how the application stores it.

\section{Production 2: authorize, then grant or deny}

\begin{lstlisting}
def authorizationGranted : Scenario :=
  scenario "authorization granted" do
    use state <- imported State "state"
    let code <- declare AuthCode "code"

    from_ .authorizationServer
    to_ .browser
    emit "authorization code returned"
      [field "state" state, field "code" code]

    from_ .browser
    to_ .app
    emit "authorization callback"
      [field "state" state, field "code" code]
    export "code" code

def authorizationDenied : Scenario :=
  scenario "authorization denied" do
    use state <- imported State "state"
    from_ .authorizationServer
    to_ .browser
    emit "authorization error returned"
      [field "state" state, field "reason" "access_denied"]
    from_ .browser
    to_ .app
    emit "authorization error callback"
      [field "state" state, field "reason" "access_denied"]

def authorizeAndDecide (password : Password) : Scenario :=
  scenario "authorize and decide" do
    use state       <- imported State "state"
    use redirectUri <- imported Uri "redirectUri"

    from_ .browser
    to_ .authorizationServer
    emit "authorization requested"
      [field "state" state, field "redirectUri" redirectUri]

    include (authenticateAtAuthorizationServer password)
    oneOf "authorization decision"
      [ include authorizationGranted
      , include authorizationDenied
      ]
\end{lstlisting}

The authorization request and its two possible continuations form one production.
At a more abstract rendering level, the entire production can be shown as one
node; expanding it reveals authentication and the explicitly bracketed choice.
The abstract contract makes both decisions possible. A product model may later
attach an estimated or measured probability distribution without changing the set
of legal traces.

\section{Scenario 3: exchange the code and use the token}

\begin{lstlisting}
def exchangeAndFetch : Scenario :=
  scenario "exchange code and fetch resource" do
    use code     <- imported AuthCode "code"
    use resource <- imported Resource "resource"
    let token    <- declare AccessToken "accessToken"
    let profile  <- declare Profile "profile"

    from_ .app
    to_ .authorizationServer
    emit "token requested" [field "code" code]

    from_ .authorizationServer
    to_ .app
    emit "access token issued" [field "accessToken" token]

    from_ .app
    to_ .resourceServer
    emit "protected resource requested"
      [field "accessToken" token, field "resource" resource]

    from_ .resourceServer
    to_ .app
    emit "protected resource returned"
      [field "resource" resource, field "profile" profile]

    from_ .app
    to_ .browser
    emit "application response" [field "profile" profile]
\end{lstlisting}

The token itself is visible only at the endpoints where the abstract protocol says
it is transmitted. The grammar makes no claim about the authorization server's
database schema or the application's session representation.

\section{Reading the scenarios together}

\begin{lstlisting}
def oauthAuthorization (resource : Resource) (password : Password) : Scenario :=
  scenario "OAuth authorization code flow" do
    include (applicationRequestAndRedirect resource)
    include (authorizeAndDecide password)
    after authorizationGranted include exchangeAndFetch

def oauthSystem (resource : Resource) (password : Password) : SystemSpec :=
  generatedBy (oauthAuthorization resource password)
  |> requireAll oauthRequirements
\end{lstlisting}

The two named productions provide the first abstraction level. A renderer may
collapse either production to a single node or expand it to its messages and
nested alternatives. The \texttt{after} line is a guarded nonterminal reference;
the denial branch ends without exchanging a code.

\section{The parallel protobuf alphabet}

The scenario and its wire alphabet are maintained side by side. The scenario says
which messages may occur, in what causal structure, and with which parameter
relationships. The protobuf file assigns field numbers and concrete wire types to
those same message atoms:

\lstinputlisting[language={},basicstyle=\ttfamily\scriptsize]{examples/oauth.proto}

Each emitted scenario message maps to exactly one member of
\texttt{EventEnvelope.payload}. The envelope carries the event identity, repeated
\texttt{prior\_ids}, \texttt{(session\_id, task\_id)} correlation key, monotonic
clock tick, and endpoints outside the payload. The payload carries only the fields
specific to that message.

Protobuf alone does not specify the protocol order, queue behavior, probability,
or dwell time; those remain in the scenario. Conversely, the scenario does not
invent byte tags. Validation checks that every scenario terminal has one protobuf
variant, that its endpoints agree with the scenario, and that every referenced
field has the expected protobuf type.

The schema determines valid protobuf encodings, but protobuf does not generally
promise one canonical byte sequence. When byte-for-byte comparison is required,
the refinement also fixes deterministic serialization and length-delimited message
framing. An instantiated envelope can then be serialized and displayed as the
actual bytes sent between the named actors.

\section{Generate one legal trace and its artifacts}

We can now run the specification in one direction. Grammar generation chooses
productions and concrete field values; everything after that is a deterministic
projection or reduction of the resulting events. For this run choose the
authentication-accepted and authorization-granted alternatives and instantiate

\begin{lstlisting}[language={}]
session = "s1"             task = "oauth"
resource = "profile"       state = "x7"
redirectUri = "https://a/cb"
protectedCredentials = aa bb
code = 01 02               accessToken = 03 04
profile = 05 06
\end{lstlisting}

The production derivation is

\begin{lstlisting}[language={}]
oauth
=> applicationRequestAndRedirect ;
   authorizeAndDecide ;
   after(authorizationGranted, exchangeAndFetch)
=> applicationRequestAndRedirect ;
   authorizationRequested ;
   credentialsSubmitted ; authenticationAccepted ;
   authorizationGranted ; exchangeAndFetch
\end{lstlisting}

Because \texttt{authorizationGranted} was selected, the \texttt{after} guard
admits \texttt{exchangeAndFetch}. Selecting the denial alternative would disable
that production. Expanding every remaining nonterminal yields this terminal word:

\begin{enumerate}[label=\texttt{e\arabic*:},leftmargin=4em]
  \item Browser $\to$ Application: \texttt{applicationRequest}
  \item Application $\to$ Browser: \texttt{authorizationRedirect}
  \item Browser $\to$ Authorization: \texttt{authorizationRequest}
  \item Browser $\to$ Authorization: \texttt{credentialsSubmitted}
  \item Authorization $\to$ Browser: \texttt{authenticationResult(true)}
  \item Authorization $\to$ Browser: \texttt{authorizationCodeReturned}
  \item Browser $\to$ Application: \texttt{authorizationCallback}
  \item Application $\to$ Authorization: \texttt{tokenRequest}
  \item Authorization $\to$ Application: \texttt{accessTokenIssued}
  \item Application $\to$ Resource: \texttt{protectedResourceRequest}
  \item Resource $\to$ Application: \texttt{protectedResourceReturned}
  \item Application $\to$ Browser: \texttt{applicationResponse}
\end{enumerate}

The choice has now disappeared into ordinary terminals. Event \texttt{e5}'s
payload bytes select the accepted authentication result. Event \texttt{e6}'s
\texttt{authorizationCodeReturned} oneof tag, source, and bytes distinguish the
grant branch from the error-returned branch. No independent ``chooser'' value is
needed.

\subsection{Envelope stream and concrete bytes}

Assign monotonically increasing clock ticks and event identifiers. This example
has a linear causal chain, so \texttt{priorIds(e1)} is empty and
\texttt{priorIds(e$n$)} is \texttt{[e$n-1$]}. A fork or join would make these
lists non-linear without changing the procedure. Deterministic protobuf
serialization of the schema on the preceding pages produces:

\lstinputlisting[language={},basicstyle=\ttfamily\tiny,
  breaklines=true]{examples/oauth-granted.bytes}

These are complete \texttt{EventEnvelope} encodings, not illustrative message
tags. They were generated with deterministic protobuf serialization. The twelve
envelopes occupy 440 bytes; the largest is 46 bytes. Protobuf deterministic mode
makes this fixture reproducible for a given implementation, while the grammar's
semantic requirement remains successful decoding to the same terminals and field
values.

\subsection{Residual state-machine path}

Parsing each envelope selects a payload alternative, checks its declared
\texttt{src}/\texttt{dst}, and consumes one grammar terminal. The residual after
each prefix is therefore:

\begin{lstlisting}[language={}]
oauth
--e1--> waitingForRedirect
--e2--> waitingForAuthorizationRequest
--e3--> authenticating
--e4--> waitingForAuthenticationResult
--e5--> waitingForAuthorizationDecision
--e6--> waitingForCallback
--e7--> waitingForTokenRequest
--e8--> waitingForToken
--e9--> waitingForResourceRequest
--e10-> waitingForResource
--e11-> waitingForApplicationResponse
--e12-> done
\end{lstlisting}

This path is one highlighted route through the generated state machine. The
machine itself is derived from all grammar residuals and therefore also contains
the rejected-authentication and denied-authorization paths.

\subsection{Actor projections}

Projection erases terminals an actor neither sends nor receives while preserving
the order of the rest. The same word generates four local replay scripts:

\begin{center}
\small
\begin{tabular}{@{}lp{.72\textwidth}@{}}
\toprule
Actor & Projected actions \\
\midrule
Browser & send e1; receive e2; send e3; send e4; receive e5; receive e6;
          send e7; receive e12 \\
Application & receive e1; send e2; receive e7; send e8; receive e9; send e10;
              receive e11; send e12 \\
Authorization & receive e3; receive e4; send e5; send e6; receive e8; send e9 \\
Resource & receive e10; send e11 \\
\bottomrule
\end{tabular}
\end{center}

Each line can become a component conformance test. The global word remains the
authority for cross-component order and parameter equality; a local projection
does not grant an actor knowledge of erased events.

\subsection{Causality, queues, and memory}

The \texttt{priorIds} fields generate a twelve-node causal graph with edges
$e_i\to e_{i+1}$. The interaction diagram is the same graph laid out by actor;
the state-machine path lays it out by grammar residual. Neither is independently
authored.

The message word does not uniquely determine a transport schedule. For a concrete
queue artifact, choose the canonical schedule that performs, for each event,
\texttt{produce; transport; receive} before generating the next event. With
positive inbound and outbound capacities, each queue peaks at one message. The
queued-byte peak for an actor is the largest encoded envelope waiting at that
actor in this schedule, and the global queued-byte peak is 46. A different legal
interleaving may have a larger peak and must be explored when checking the
universal memory-budget property. The selected schedule is a witness, not the
capacity proof.

\subsection{Measurements, plots, and verdicts}

From the clocks and correlation key, the generated task attempt is

\begin{lstlisting}[language={}]
{ key = ("s1", "oauth"), startedAt = 0, completedAt = 23,
  outcome = succeeded, latency = 23 ticks }
\end{lstlisting}

It contributes one point \texttt{(maxConcurrency=1, latency=23)} to the latency
XY plot, a cumulative-byte series ending at \texttt{(clock=23, bytes=440)}, and
one successful slice to the outcome chart. It does \emph{not} establish a 100
percent success probability. The grammar-level weight predicts 0.87 mass on the
grant branch; estimating that probability requires many generated or observed
sessions, including incomplete ones.

Trace-local monitors accept the matching \texttt{state=x7}, the code flow
\texttt{01 02}, and the fact that no exchange follows denial. CTL obligations
such as ``every decision reaches the application'' are not proved by this trace;
the checker must examine every reachable grammar residual. The complete artifact
pipeline is thus

\begin{lstlisting}[language={}]
grammar + field values
  -> legal terminal word
  -> typed EventEnvelope stream
  -> framed protobuf bytes
  -> causal graph + interaction diagram
  -> residual FSM path + per-actor projections
  -> queue schedule + byte-pressure samples
  -> task attempt + probability/latency/XY reducers
  -> replay fixture + trace-local property verdicts
\end{lstlisting}

Every arrow is reproducible. Only the initial branch and value generation, and
the separately stated transport schedule, add choices.

\section{Requirements as observable constraints}

\begin{lstlisting}
def oauthRequirements : List Requirement :=
  [ require "callback state matches request"
      (on "authorization callback" (previouslySame "state"
        "authorization requested"))

  , forbid "code exchange after denial"
      (previously "authorization denied" && event "token requested")

  , require "issued token came from a code"
      (on "access token issued" (previouslySame "code" "token requested"))

  , ctl "every decision reaches the application"
      (AG (decisionAtAuthorizationServer --> AF callbackAtApplication))

  , ctl "a protected result is never returned without a token request"
      (AG (resourceReturned --> previously tokenRequested))
  ]
\end{lstlisting}

\subsection{Who knows the password?}

\index{knowledge!derived from events}
Observable bytes are not the same as knowledge of their plaintext. Rather than
introducing ``secrecy'' as a special property, calculate the actors that can
derive the password from initial knowledge and the event list.

\begin{lstlisting}
def passwordKnowers (trace : Trace WireEvent) : List Actor :=
  allActors.filter fun actor =>
    Derives (knowledgeFrom actor trace) (value password)

theorem oauth_password_knowers
    (trace : Trace WireEvent)
    (accepted : (oauthSystem resource password).Accepts trace)
    (initial : InitiallyKnown password [.browser, .authorizationServer])
    (honest : Uncompromised [.browser, .authorizationServer])
    (protection : PerfectProtection protectFor) :
    passwordKnowers trace = [.browser, .authorizationServer] := by
  exact knowledgeClosureOfProtectedField accepted initial honest protection
\end{lstlisting}

The result says directly who knows the value. A password typed into the modeled
browser is derivable by that browser; hiding this behind the word ``secret'' would
lose information. If a narrower result is required, the actor model must represent
a trusted credential component separately. The calculation remains conditional:
a compromised endpoint, logging event, newly visible key, or failed protection
refinement changes the knowledge closure and therefore changes the returned set.

\subsection{Byte-level refinement without choosing a transport}

Every vague OAuth message can be assigned a canonical byte term before HTTP or
protobuf is chosen:

\begin{lstlisting}
refineMessage "authorization requested" where
  term := tuple
    [ tagBytes 0x01
    , namedBytes "state" (encode state)
    , namedBytes "redirectUri" (encode callback)
    ]
  bytes := encodeCanonical term

refineMessage "token requested" where
  term := tuple [tagBytes 0x02, namedBytes "code" (encode code)]
  bytes := encodeCanonical term
\end{lstlisting}

This fixes framing, tags, and value relationships at an abstract byte-algebra level.
A subsequent HTTP mapping might put those bytes into form fields; a protobuf mapping
might use numbered fields. Either concrete alphabet must prove that decoding and
re-encoding preserve the abstract terminal and its parameter bindings.

The use of \texttt{previously} is deliberately a trace predicate in this first
version. It can later receive dedicated past-time syntax without changing the event
model.

\section{Probabilities and charts}

The authorization service need not be random. The user supplies random input by
granting or denying consent; the browser, queues, transport, and authorization
service then react deterministically to the input they receive:

\begin{lstlisting}
def consentDecision : Scenario :=
  weightedOneOf "consent decision"
    [ weighted (87 / 100) authorizationGranted
    , weighted (13 / 100) authorizationDenied ]

def oauthCharts : List ChartSpec :=
  [ pie "authorization outcomes" do
      source events; groupBy terminalOutcome; value count
  , line "end-to-end authorization latency" do
      source (correlate events by "state")
      x clock; y (elapsed "authorization requested" "application response")
  ]
\end{lstlisting}

No separate field says that the user ``owns'' this choice. The grant and denial
branches resolve to different consent-event bytes, and that terminal's source
identifies the user-facing actor that emitted them. After those bytes select a
branch, every transition may have probability one and the global model is still
probabilistic. The grant branch carries probability mass $0.87$ through the
outbound queue, transport, the server's inbound queue, and the deterministic
grant response. The denial branch similarly carries mass $0.13$. Deterministic
processing transports probability mass; it does not remove it.

For the simplified path with no loss or timeout,
\[
  P(\text{grant callback}) = 0.87 \cdot 1 \cdot 1 \cdot 1 = 0.87,
  \qquad
  P(\text{denial callback}) = 0.13.
\]
The factors of one are deterministic enqueue, transport, and server steps. Their
dwell times still affect the latency distribution even though they do not split
the probability mass.

With queue scheduling and other unresolved choices included, the complete system
is therefore a Markov decision process. Probabilistic edges describe inputs or
measured outcomes; nondeterministic edges describe decisions not assigned a
distribution, such as which enabled actor is scheduled next. An analysis first
fixes or quantifies over a scheduling policy and then propagates the user-originated
mass through the resulting paths.

For several sessions in flight, the MDP state contains every actor's bounded
queues and its per-\texttt{(session, task)} residuals. One user's random event can
change later queue pressure and scheduling possibilities for other sessions, so
the probabilistic state is the composed system state rather than a special marker
attached only to the user actor.

The percentages remain model inputs or measurements, not truths inferred from the
grammar. The grammar defines which behaviours are possible; the probabilistic
refinement says how mass is distributed over them.

This automaton is intentionally behavioural. It does not contain browser cookies,
database rows, server threads, or cryptographic library state. Those details may be
essential to an implementation proof, but they are refinements of this contract,
not the contract itself.
