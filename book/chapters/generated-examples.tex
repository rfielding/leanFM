\index{generated examples}
\index{probability overlay}
Most specifications explain themselves with hand-written examples: a trace
someone typed, a sequence diagram someone drew. Those examples drift. This
chapter takes the opposite approach. Every example below is the answer to a
question asked of the specification, and every number is computed from it.
Nothing in the figures was drawn by hand; regenerate them with
\texttt{lake env lean --run ProbabilityOverlayExample.lean}.

A global type generates runs, and each run is an example of the conversation.
The reading of the temporal operators is generative. If we generate event
lists from the grammar, then
\begin{description}
\item[$EF\,p$] means some generated list contains $p$; the witness is that
list, and it is the example.
\item[$AG\,p$] means every generated list satisfies $p$; a counterexample is a
generated list that does not.
\item[$AF\,p$] means every generated list eventually reaches $p$; a
counterexample is a list that loops forever without it.
\end{description}

\section{The core says what can happen}

A client sends a \texttt{Request}. The server answers with a
\texttt{Response}, or a \texttt{Timer} fires a \texttt{Timeout} and the client
retries. After the third timeout the client gives up. Retries are bounded, so
the task unrolls them into states: one waiting state per attempt.

The core carries no numbers. It says only which messages can follow which, and
it already answers the qualitative questions: every run ends, and giving up is
possible.

\section{The overlay says how likely and how long}

A separate table, the \emph{overlay}, annotates each transition with a branch
probability and a delivery delay. This one is \emph{declared}: it states what
we expect (a 10\% timeout rate, 40\,ms responses, 200\,ms timeouts). A
\emph{measured} overlay would have exactly the same shape, reduced from
recorded traces instead of asserted, and the same questions could be asked of
either. Keeping the numbers out of the grammar means a project without
probabilities loses nothing, and declared and measured values can be compared
on one unchanged specification.

The overlay is validated before use: every transition must be annotated,
nothing else may be, and the probabilities leaving each state must sum to
exactly~1. They are exact fractions and are never normalized silently.

Keeping probabilities outside the model is a deliberate break with tools such
as PRISM \citep{kwiatkowska2011prism}, where branch probabilities are part of
the model itself, and it follows FizzBee \citep{fizzbee}, which leaves the
specification unchanged and supplies probabilities and costs in a separate
performance file. The same separation lets one specification be checked under a
declared overlay and a measured one.

The session tools now accept timing and probability annotations alongside the
message grammar. The following settlement example is implemented in the text

Its probabilities are illustrative declarations, not measurements or legal
claims. Days mean fixed 24-hour durations.

Erasing these annotations preserves the global interaction grammar. The
obligation starts at the maximum of the two named event times; either required
message from its actor satisfies it at or before the deadline. A late return
remains a legal message trace and produces a separate violation report.
\texttt{on breach record} never fabricates a message.

An external \texttt{overlay} argument remains available. It contains a
\texttt{name}, a \texttt{choices} array of named choices and exact fraction
strings in \texttt{weights}, and an optional \texttt{timings} array whose
\texttt{message} targets a unique id or label and whose \texttt{at} is a time
expression. Entries replace matching inline annotations and retain their
origin in the effective-layer report. Plain choices are addressed by traversal
index, starting with \texttt{choice:0}. Zero mass never removes a structural
branch or establishes a CTL impossibility.

\texttt{session\_simulate} samples the finite paths with a seed and emits
session-relative milliseconds. \texttt{session\_conform} checks recorded
messages against the unchanged grammar, then monitors their actual timestamps
independently of the sampling distribution. Its \texttt{horizonMs} argument
can advance an incomplete observation: an unsatisfied obligation is pending
at its boundary and violated after it.

The supported execution boundary is finite sequential choices, with bounded
path expansion. Annotated concurrency, recursion and includes report missing
scheduling semantics rather than silently choosing a scheduler. Unannotated
session tools retain their existing behavior. Requirements
\texttt{selfhost.session.generative}, its execution and monitor clauses,
and \texttt{SessionImplementation.lean} record this boundary;
\texttt{GenerativeTests.lean} checks erasure, replacement, seeded traces,
deadline boundaries and rejection cases.


\subsection{Decision-process rendering through MCP}

The \texttt{session\_mdp} tool renders the checked session directly as a finite
decision tree under its supplied policy. It accepts the same \texttt{lean}
text and optional external \texttt{overlay}, with light or dark themes.
Policy edges choose actions; transition edges carry conditional outcome
probabilities. Each terminal shows its final message, time, obligation reports
and exact probability. The tool checks that all terminal probabilities sum
to one, and refuses incomplete weights rather than normalizing them.

The separate \texttt{violationProbability} is the probability that at least
one obligation is violated at the terminal observation time. It counts each
terminal once, even when several obligations fail there. A pending deadline
remains pending. Zero-mass outcomes remain in the drawing. SVG and the MCP
Apps view are generated from the same checked graph, and the editor's
\texttt{MDP diagram} button preserves the external layer.

This view preserves branch histories rather than merging states by their
visible labels. It unfolds a finite process under a fixed policy; optimal-policy
search and unbounded MDP solving remain outside its scope. Graphs exceeding
96 nodes or the response/dimension bounds fail explicitly instead of appearing
complete after truncation. Requirement \texttt{selfhost.session.mdp},
\texttt{Decision.lean}, and \texttt{DecisionTests.lean} record and check these
semantics.

\section{Promises, assumptions and observation periods}
\label{sec:sla}

A probability on a choice is an \emph{assumption}. It describes what a peer
decides where no other role can see, such as whether the network delivers a
forward or whether a database row exists. A requirement is a \emph{promise}: a
minimum or maximum that the protocol keeps whatever happens inside one entry.
LeanFM writes promises after the protocols, in one block for each entry
message id:

\lstinputlisting[language={},basicstyle=\ttfamily\scriptsize,breaklines=true]{../examples/sessions/UserLookup.leanfm}

There are two kinds of clause. \texttt{every q reaches \dots\ within d} is a
hard deadline. One miss is a counterexample, so the clause takes no window.
\texttt{at least} and \texttt{at most} are promised fractions, and each needs
an observation period (\texttt{over 1 hour} or \texttt{over 500 entries}).
Without one, the first slow answer after deployment would break a promise about
ninety-nine answers in a hundred before there had been any observation to judge
it by. \texttt{confidence} (95/100 by default) is how sure a window's verdict
must be, and \texttt{expecting 500 per hour} states the traffic, so the size of
a time window can be checked before anything runs.

\subsection{At design time: promises against assumptions}

\texttt{session\_sla} checks each promise against the assumptions on the
session's Markov chain. It starts from each occurrence of the entry and follows
every path, keeping exact rational masses. A path hits when it reaches a target
within the deadline. It misses when it passes the deadline, the next entry or
the end of the session. The result is the exact per-entry probability (an
interval if exploration stops at its bound) and a verdict. When the verdict is
violated, the result also gives the most probable path that breaks the promise,
with each assumption it passes through shown as \texttt{[name: p]}:

\lstinputlisting[language={},basicstyle=\ttfamily\scriptsize,breaklines=true]{generated/sla-userlookup.txt}

The error budget cannot be met: $\frac{999}{1000}\cdot\frac{1}{100} +
\frac{1}{1000} = \frac{1099}{100000}$ is more than $\frac{1}{200}$. The report
names the two assumptions responsible, and a design change, such as a retry
after \texttt{Failure} or a fallback replica, is the way to meet it. The
window size follows from the margin between the promise and the worst case:
$\lceil\ln(1/(1-c))/\textit{margin}\rceil$ entries are enough to tell the
promise apart from a failure rate of 0 or 1. That is 150 entries for 98/100
and 600 for 1/200, and an hour at 500 an hour holds only the first.

\subsection{At run time: the event stream is the state}

Actors keep no state of their own. Each event in the stream is named by a
unique timestamp \texttt{ts}, and \texttt{prev} and \texttt{cause} link it to
earlier events. A role's state is its view: its own events and their causal
past. A reward vector \texttt{\{role: \{unit: amount\}\}} is written only on an
event where it changes. The vector at any event is found by walking
\texttt{prev} back to the latest one written, and none found means zero.
Writing a vector equal to the one inherited is refused, so every vector in the
stream marks a change.

An entry \emph{hits} when a target lies in its causal future within the
deadline. An answer that names no cause does not count, however soon it comes.
An entry whose deadline outlives the stream is \emph{pending}, not missed. Each
window is judged with an exact one-sided binomial test, but only once it has
closed. A time window closes when the stream has passed its end plus the
deadline, and an entry window closes when it holds its count of decided
entries. Until then the window is \emph{open}. Here, a short execution misses
its third ask:

One miss in four would break a promise of 99/100 if it were judged at once.
Because the 300-entry period has not closed, the promise is still open. Of 300
closed entries, 300 hits is met at 95/100 confidence ($0.99^{300} \approx
0.049$), 299 is undecided, and 290 is violated. \texttt{SlaTests.lean} checks
these cases, along with the refusals: a fraction without a window, a window on
\texttt{every}, unknown names, a choice without an assumption, duplicate
timestamps, links to later events, and a vector rewritten unchanged. Clauses
\texttt{selfhost.session.sla} and \texttt{selfhost.session.execution} record
the semantics. \texttt{SlaChapterExample.lean} generates both reports above,
and \texttt{generated/sla-provenance.txt} records the prompt, question, source,
reducer, units and boundary.

\section{What comes next}

The same functions accept a measured overlay, reduced from recorded traces by
counting how often each branch was taken and averaging the delay before each
message. Chapter~\ref{ch:bakery} does exactly that for 20{,}000 recorded
sales, compares the result with a declared overlay, and shows why measured
delays must eventually be distributions rather than means. Retry loops here are
unrolled into bounded states; unbounded loops need the linear-equation
solution of probabilistic model checking rather than run enumeration, and the
current implementation reports them instead of truncating them.
