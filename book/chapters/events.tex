\chapter{Histories Made of Events}
\label{ch:events}

\index{event}
\index{trace}
Every execution is represented by an event sequence. A deliberately small common
envelope makes histories comparable across protocols:

\begin{lstlisting}
structure Event (Actor Session Task Kind Payload : Type) where
  timeAt  : ClockTimestamp
  id      : String
  priorIds : List String
  causeId : Option String
  session : Session
  task    : Task
  from    : Actor
  to      : Actor
  kind    : Kind
  payload : Payload

abbrev Trace (Actor Session Task Kind Payload : Type) :=
  List (Event Actor Session Task Kind Payload)
\end{lstlisting}

The fields have different jobs. \texttt{id} identifies a visible fact;
\texttt{priorIds} records zero or more immediate predecessor backpointers;
\texttt{causeId} optionally identifies the one direct causal event; \texttt{from} and
\texttt{to} name the parties; \texttt{(session, task)} correlates independently
progressing conversations; and \texttt{kind} supplies a stable discriminator.
The payload is protocol-specific and carries the parameters that flow from one
production to the next. \texttt{timeAt} is sampled from the model's shared monotonic
clock. Its differences measure elapsed time; it is not a civil-time date and its
origin is immaterial.

The predecessor links form a directed acyclic graph rather than a singly linked list.
An initial event has no prior identifiers. A fork is represented by several later
events that each name the same prior event. A join is represented by one event
whose \texttt{priorIds} names every branch on which it depends. An end event of
any kind may also name its corresponding start event. That backpointer makes
elapsed time simply \texttt{end.timeAt - start.timeAt}, even when several
attempts with the same \texttt{(session, task)} overlap. A backpointer to an
already-ancestral start is a redundant ordering edge, but it is useful
correlation data and does not alter the partial order. The edge says ``ordered
after,'' not ``caused by.'' A causal interpretation requires a separate grammar
or domain assertion.

Causality uses a different backpointer. An event's optional \texttt{causeId}
names the event that directly caused it and does not add or remove permitted
interleavings. It is not restricted to terminal events. A task-start event may
cause intermediate messages; those messages may cause nested task starts; and
terminal events may point to the event whose work they finish. Following the
reverse \texttt{causeId} relation produces a causal subtree. A renderer places
that subtree inside a labeled box, recursively, so nested work remains visible
without pretending that concurrent causal children have a fixed order.

For a request/response production, the response's
\texttt{causeId} is the request's \texttt{id}; read it as ``this response
answers this request.'' The rule remains unambiguous when many requests are in
flight because correlation follows event identity rather than adjacency or
arrival order. \texttt{priorIds} remains exclusively the partial-order relation.

For an $m$-of-$n$ join, the event additionally records $m$, $n$, and the exact
$m$ branch-terminal IDs that satisfied the threshold. The selected IDs must be
distinct members of \texttt{priorIds}. Merely seeing two predecessors is not
enough to distinguish a two-of-three threshold from an ordinary two-branch
all-of join.

\subsection{Durations from boundary events}

Each event is one observation at one instant. Starting and completing are
different messages, so an event does not contain an interval. Durations are
derived by selecting the two boundary events and subtracting their timestamps.

\begin{lstlisting}
structure AnalysisEvent where
  id       : EventId
  priorIds : List EventId
  timeAt   : ClockTimestamp
  bytes    : ByteArray
  reveals  : List ValueRef
\end{lstlisting}

The subscripted arguments identify each duration's exact start and end events.

Two events are concurrent in this order when neither is an ancestor of the other:

\begin{lstlisting}
def concurrent (events : List AnalysisEvent) (a b : EventId) : Bool :=
  !reachable events a b && !reachable events b a
\end{lstlisting}

The maximum concurrency permitted by the trace is the width of this partial
order: the size of its largest antichain. This purchase is a chain, so its width
is one. Other purchases and the morning production and transport streams may
still be concurrent. Incomparable events may commute in a linear serialization,
provided each event still appears after all of its named predecessors. A timestamped point event has no active interval;
runtime concurrency requires separate start and completion messages. This is stronger than counting
adjacent list elements and different from measuring average runtime concurrency.

\begin{lstlisting}
edgeTime(prior, event) := event.timeAt - prior.timeAt

Knowledge is another event reduction. For a value $v$, calculate the actors that
can derive it from initial knowledge and the bytes visible to them:

\begin{lstlisting}
def knowers (actors : List Actor) (v : ValueRef)
    (events : List AnalysisEvent) : List Actor :=
  actors.filter fun actor =>
    Derives (knowledgeFrom actor events) v
\end{lstlisting}

Encryption, signing, projection, key possession, and compromise contribute rules
to \texttt{Derives}. The primary result is the set \texttt{knowers v events}.
``Only these actors know $v$'' is a comparison between that computed set and an
allowed set, not a separate primitive called secrecy.

\section{Derived state}

A current session, an authenticated principal, or an outstanding request can often
be computed by folding the trace. Such a fact need not also exist as primitive
model state. This discipline has two benefits: evidence for a fact remains visible,
and the state representation does not multiply independently of the history that
justifies it.

Some implementations necessarily maintain private state. The model includes it
only when two executions with the same visible trace may make different future
behaviour legal. Even then, the first remedy is to expose the relevant distinction
as an event or a grammar parameter rather than copying an implementation object
graph into the specification.

\section{Time is more than a timestamp}

\index{time}
Timing constraints pair explicit boundaries; changing a timeout bound changes
the temporal requirement, not the event-order or causal relations defined above.

For two events from the same \texttt{(session, task)}, elapsed time is defined when
the first event's \texttt{timeAt} value does not exceed the second's:

\begin{lstlisting}
def elapsed (start finish : Event) : Option Duration :=
  if start.session = finish.session &&
     start.task = finish.task &&
     start.timeAt <= finish.timeAt
  then some (finish.timeAt - start.timeAt)
  else none
\end{lstlisting}

Latency queries name their boundary event kinds and use the terminal's
\texttt{priorIds} backpointer to select the start. Matching
\texttt{(session, task)} values alone cannot disambiguate overlapping attempts,
so reducers never pair by adjacency. Completion, failure, cancellation, timeout,
and other declared terminals use the same explicit pairing for elapsed time,
byte deltas, and other measurements.

This pairing is how a view may elide detail without becoming hand-waving. A
collapsed production retains its boundary event IDs, complete predecessor
links, parameter assignment, aggregate deltas, and validation status. Opening
it reveals the intervening events. Closing it again changes only presentation,
not the history or the evidence supporting the displayed duration, bytes, or
outcome.

\section{Estimating completion from an event stream}

The same boundary-event model can consume observed events. The
\texttt{LeanFM.StreamStats} implementation reconstructs attempts from stored
terminal-to-start predecessor links and computes completion, conditional-success,
and completed-latency statistics.

For an observation window containing $M$ starts, $C$ matched terminal events,
$S$ successful terminals, and completed latencies $L_1,\ldots,L_C$, the basic
estimates are
\AccessibleEquation{Estimated completion probability equals completed count C divided by started count M. Estimated probability of success given completion equals success count S divided by completed count C. Estimated expected latency given completion equals the sum of completed latencies L sub i divided by C.}{\[
  \widehat P(\text{complete}) = \frac{C}{M}, \qquad
  \widehat P(\text{success}\mid\text{complete}) = \frac{S}{C}, \qquad
  \widehat E[L\mid\text{complete}] = \frac{\sum_i L_i}{C}.
\]}

The vertical bar means ``given''; hats mark estimates from the observation
window. Attempts without a terminal event remain \emph{in flight}. They
contribute to the number started and to queue/load measurements, but not to
completed-task latency or to the conditional-success denominator. Calling them
failures would bias both probability and latency whenever the observation
window ends before they do.

The reducer can group these sufficient statistics by task, actor, time bucket,
maximum concurrency, or queue occupancy and feed them to charts. Specified
probabilities and dwell times are predictions; stream-derived estimates are
measurements to compare with them.

\section{Charts as declarative trace reductions}

\index{chart specification}
The proposed chart declaration names an observable event source, a grouping or
\(x\) expression, and an aggregate or \(y\) expression. It describes the
reduction, not rendering code; this syntax is illustrative, not an implemented
renderer.

\begin{lstlisting}
def outcomeShare : ChartSpec :=
  pie "quote outcomes" do
    source events
    where_ (kind == "quote accepted" || kind == "quote declined")
    groupBy kind
    value count

def responseLatency : ChartSpec :=
  line "quote response latency" do
    source (correlate events by "quoteId")
    x clock
    y (elapsed "quote offered" "customer decision")
    series "p50" median

def latencyByConcurrency : ChartSpec :=
  xyplot "latency by concurrent sessions" do
    source completedRuns
    x maxConcurrentSessions
    y (mean (elapsed firstEvent terminalEvent))

def queueByOfferedLoad : ChartSpec :=
  xyplot "queue occupancy by offered load" do
    source completedRuns
    x requestsPerSecond
    y (mean totalQueueOccupancy)

def propagatedGrantProbability : ChartSpec :=
  xyplot "user probability propagated through deterministic servers" do
    source parameterSweep
    x userGrantProbability
    y terminalGrantProbability
\end{lstlisting}

An XY plot preserves two numeric axes. It differs from a time series, whose
\(x\)-axis is specifically an event clock, and from a categorical chart,
whose \(x\) values are labels. The first two examples reduce each completed
model run to one point. The third sweeps a model parameter and checks that
deterministic downstream processing transports the user's probability mass.

Apply the provenance and implementation-status rule in
Section~\ref{ch:scenarios} to each generated chart.

\section{Round trip through bytes}

A generated scenario is not complete until it can cross the byte boundary in
both directions. \texttt{ScenarioEvent} in \texttt{Requirements.proto} carries
the event identity, complete \texttt{prior} list, correlation key, actors,
\texttt{timeAt}, and the selected protobuf atom. Encoding a \texttt{Scenario}
therefore produces bytes for both its ordering envelope and payload. Decoding those
bytes must reconstruct the same ordered event list. The executable round-trip
check compares the decoded protobuf value with the generated value and separately
checks the reconstructed \texttt{prior} graph; loss of a fork or join fails the
build.
