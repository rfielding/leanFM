\section{The argument loop}

The interface resembles ChatGPT because natural language is convenient for
finding omissions. The loop, however, has a formal boundary:

\begin{center}
\begin{tikzpicture}[>=Latex,node distance=1.15cm,
  box/.style={draw,rounded corners,align=center,minimum width=3.1cm,
    minimum height=.75cm,fill=diagramsurface},flow/.style={->,thick}]
  \node[box] (claim) {state or challenge\\a requirement};
  \node[box,right=of claim] (draft) {materialize a candidate\\Lean + protobuf pair};
  \node[box,below=of draft] (check) {compile, validate,\\simulate, and render};
  \node[box,left=of check] (evidence) {inspect traces, plots,\\violations, and obligations};
  \draw[flow] (claim) -- (draft);
  \draw[flow] (draft) -- (check);
  \draw[flow] (check) -- (evidence);
  \draw[flow] (evidence) -- node[left,align=right,font=\small]
    {counterexample or\\sharper question} (claim);
\end{tikzpicture}
\end{center}

The human contribution is often adversarial. ``The upload completes'' should
prompt: what observable event constitutes completion, who observes it, and does
it mean receipt, durable storage, or policy acceptance? ``The service handles
load'' should prompt: how many messages fit in each queue, how many
\texttt{(session, task)} pairs may be active, and what happens at the bound?
The assistant's job is to turn each answer into structure, not merely agreeable
prose.

A productive exchange might proceed as follows.

\begin{quote}\small
\textbf{Person:} A submitted upload eventually completes.\\
\textbf{Assistant:} I will treat an \texttt{uploadCompleted} response as
completion.\\
\textbf{Person:} No. Completion requires the storage actor's acknowledgment,
and the client must be able to distinguish rejection from timeout. Both queues
are finite.\\
\textbf{Assistant:} Then the grammar has accepted, rejected, and timed-out
alternatives; acceptance contains a storage acknowledgment before the response.
I will add queue capacities and a bounded-liveness obligation.\\
\textbf{Person:} Also show the behavior with many sessions in flight, estimate
the completion distribution from an event stream, and fail the requirement if
queued bytes exceed the memory budget.
\end{quote}

Every turn should change a named assumption, artifact, check, or open
obligation. If it changes none of them, it has not improved the specification.

\section{The server is a staging environment}

The executable \texttt{lake exe leanfm-server} serves the assistant workbench
on the loopback interface. Each new project owns one exclusive project-root
directory. Its editable and rendered book, \texttt{Requirements.lean},
\texttt{Requirements.proto}, \texttt{Implementation.lean}, source, tests,
generated views, traces, reports, logs and project-specific caches all remain
beneath that root. The first two specifications describe observable behavior
and values that resolve to bytes; they do not imply HTTP. The implementation
file selects how those bytes travel---for example HTTP method and path, an
in-process channel, TCP, or another adapter. Validation, rendered views,
metrics, reports and OpenAPI descriptions are projections of the same model.

Chapter~\ref{ch:bootstrap-contract} defines the portable root and ownership
contract; the Preface explains the project-copy and deletion rationale. Path
checks accept project-relative or canonical absolute forms only when the
resolved target remains beneath the selected root; traversal and escaping
symlinks fail closed.

The server may use a language model to propose edits. Compilation and validation
remain deterministic. The model is not the proof checker, and fluent prose is
not evidence that an obligation holds.

\subsection{The code that creates the TCP listener}

An address value does not open a port. The running server performs four distinct
operations: create a socket, bind it to an address, put it into listening mode,
and repeatedly accept clients. This is the relevant executable pattern from
\texttt{Server.lean}:

\begin{lstlisting}[language=Lean]
import Std.Internal.Async.TCP

open Std
open Std.Net

abbrev TcpServer := Std.Internal.IO.Async.TCP.Socket.Server

def bindAddr : SocketAddress :=
  SocketAddress.v4
    { addr := IPv4Addr.ofParts 127 0 0 1
    , port := 8080
    }

partial def serveLoop (server : TcpServer) : IO Unit := do
  let client ← (server.accept).block
  let _ ← IO.asTask (handleClient client) Task.Priority.dedicated
  serveLoop server

def main : IO Unit := do
  let server ← Std.Internal.IO.Async.TCP.Socket.Server.mk
  server.bind bindAddr
  server.listen 128
  IO.println "LeanFM server listening on http://127.0.0.1:8080"
  serveLoop server
\end{lstlisting}

Read the final definition as follows: \texttt{Server.mk} creates the TCP socket;
\texttt{bind} attaches it to loopback port 8080; \texttt{listen 128} changes it
into a listener with a pending-connection backlog of 128; and
\texttt{serveLoop} calls \texttt{accept} for each connection. Only after
\texttt{listen} succeeds is there a TCP listener. HTTP is the application
protocol implemented by \texttt{handleClient}; there is no separate HTTP socket.
The actual handler catches per-request errors before returning to the accept
loop. This shortened excerpt leaves that response logic out so the listener
lifecycle remains visible.

\section{Using the agent in Codex}

\index{Codex}
Codex can drive the complete bootstrap, not only the final code-generation
step. Open the LeanFM repository as the Codex workspace, or start its
command-line interface from the repository root:

\begin{lstlisting}[language=bash]
cd /path/to/leanFM
codex
\end{lstlisting}

The repository's \texttt{AGENTS.md} directs the agent to the LeanFM workflow in
\texttt{SKILL.md}. Both files make \texttt{book/main.pdf} a critical prompt
input rather than merely the publication produced by the source in
\texttt{book/}. The agent must read the book together with the live language
references and the existing source tree while developing LeanFM itself. Once
that software is operational, the agent uses it to construct and check the
durable requirements for the target system. Only accepted requirements become
input to a separately checked implementation specification, and only both
accepted specifications authorize generation or revision of application code.

Thus the intended order is:

\begin{enumerate}
  \item develop and verify the LeanFM tooling described by this book;
  \item use the running tooling and the book to interrogate the target system,
        produce its durable requirements artifacts, and validate their
        prompt-derived views;
  \item after explicit requirements acceptance, produce and validate the
        traceable implementation specification; and
  \item after explicit implementation acceptance, generate or revise the actual
        application from the book, all three accepted artifacts, and the existing
        source tree.
\end{enumerate}

A Codex prompt can state this bootstrap explicitly. For example:

\begin{lstlisting}[breaklines=true]
Treat book/main.pdf as a required system-prompt input, not merely an output of
this repository. Read it with AGENTS.md, SKILL.md, the live LeanFM language
references, and the existing source tree. First develop and verify the LeanFM
software described by the book. Once LeanFM is operational, use it to develop
verified requirements for an order-cancellation service: a customer may cancel
an order until warehouse packing starts. Generate from the specification an
interaction diagram, state machine, cancellation-success rate, and p95
cancellation latency, each retaining its question, event source, reducer, unit,
and boundary. Stop for my explicit acceptance of Requirements.lean,
Requirements.proto, and those derived outputs. Then develop a separately
traceable Implementation.lean and stop for my explicit acceptance. Only after
both gates, implement the application from book/main.pdf, the three accepted
artifacts, and the existing source tree; add tests and run the repository checks.
\end{lstlisting}

The book remains in the input set throughout this process because it defines the
language and method by which the typed artifacts are interpreted. The artifacts
then add the target system's accepted facts: observable behavior in
\texttt{Requirements.lean}, byte-resolving values in
\texttt{Requirements.proto}, and runtime choices plus traceability in
\texttt{Implementation.lean}. A person can reject either candidate
specification and continue the argument; a successful build does not count as
acceptance.

\section{MCP: the agent-facing entrance}

\index{Model Context Protocol}
The browser UI is for stakeholders; the Model Context Protocol endpoint is for
an LLM agent. LeanFM serves stateless JSON-RPC requests at \texttt{POST /mcp}.
On initialization, the server tells the agent that the book is durable project
context---effectively a maintained section of the system prompt---rather than
optional background reading. The agent can enumerate and read fixed resource
URIs for \texttt{book/main.pdf}, its dark rendering, the canonical requirements,
protobuf and implementation files, and both live language references.

This interaction is generated from the implemented MCP dispatch surface:

\begin{figure}[htbp]
\centering
\resizebox{\textwidth}{!}{\input{generated/mcp-interaction.tex}}
\caption{An agent obtains durable project context and deterministic evidence
through MCP. Source: \texttt{LeanFM.MCP}; reducer and provenance:
\texttt{book/generated/mcp-interaction-provenance.txt}.}
\label{fig:mcp-interaction}
\end{figure}

The first surface is intentionally read-only. It provides resource and prompt
discovery, the requirements interrogation, the post-acceptance code-generation
prompt, and canonical artifact validation. It exposes no arbitrary pathname and
no tool can accept a requirements or implementation gate. Those are stakeholder
decisions, not consequences of a successful tool call. MCP transports context
and evidence; the existing LeanFM workflow controls revision and acceptance.

The bundled server listens only on loopback. A deployment that exposes MCP to a
network must add authentication and authorization at the transport or reverse
proxy before treating the resource contents as safe to publish. Statelessness
does not make project data public, and a future writable MCP surface must bind
every request to a user, project, revision and accepted snapshot.

A local Codex client can register the running endpoint and inspect the result:

\begin{lstlisting}[language=bash]
codex mcp add leanfm --url http://127.0.0.1:8080/mcp
codex mcp list
\end{lstlisting}

The MCP interface does not replace the book; it makes the book, specifications
and live checker discoverable to an agent client.

\section{A tour of the LeanFM chat}

The Chat phase is the ordinary front door to a project. Select one project in
the left rail and then select \textbf{Chat}. Each project owns one complete
mounted workspace containing Project memory, Chat, Book, Grammar, Tasks and
Source. Switching project or phase changes visibility without destroying the
inactive workspace, so drafts, selections, scroll positions, queues, timers,
previews and fetched results remain in place. An active turn continues while
its project or Chat phase is hidden. Nothing from a previously selected project
is a fallback. The header identifies the
provider, model and non-secret key fingerprint that will be billed, while the
per-turn usage line reports the tokens attributed to that response.  Every
message has its own visible timestamp.  While a turn is active, an incrementing
timer distinguishes a slow operation from a stopped browser request, and more
prompts may be placed in the project-local FIFO without interrupting the active
one.

Chat is deliberately earlier than Book, Grammar, Tasks and Source.  A
stakeholder can begin with ordinary language, images, rough pseudocode or a
question about an unfamiliar protocol.  The response may revise the project
book, ask one focused blocking question, derive a view from the current
requirements, or create a scratch visual explanation.  It must not pretend
that an attractive explanation has passed either acceptance gate.

This is one conversation, not a hidden mode selector.  For every turn the
server supplies the model with the \emph{selected} project's complete editable
book and canonical requirements and implementation specifications, followed by
a bounded recent transcript.  The LeanFM book and a previously selected
project are never fallback context.  This boundary matters: otherwise a fluent
answer can describe GoServer while silently editing nothing, or can display
LeanFM's own book inside GoServer.

\subsection{Progress, cancellation and the Operational trace}

Long model turns must remain inspectable work, not a blocking chat spinner. A
project-wide \textbf{Agent running} banner remains visible in every phase. It
names the model captured for the active prompt, shows elapsed time and the
latest real stage, and supplies a cooperative \textbf{Cancel} control. The
client polls status, Project memory, Source and the Operational trace every two
seconds; a transient polling failure retains the last successful value and is
retried. Users may therefore inspect a changing book, specification or source
tree while the agent continues.

The Operational trace is appended before the next agent step. It records each
bounded workspace action as started, completed, failed or rejected. A proposed
write names its normalized project-relative destination, content kind and
character count before validation, so a path failure says what LeanFM was
trying to write. Failures are highlighted in the collapsed banner summary and
the accumulated trace may be expanded before the turn completes. Cancellation
is checked at provider and workspace-tool boundaries: no new mutation begins
after the request is observed, while already completed durable edits remain
truthful project state.

Prompts typed during a turn enter a visible removable project-local FIFO and
execute exactly once in order. Each queued prompt captures the model visible at
the time it is enqueued. In the composer, focus order is prompt editor,
\textbf{Send}, then model selector. Thus \textbf{Tab}, \textbf{Enter} commits a
typed prompt with the already visible model rather than opening the selector.

Structured clarification is also observable: a returned question logs its
stable ID, and a composer submission while that question is pending logs that
it bypassed the answer form. Both events appear in the turn trace and the
project diagnostic journal. They retain the question ID and bounded text
lengths, never the operator's prompt or answer text.

\subsection{A private fault barrier and actionable errors}

The visible trace is for stakeholder decisions; a separate bounded private
engineering journal supports diagnosis across navigation, server restarts and
discarded chat history. Each project stores it at
\texttt{logs/runtime-diagnostics.jsonl}. It contains sanitized stage
transitions, tool destinations, compiler diagnostics, failed required
artifacts, warning results, terminal provider failures, authorized project HTTP
errors and correlated unhandled server exceptions. A later agent request
receives the twenty newest unresolved entries before choosing a recovery
strategy. Verified matching writes and book builds remove superseded failure
clusters and leave one compact resolution, so the journal remains memory rather
than an ever-growing graveyard.

The React client is inside the same fault boundary. A React error boundary,
global JavaScript exception listener, unhandled-promise listener, API wrapper,
and explicit Mermaid and LaTeX renderer catches send an authenticated report
back to the server. A report names the operation, error type and message,
sanitized JavaScript stack, component stack when available, page, time and
active project. The reporting request uses a recursion guard, bounded fields
and at most twenty reports per browser minute. Project authorization is checked
again on the server. Prompts, form and workspace-write bodies, credentials,
cookies, arbitrary provider responses, URL queries and cross-project data are
never diagnostic payloads.

Every error shown to a person still has a separate obligation: state what
happened, recommend a concrete next action, provide a stable code and offer a
bounded diagnostic safe to paste to Codex. An unknown proxy response such as
``527 Something went wrong'' is insufficient. The private journal normally
means the person need not paste anything: LeanFM or Codex can inspect the
project root, repair the cause and continue the original task.

Repeated failure is bounded at the point of expense. Within an active turn, a
second tool call with the same name and exact arguments after an error is not
executed; it terminates that strategy before a third paid attempt. Provider
timeouts are never automatically retried because a timed-out request may have
consumed tokens or completed an earlier mutation. The agent instead reads the
diagnostic, changes strategy, exhausts safe reversible alternatives, validates
the result and resumes the requested task. Only missing authority, a destructive
choice or an unavailable dependency should return control to the user.

\subsection{Requirements properties and implementation provenance}

The Tasks page separates four views of one selected task: interaction
productions, residual states, temporal properties and guarded constraints. A
property is an observable requirement originating in
\texttt{Requirements.lean}; it is not silently invented by
\texttt{Implementation.lean}. The UI renders its actual CTL wrapper rather than
labeling prose as CTL: \texttt{always} becomes $AG\,p$,
\texttt{eventually} becomes $AF\,p$, \texttt{never} becomes
$AG\,\neg p$, and \texttt{preparedFor} becomes $EF\,p$. A
\texttt{where\_} trace predicate is displayed with its stable identifier under
the invariant $AG\,p$. Each card identifies its requirements origin.

The implementation specification remains separate. Requirements define the
observable behavior the system must provide. For a wire protocol, the accepted
grammar is the oracle over messages among all actors: a complete, decoded
traffic trace should be classifiable as conforming or rejected with a
counterexample. An incomplete capture is not evidence of conformance.

Implementation records choices needed to realize that accepted behavior in
code, mapping each choice to the relevant requirement; it does not add
requirements or change the contract. It may choose a queue, transport, journal
or browser mechanism. Once requirements are accepted, implementation questions
ask how to realize them, not what the protocol should be. Record their answers
in \texttt{Implementation.lean}. If an answer changes messages, fields,
ordering, or any other observable behavior, it is not merely an implementation
choice: revise and reaccept Requirements first. Conversely, if a requirements
change makes an implementation answer unnecessary, remove that answer without
changing the protocol. This provenance keeps the two acceptance gates
meaningful.

\subsection{How a chat turn becomes a durable edit}

Ordinary design discussion should normally improve the book.  The provider
therefore returns a small structured envelope containing a conversational
reply and, when the turn changes durable understanding, the complete proposed
\texttt{book/main.tex}.  The server does not trust the claim that this is an
update.  It enforces the project-root and size boundaries, writes the candidate
atomically, and builds the project PDF in the isolated book worker.  Only a
successful build commits the revision and sets \texttt{book\_updated=true}.
If compilation fails, the first bounded compiler diagnostic becomes visible
before repair begins and the exact previous source is restored after every
candidate. At most three repair requests may run, each with a short deadline.
Each request receives only the compiler diagnostic and a numbered nine-line
source excerpt, asks for one replacement line with at most 2000 output tokens,
and is rejected if it targets another line or makes no change. A successful
candidate is rebuilt before commit; exhaustion produces WARN and leaves the
last valid book authoritative. Deterministic syntax mistakes such as literal
ampersands and underscores should be corrected directly when their intended
prose meaning is unambiguous rather than rediscovered through repeated paid
model calls.

The same rule becomes stricter at the implementation boundary.  After both
acceptance gates and the security critique, an implementation request writes
real buildable files, generated bindings, and tests beneath the selected
project's \texttt{source/} directory by using the project-confined workspace
tools.  The Source phase reads those files directly.  A provider response that
says ``implemented,'' or pastes a Go listing into chat, cannot be SUCCESS while
\texttt{source/} is empty.  When a gate or material implementation decision is
missing, the valid alternative is a focused selectable question naming that
blocker---not an invented implementation and not another generic plan.

These positive and negative requirements are paired deliberately.  The
positive invariant is that a substantive turn can create a validated durable
artifact.  The negative invariant is that no malformed, oversized,
cross-project, unbuildable, or merely narrated artifact can be reported as
committed.  The deterministic HTTP conformance test exercises both a compiled
book update and an actual \texttt{source/main.go} workspace write, and separately
checks that an implementation claim with an empty Source phase is rejected.

\subsection{Example: ask to see MCP move}

The following is a useful prompt because it asks for both an explanation and a
specific interaction technique.  It is reproduced as entered; spelling does
not need to be polished before the model can act.

\begin{quote}\ttfamily
i want to understand what MCP looks like. make me an animation that i can step
forwrd or back in, showing messages passing back and forth in dynamic
interaction diagrams. visualized right here in the chat ui
\end{quote}

Here \emph{MCP} means the Model Context Protocol, not MQTT and not a generic
message broker.  A faithful first tour uses a host or MCP client and an MCP
server as lifelines.  When the selected example invokes a real downstream tool,
that tool may be a third lifeline; otherwise it is omitted.  A representative
walk is:

\begin{enumerate}
  \item the client sends a JSON-RPC \texttt{initialize} request declaring its
  protocol version and capabilities;
  \item the server returns its supported protocol version, capabilities and
  identity;
  \item the client sends \texttt{notifications/initialized};
  \item the client sends \texttt{tools/list} and the server returns the tools it
  exposes;
  \item the client sends \texttt{tools/call} with a tool name and arguments;
  and
  \item the server returns the correlated JSON-RPC result or error.
\end{enumerate}

This is the same kind of interaction shown durably in
\cref{fig:mcp-interaction}, but projected into a small review instrument.  The
inline view should show the participating lifelines, one selected message in
motion, its method or result label, and a detail panel containing the request
ID, direct cause, arguments or result summary.  \textbf{Forward} completes the
next event; \textbf{Back} restores the immediately preceding prefix;
\textbf{Play/Pause} advances or suspends automatic stepping;
\textbf{Restart} returns to the empty prefix; and a scrubber may select any
event boundary directly.  Keyboard left and right arrows are convenient
equivalents when focus is inside the animation.

Stepping backward does not send an inverse protocol message.  It changes which
prefix of the same immutable example trace is visible.  At step $k$, the canvas
shows exactly events $e_1,\ldots,e_k$; advancing exposes $e_{k+1}$ and stepping
back hides $e_k$.  Request and response remain correlated by their JSON-RPC
identifier, while LeanFM's richer event representation can separately retain a
direct causal pointer and predecessor links.  Thus the animation may explain
causality without falsely claiming that temporal adjacency alone pairs a
response with a request.

\subsection{What should appear in the response}

The chat response should contain a short explanation followed by the working
animation itself.  Its HTML and JavaScript are transport material, not the
answer: they must not fill the message as pages of source code.  LeanFM expects
an actual \texttt{leanfm-canvas} fenced block and removes that block from the
prose before placing its canvas and self-contained script in an isolated frame.
The frame has no network access, cannot navigate the parent, and may load no
external library or image.  Stop and Restart controls outside the frame allow
the stakeholder to halt an expensive or confusing animation.

There is one bounded repair for a common provider formatting error.  If the
model literally writes ``fenced leanfm-canvas'' and immediately follows it with
exactly one canvas element and one script element, the client recovers that
pair into the same sandbox instead of displaying it as noise.  This exception
does not turn chat into a general HTML renderer: unmarked or arbitrary HTML is
escaped and remains inert text.  A response that shows the raw program instead
of an animation is a rendering failure, not SUCCESS.  Resend preserves the
original user request while allowing the corrected renderer and prompt contract
to try the turn again.

The animation is initially a scratch explanation.  It answers ``what would this
interaction look like?'' quickly, but it is not yet a generated view of accepted
requirements.  If the discussion changes the project design, retain the
originating prompt, bind the selected messages to a named scenario, update the
typed grammar and regenerate the interaction diagram from that specification.
Only that provenance-bearing derived view can serve as evidence at the
requirements gate.  If stakeholders instead want to share the exact motion,
promote the chosen canvas revision to a project-owned GIF or MP4 with fixed
frame timing and serve that media inline.

Every still image displayed in Chat retains a reference that can leave the
screen. An adjacent keyboard-accessible \textbf{Copy reference} control copies
a project image as its stable project-relative artifact path. For a public-web
image it copies Markdown containing the displayed HTTPS image URL followed by
the visible source-page URL. It never copies image bytes, a data or ephemeral
object URL, the host filesystem path, credentials or unrelated response text.
This makes ``use the image above'' a durable artifact reference that can be
pasted into a later Chat turn, the book or Codex even after conversation state
has been discarded. Clipboard failures cross the same client fault barrier as
other JavaScript errors.

\subsection{From conversation to implementation artifacts}

After the visual argument becomes precise, the same project proceeds through
the horizontal phases rather than turning chat into a source-code dump:

\begin{description}
  \item[Book] records the durable design argument and embeds or references the
  views that explain it.
  \item[Grammar and Tasks] expose the accepted task grammar, task-local
  interaction diagrams, state machines, temporal properties and guards.
  \item[Source] lists the actual implementation files, generated bindings,
  build files and tests beneath the selected project's \texttt{source/}
  directory.
\end{description}

After both gates and the security critique, an implementation request must
create and check real project files; a chat-only listing with Source empty fails.
The response summarizes the artifacts and validation. If a gate or material
decision is missing, it asks a focused question instead of inventing an
implementation.

\subsection{Screenshot-first documentation}

Once the scenario runner is available, this tour should become substantially
shorter.  A named scenario will drive the production React DOM with a
deterministic provider, stop at an exact event prefix, and capture the real
LeanFM interface.  A small sequence---prompt submitted, MCP initialization in
flight, tool discovery complete, and Source artifacts visible---can replace
several pages of instructions.  The prose around each image should say only
what prompt produced it, what to notice, and which claim it demonstrates.

A screenshot is useful evidence only when it is reproducible.  Its manifest
retains the project and requirements revision, scenario and visible event IDs,
viewport, font scale, theme, browser version, capture time, reducer and content
digest.  The image receives meaningful PDF alternative text.  Headless capture
runs with a disposable account and deterministic data, without a provider key,
external network or arbitrary target URL.  A missing or stale required capture
fails the book build instead of silently leaving a blank figure.

This is an editorial rule, not permission to decorate every page.  Prefer one
real UI example over a wall of procedural text when the screen carries the
structure.  Keep formal definitions, security boundaries and qualifications in
text when a screenshot cannot express them.  Until the runner produces those
artifacts, this section describes the intended replacement and does not claim
that screenshots already exist.

\section{Local credentials and visible billing identity}

The login shown by LeanFM is not an OpenAI login. The user's LeanFM password
protects the OpenAI API key with authenticated encryption and unlocks it for the
active session; the key is never stored in plaintext. The project list exposes
the checked-in GoServer project under one canonical \texttt{GoServer} identity,
not a separate ``GoServer example'' tab.

Account records are runtime state, not source. By default the salted password
verifier, password-encrypted provider key, private conversations, and session
state remain beneath the operator's local \texttt{data/} directory. Git ignores
that directory and continuous integration rejects any tracked file below it.
Checked-in example projects therefore contain books, specifications, source,
tests, and deliberately selected media, but never user logins or credentials.

An authenticated header continuously identifies the provider, model,
credential reference, and a one-way fingerprint of the exact key used for the
next request. It also shows provider-reported session tokens used and tokens
remaining in a finite local safety budget; exhaustion stops another request.
That number is not an OpenAI credit or dollar balance, because the model
response does not expose such a balance. The UI says so explicitly. A provider
project spend cap remains the authoritative protection against monetary
overrun, while per-response token counts remain attached to the request that
incurred them.

\section{Cursor as an agent client}

A Cursor subscription connects to LeanFM as an authenticated agent client, not
as a model-provider API key. A project may commit
\texttt{.cursor/mcp.json} with the local URL
\texttt{http://127.0.0.1:8080/mcp}. Cursor Agent opens the project root, reads
\texttt{AGENTS.md}, and discovers LeanFM's book, canonical artifacts, language
references, prompts and validation tools through MCP. Cursor continues to own
its subscription authentication and billing; LeanFM receives no Cursor login
secret. The current MCP surface remains read-only, so Cursor edits files using
its ordinary project tools and cannot accept either gate through MCP.

For the inverse arrangement---the LeanFM browser driving a Cursor-backed
conversation---Cursor CLI exposes the Agent Client Protocol over standard input
and output. A \texttt{CursorACP} adapter can initialize and authenticate the
local agent, create or load one session for each LeanFM project conversation,
submit prompts, stream updates, answer explicit permission requests and cancel
work. This is an implementation direction, not a claim about the running
server. The adapter must isolate user, project, conversation, process and
request identity; bound its queues; preserve tool and permission evidence; and
terminate the process only after its queue is closed and drained. Cursor's
authentication token is never imported into LeanFM's provider-key store.

\section{One project, one directory}

\index{project!directory boundary}
The portable root and containment rules are in
Chapter~\ref{ch:bootstrap-contract}; this section records the hosted-runtime
mapping. \texttt{LeanFM.ChatUI.Store.createProject} creates account-owned roots
under \texttt{data/accounts/<user>/projects/<id>}, writes a runtime
\texttt{manifest.json}, and provisions the book, \texttt{spec/}, source, tests,

root. The copyable bootstrap template instead uses \texttt{project.json} and
\texttt{Specification/}; these are distinct template and runtime layouts, not a
single manifest/path contract.

\section{What the Lean artifact must settle}

The Lean file is the semantic source. It records actors, messages, per-task
state machines, multiparty grammar productions, CSP-style processes, framing,
properties, proof obligations, probability summaries, charts, and explanatory
Markdown. A serious argument should force answers in each of the following
dimensions.

\begin{description}[style=nextline]
  \item[Observable behavior]
  Which actor sends and receives each event? Which fields can an observer see?
  A message carries its \texttt{session} and \texttt{task}, its clock timestamp,
  and a list of prior event identifiers. Thus a join may cite several prior
  events, while several events may fork from the same prior event.

  \item[Component interactions]
  Global grammar productions state legal conversations; actor projections state
  what each component may send or receive. Composition must preserve endpoints,
  message types, correlation, and predecessor references. A diagram is useful
  evidence, but the grammar is the compositional object.

  \item[Statistical properties]
  User choices make the input probabilistic even when every server component is
  deterministic. Those choices propagate through the composed system as an MDP.
  The specification distinguishes unconstrained alternatives from weighted
  choices, states dwell-time distributions, and names reducers for success,
  latency, throughput, and queue occupancy. An observed event stream can then
  estimate the same quantities and be compared with the model.

  \item[Queueing and concurrency]
  Every actor has finite inbound and outbound queues. Several
  \texttt{(session, task)} pairs may be in flight at once, so a requirement must
  not silently reason about only one conversation. Full and empty queues produce
  observable blocking or sleeping behavior, and transport is a separate step
  from production and receipt.

  \item[Memory pressure]
  Message-count capacity alone is insufficient when payload sizes vary. A
  checkable requirement should declare a byte budget and derive queued bytes from
  the encoded envelopes. If active tasks retain additional state, the model must
  declare a bounded footprint for that state too. A representative obligation is
  \AccessibleEquation{Necessarily at every reachable observation the queued bytes for actor a plus its in-flight bytes are less than or equal to its byte budget.}{\[
    \mathrm{AG}\bigl(\operatorname{queuedBytes}(a) +
      \operatorname{inFlightBytes}(a) \leq \operatorname{budget}(a)\bigr).
  \]}
  Read this as: ``necessarily, at every reachable observation, queued bytes for
  actor $a$ plus in-flight bytes for actor $a$ is no greater than actor $a$'s
  byte budget.''  $\mathrm{AG}$ means ``on every permitted future, at every
  position''; the repeated argument $a$ identifies the same actor throughout.
  This is a modeling obligation for LeanFM, not a claim that the present
  validator already proves heap usage of an arbitrary implementation.
\end{description}

\section{Interrogate, characterize, synthesize, replay}

\subsection{The first question}

Fresh sessions resume from the project root, as specified in
Chapter~\ref{ch:bootstrap-contract}; no copied transcript or restart prompt is
required.

If the root has no durable problem statement, the first message is
``What problem are you trying to solve?'' The system records the answer before
proposing frameworks or solutions. Later questions identify a concrete
ambiguity and the requirement, view, proof, implementation choice or gate it
affects. Each useful turn records a decision, updates a view, asks a blocking
question, reports validation or advances an acceptance gate.

Each durable decision regenerates both PDF variants and links its explanation
and generated views to the matching requirements, implementation and evidence
revisions.

The conversational interface is not merely a code generator. Its first job is
to discover whether the desired claims are identifiable. It asks for scenario
and task boundaries, start-to-end backpointers, concrete actor populations,
clock and work units, observation windows, queue and memory limits, outage and
recovery events, and the provenance of probabilities. A missing answer is
reported as an indeterminate metric rather than replaced by an invented value.

Once those fields are available, one event stream should produce a standard
characterization. The canonical artifact inventory is
\texttt{outOfBoxArtifacts} in \texttt{LeanFM/Characterization.lean};
\texttt{baselineDerivedProperties} records each property's required fields,
reducer, unit, visualization and boundary. A domain explicitly retains,
replaces, extends, or marks each applicable property indeterminate.

Some streams contain observations; other requirements contain only expected
distributions. These are labeled separately. An expected distribution can drive
generation, but it is not presented as a measurement.

Generative similarity closes the loop. Reducers first turn the source stream
into a named metric vector, including histogram bins as individual exact ratios.
The generator produces a candidate scenario, serializes it to bytes, decodes it,
and runs the same reducers. The candidate is accepted only when every required
metric lies within its declared relative tolerance. Thus ``similar'' means
measurement-equivalent for the stated characterization, not visually plausible
or textually similar. Several very different event processes may satisfy the
same finite metric vector; the grammar, invariants, and byte-level language still
constrain which candidates are legal.

\section{The protobuf artifact is part of the requirement}

The parallel protobuf schema answers a question that a state diagram cannot:
what bytes can cross a component boundary? Atomic payload messages and a
\texttt{RequirementEnvelope.oneof} discriminator connect a grammar terminal to
its wire representation. Validation checks, among other things, that field tags
are nonzero and unique and that framing is explicit.

This pairing exposes useful disagreements. A Lean event may require a
\texttt{priorIds} list while the wire schema provides only one predecessor. A
latency property may depend on a clock that is never transmitted or recorded. A
memory budget may be stated in bytes while an unbounded protobuf field remains.
These are requirements defects, not serialization trivia.

The exact wire size is also an input to resource analysis:

\begin{lstlisting}
queuedBytes actor observation :=
  (observation.inbound actor).sum encodedSize
  + (observation.outbound actor).sum encodedSize

memoryPressure actor observation :=
  queuedBytes actor observation
  + inFlightFootprint actor observation.activeWork
\end{lstlisting}

The first term can be computed from concrete envelopes. The second requires a
declared abstraction of implementation state and must remain visibly labeled as
such.

\section{A ladder of checks}

No single green check answers every kind of requirement. The workbench should
present a ladder of evidence:

\begin{enumerate}
  \item Lean elaboration and protobuf parsing establish well-formed artifacts.
  \item Structural validation rejects missing actors, endpoints, terminals,
        framing, terminal states, process coverage, or real proof obligations.
  \item Grammar and projected state-machine checks cover ordering and component
        interaction.
  \item Temporal checking covers safety, reachability, and appropriately bounded
        liveness over observable states.
  \item Probability and dwell reducers predict completion probability and
        latency; event-stream reducers estimate them from observations.
  \item Queue and byte-budget checks cover capacity, backpressure, concurrency,
        and modeled memory pressure.
  \item Rendered interaction diagrams, state machines, plots, and reports make
        the same typed model reviewable by people.
\end{enumerate}

The distinction between model prediction and measurement must remain visible.
An incomplete observation window may censor slow tasks; a frequency estimate is
not automatically a proof of the declared probability; and a bounded trace does
not establish unbounded liveness. Good generated reports say which claim was
proved, calculated, sampled, or merely assumed.

\section{How to argue well}

The most useful prompts attack boundaries rather than ask for polish:

\begin{itemize}
  \item ``Show me the observable event that makes that sentence true.''
  \item ``Which alternative ends here, and how is it bracketed in the grammar?''
  \item ``What happens when this inbound or outbound queue is full?''
  \item ``Run two sessions and two tasks concurrently; which events correlate?''
  \item ``Which random choice belongs to the user, and how does it change the
        downstream completion and latency distributions?''
  \item ``Derive the plot from the event stream, including incomplete tasks.''
  \item ``Show the corresponding protobuf payload and its encoded-size bound.''
  \item ``Is this result proved, model-checked, simulated, measured, or assumed?''
\end{itemize}

The argument is finished enough to review when deleting the transcript loses no
normative information; a clean checkout can compile and validate the artifacts;
every diagram and plot is derived rather than independently drawn; failures have
observable outcomes; quantitative assumptions have units and scope; and every
unsettled claim is an explicit obligation. That is the requirements-centered
meaning of vibecoding in LeanFM: conversation discovers the specification, but
the checked artifacts outlive the conversation.
