\section{The argument loop}

What the user and the agent argue about is a global type: its roles, messages,
choices and channel physics. The interface looks like a chat because natural
language is good at finding omissions, but the loop has a formal boundary:

\begin{center}
\begin{tikzpicture}[>=Latex,node distance=1.15cm,
  box/.style={draw,rounded corners,align=center,minimum width=3.1cm,
    minimum height=.75cm,fill=diagramsurface},flow/.style={->,thick}]
  \node[box] (claim) {state or challenge\\a requirement};
  \node[box,right=of claim] (draft) {materialize a candidate\\Lean + protobuf pair};
  \node[box,below=of draft] (check) {compile, validate,\\simulate, and render};
  \node[box,left=of check] (evidence) {inspect traces, plots,\\violations, and obligations};
  \draw[flow] (claim) -- (draft);
  \draw[flow] (draft) -- (check);
  \draw[flow] (check) -- (evidence);
  \draw[flow] (evidence) -- node[left,align=right,font=\small]
    {counterexample or\\sharper question} (claim);
\end{tikzpicture}
\end{center}

The human contribution is often adversarial. ``The upload completes'' should
prompt: which observable event is completion, who observes it, and does it mean
receipt, durable storage, or policy acceptance? ``The service handles load''
should prompt: how many messages fit in each queue, how many
\texttt{(session, task)} pairs may be active, and what happens at the bound? The
assistant turns each answer into structure.

\begin{quote}\small
\textbf{Person:} A submitted upload eventually completes.\\
\textbf{Assistant:} I will treat an \texttt{uploadCompleted} response as
completion.\\
\textbf{Person:} No. Completion requires the storage actor's acknowledgment,
and the client must be able to distinguish rejection from timeout. Both queues
are finite.\\
\textbf{Assistant:} Then the grammar has accepted, rejected, and timed-out
alternatives; acceptance contains a storage acknowledgment before the response.
I will add queue capacities and a bounded-liveness obligation.\\
\textbf{Person:} Also show the behavior with many sessions in flight, estimate
the completion distribution from an event stream, and fail the requirement if
queued bytes exceed the memory budget.
\end{quote}

Every turn should change a named assumption, artifact, check or open obligation;
one that changes none has not improved the specification.

\section{The server is a staging environment}

\texttt{lake exe leanfm-server} serves the workbench on loopback. Every project
owns one exclusive root (hosted layout: Section~\ref{sec:one-project-directory};
portable contract: Chapter~\ref{ch:bootstrap-contract}). Paths are accepted only
when they resolve beneath that root; traversal and escaping symlinks fail closed.
The three specifications have the roles defined in Section~\ref{sec:three-layers}.
HTTP, in-process channels and TCP are implementation choices; validation, views,
metrics, reports and OpenAPI project the same model. A language model may propose
edits, but compilation and validation stay deterministic: prose proves nothing.

\subsection{The code that creates the TCP listener}

An address value does not open a port. The server creates a socket, binds it,
puts it into listening mode, and repeatedly accepts clients. From
\texttt{Server.lean}:

\begin{lstlisting}[language=Lean]
import Std.Async.TCP

open Std
open Std.Net

abbrev TcpServer := Std.Async.TCP.Socket.Server

def bindAddr : SocketAddress :=
  SocketAddress.v4
    { addr := IPv4Addr.ofParts 127 0 0 1
    , port := 8080
    }

partial def serveLoop (server : TcpServer) : IO Unit := do
  let client ← (server.accept).block
  let _ ← IO.asTask (handleClient client) Task.Priority.dedicated
  serveLoop server

def main : IO Unit := do
  let server ← Std.Async.TCP.Socket.Server.mk
  server.bind bindAddr
  server.listen 128
  IO.println "LeanFM server listening on http://127.0.0.1:8080"
  serveLoop server
\end{lstlisting}

\texttt{listen 128} turns the socket into a listener with a backlog of 128, and
\texttt{serveLoop} accepts each connection. HTTP is the application protocol
implemented by \texttt{handleClient}; there is no separate HTTP socket. The real
handler also catches per-request errors before returning to the accept loop.

\section{Consulting MCP about logic}
\label{sec:mcp-logic}

\index{Model Context Protocol!logic consultation}
An agent writing LeanFM requirements makes three kinds of logical mistake more
often than any other. It writes a temporal formula whose reading differs from the
sentence it was formalizing. It invents a sequence of events that no grammar
accepts, or whose causes run backwards, and draws a diagram from it. And it
states a requirement over something no observer can see (``the server knows the
password'', ``the cache is consistent''), which no event trace can test. The
\texttt{selfhost.mcp.logic} clauses, implemented by \texttt{LeanFM.Logic}, let the
agent ask before it commits to any of these.

The consultation is a task in the self-hosting requirements: one request,
answered by exactly one of two outcomes.

\subsection{The tools}

\begin{description}[style=nextline]
\item[\texttt{leanfm://language/logic-reference}] A resource stating the JSON
formula grammar, each operator's meaning, the terminal-state convention, and
worked examples.
\item[\texttt{explain\_formula}] The formula read back in English, its negation
and duals, whether it is a state or path formula, typing errors, and lints: a
vacuous implication, an \texttt{EF} where the sentence said ``always'', or a
plain implication where \texttt{stronglyImplies} was meant.
\item[\texttt{check\_ctl}] Decides a formula over a canonical task or an inline
draft. The atoms are observable: \texttt{at(state)}, \texttt{after(message)} and
\texttt{terminal}. Every verdict carries evidence: a witness path for a
satisfied existential, a counterexample for a refuted universal or violated
\texttt{never}. A draft may give its transitions symbolic terms and declare what
some actors know at the start; then \texttt{knows(actor, term)} is an atom too.
A state of the model is then the task state together with what each declared
actor holds, so ``never (Bob has finished with Alice and the network knows Bob's
nonce)'' is checked directly. A draft transition may also carry a claim, which
\texttt{claimed(claim)} observes.
\item[\texttt{check\_trace}] Checks event envelopes (\texttt{id},
\texttt{prevIds}, \texttt{causeIds}) for identifiers, cycles, cause order, each
message's declared \texttt{src} and \texttt{dst}, and grammar acceptance per
task. An admissible trace comes back as an interaction diagram and causal graph:
the agent designs a sequence diagram by writing events, not by drawing.
\item[\texttt{classify\_requirement}] Classifies each atom of a requirement as
observable, derived, or implementation-only, says which artifact should hold it,
and proposes events that would make an implementation-only atom testable.
\item[\texttt{knows}] Given events whose payloads are symbolic terms (atoms,
keys, key pairs, pairs, encryption, hashes), an actor and an event, returns what
the actor can derive there: every message in the event's causal past that it
sent or received, taken apart until nothing new appears, each piece with the
event that first gave it. With a query term it answers \texttt{proved} with the
derivation, or \texttt{disproved}. The decision is the one in
\texttt{LeanFM.Session.Knowledge}, proved sound
(Section~\ref{sec:knowledge-closure}).
\item[\texttt{check\_protocol}] Takes a security protocol as data: honest roles
as scripts of choices, fresh values, sends, receives and claims over message
patterns; an attacker who is the network; and one formula. The state space is
generated from the declaration and decided by \texttt{check\_ctl}, with
\texttt{claimed} and \texttt{knows} atoms. The answer lists the messages on the
returned path: a send with its sender, addressee and the attacker it went
\emph{via}; a delivery with the attacker it came from. A role may run several
sessions at once, and an optional defender may stand in front of named roles,
filtering only what its keys let it see. Needham--Schroeder declared this way
gives back Lowe's attack (Section~\ref{sec:needham-schroeder}; defenders,
Section~\ref{sec:defender}).
\item[\texttt{check\_reassembly}] Asks whether a defender scanning a stream for a
signature and the host behind it can be made to disagree when the attacker
chooses every segment and each side keeps either the first or the last bytes of
an overlap. An evasion comes back as its segments
(Section~\ref{sec:reassembly}).
\end{description}

Every answer is one result in \texttt{structuredContent}, with a one-line text
summary beside it. The modal operators ($K_a$ over indistinguishable histories,
$O$, $P$) are reported as \texttt{unsupported} inside a CTL formula, so an agent
is told plainly rather than given a guess.

\subsection{Formulas as data}

A formula travels as JSON. Whether every consultation ends:

\begin{lstlisting}
{ "task": "mcp_logic_consult",
  "formula": { "AG": { "implies": [
      { "after": "LogicConsultRequested" },
      { "AF": "terminal" } ] } } }
\end{lstlisting}

It is parsed into a closed syntax tree and evaluated by LeanFM, never compiled,
interpreted as Lean, or passed to a shell. The obligation \emph{Submitted logic
never runs as code} is tested, not proved; its control is that the parser has no
constructor that names code.

\subsection{Five verdicts}

\begin{description}
\item[\texttt{proved}] The formula holds on every reachable state within the
stated bounds, with a witness where it is existential: a \emph{finite-model
check}, not a Lean proof.
\item[\texttt{disproved}] A counterexample path is returned.
\item[\texttt{unknown}] The model cannot decide: a derived atom, a predicate
text, or a message field value, none of which a task's state machine carries.
\item[\texttt{unsupported}] The operator is outside the implemented logic.
\item[\texttt{resource-limit}] The reachable model exceeded its bound of 4096
nodes. The tested obligation \emph{Exhausted search never proves} forbids
reporting this as \texttt{proved}.
\end{description}

Malformed or oversized input (an unknown operator, a bare \texttt{G} without its
path quantifier, a misspelled state or message, a formula beyond 256 nodes) is
rejected with the reason, so a typo is never silently read as \emph{false}.

\subsection{Requirements without observable behavior}

A requirement over hidden state is incomplete, not wrong. An \emph{observable}
atom is decided by the event trace alone; a \emph{derived} atom is computed from
it by a declared reducer (a balance, a count, the values an actor could have
read); an \emph{implementation-only} atom refers to state no event reveals. The
tested obligation \emph{Hidden predicates never pass as observable} keeps the
third kind out of conformance tests. The classifier proposes events, such as a
\texttt{CacheAudited} or \texttt{KeyRotated} message with the fields that expose
the predicate, so the requirement can be rewritten over them and decided by
\texttt{check\_ctl}.

\subsection{The design loop}

\begin{enumerate}
\item Classify each sentence; turn implementation-only atoms into proposed events.
\item Write example traces with those events, check them with
\texttt{check\_trace}, and read the returned diagram.
\item Formalize each positive and negative property, read it back with
\texttt{explain\_formula}, and decide it with \texttt{check\_ctl}.
\item Treat every counterexample as a defect in the grammar or in the formula,
and say which before revising.
\end{enumerate}

A \texttt{proved} verdict is evidence for the stakeholder, who still decides what
to commit.

\subsection{Real answers}

These requests and responses are produced by running \texttt{LeanFM.Logic} while
the book is built, so they cannot drift from the implementation. The bounds block
is omitted.

\section{A tour of the LeanFM chat}

Chapter~\ref{ch:chat-ui-guide} walks through the screens. This section states
the rules behind them.

Select a project, then \textbf{Chat}. The workspace holds Project memory, Chat,
Book, Grammar, Tasks and Source; switching project or phase preserves drafts,
selections, queues and fetched results, and active work continues while hidden.
The header names the billed provider, model and key fingerprint; each turn shows
its token usage. For each turn the model receives the selected project's book
and canonical specifications, then a bounded recent transcript; no other project,
and not LeanFM's own book, supplies fallback context.

Chat accepts ordinary language, images, rough pseudocode and protocol questions
before anything is settled. The ordinary outcome is a decision and a checked
artifact, with no question. The agent reads prior answers and recorded choices,
picks reversible defaults within the recorded requirements and authorization,
records them, and lists only choices the stakeholder is likely to challenge. A
question must name a consequential, hard-to-reverse effect (scope, observable
behavior, compatibility, security or privacy, irreversible data, material
spending) that no recorded decision resolves. There is no approval step: the
stakeholder reviews the diff and commits it. Compiler and routine check failures
go through the bounded recovery below, not to the stakeholder.

\subsection{Progress, cancellation and the Operational trace}

A running turn shows an \textbf{Agent running} banner with the captured model,
elapsed time, latest stage and a cooperative \textbf{Cancel}. Status, Project
memory, Source and the Operational trace are polled every two seconds. The trace
records each bounded workspace action as started, completed, failed or rejected;
a proposed write names its project-relative destination, content kind and size
before validation, so a path failure says what LeanFM was trying to write.
Cancellation is checked at provider and tool boundaries: no new mutation starts
after it is seen, and completed edits remain.

Prompts typed during a turn join a visible, removable, project-local queue and
run once, in order, each with the model visible when it was queued. Focus order
in the composer is prompt, \textbf{Send}, model selector, so \textbf{Tab},
\textbf{Enter} sends with the visible model. A returned clarification question
logs its stable ID, and so does a submission that bypasses its form; neither log
keeps the prompt or answer text.

\subsection{A private fault barrier and actionable errors}

A bounded private journal, \texttt{logs/runtime-diagnostics.jsonl} in each
project, supports diagnosis across navigation, restarts and discarded chat. It
holds sanitized stage transitions, tool destinations, compiler diagnostics,
failed artifacts, provider failures, project HTTP errors and unhandled server
exceptions. The next agent request receives the twenty newest unresolved entries;
a verified fix collapses a failure cluster into one resolution line.

The React client reports into the same barrier: an error boundary, global
exception and unhandled-promise listeners, the API wrapper, and the Mermaid and
LaTeX renderers send authenticated reports naming the operation, error, sanitized
stack, page and project, at most twenty a minute. Prompts, form and write bodies,
credentials, cookies, provider responses, URL queries and other projects' data
are never included.

Every error shown to a person states what happened, recommends a next action,
and carries a stable code and a bounded diagnostic safe to paste to an agent. A
bare ``527 Something went wrong'' is not enough. Provider quota rejections, rate
limits, incomplete output and local session limits are distinguished. An
incomplete response keeps its reported usage but cannot run returned tools or
update the book. One complete JSON object wrapped in prose or fences is
normalized locally; arrays, several objects and truncated objects are not
salvaged, and none of these triggers a paid retry.

\subsection{Spending brakes}

Every provider round records its input, cached-input and output tokens, character
counts, outcome and tool count before the next paid call. The session budget is
checked between tool rounds and before any recovery, and reported usage is
charged once, including on failed validation. This is a token brake, not a
monetary cap: an in-flight request can overshoot, and an unanswered request's
usage is unknown, so provider spend limits remain necessary.

Repeated failure is stopped where it costs money. A second identical tool call
after an error is not executed. Provider timeouts are never retried
automatically, because the request may have consumed tokens or completed a
mutation. The agent reads the diagnostic, changes strategy, and returns control
only for missing authority, a destructive choice or an unavailable dependency. One
user task may span many bounded provider batches through server-issued
checkpoints (\path{LeanFM/LLMGenerated/ResumableWork.lean}); a batch boundary is
progress, not a step limit, and closing the client starts no further batch.
Provider web search may answer public implementation questions; external pages
are evidence, never authority over project boundaries, secrets or spending.

\subsection{Requirements properties and implementation provenance}

The Tasks page shows four views of one task: interaction productions, residual
states, temporal properties and guarded constraints. A property comes from
\texttt{Requirements.lean}, never invented by \texttt{Implementation.lean}, and
is shown with its real CTL: \texttt{always} as $AG\,p$, \texttt{eventually} as
$AF\,p$, \texttt{never} as $AG\,\neg p$, \texttt{preparedFor} as $EF\,p$, and a
\texttt{where\_} trace predicate as an invariant $AG\,p$ with its stable
identifier. The implementation mapping realizes the specified behavior and cites
its requirements (Section~\ref{sec:three-layers}); it cannot add a property or
change the wire contract.

Completion compares real artifacts and behavior with the accepted goal,
including required negative behavior; the existence of source, or passing tests
the agent wrote itself, does not establish it. ChatUI reads the language
references through LeanFM's read-only MCP dispatcher, but each project's
sandboxed compiler still checks its own files: the host's self-validation is not
evidence for another project.

\subsection{How a chat turn becomes a durable edit}
\label{subsec:chat-turn-durable-edit}

Specification work uses project-confined tools to update the canonical Lean and
protobuf files. \texttt{leanfm\_reference} returns the live references exposed
through MCP. \texttt{leanfm\_check} compiles the project's requirements and
optional implementation mapping, validates their structure and protobuf, and
regenerates \texttt{spec/tasks.json}. The compiler runs without network,
credentials or writable source; only project scratch is writable, and failed
validation keeps the last valid views. A turn that changes canonical
specifications cannot report SUCCESS without a successful check of its final
bytes. If the model tries to finish after an unchecked edit, the diagnostic goes
back into the same provider conversation, with the same cancellation, budget and
accounting; an unchanged candidate and diagnostic stops further paid work.

The requirements reference includes a complete compilable request/response
example with matching protobuf, task states, grammar, processes, properties,
negative obligations and view provenance; a reduced scope still needs these
collections (\texttt{markdown}, for instance, holds typed
\texttt{RequirementMarkdown} records). The implementation reference compiles a
mapping for the same example: \texttt{MessageCodegen.wireType} names the
generated protobuf type, and each \texttt{ChannelCodegen} states send, receive,
drain and close semantics, while capacities stay in the requirements.

A book revision arrives as a complete \texttt{book/main.tex}. The server enforces
root and size limits, writes atomically, and builds in an isolated worker; only a
successful build commits it and sets \texttt{book\_updated=true}. On failure the
first compiler diagnostic is shown, the previous source is restored, and at most
three short repair requests run, each given only the diagnostic and a
seventeen-line excerpt and allowed to replace one line. Exhaustion gives WARN and
leaves the last valid book in place. Deterministic mistakes such as a literal
ampersand or underscore are corrected directly rather than by paid retries.

Once the specification checks and the security critique is done, an
implementation request writes real buildable files, bindings and tests under the
project's \texttt{source/}. A response that says ``implemented'', or pastes a Go
listing into chat, is not SUCCESS while \texttt{source/} is empty; a missing
material decision becomes one focused question. This instantiates
Chapter~\ref{ch:feature-discipline}, and the deterministic HTTP test checks a
compiled book update, a real \texttt{source/main.go} write, and rejection of an
implementation claim with empty Source.

Application delivery ends with a working \texttt{source/Makefile}: every
generated HTTP application exposes \texttt{build}, \texttt{run}, \texttt{stop},
\texttt{test}, \texttt{check}, \texttt{clean} and \texttt{serve}, and LeanFM
invokes only these, reporting a missing target instead of running an arbitrary
command. \texttt{make run} uses a loopback port separate from LeanFM. The
\texttt{run} check launches it in a private network without host credentials,
writes only project cache, checks readiness and the application page, and stops
only its own process group; changed source makes its evidence stale. Passing it
establishes these bounded observations, not refinement of the specification.
\path{spec/runtime.json} and \path{spec/ProjectMemory.md} keep the goal, defaults,
known remedies and remaining gaps across an erased chat.

\subsection{Example: ask to see MCP move}

This prompt asks for an explanation and a specific interaction technique,
reproduced as entered:

\begin{quote}\ttfamily
i want to understand what MCP looks like. make me an animation that i can step
forwrd or back in, showing messages passing back and forth in dynamic
interaction diagrams. visualized right here in the chat ui
\end{quote}

\emph{MCP} here is the Model Context Protocol, not MQTT. A faithful tour has a
host or MCP client and an MCP server as lifelines, and a downstream tool only
when the example really calls one. The client sends JSON-RPC \texttt{initialize};
the server replies with its version, capabilities and identity; the client sends
\texttt{notifications/initialized}, lists tools with \texttt{tools/list}, then
calls one with \texttt{tools/call} and receives its result or error, correlated
by JSON-RPC ID (compare \cref{fig:mcp-interaction}).

The view shows the lifelines, one message in motion, its label, and a detail
panel with the request ID, direct cause and arguments or result.
\textbf{Forward}, \textbf{Back}, \textbf{Play/Pause}, \textbf{Restart}, a scrubber
and the arrow keys move through it. Stepping back sends no inverse message: at
step $k$ the canvas shows exactly events $e_1,\ldots,e_k$ of one immutable trace.
Request and response are paired by their ID, while LeanFM's events can also keep
a causal pointer, so the animation does not pretend that adjacency pairs them.

\subsection{What should appear in the response}

The response is a short explanation followed by the working animation, not pages
of HTML. LeanFM expects a \texttt{leanfm-canvas} fenced block, removes it from the
prose, and runs its canvas and script in an isolated frame with no network, no
parent navigation and no external library or image; Stop and Restart sit outside
the frame. Unless the user asks for a color, labels contrast with the canvas's own
background, not the page theme. One bounded repair recovers a reply that writes
``fenced leanfm-canvas'' followed by exactly one canvas and one script; any other
HTML stays inert text, and a response that shows the program instead of the
animation is a rendering failure.

The animation is a scratch explanation, not a generated view. If the discussion
changes the design, the selected messages become a named scenario in the typed
grammar and the diagram is regenerated from it; only that view is evidence. To
share the exact motion, the chosen revision becomes a project-owned GIF or MP4.

\subsection{Images}

\textbf{Attach image} accepts PNG, JPEG, GIF and static SVG, up to 2~MiB and 16
megapixels each, with a removable preview kept with the queued prompt. Originals
and a digest manifest stay under the project's \texttt{artifacts/attachments/};
the provider receives normalized PNG pixels (a GIF's first frame), at most four
images a turn. External SVG resources and executable content are rejected; the
negative tests are listed in \path{evidence/chat-images/security.md}. Every image
shown in Chat has a \textbf{Copy reference} control that copies its
project-relative path, or for a web image its HTTPS URL and source page, never
bytes, a data URL, a host path or a credential, so ``the image above'' survives a
cleared chat.

Task renderers receive the owning specification with the task; looking a
project's task up in LeanFM's own grammar gave a misleading placeholder, and a
regression test now uses a project task whose ID collides with ChatUI's.

\subsection{Screenshot-first documentation}

Chapter~\ref{ch:chat-ui-guide} gives named captures of the production React DOM,
made by a local deterministic provider and an isolated scenario runner. A capture
is evidence only when it is reproducible: its manifest keeps the project and
requirements revision, scenario and event IDs, viewport, font scale, theme,
browser version, time, reducer and digest, and the image has alternative text.
Capture uses a disposable account, no provider key, no external network and no
arbitrary URL. The PNGs, accessibility snapshots, keyboard traces and manifest
are in \path{book/assets/ui-tour/}; \texttt{make ui-snapshots} reproduces them,
and a missing, altered or stale capture fails the book build.

\section{Local credentials and visible billing identity}

The LeanFM login is not a provider login. One account password unlocks the
user's OpenAI and Anthropic keys together; they are authenticated together inside
one password-encrypted bundle, never stored in plaintext and never returned to the
browser. The \texttt{API keys} form, also opened by the \texttt{?keys=1} link,
adds or replaces either key; blank fields keep the stored ones, and adding a key
keeps the current session. A password change verifies the current password and
writes one atomic envelope holding the new verifier and the re-encrypted bundle,
so an interruption cannot split them. Replacing a key or the password revokes
older sessions, including in another server process sharing the vault: an
already-running provider request may finish, but its tools cannot run afterward.
Saved keys survive restarts; only unlocked sessions do not.

Account records are runtime state, not source. The salted verifier and encrypted
keys live in the git-ignored vault \texttt{.leanfm/accounts/}. Projects contain
books, specifications, source, tests and chosen media, never logins or
credentials.

The model selector combines models discovered for the unlocked providers and binds
each to one provider and the exact account-owned key; an unknown model or missing
key fails without a paid call or a fallback provider. OpenAI Responses and
Anthropic Messages use the same tools, brakes and recovery. The header shows a
one-way fingerprint of the key that will be used, and the session's tokens used
and remaining in a local safety budget, which is a count, not a credit balance.
The localhost HTTP interface accepts UTF-8 with one Content-Length, headers up to
32~KiB, bodies up to 8~MiB, and expires incomplete requests after 15 seconds;
ambiguous lengths, transfer encodings and pipelined bytes are rejected before any
provider call.

\section{One project, one directory}
\label{sec:one-project-directory}

\index{project!directory boundary}
Ordinary projects live in \texttt{projects/<readable-project-name>} and have no
owner: the workspace opens before login, and login is needed only for model calls
and key management. \texttt{LEANFM\_WORKSPACE\_ROOT} selects the workspace and
defaults to the server's directory. A project holds its own book, canonical
specifications, source, tests, media, conversation, evidence and caches; deleting
its root removes its state. The credential vault is outside every project's
reach. Foreign browser origins and unapproved Host values cannot mutate the
loopback workspace, a conflicting writer is rejected before any work, and queued
prompts keep their credential identity and wait if it changes.

\texttt{LeanFM.ChatUI.Store.createProject} reserves the root atomically (never
adopting an occupied one), writes a \texttt{manifest.json} with every canonical
project-relative path, and provisions book, \texttt{spec/}, source, tests,
artifacts, renders, events, reports, logs, cache and conversations. Directory
names come from project names, with safe separators and a numeric suffix on
collision; the manifest's stable identifier is independent of the name, so a moved
root keeps its URLs, conversation and revisions. Portable \texttt{project.json}
roots are discovered when they validate (Chapter~\ref{ch:bootstrap-contract}), and
duplicate identities are rejected rather than resolved arbitrarily.

Project memory shows, for the requirements and the implementation mapping,
whether each passes its canonical check and whether it is committed in git. LeanFM
blocks no edit, write or launch on an approval, model tools cannot write checker
evidence, and project checks and media generators run without network or host
credentials, writing only project cache or scratch.

The typed component is \path{LeanFM/LLMGenerated/SharedProjects.lean}, composed
into the self-hosting product, with its realization in the canonical
\path{LeanFM/LLMGenerated/Implementation.lean}. \texttt{lake env lean --run
ReviewSharedProjects.lean} derives the review and views in
\path{reports/shared-projects/}. The reset that introduced this layout, on
October 23, 2026, discarded five ordinary projects and the legacy
\texttt{./data}, after verifying the preserved credential bytes; its report is
\path{reports/shared-projects/reset-result.json}.

\section{What the Lean artifact must settle}

The Lean artifacts are the semantic source for actors, framed messages, process
projections, grammars, properties, proof obligations and desired outputs:
Chapter~\ref{ch:events} defines event fields, correlation, order, causation and
time; Chapter~\ref{ch:grammar} legal conversations, projections and bounded
queues; Chapter~\ref{ch:authoring-language} choices, dwell, rates, scalability,
reliability and cost.

Message-count capacity alone does not bound memory when payload sizes vary.
Queued bytes come from encoded envelopes, and active task state needs a declared
footprint. A representative requirement is
\AccessibleEquation{Necessarily at every reachable observation the queued bytes for actor a plus its in-flight bytes are less than or equal to its byte budget.}{\[
  \mathrm{AG}\bigl(\operatorname{queuedBytes}(a) +
    \operatorname{inFlightBytes}(a) \leq \operatorname{budget}(a)\bigr).
\]}
This is a modeling obligation, not a claim that the validator proves an arbitrary
implementation's heap usage.

\section{Interrogate, characterize, synthesize, replay}

Characterization tests whether desired claims can be identified from evidence:
scenario and task boundaries, terminal-to-start links, actor populations, clocks
and units, observation windows, resource bounds, failure evidence and probability
provenance. Missing inputs stay indeterminate. One event stream produces the
standard characterization, whose inventory is \texttt{outOfBoxArtifacts} in
\texttt{LeanFM/Characterization.lean}; \texttt{baselineDerivedProperties} records
each property's fields, reducer, unit, visualization and boundary. Specified
distributions may drive predictions or generation but are never presented as
measurements (estimators: Chapter~\ref{ch:events}).

For generative similarity, reducers map the source stream to a named metric
vector with each histogram bin as an exact ratio. A candidate is serialized,
decoded and reduced the same way, and passes only when every metric is within its
declared tolerance: ``similar'' means equivalent under this finite
characterization. The grammar, invariants and byte language still constrain
legal traces.

\section{The protobuf artifact is part of the requirement}

The protobuf schema answers what a state diagram cannot: which bytes cross a
boundary. Atomic payload messages and a \texttt{RequirementEnvelope.oneof}
discriminator connect each grammar terminal to its wire form; validation checks,
among other things, that field tags are nonzero and unique and that framing is
explicit. The pairing exposes real defects: an event that needs a
\texttt{priorIds} list where the wire carries one predecessor, a latency property
over a clock that is never recorded, a byte budget beside an unbounded field.

The exact wire size feeds resource analysis:

\begin{lstlisting}
queuedBytes actor observation :=
  (observation.inbound actor).sum encodedSize
  + (observation.outbound actor).sum encodedSize

memoryPressure actor observation :=
  queuedBytes actor observation
  + inFlightFootprint actor observation.activeWork
\end{lstlisting}

The first term is computed from concrete envelopes; the second is a declared
abstraction of implementation state, and stays labeled as one.

\section{A ladder of checks}

No single green check answers every kind of requirement. Lean and protobuf check
syntax; structural validation checks actors, endpoints, terminals, framing,
process coverage and proof obligations; grammar and temporal checks cover
ordering, safety, reachability and bounded liveness; probability and dwell
reducers predict outcomes and event-stream reducers estimate them; queue and
byte-budget checks model capacity, backpressure and memory; generated diagrams,
plots and reports support review. Each result carries an evidence label from
Chapter~\ref{ch:vision}. Predictions are not measurements, incomplete windows
censor tasks, frequencies do not prove probabilities, and bounded traces do not
prove unbounded liveness.

\section{How to argue well}

The most useful prompts attack boundaries:

\begin{itemize}
  \item ``Which event and grammar branch make this claim true?''
  \item ``With two concurrent sessions and tasks, what blocks on a full queue
        and which events correlate?''
  \item ``Which random choice belongs to the user, and how does it change the
        downstream completion and latency distributions?''
  \item ``Derive the plot from the event stream, including in-flight tasks.''
  \item ``Show the corresponding protobuf payload and its encoded-size bound.''
  \item ``Which evidence label applies: Lean proof, finite-model check, test,
        generated analysis, or assumption?''
\end{itemize}

Conversation discovers the specification; durable artifacts retain it
(Chapters~\ref{ch:bootstrap-contract}, \ref{ch:scenarios}, \ref{ch:events} and
\ref{ch:feature-discipline}).

\section{Persistent application launch}

The \texttt{run} check starts a private smoke test and stops it at readiness; it
is not a preview. \path{LeanFM/LLMGenerated/ApplicationLaunch.lean}, exposed as
\texttt{applicationLaunchProposal}, adds start, live-status and stop tasks: the
project shows Start/Restart, Stop and Open app, and a chat request to launch
returns the verified link. Only a ready owned instance at the current source
revision may be called running, and preview code never inherits the engineering
UI's credentials or origin. The \texttt{run} target stays in the foreground for
supervision, and \texttt{stop} stops only its own application. Review records and
negative controls are in \path{reports/application-launch-review/};
Chapter~\ref{ch:chat-ui-guide} shows the controls.
