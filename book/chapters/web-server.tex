\chapter{Arguing Requirements through the Lean Web Server}
\label{ch:web-server}

\index{vibecoding}
\index{requirements!durable}
The LeanFM web server presents a conversational workbench, but conversation is
not its product. Its product is a durable set of artifacts: a typed Lean
requirements model, a protobuf description of the bytes exchanged by the
participants, and a separate Lean implementation plan. The useful form of requirements vibecoding is therefore not
``ask a model to write the system.'' It is an argument in which a person keeps
challenging a proposed boundary until the remaining claims can be compiled,
checked, measured, or left as explicit proof obligations.

Chat history is evidence about how a decision was reached. It is not the
decision. A future reader must be able to discard the transcript, open the
generated files, and recover the actors, observable events, alternatives,
correlation rules, timing assumptions, resource bounds, and properties.

\section{The argument loop}

The interface resembles ChatGPT because natural language is convenient for
finding omissions. The loop, however, has a formal boundary:

\begin{center}
\begin{tikzpicture}[>=Latex,node distance=1.15cm,
  box/.style={draw,rounded corners,align=center,minimum width=3.1cm,
    minimum height=.75cm,fill=diagramsurface},flow/.style={->,thick}]
  \node[box] (claim) {state or challenge\\a requirement};
  \node[box,right=of claim] (draft) {materialize a candidate\\Lean + protobuf pair};
  \node[box,below=of draft] (check) {compile, validate,\\simulate, and render};
  \node[box,left=of check] (evidence) {inspect traces, plots,\\violations, and obligations};
  \draw[flow] (claim) -- (draft);
  \draw[flow] (draft) -- (check);
  \draw[flow] (check) -- (evidence);
  \draw[flow] (evidence) -- node[left,align=right,font=\small]
    {counterexample or\\sharper question} (claim);
\end{tikzpicture}
\end{center}

The human contribution is often adversarial. ``The upload completes'' should
prompt: what observable event constitutes completion, who observes it, and does
it mean receipt, durable storage, or policy acceptance? ``The service handles
load'' should prompt: how many messages fit in each queue, how many
\texttt{(session, task)} pairs may be active, and what happens at the bound?
The assistant's job is to turn each answer into structure, not merely agreeable
prose.

A productive exchange might proceed as follows.

\begin{quote}\small
\textbf{Person:} A submitted upload eventually completes.\\
\textbf{Assistant:} I will treat an \texttt{uploadCompleted} response as
completion.\\
\textbf{Person:} No. Completion requires the storage actor's acknowledgment,
and the client must be able to distinguish rejection from timeout. Both queues
are finite.\\
\textbf{Assistant:} Then the grammar has accepted, rejected, and timed-out
alternatives; acceptance contains a storage acknowledgment before the response.
I will add queue capacities and a bounded-liveness obligation.\\
\textbf{Person:} Also show the behavior with many sessions in flight, estimate
the completion distribution from an event stream, and fail the requirement if
queued bytes exceed the memory budget.
\end{quote}

Every turn should change a named assumption, artifact, check, or open
obligation. If it changes none of them, it has not improved the specification.

\section{The server is a staging environment}

The executable \texttt{lake exe leanfm-server} serves the assistant workbench
on the loopback interface. An authenticated session has its own generated
\texttt{Requirements.lean}, \texttt{Requirements.proto}, and
\texttt{Implementation.lean}. The first two specify observable behavior and
values that resolve to bytes. They do not imply HTTP. The implementation file
selects how those bytes travel---for example HTTP method and path, an
in-process channel, TCP, or another adapter. The HTTP interface
can read and replace these files through
\texttt{/api/session/generated/requirements.lean} and
\texttt{/api/session/generated/requirements.proto}, and
\texttt{/api/session/generated/implementation.lean}. Validation, rendered views,
metrics, reports, and OpenAPI descriptions are projections of the same model.

Session isolation is useful during an argument, but the current session files
live below \texttt{/tmp/leanfm-sessions}. That is a workspace, not durable
storage. A concluded argument must export or commit the accepted files---for
example as \texttt{LeanFM/LLMGenerated/Requirements.lean},
\texttt{LeanFM/LLMGenerated/Requirements.proto}, and the separate
\texttt{LeanFM/LLMGenerated/Implementation.lean}---together with any evidence
needed by the project. Durability means that the specification has an ordinary
name, history, review boundary, and reproducible checks independent of the chat
service.

The server may use a language model to propose edits. Compilation and validation
remain deterministic. The model is not the proof checker, and fluent prose is
not evidence that an obligation holds.

\subsection{The code that creates the TCP listener}

An address value does not open a port. The running server performs four distinct
operations: create a socket, bind it to an address, put it into listening mode,
and repeatedly accept clients. This is the relevant executable pattern from
\texttt{Server.lean}:

\begin{lstlisting}[language=Lean]
import Std.Internal.Async.TCP

open Std
open Std.Net

abbrev TcpServer := Std.Internal.IO.Async.TCP.Socket.Server

def bindAddr : SocketAddress :=
  SocketAddress.v4
    { addr := IPv4Addr.ofParts 127 0 0 1
    , port := 8080
    }

partial def serveLoop (server : TcpServer) : IO Unit := do
  let client ← (server.accept).block
  let _ ← IO.asTask (handleClient client) Task.Priority.dedicated
  serveLoop server

def main : IO Unit := do
  let server ← Std.Internal.IO.Async.TCP.Socket.Server.mk
  server.bind bindAddr
  server.listen 128
  IO.println "LeanFM server listening on http://127.0.0.1:8080"
  serveLoop server
\end{lstlisting}

Read the final definition as follows: \texttt{Server.mk} creates the TCP socket;
\texttt{bind} attaches it to loopback port 8080; \texttt{listen 128} changes it
into a listener with a pending-connection backlog of 128; and
\texttt{serveLoop} calls \texttt{accept} for each connection. Only after
\texttt{listen} succeeds is there a TCP listener. HTTP is the application
protocol implemented by \texttt{handleClient}; there is no separate HTTP socket.
The actual handler catches per-request errors before returning to the accept
loop. This shortened excerpt leaves that response logic out so the listener
lifecycle remains visible.

\section{Using the agent in Codex}

\index{Codex}
Codex can drive the complete bootstrap, not only the final code-generation
step. Open the LeanFM repository as the Codex workspace, or start its
command-line interface from the repository root:

\begin{lstlisting}[language=bash]
cd /path/to/leanFM
codex
\end{lstlisting}

The repository's \texttt{AGENTS.md} directs the agent to the LeanFM workflow in
\texttt{SKILL.md}. Both files make \texttt{book/main.pdf} a critical prompt
input rather than merely the publication produced by the source in
\texttt{book/}. The agent must read the book together with the live language
references and the existing source tree while developing LeanFM itself. Once
that software is operational, the agent uses it to construct and check the
durable requirements for the target system. Only accepted requirements become
input to a separately checked implementation specification, and only both
accepted specifications authorize generation or revision of application code.

Thus the intended order is:

\begin{enumerate}
  \item develop and verify the LeanFM tooling described by this book;
  \item use the running tooling and the book to interrogate the target system,
        produce its durable requirements artifacts, and validate their
        prompt-derived views;
  \item after explicit requirements acceptance, produce and validate the
        traceable implementation specification; and
  \item after explicit implementation acceptance, generate or revise the actual
        application from the book, all three accepted artifacts, and the existing
        source tree.
\end{enumerate}

A Codex prompt can state this bootstrap explicitly. For example:

\begin{lstlisting}[breaklines=true]
Treat book/main.pdf as a required system-prompt input, not merely an output of
this repository. Read it with AGENTS.md, SKILL.md, the live LeanFM language
references, and the existing source tree. First develop and verify the LeanFM
software described by the book. Once LeanFM is operational, use it to develop
verified requirements for an order-cancellation service: a customer may cancel
an order until warehouse packing starts. Generate from the specification an
interaction diagram, state machine, cancellation-success rate, and p95
cancellation latency, each retaining its question, event source, reducer, unit,
and boundary. Stop for my explicit acceptance of Requirements.lean,
Requirements.proto, and those derived outputs. Then develop a separately
traceable Implementation.lean and stop for my explicit acceptance. Only after
both gates, implement the application from book/main.pdf, the three accepted
artifacts, and the existing source tree; add tests and run the repository checks.
\end{lstlisting}

The book remains in the input set throughout this process because it defines the
language and method by which the typed artifacts are interpreted. The artifacts
then add the target system's accepted facts: observable behavior in
\texttt{Requirements.lean}, byte-resolving values in
\texttt{Requirements.proto}, and runtime choices plus traceability in
\texttt{Implementation.lean}. A person can reject either candidate
specification and continue the argument; a successful build does not count as
acceptance.

\section{MCP: the agent-facing entrance}

\index{Model Context Protocol}
The browser UI is for stakeholders; the Model Context Protocol endpoint is for
an LLM agent. LeanFM serves stateless JSON-RPC requests at \texttt{POST /mcp}.
On initialization, the server tells the agent that the book is durable project
context---effectively a maintained section of the system prompt---rather than
optional background reading. The agent can enumerate and read fixed resource
URIs for \texttt{book/main.pdf}, its dark rendering, the canonical requirements,
protobuf and implementation files, and both live language references.

This interaction is generated from the implemented MCP dispatch surface:

\begin{figure}[htbp]
\centering
\resizebox{\textwidth}{!}{\input{generated/mcp-interaction.tex}}
\caption{An agent obtains durable project context and deterministic evidence
through MCP. Source: \texttt{LeanFM.MCP}; reducer and provenance:
\texttt{book/generated/mcp-interaction-provenance.txt}.}
\label{fig:mcp-interaction}
\end{figure}

The first surface is intentionally read-only. It provides resource and prompt
discovery, the requirements interrogation, the post-acceptance code-generation
prompt, and canonical artifact validation. It exposes no arbitrary pathname and
no tool can accept a requirements or implementation gate. Those are stakeholder
decisions, not consequences of a successful tool call. MCP transports context
and evidence; the existing LeanFM workflow controls revision and acceptance.

The bundled server listens only on loopback. A deployment that exposes MCP to a
network must add authentication and authorization at the transport or reverse
proxy before treating the resource contents as safe to publish. Statelessness
does not make project data public, and a future writable MCP surface must bind
every request to a user, project, revision and accepted snapshot.

A local Codex client can register the running endpoint and inspect the result:

\begin{lstlisting}[language=bash]
codex mcp add leanfm --url http://127.0.0.1:8080/mcp
codex mcp list
\end{lstlisting}

The MCP interface does not replace the book. It makes the book, specifications,
and live checker discoverable in a standard agent conversation so that a new
session need not reconstruct the method from chat history.

\subsection{Cursor as an agent client}

A Cursor subscription connects to LeanFM as an authenticated agent client, not
as a model-provider API key. A project may commit
\texttt{.cursor/mcp.json} with the local URL
\texttt{http://127.0.0.1:8080/mcp}. Cursor Agent opens the project root, reads
\texttt{AGENTS.md}, and discovers LeanFM's book, canonical artifacts, language
references, prompts and validation tools through MCP. Cursor continues to own
its subscription authentication and billing; LeanFM receives no Cursor login
secret. The current MCP surface remains read-only, so Cursor edits files using
its ordinary project tools and cannot accept either gate through MCP.

For the inverse arrangement---the LeanFM browser driving a Cursor-backed
conversation---Cursor CLI exposes the Agent Client Protocol over standard input
and output. A \texttt{CursorACP} adapter can initialize and authenticate the
local agent, create or load one session for each LeanFM project conversation,
submit prompts, stream updates, answer explicit permission requests and cancel
work. This is an implementation direction, not a claim about the running
server. The adapter must isolate user, project, conversation, process and
request identity; bound its queues; preserve tool and permission evidence; and
terminate the process only after its queue is closed and drained. Cursor's
authentication token is never imported into LeanFM's provider-key store.

\section{One project, one directory}

\index{project!directory boundary}
Project creation establishes one exclusive filesystem root. Everything owned by
that project must be below it. This is both an operational requirement and a
reproducibility boundary: deleting that one directory must remove the project
without requiring a search for session files, generated diagrams, caches, or
logs elsewhere on the machine.

The exact book used as a critical prompt input is part of the project itself.
Every project always has \texttt{book/main.pdf}; a dark reading copy,
\texttt{book/main-dark.pdf}, is generated from the same source. The specification
paths are stable within the project and recorded by its manifest rather than
rediscovered by searching. A representative exported layout is:

\begin{lstlisting}
order-cancellation/
  project.toml
  book/main.tex
  book/main.pdf
  book/main-dark.pdf
  specification/Requirements.lean
  specification/Requirements.proto
  specification/Implementation.lean
  source/
  tests/
  generated/renders/
  generated/metrics/
  evidence/traces/
  evidence/reports/
  .cache/
  logs/
\end{lstlisting}

There is one canonical accepted \texttt{Implementation.lean} for each project
revision. Multiple intentional implementation targets may add explicitly named
siblings such as \texttt{Implementation.server.lean}; each must identify its
target and retain complete requirement traceability. They may not become an
unindexed collection from which an agent guesses.

The LeanFM repository is itself one such project. Its canonical self-hosting
specifications currently live together under \texttt{LeanFM/LLMGenerated/}; its
manifest and agent instructions make those stable repository-relative paths
explicit. Copying the complete project directory therefore produces a repository
candidate that Codex can enter and use without external project-owned state.

The exported directory names may vary only when the manifest states their stable
locations; the containment invariant may not. Configured output
paths and symbolic links must resolve inside the project root. Temporary files
must be created there and atomically renamed there. Export is an explicit copy
of a declared artifact, not an unrecorded second project location. Import must
copy an input into the root or record a content-addressed, immutable dependency;
it must not silently turn an arbitrary external pathname into project state.

Globally installed LeanFM binaries and content-addressed dependency caches may
be shared because they are tooling, not state owned by one project. They must not
hold mutable project-specific data. A launcher may keep a global recent-project
index, but that index is disposable: it must be reconstructible from manifests
inside project roots and must not be needed to delete a project completely.

This changes the current staging design. A session directory under
\texttt{/tmp/leanfm-sessions} and committed artifacts under a separate source
tree cannot jointly be the durable project. A conforming implementation chooses
the project root first, places session work beneath it, and promotes accepted
artifacts by atomic moves within that same root. Project deletion resolves and
validates the exact root, refuses filesystem-root or escaping targets, and then
removes only that directory.

\section{What the Lean artifact must settle}

The Lean file is the semantic source. It records actors, messages, per-task
state machines, multiparty grammar productions, CSP-style processes, framing,
properties, proof obligations, probability summaries, charts, and explanatory
Markdown. A serious argument should force answers in each of the following
dimensions.

\begin{description}[style=nextline]
  \item[Observable behavior]
  Which actor sends and receives each event? Which fields can an observer see?
  A message carries its \texttt{session} and \texttt{task}, its clock timestamp,
  and a list of prior event identifiers. Thus a join may cite several prior
  events, while several events may fork from the same prior event.

  \item[Component interactions]
  Global grammar productions state legal conversations; actor projections state
  what each component may send or receive. Composition must preserve endpoints,
  message types, correlation, and predecessor references. A diagram is useful
  evidence, but the grammar is the compositional object.

  \item[Statistical properties]
  User choices make the input probabilistic even when every server component is
  deterministic. Those choices propagate through the composed system as an MDP.
  The specification distinguishes unconstrained alternatives from weighted
  choices, states dwell-time distributions, and names reducers for success,
  latency, throughput, and queue occupancy. An observed event stream can then
  estimate the same quantities and be compared with the model.

  \item[Queueing and concurrency]
  Every actor has finite inbound and outbound queues. Several
  \texttt{(session, task)} pairs may be in flight at once, so a requirement must
  not silently reason about only one conversation. Full and empty queues produce
  observable blocking or sleeping behavior, and transport is a separate step
  from production and receipt.

  \item[Memory pressure]
  Message-count capacity alone is insufficient when payload sizes vary. A
  checkable requirement should declare a byte budget and derive queued bytes from
  the encoded envelopes. If active tasks retain additional state, the model must
  declare a bounded footprint for that state too. A representative obligation is
  \AccessibleEquation{Necessarily at every reachable observation the queued bytes for actor a plus its in-flight bytes are less than or equal to its byte budget.}{\[
    \mathrm{AG}\bigl(\operatorname{queuedBytes}(a) +
      \operatorname{inFlightBytes}(a) \leq \operatorname{budget}(a)\bigr).
  \]}
  Read this as: ``necessarily, at every reachable observation, queued bytes for
  actor $a$ plus in-flight bytes for actor $a$ is no greater than actor $a$'s
  byte budget.''  $\mathrm{AG}$ means ``on every permitted future, at every
  position''; the repeated argument $a$ identifies the same actor throughout.
  This is a modeling obligation for LeanFM, not a claim that the present
  validator already proves heap usage of an arbitrary implementation.
\end{description}

\section{Interrogate, characterize, synthesize, replay}

\subsection{The first question}

A fresh LeanFM conversation is not an empty general-purpose chat. Its only
required external input is the project-root directory. The server and agent
load the manifest, editable and rendered book, canonical requirements and
protobuf, implementation mapping, acceptance revisions, source, generated
views and evidence from stable paths beneath that root. They do not require a
copied transcript or a specially composed restart prompt.

When that directory contains no durable problem statement, the first visible
assistant message is: ``What problem are you trying to solve?'' The answer is
recorded before the system proposes frameworks or solutions. Subsequent
questions name a concrete ambiguity and identify which requirement, view,
proof obligation, implementation choice or acceptance gate depends on the
answer. A useful turn records a durable decision, updates a derived view, asks
such a blocking question, reports validation, or advances one of the two
acceptance gates. Unrelated conversational assistance is outside this project
conversation's purpose.

The book is produced during this argument rather than written afterward. A
durable decision revises its editable source and regenerates
\texttt{book/main.pdf} and \texttt{book/main-dark.pdf} from the same content.
The revision links its explanation and generated diagrams to the corresponding
requirements, implementation and evidence revisions. Consequently, starting a
new model session with the project directory is enough to continue the design
without reconstructing intent from chat history.

The conversational interface is not merely a code generator. Its first job is
to discover whether the desired claims are identifiable. It asks for scenario
and task boundaries, start-to-end backpointers, concrete actor populations,
clock and work units, observation windows, queue and memory limits, outage and
recovery events, and the provenance of probabilities. A missing answer is
reported as an indeterminate metric rather than replaced by an invented value.

Once those fields are available, one event stream should produce a standard
characterization out of the box:

\begin{itemize}
  \item one interaction diagram and derived state machine per scenario;
  \item XY line graphs for time-, load-, population-, and replica-indexed metrics;
  \item pie-chart histograms for categorical outcomes and distributions;
  \item uptime, outage fraction, reliability, and MTTR;
  \item client-experienced and server-aggregate throughput; and
  \item latency distributions and named percentiles.
\end{itemize}

Some streams contain observations; other requirements contain only expected
distributions. These are labeled separately. An expected distribution can drive
generation, but it is not presented as a measurement.

Generative similarity closes the loop. Reducers first turn the source stream
into a named metric vector, including histogram bins as individual exact ratios.
The generator produces a candidate scenario, serializes it to bytes, decodes it,
and runs the same reducers. The candidate is accepted only when every required
metric lies within its declared relative tolerance. Thus ``similar'' means
measurement-equivalent for the stated characterization, not visually plausible
or textually similar. Several very different event processes may satisfy the
same finite metric vector; the grammar, invariants, and byte-level language still
constrain which candidates are legal.

\section{The protobuf artifact is part of the requirement}

The parallel protobuf schema answers a question that a state diagram cannot:
what bytes can cross a component boundary? Atomic payload messages and a
\texttt{RequirementEnvelope.oneof} discriminator connect a grammar terminal to
its wire representation. Validation checks, among other things, that field tags
are nonzero and unique and that framing is explicit.

This pairing exposes useful disagreements. A Lean event may require a
\texttt{priorIds} list while the wire schema provides only one predecessor. A
latency property may depend on a clock that is never transmitted or recorded. A
memory budget may be stated in bytes while an unbounded protobuf field remains.
These are requirements defects, not serialization trivia.

The exact wire size is also an input to resource analysis:

\begin{lstlisting}
queuedBytes actor observation :=
  (observation.inbound actor).sum encodedSize
  + (observation.outbound actor).sum encodedSize

memoryPressure actor observation :=
  queuedBytes actor observation
  + inFlightFootprint actor observation.activeWork
\end{lstlisting}

The first term can be computed from concrete envelopes. The second requires a
declared abstraction of implementation state and must remain visibly labeled as
such.

\section{A ladder of checks}

No single green check answers every kind of requirement. The workbench should
present a ladder of evidence:

\begin{enumerate}
  \item Lean elaboration and protobuf parsing establish well-formed artifacts.
  \item Structural validation rejects missing actors, endpoints, terminals,
        framing, terminal states, process coverage, or real proof obligations.
  \item Grammar and projected state-machine checks cover ordering and component
        interaction.
  \item Temporal checking covers safety, reachability, and appropriately bounded
        liveness over observable states.
  \item Probability and dwell reducers predict completion probability and
        latency; event-stream reducers estimate them from observations.
  \item Queue and byte-budget checks cover capacity, backpressure, concurrency,
        and modeled memory pressure.
  \item Rendered interaction diagrams, state machines, plots, and reports make
        the same typed model reviewable by people.
\end{enumerate}

The distinction between model prediction and measurement must remain visible.
An incomplete observation window may censor slow tasks; a frequency estimate is
not automatically a proof of the declared probability; and a bounded trace does
not establish unbounded liveness. Good generated reports say which claim was
proved, calculated, sampled, or merely assumed.

\section{How to argue well}

The most useful prompts attack boundaries rather than ask for polish:

\begin{itemize}
  \item ``Show me the observable event that makes that sentence true.''
  \item ``Which alternative ends here, and how is it bracketed in the grammar?''
  \item ``What happens when this inbound or outbound queue is full?''
  \item ``Run two sessions and two tasks concurrently; which events correlate?''
  \item ``Which random choice belongs to the user, and how does it change the
        downstream completion and latency distributions?''
  \item ``Derive the plot from the event stream, including incomplete tasks.''
  \item ``Show the corresponding protobuf payload and its encoded-size bound.''
  \item ``Is this result proved, model-checked, simulated, measured, or assumed?''
\end{itemize}

The argument is finished enough to review when deleting the transcript loses no
normative information; a clean checkout can compile and validate the artifacts;
every diagram and plot is derived rather than independently drawn; failures have
observable outcomes; quantitative assumptions have units and scope; and every
unsettled claim is an explicit obligation. That is the requirements-centered
meaning of vibecoding in LeanFM: conversation discovers the specification, but
the checked artifacts outlive the conversation.
