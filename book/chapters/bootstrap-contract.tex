\chapter{The LeanFM Project Bootstrap Contract}
\label{ch:bootstrap-contract}

This chapter defines the minimum machine-readable context that makes a LeanFM
project self-hosting. It belongs in the machine reference because an agent must
apply it before it can turn the rest of the book into checked artifacts. The
bootstrap defines the language and its tools; it must not contain a hidden copy
of the product requirements or implementation.

The intended handoff is deliberately simple: send another person the URL of
this PDF, ask Claude, Gemini, Codex, or another capable construction agent to
read it, and ask that agent to make the software. The current generic bootstrap
distribution is published at
\url{https://github.com/rfielding/leanFM/tree/main/projects/blank-leanfm-webserver}.
An agent using only the PDF may follow that URL for the language files and
commands named below. It must not copy the existing LeanFM application source
or prior ChatUI specifications as an answer key.

\section{Required project inputs}

A copyable project root contains the following stable inputs:

\begin{description}[style=nextline]
  \item[\texttt{book/main.pdf}] Central product-design argument and maintained
        system-prompt context.
  \item[\texttt{book/main-dark.pdf}] Accessible rendering of the same source.
  \item[\texttt{LeanFM/}] Versioned generic authoring types and deterministic
        validators. Product actors, messages, tasks and routes do not belong in
        this directory.
  \item[\texttt{bootstrap/}] Programs that print the language references and
        interrogation checklist, validate the conventional specification, and
        derive review views from its typed value.
  \item[\texttt{lean-toolchain} and \texttt{lakefile.toml}] The exact compiler
        selection and module roots needed to run the bootstrap locally.
  \item[\texttt{project.json}] Project identity, stable artifact paths,
        acceptance state and the classification of design versus language
        inputs.
\end{description}

All project-owned state and acceptance decisions belong below the exclusive
root: inputs, conversations, artifact revisions, source, tests, generated views,
traces, reports, logs, and project-specific caches. Choose the root before
session work; temporary files and atomic promotion stay inside it. Reject
configured outputs and symlinks that escape. Export declared artifacts
explicitly; import by copying into the root or recording an immutable,
content-addressed dependency. Shared tools and caches may live outside only
without project-owned state. A global index must be reconstructible from
manifests, and deleting one root must remove all its state without an external
search.

The project root is also the complete input to a fresh agent conversation. The
agent discovers the stable paths from the manifest and repository instructions;
the stakeholder need not paste a transcript or restate a bootstrap procedure.
If the root has no durable problem statement, LeanFM creates the minimal
editable book shell and begins with the visible question ``What problem are you
trying to solve?'' The answer starts requirements discovery. Named ambiguity
questions, book revisions, validation evidence and the two acceptance decisions
then accumulate beneath that same root.

\section{Conventional generated interface}

The requirements candidate lives at
\texttt{Specification/Requirements.lean}, imports
\texttt{LeanFM.Artifacts}, and defines:

\begin{lstlisting}[language=Lean]
namespace LeanFMProject.Requirements
def spec : LeanFM.RequirementSpec := ...
def all : List LeanFM.GeneratedRequirement := [.requirement spec]
end LeanFMProject.Requirements
\end{lstlisting}

The byte vocabulary lives beside it at
\texttt{Specification/Requirements.proto}. After requirements acceptance, the
separate implementation mapping lives at
\texttt{Specification/Implementation.lean}. Capitalization is significant
because these are Lean module paths, not informal filenames.

\section{Required commands and order}

The project supplies deterministic equivalents of these commands:

\begin{lstlisting}[language=bash]
make reference       # print the complete requirements-language reference
make interrogation   # print questions that expose missing observations
make validate        # elaborate and run LeanFM plus protobuf validation
make render          # derive interaction and residual-state review views
make check           # validate, then render
\end{lstlisting}

An agent runs \texttt{reference} and \texttt{interrogation} before authoring.
It must not infer constructors from prose or invent a smaller Lean lookalike.
The validator consumes the exported \texttt{RequirementSpec}; successful Lean
elaboration by itself is not LeanFM validation. The renderer also consumes that
same value. A separately written diagram is not evidence that it matches the
requirements.

\section{Acceptance gates}
\label{sec:acceptance-gates}

The first gate accepts observable requirements; the second separately accepts
their realization mapping. Both require explicit stakeholder acceptance, not a
successful build, model response or attractive diagram. Application source and
tests follow only after both gates and the security review in
Chapter~\ref{ch:feature-discipline}.

\texttt{Requirements.lean} defines the contract. Its accepted multi-actor wire
grammar is the conformance oracle: complete decoded traffic is legal or has a
counterexample; an incomplete capture cannot establish conformance.
\texttt{Requirements.proto} fixes byte values without choosing transport.
\texttt{Implementation.lean} records choices needed to realize accepted
behavior---for example queues, transports, journals or browser mechanisms---each
mapped to its requirement. Answers to implementation questions belong there
when they leave observable behavior unchanged. An answer changing messages,
fields, ordering or another observable must instead revise Requirements and
return to the first gate. Remove implementation answers made unnecessary by
later requirements changes rather than preserving them as requirements.

The bootstrap therefore solves a circularity without weakening the gates. The
book explains what is being built; the generic distribution makes the LeanFM
language executable; accepted project artifacts preserve the decisions. None
is a substitute for the other two.

\section{Construction is not a runtime dependency}

The construction agent is not part of the delivered server. After construction,
the user starts LeanFM, visits its root URL in an ordinary browser, creates or
logs into an account, supplies a model-provider key, and conducts the
requirements argument through LeanFM's own ChatGPT-like interface. The server
talks to the selected model provider through its documented message protocol;
it does not require the construction agent, its conversation, or local tooling.

Consequently, a reconstruction is not successful merely because it can be
driven from a coding-agent terminal. It must build a standalone executable,
serve the complete browser workflow, start without a platform API key, isolate
concurrent users and their credentials, and pass its conformance tests without
Codex being present.

\section{Build, runtime, and publication dependency inventory}
\label{sec:dependency-inventory}

The repository does not treat one developer's workstation as an implicit build
input. The machine-readable \texttt{toolDependencyInventory} in
\texttt{LeanFM/ChatUI/Requirements.lean} is normative; this section is its
human review view. ``Required'' means that the default check, server, book, or
stakeholder-media path invokes the dependency. ``Optional'' means the named
workflow is outside the default product build. JavaScript versions are fixed by
\texttt{ui/package-lock.json}, Python ranges by
\texttt{scripts/chatui\_requirements.txt}, and Lean and Go by
\texttt{lean-toolchain} and the top-level \texttt{Makefile}.

\begin{description}[style=nextline]
\item[Lean and Lake --- required.] Lean 4.28.0 from
  \texttt{lean-toolchain} compiles the DSL, validators, renderers, tests, and
  server. Lake resolves modules and drives native linking.
\item[C toolchain and libc headers --- required.] A compiler and linker
  supported by Lean 4.28 link the native executables emitted by Lean.
\item[GNU Make, Bash, and coreutils --- required.] The workflows use
  \texttt{timeout}, \texttt{cmp}, \texttt{cp}, \texttt{tar}, \texttt{gzip},
  and \texttt{sha256sum} for bounded commands and verified tool downloads.
\item[Node and npm --- required.] Node 22.12 or newer and \texttt{npm ci}
  type-check and bundle the React UI. The lockfile fixes React, ReactDOM,
  TypeScript, Vite, KaTeX, and their transitive packages.
\item[Python packages --- required.] Python 3.12 or newer with Cryptography
  41--50, Pillow 10--12, and Protobuf 5--6 protects retained keys, performs
  protobuf round trips and reductions, and generates animated GIFs.
\item[Protocol Buffers compiler --- required.] A \texttt{protoc} supporting
  proto3 and Python output generates the temporary byte-round-trip binding.
  Target-language generators are declared separately when needed.
\item[Graphviz --- required.] \texttt{dot} with PNG output rasterizes generated
  DOT diagrams during \texttt{make diagrams}.
\item[TeX Live and pdfLaTeX --- required.] Install the base, recommended, extra,
  pictures, and recommended-font collections. The source uses \texttt{lmodern},
  TeX Gyre Heros, geometry, microtype, xcolor, graphicx, tagpdf, AMS math,
  mathtools, booktabs, longtable, enumitem, listings, natbib, imakeidx, TikZ,
  pgfplots, hyperref, and cleveref.
\item[Go --- required.] Go 1.23.12, whose archive hash is fixed by the Makefile,
  compiles and tests the repository Go/Paxos target.
\item[Bubblewrap --- required on the Linux server.] \texttt{bwrap} with
  namespace and bind-mount support runs project-local Python/Pillow GIF
  generators without network access.
\item[FFmpeg --- required for shareable video.] FFmpeg with \texttt{libx264}
  H.264 and AAC encoders converts GIF/WebM to validated MP4, adds fast-start
  metadata, and muxes optional narration.
\item[curl, ripgrep, and iproute2 --- required for development checks.]
  \texttt{curl}, \texttt{rg}, and \texttt{ss} exercise HTTP contracts, select
  validation evidence, and identify the local server.
\item[Java and TLA+ tools --- optional.] A Java runtime and the checksummed
  \texttt{tla2tools.jar} 1.7.4 run the separate \texttt{tla-check} example.
\item[Manim and Piper --- optional.] A project-local video Python environment
  and selected voice model render explanatory videos and synthetic narration.
\item[Target compilers and SDKs --- conditional.] The accepted
  \texttt{ImplementationSpec} inventories every compiler, code generator, SDK,
  runtime, native library, and version bound before source generation.
\end{description}

An agent can reconcile this declaration with the current host and report each
item as satisfied, missing, incompatible, or optional. Installing or upgrading
host software remains an explicit bounded action; inspection alone never
silently mutates the machine. DuckDB is not currently invoked by a checked
LeanFM target and is therefore not a build dependency. If a DuckDB-backed
reducer is accepted, its CLI or library, binding, storage format, and version
contract must first enter this inventory and the implementation mapping. The
same rule prevents a locally installed compiler or media program from silently
becoming part of the product contract.

\section{Local and server-hosted references}

The local commands are authoritative when no server is running. A running
LeanFM server additionally exposes the requirements and implementation language
references, the interrogation checklist, and read-only MCP context without
requiring a user login. These public endpoints contain language documentation,
not project or account data. Project artifacts, conversations, credentials and
acceptance mutations remain authenticated and owner-scoped.
