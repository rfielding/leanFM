\chapter{Using the LeanFM Chat UI}
\label{ch:chat-ui-guide}

LeanFM's Chat UI takes a project from a problem statement to a maintained book,
checked requirements, an implementation mapping, source files and a running
application. Work in Chat; use the other panes to inspect what the conversation
actually produced. There is no approval button: you review the result and commit
it with git.

This walkthrough uses the production interface with a disposable GoServer project
(real checked specifications and runnable code) and a local test provider, so the
model name and token readings are fixture data. The screenshots hold no live
credentials; their keyboard traces, accessibility snapshots and capture boundaries
are kept in \path{book/assets/ui-tour/}.

\section{Open the service and unlock your account}

Start LeanFM with \texttt{make serve} from the repository root and open
\url{http://127.0.0.1:8080/} (or the served address from another machine). The
application you are building runs separately.

\textbf{Sign in} with your LeanFM username and password, which unlocks your
encrypted provider keys; it is not your OpenAI or Anthropic password. After a
restart, sign in again; empty key fields do not mean the saved keys are gone.

\UITourFigure{01-sign-in}
  {Sign in unlocks the keys already retained for the LeanFM account.}
  {The actual LeanFM sign-in dialog shows username and password fields. Optional provider-key inputs and a password-change section precede the Log in button.}
  {Capture boundary: before LoginSubmitted. Both credential fields are empty.}

\textbf{Create account} takes a username, a password of at least eight
characters, and at least one provider key (OpenAI, Anthropic, or both), which is
verified before it is kept. Put keys only in these fields, never in a chat,
screenshot, source file or book. Once signed in, \textbf{API keys} adds or
replaces a key after you re-enter your password; blank fields keep stored keys,
and the optional password change re-encrypts them and ends older sessions.

\section{Choose the project before writing the prompt}

The sidebar selects a project; \textbf{New project name} and \textbf{Add project}
create one, with its own directory, book and specification paths. Confirm the
name in the header before sending a prompt. A project owns its book,
specifications, source, tests, views, conversation and evidence. A running turn
continues while you look at another project. Deleting a project removes its whole
directory and stops its application.

The horizontal navigation groups the work by purpose:
\begin{description}[style=nextline]
\item[Chat] Describe the problem, answer consequential questions, and request
  concrete changes or checks.
\item[Book] Read or edit the durable design argument and preview its PDFs.
\item[Grammar and Tasks] Inspect the current project's generated behavioral
  views rather than relying on an illustration invented in a reply.
\item[Project memory] Review canonical artifact files and whether each is checked and committed.
\item[Source] Inspect the implementation files and tests actually written.
\end{description}
The sidebar's text-size controls scale the interface, and navigation keeps drafts
and scroll positions. \texttt{Tab}, \texttt{Shift+Tab}, \texttt{Enter} and
\texttt{Space} work everywhere; the multiline composer has its own Send button.

\section{Send a useful prompt and understand the queue}

Begin with the problem and an observable outcome. For example:
\begin{quote}
People should be able to create named chat rooms, open a room, and post named
game challenges inside that room. Keep each room's conversation separate from
each challenge's conversation.
\end{quote}
Add a failure case when it matters: another room must not receive the message; a
retry must not create a second challenge. LeanFM resolves ordinary details from
the project files; a consequential ambiguity may still need your answer.

\textbf{Model} picks the model for the next prompt; the header shows its provider
and key fingerprint. The choice is captured when the prompt is queued, and an
unavailable provider is never silently replaced. You may keep sending prompts
while one runs: the visible queue runs them in order, each seeing earlier
results, and \textbf{Remove} discards one before it starts. \textbf{Attach image}
takes PNG, JPEG, GIF (first frame) and static SVG, up to 2~MiB and four images,
with a preview; \textbf{Copy reference} on a displayed image copies a stable
reference for a later prompt.

\UITourFigure{04-chat-running}
  {The active turn remains visible while the agent works.}
  {A real submitted fixture prompt appears in Chat. The Agent running banner names the captured model and shows elapsed time and the current stage. Cancel and the composer remain available.}
  {Capture boundary: ChatPromptSubmitted and ModelRequestIssued, before ModelResponseReturned. The local test provider deliberately holds the response for this capture.}

Expand \textbf{Operational trace} for real tool destinations, checks and
failures; it says more than the clock. \textbf{Cancel} stops work at the next safe
boundary, so a request already in flight may still finish. A saved multi-batch
task offers \textbf{Check progress}, \textbf{Resume task} and \textbf{Restart from
current files}.

\section{Read the result before retrying}

A completed message keeps its time, model, duration and usage. The header's
remaining-token figure is a local safety allowance, not a provider credit balance.

\UITourFigure{05-chat-response}
  {Review the answer and its evidence before taking the next action.}
  {The actual Chat pane shows the completed local-provider explanation of CreateRoom with its timestamp and usage. User-message Resend and message Delete controls appear beside the messages. The composer and model selector remain visible.}
  {Capture boundary: after ChatResponseRendered. The fixture reply explains existing checked behavior; it does not generate implementation files.}

\textbf{Resend} queues a prompt again with its attachments, which may cost a new
request; use it once you understand the failure. \textbf{Delete} removes a message
but undoes no file change. A structured question is answered in its form, which
queues the answer as a turn. A passing check, or a model saying ``done'', means
ready to review; acceptance is your commit.

An error carries a diagnostic, and often \textbf{Diagnostic for Codex} with
\textbf{Copy diagnostic}; keep it when reporting a problem. A provider credit
rejection is never retried automatically: fix billing or pick another model first.
Token limits, rate limits, incomplete responses, compiler and network failures
need different remedies, and the trace says which boundary failed.

\section{Keep the book and inspect the generated behavior}

\textbf{Book} shows the editable source beside its PDF. \textbf{Save source}
saves; \textbf{Build \& preview} also builds, and the status line says which
happened. \textbf{Light PDF} and \textbf{Dark PDF} render the same source;
\textbf{Maximize PDF} and \textbf{Restore split} change the layout.

\section{Review the specification, then inspect the implementation}

\textbf{Project memory} shows the book, requirements, protobuf schema,
implementation mapping and source summary, each marked absent, bootstrap or
current, with cards saying whether the requirements and mapping pass their check
and are committed. A file's presence proves nothing about its content.

\UITourFigure{06-project-memory}
  {Project memory makes the durable files and their check status inspectable.}
  {The Project memory pane shows canonical artifact tabs and source inventory. Requirements and Implementation specification each show whether they pass the canonical check and whether they are committed.}
  {Capture boundary: both checked specification revisions loaded.}

Review the requirements first (messages, outcomes, errors, boundaries, views),
then the implementation mapping and how its runtime, files, transports, bounds,
security controls and tests realize them. Commit what says what you mean; say so
in Chat when it does not. You can ask for the implementation at any time, and
LeanFM writes and checks whatever specification it needs first. The committed
artifacts and source are the inputs, so deleting conversation history loses no
design.

\UITourFigure{09-source}
  {Source displays the implementation files actually present in the project.}
  {The real Source pane lists GoServer source and test files and displays the selected file. This is an inspectable source inventory.}
  {Capture boundary: the implementation's actual source tree opened.}

\textbf{Source} is for inspection; ask Chat for edits. A successful startup shows
the app starts and answers its probes, not that every rule or security property
holds.

\section{Start, open, and stop the app}

\textbf{Start app} runs the project through its fixed application contract, waits
for readiness and a page response, and keeps the process running; the bar shows
\textbf{running}, and \textbf{Open app} becomes a link, also posted in Chat. No
model request is involved.

\UITourFigure{10-app-ready}
  {A verified running instance produces Open app in both the bar and Chat.}
  {The actual project workspace shows App running with Start app and Stop app controls and a served Open app link. A native runtime chat message also provides a clickable Open app link.}
  {Capture boundary: ApplicationReady after real startup and page probes. The link names the served preview, not a private loopback endpoint.}

The preview runs inside its own filesystem, process, network and browser-authority
boundary; from a remote browser, use the link rather than guessing a port. Apps
need relative or prefix-compatible URLs, and an incompatible app is reported
rather than given a broken link.

\UITourFigure{11-app-preview}
  {The running GoServer preview supports real room and challenge operations.}
  {The actual isolated GoServer browser shows a created room and a named challenge. Separate room and challenge conversation areas include a message delivered through the preview API.}
  {Capture boundary: RoomCreated, GameCreated, and GameChat observed through the real preview route. The app remains a local in-memory inspection slice.}

Changed source makes the runtime \textbf{stale}; \textbf{Restart app} runs the new
revision, and Start on a current one reuses it. \textbf{Stop app} ends only this
project's instance. Every HTTP application exposes the same targets in
\texttt{source/}:
\begin{center}
\begin{tabular}{ll}
\toprule
Target & Purpose \\
\midrule
\texttt{make build} & Build the application. \\
\texttt{make run} & Run in the foreground for supervision. \\
\texttt{make serve} & Alias for \texttt{run}. \\
\texttt{make stop} & Stop only this project's owned app. \\
\texttt{make test} & Execute the application's tests. \\
\texttt{make check} & Run its proportional verification. \\
\texttt{make clean} & Remove its disposable build outputs. \\
\bottomrule
\end{tabular}
\end{center}
Missing targets, invalid profiles, capacity limits and failed readiness give
explicit errors, and an occupied port is never freed by stopping someone else's
listener.

\section{Reproduce and review the screenshots}

\texttt{make ui-snapshots} regenerates the tour from the production bundle, a
disposable project replica, an isolated network and a deterministic provider,
driving named controls by keyboard and recording focus, accessible roles, message
IDs, viewport, browser version, digests and capture boundary. Regenerating needs
the GoServer example; building the book does not. Each image has
\texttt{.accessibility.json} and \texttt{.keyboard.json} companions, bound to
their revisions by \path{book/assets/ui-tour/manifest.json}, and the book build
rejects missing, altered or stale captures. Alternative text in both PDF editions
describes each control state.
