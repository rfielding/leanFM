\chapter{The Scenario Authoring Language}
\label{ch:authoring-language}

\index{scenario}
\index{observable event}
\textbf{Proposed notation:} this chapter develops a surface language from ordinary
Lean \texttt{def}, parameters, \texttt{let}, typed values and \texttt{do} notation,
with library operations for scenarios, endpoints, choices, probability and
rendering; names may change. The worked MDP is a \textbf{finite-model check}, and
its figures are \textbf{generated analyses}.

\section{Proposed scenario notation}

\index{alphabet!vague}
A scenario is a named fragment of a global type: a grammar whose terminals are
observable messages, each with a sender and a receiver. \texttt{from\_} and
\texttt{to\_} (avoiding Lean's \texttt{from}) set the endpoints copied into each
event, and an \texttt{emit} without both is invalid. \texttt{let x := e} evaluates
a Lean expression; \texttt{let x <- declare T "x"} introduces an immutable typed
symbolic value bound by generation or matching. Reusing a binding expresses
identity, and receiving an event binds its fields for later messages.
\texttt{emit} and \texttt{receive} are the same kind of terminal, differing only
in projection.

\begin{lstlisting}
def requestQuote (customer shop : Actor) : Scenario :=
  scenario "request a quote" do
    let requestId <- declare RequestId "requestId"
    let quoteId <- declare QuoteId "quoteId"
    let amount <- declare Money "amount"
    from_ customer; to_ shop
    emit "quote requested" [field "requestId" requestId]
    from_ shop; to_ customer
    emit "quote offered"
      [field "requestId" requestId, field "quoteId" quoteId,
       field "amount" amount]
\end{lstlisting}

Early requirements can use semantic message names and typed fields without a
protobuf schema; that suffices for ordering, correlation and temporal properties.
A later refinement maps the fields to a concrete alphabet, with the obligation of
language inclusion once representation details are erased: serialization, retries
and internal state may be chosen there, but no visible behavior the abstract
grammar forbids.

Named inclusions are reusable productions, not textual copies; they can export
values for later events, and a compiler resolves references, checks exports and
rejects cycles. A quote outcome, for example, chooses between named accepted and
declined branches, each renderable on its own (diagram contract:
Chapter~\ref{ch:scenarios}; generated examples: Chapter~\ref{ch:grammar}).

\index{probability}
\texttt{oneOf} states nondeterminism without frequencies; \texttt{weightedOneOf}
supplies a distribution when one is supported. The first distinguishing terminal
decides who chooses (Chapter~\ref{ch:grammar}), and deterministic service
transitions carry probability mass forward. Requirements may start with unresolved
choices or symbolic weights; refinement resolves them and keeps every abstractly
legal branch, even one the implementation gives probability zero.

\section{Actor specifications and instances}

An actor name in a grammar denotes a reusable specification, not necessarily one
process. A finite population gives that specification concrete identities:

\begin{lstlisting}
actor Client
  |>.instances "client-" 20 (sticky "session")

actor Server
  |>.instances "server-" 2 (shardHash "tenant_id")
\end{lstlisting}

Generated scenarios resolve roles to instances such as \texttt{client-7}, each
inheriting its actor's behavior and resource bounds and the queue and in-flight
\texttt{(session,task)} semantics of Chapter~\ref{ch:grammar}. A population is
homogeneous: a cluster cannot mix gateways and databases because they share a
deployment. Routing is declared: \texttt{sticky} keeps an observable affinity
field on one member, \texttt{roundRobin} cycles in order, and \texttt{shardHash}
hashes an observable key (as Kafka and DynamoDB partition keys do, each with more
semantics of its own). Routing changes per-instance histories, queue pressure,
hot spots, failure impact and replay; finite populations keep every check
bounded.

\section{Non-functional requirements: rates and scalability}

With the boundary events of Chapter~\ref{ch:events}, suppose every client
repeatedly creates a fresh server task, each completed unit recording a start, a
terminal that points back to it, and a nonnegative amount of work (here, bytes
moved; timestamps in milliseconds).

\emph{Load} is too ambiguous to be a variable. Let $N$ be the study's upper
limit on active clients and $n$, with $1\leq n\leq N$, the active-client
population of one observation. Separately, $\lambda_o$ is work offered per unit
time, $\lambda_a$ work admitted, and $X$ work completed: three different
observable boundaries. The client-experienced rate weights long requests by their
duration:

\AccessibleEquation{Client throughput at active-client population n equals the sum of work over requests i divided by the sum of each request end time minus its start time.}{\[
 X_{\mathrm{client}}(n)=
 \frac{\sum_i \mathrm{work}_i}
      {\sum_i(e_i.timeAt-s_i.timeAt)}.
\]}

The aggregate server rate counts overlapping waits once:

\AccessibleEquation{Server throughput at active-client population n equals the sum of work over requests i divided by the latest end time minus the earliest start time.}{\[
 X_{\mathrm{server}}(n)=
 \frac{\sum_i \mathrm{work}_i}
      {\max_i(e_i.timeAt)-\min_i(s_i.timeAt)}.
\]}

Over a window of duration $T$, the boundary rates and backlog obey

\AccessibleEquation{Offered rate lambda sub o equals offered work W sub o divided by duration T. Admitted rate lambda sub a equals admitted work W sub a divided by T. Completed throughput X equals completed work W sub c divided by T. Ending backlog B one equals starting backlog B zero plus admitted work minus completed work.}{\[
 \lambda_o=\frac{W_o}{T},\qquad
 \lambda_a=\frac{W_a}{T},\qquad
 X=\frac{W_c}{T},\qquad
 B_1=B_0+W_a-W_c.
\]}

The backlog identity assumes a conserved work unit, so cancellations, expiry and
failures are recorded as terminal dispositions. If $\lambda_o>X$, offered work is
rejected, queued, in flight, or otherwise disposed of. The Universal Scalability
Law is fitted against the active-client population, not $\lambda_o$, unless the
experiment defines a mapping:

\AccessibleEquation{Throughput X at load n equals gamma times n divided by one plus alpha times n minus one plus beta times n times n minus one. n is between one and upper limit N inclusive.}{\[
 X(n)=\frac{\gamma n}{1+\alpha(n-1)+\beta n(n-1)},
 \qquad 1\leq n\leq N.
\]}

Gunther develops the USL as a capacity-planning tool that exposes contention,
coherency, saturation and retrograde scaling before deployment
does~\citep{gunther2007guerrilla}. Each observation records $n$, the chosen
throughput and boundary, $\lambda_o$, $\lambda_a$, $X$, latency, backlog,
terminal outcomes, server count and window; parameters are fitted only on
exhaustive windows, so omitted or unfinished work cannot bias them.

\subsection{The three USL regimes and capacity}

$\gamma$ is the single-client service rate, analogous to a clock speed: it scales
the curve vertically without moving its peak. The overhead parameters act
differently:

\AccessibleEquation{If alpha and beta are zero then X of n equals gamma n: ideal linear scaling. If beta is zero then X of n equals gamma n divided by one plus alpha times n minus one: contention-limited saturation. If beta is positive then X of n equals gamma n divided by one plus alpha times n minus one plus beta times n times n minus one: coherency-limited retrograde scaling.}{\begin{align*}
 \alpha=0,\ \beta=0 &: \quad X(n)=\gamma n,
   &&\text{ideal linear scaling},\\
 \beta=0 &: \quad X(n)=\frac{\gamma n}{1+\alpha(n-1)},
   &&\text{contention-limited saturation},\\
 \beta>0 &: \quad X(n)=
   \frac{\gamma n}{1+\alpha(n-1)+\beta n(n-1)},
   &&\text{coherency-limited retrograde scaling}.
\end{align*}}

For $0\leq\alpha<1$ and $\beta>0$ the curve peaks at

\AccessibleEquation{Peak load n star equals the square root of one minus alpha divided by beta.}{\[
 n_* = \sqrt{\frac{1-\alpha}{\beta}}.
\]}

which need not equal $N$; the integer capacity is whichever adjacent population
has the larger throughput. With $\beta=0$ the curve approaches $\gamma/\alpha$
without a peak, and with both zero the model has no limit, so a real system must
eventually show a bottleneck the model omits. Figure~\ref{fig:usl-regimes} uses
$\alpha=0.1$ and, in its third panel, $\beta=0.005$, with $n_*\simeq13.42$.

Population is not the only overload boundary. For a fixed deployment with
sustainable service rate $\mu$, offered load $\lambda$ is at capacity when
$\lambda=\mu$. Below it, a simple queue has response time proportional to
$1/(\mu-\lambda)$ and work in the system proportional to
$\lambda/(\mu-\lambda)$; at and above it these are unbounded: throughput is
capped at $\mu$ while unfinished work, latency, queued bytes and memory pressure
grow. A finite queue turns that growth into blocking or rejection, and exhausting
the memory budget is a fatal terminal event, not another slow sample. Menasc\'e,
Almeida and Dowdy give the queueing foundation~\citep{menasce2004performance}.
USL summarizes scaling across populations; queueing explains how work waits for
finite service. Neither rescues a model whose demand, service rates, queue
bounds, window and overload behavior were never stated.

The queues are the finite blocking queues of Chapter~\ref{ch:grammar}. A queue
also has an idempotent \texttt{close()}: it forbids later pushes, wakes a blocked
sender with a closed rejection, and lets values accepted before it drain exactly
once in order. Receivers report closed only after draining, so iteration ends when
the queue is closed \emph{and} empty; empty while open means ``wait''.

\paragraph{Current costs (not optimized).} With $C$ queued items the list-backed
channel sends in $O(C)$ and receives in $O(1)$, and does not yet implement
\texttt{close}; a ring buffer would make both amortized $O(1)$. With $H$ task
events and $R$ predecessor references, the attempt reducer costs $O(H^2)$; an
indexed successor map and open-attempt table target expected $O(H+R)$. Validation
of $N$ declarations is $O(N^2)$, grammar traversal $O(G)$ but $O(G^2)$ on skewed
trees, and enumerating every path is exponential only when all paths are
materialized. The initial ChatUI profile gives browser and session actors queue
capacities 32 with 4 in flight and 64~MiB, the server 256, 32 and 512~MiB, and
provider workers 64, 16 and 256~MiB: replaceable starting values, not
measurements.

\section{Outages, recovery, and replica populations}

Reliability assumptions belong to actor specifications and are inherited by
instances. A contract may set an outage probability and a mean time to repair:

\begin{lstlisting}
actor Server
  |>.instances "server-" 2 (roundRobin)
  |>.outageProbability (20 / 10000)
  |>.meanTimeToRepair 45.seconds
\end{lstlisting}

A failed actor does not announce its failure; there is no \texttt{Unavailable}
message to receive. Failure is inferred by an observer: heartbeats stop, an inbound
queue stops draining, or expected outbound messages stop appearing. Each detector
declares its expectation, timeout, clock, observer and attribution boundary;
silence without an expectation is not evidence. A detector may emit
\texttt{AvailabilityLost} and \texttt{AvailabilityRestored}, which are observer
conclusions, not protocol messages. A loss keeps the last healthy time, the missed
deadline, the detection time and the evidence; a restoration keeps the progress
that justifies it and points back to the loss. The true failure time lies between
the last healthy observation and detection. With declared boundary times $u_i$ and
$r_i$, for $R$ replicas observed from $t_0$ to $t_1$:

\AccessibleEquation{Estimated outage fraction O hat equals the sum of each recovery time minus its unavailability time divided by replica count R times observation duration t one minus t zero. Estimated mean time to recovery equals that same outage-duration sum divided by the number of incidents.}{\[
 \widehat O=
 \frac{\sum_i (r_i.timeAt-u_i.timeAt)}{R(t_1-t_0)},
 \qquad
 \widehat{MTTR}=
 \frac{\sum_i (r_i.timeAt-u_i.timeAt)}{\lvert incidents\rvert}.
\]}

Availability over the window is $1-\widehat O$. Reports name which boundary each
$u_i$ uses (last healthy, missed deadline, or detection), since it changes both
estimates. In Kubernetes-style experiments pods may be instances and restarts
recoveries, compared with, not substituted for, the configured values.

\noindent\textbf{Actor topology for a targeted document write.}
Generated from \texttt{RuntimeReliabilityDiagram.lean}, with provenance in
\texttt{runtime-actor-network-provenance.txt}. Arrows denote required provider

\begin{description}
  \item[Request path.] A write needs ingress, web, router and its shard; required
    series stages multiply their availabilities, so adding one cannot help.
    Kubernetes restarts actors but does not supply quorum or consistency.
  \item[Replica pools.] Proxy and web actors are parallel alternatives within a
    stage; each shard has its own replica gate. Shared failure domains and higher
    quorum thresholds can erase the benefit, and shards are partitions, not
    failover copies.
  \item[Stateless pool.] With no ready instance, new requests fail; otherwise
    overload can cause rejection, queue growth or missed deadlines while heartbeats
    continue. Round-robin counts need not balance unequal work.
  \item[Replicated shard.] Majority writes need a primary and a communicating
    quorum; one observer's heartbeats do not prove mutual reachability, and a
    restarted member is not ready until it catches up.
  \item[Reads and shared dependencies.] Read consistency is declared separately:
    a lost write quorum may still allow stale local reads. Ingress or routing
    failure can affect every shard; metadata failure depends on the operation and
    cached routing.
  \item[Sharding.] More partitions add capacity when work spreads well; hot keys,
    shared dependencies and cross-shard operations limit the gain.
\end{description}

Availability is per operation, computed from detector indicators
$u_i(t)\in\{0,1\}$ through each operation's gates. A series gate needs every
member:

\AccessibleEquation{Series availability at time t equals the product over components i of component availability u sub i at time t.}{\[
 u_{\mathrm{series}}(t)=\prod_i u_i(t).
\]}

a parallel gate at least one:

\AccessibleEquation{Parallel availability at time t equals one minus the product over components i of one minus component availability u sub i at time t.}{\[
 u_{\mathrm{parallel}}(t)=1-\prod_i(1-u_i(t)).
\]}

and a threshold gate $k$ of them, $\sum_i u_i(t)\geq k$. Measured availability is
the fraction of the window in which the gate holds. Working on synchronized
indicators keeps simultaneous and correlated failures; products of marginal
availabilities such as $\prod_i A_i$ assume independence and must not replace the
interval calculation when joint observations exist.

A dependency edge points from a consumer to the provider gate it requires. At each
outage boundary, propagation marks a consumer unavailable when a series
requirement is down or a parallel or threshold requirement has too few providers.
The fixed point for an initiating failure set $F$ is $C(F)$, its structural blast
radius. Reports keep the propagation paths, affected shards, request classes,
tenants, tasks, client-visible outcomes and recovery order; a degraded read path
and an unavailable write path are different outcomes. ``What if the database and
one authorization replica fail together?'' becomes answerable without assuming
independence, and minimal cut sets name the smallest sets that disable each
operation. Unobserved named scenarios stay replayable, labeled as predictions.

\paragraph{Calculate impact before estimating its frequency.} Uptime and MTTR
estimates help assign probabilities and durations to scenarios, but the dependency
graph decides which operations are exposed. If scenarios $F_j$ partition a declared
snapshot model with probabilities $\pi_j$, the expected number of unavailable
operations is
\AccessibleEquation{Expected blast-radius count B equals the sum over failure scenarios j of scenario probability pi sub j times the cardinality of the failure closure of F sub j.}{\[
 \mathbb{E}[B]=\sum_j \pi_j\,\lvert C(F_j)\rvert.
\]}
(or a declared demand or business-impact weighting); overlapping scenarios cannot
be added as if disjoint. With $C(t)$ the unavailable set at time $t$ and
$\lambda_o(t)$ the offered rate of operation $o$, the offered-request exposure is
\AccessibleEquation{Lost work L equals the integral from t zero to t one of the sum over affected operations o in the failure closure at time t of offered rate lambda sub o at time t with respect to t.}{\[
 L=\int_{t_0}^{t_1}\sum_{o\in C(t)}\lambda_o(t)\,dt.
\]}
This counts exposed requests, not necessarily lost work: queues, retries and
deadlines decide which ultimately fail or complete late.

\paragraph{Repair the operation, not just the process.} Actor MTTR is not service
MTTR. Recovery may include detection, rescheduling, volume attachment, election,
catch-up, routing refresh and draining the backlog, stages that overlap and are
composed by their event dependencies rather than added. Recovery ends at restored
readiness or the declared latency target, not the first heartbeat; incidents still
open at the window's end are censored, not zero-length. Forecasts need a declared
failure and repair process, correlated domains, placement, workload and recovery
policy, kept separate from observations. This is an analysis contract, not a
claim that a forecast engine is implemented.

The PaxosKV project's view \texttt{renders/quorum-shutdown-network.svg} is a
concrete case: a one-of-three pool of stateless web actors (each up
$9999/10000$) in series with a two-of-three database quorum (each replica up
$999/1000$). If replica outages were independent with uptime $p$, the quorum
would be up
\AccessibleEquation{Two-of-three availability equals three times p squared times one minus p plus p cubed.}{\[
 A_{2\text{-of-}3}=3p^2(1-p)+p^3.
\]}
That baseline excludes correlated shutdowns. Stopping \texttt{kv-1} and then
\texttt{kv-2} leaves \texttt{kv-3} below quorum and makes the web service
unavailable however many web instances run, which only accumulate waiting
requests. Planned shutdowns, shared power, partitions and common automation belong
in named joint scenarios.

Work waiting on an unavailable instance stalls, is rejected, or ends in an
explicit timeout or cancellation, as the requirement says. A send or receive
attributed to that instance after a detected loss is evidence of recovery or of a
wrong detector, never silently discarded. An outage commonly falsifies a nominal
liveness promise (``every accepted request eventually receives a response'') while
safety holds, so the nominal language is distinguished from its failure extension,
which adds heartbeat expectations, progress observations, availability boundaries,
stalled or censored work, failure outcomes and legal retries. Cascade analysis
suppresses progress for every instance unavailable at the fixed point and reports
which properties remain true, become false, or are undecided when the window
closes.

The same graph supports denial-of-service analysis. A PageRank-like centrality,
with edges pointing toward the consumers they enable and weights from traffic,
task value or cascade frequency (the weighting is part of the requirement),
highlights nodes whose failure influence is reinforced by other important
services. Centrality is a heuristic: it can miss a low-traffic series dependency,
a cut vertex, or the replica count that crosses a quorum threshold. A
denial-of-service report therefore sets it beside single-node and named multi-node
cascades, minimal cut sets, lost capacity and client-visible outcomes, answering
``what actually stops if an attacker takes this set down?''. Today only a
checklist item and a \texttt{Characterization.lean} plan exist.

\section{Infrastructure cost and demand-constrained supply}

Hardware accrues per provisioned hour; licenses, managed services and operations
may cost per available hour. Neither is a per-request cost:

\begin{lstlisting}
cost Server
  |>.hardwarePool "general-purpose"
  |>.hardwareCostPerProvisionedHour 12 USD.cent
  |>.serviceCostPerAvailableHour 3 USD.cent
  |>.sustainableCapacityPerHour 3600000 bytes
\end{lstlisting}

For $R$ replicas with provisioned hours $H_r$, available hours $A_r$, hardware
rate $c_h$ and service rate $c_s$:

\AccessibleEquation{Cost at replica count R equals the sum from replica r equals one through R of provisioned hours H sub r times hardware cost c sub h plus available hours A sub r times service cost per hour c sub s.}{\[
 C(R)=\sum_{r=1}^{R}(H_r c_h + A_r c_s).
\]}

Supply planning is constrained optimization. With per-replica capacity $\mu$,
required availability $a$ and demand $D$ within the latency boundary, a necessary
condition is

\AccessibleEquation{Replica count R times per-replica completed-work capacity mu times availability a must be greater than or equal to demand D.}{\[
R\mu a \ge D.
\]}

and routing imbalance, queues or latency can still make it infeasible. The
offered rate splits across replicas, evenly only under ideal balance:

\AccessibleEquation{Total offered rate lambda sub o equals the sum from replica r equals one through R of per-replica offered rate lambda sub o comma r. Per-replica offered rate equals total offered rate divided by R only under ideal balance.}{\[
 \lambda_o=\sum_{r=1}^{R}\lambda_{o,r},
 \qquad
 \lambda_{o,r}=\frac{\lambda_o}{R}\ \text{only under ideal balance}.
\]}

\textbf{Executable code and finite-model tests:} \texttt{optimalSupply?} in
\texttt{LeanFM/Artifacts.lean} searches replica counts up to
\texttt{maxReplicas}, rejects availability-adjusted capacity below demand, and
picks the least expected hourly cost; \texttt{LeanFM/ArtifactsTests.lean} checks a
feasible optimum and an infeasible demand. It does not model routing imbalance,
latency or windows, so the full supply-planning plot remains a target. Shard
hashing can create a hot shard despite spare capacity, and replication, reserved
pricing, autoscaling delay and pricing tiers need explicit constraints. Only demand
completed within the declared outcome and latency boundary counts.

\section{Specified dwell time}

A \texttt{dwell} constrains modeled duration for a step or named production;
observed event-pair durations are defined in Chapter \ref{ch:events}:

\begin{lstlisting}
emit "token requested" [field "code" code]
  |>.dwell 3.milliseconds

include exchangeAndFetch
  |>.dwell 12.milliseconds
\end{lstlisting}

Step dwell $d$ advances the model clock by $d$ before timestamping the completion
event; production dwell constrains entry-to-exit time, not each contained event.
Values may be exact, ranges or weighted outcomes. Dwell drives modeled latency,
throughput, timeout and queue-pressure predictions, but never event order, which
comes from \texttt{priorIds} and the grammar.

\section{Composing requirements means intersecting constraints}

\index{composition!requirement intersection}
Scenarios compose with the grammar's operations (Chapter~\ref{ch:grammar}).
Requirements add a different one: \texttt{requireAll} intersects the generated
trace language with independent constraints instead of adding messages.

\begin{lstlisting}
def quoteSystem : SystemSpec :=
  generatedBy quoteOutcome
  |> requireAll
      [ correlate "offered quote matches request"
          (sameField "requestId")
      , forbid "confirmation without acceptance"
          (event "order confirmed" && notPreviously "quote accepted")
      , ctl "every accepted quote is answered"
          (AG (accepted --> AF (confirmed || rejected)))
      , timing "answer within service objective"
          (accepted --> within 2.seconds (confirmed || rejected))
      ]
\end{lstlisting}

The requirements are consistent when the intersection is nonempty; otherwise
tooling should report a minimal conflicting set and the shortest counterexample
prefix.
