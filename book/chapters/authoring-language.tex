\chapter{The Scenario Authoring Language}
\label{ch:authoring-language}

\index{scenario}
\index{observable event}
This chapter proposes the first concrete surface language. It is intentionally a
small Lean DSL: ordinary \texttt{def}, function parameters, \texttt{let}, typed
values, and \texttt{do} notation provide the host language; a fixed library adds
scenario, endpoint, choice, probability, and rendering operations. The examples
are a design target. Names may change as the Lean implementation makes their
semantics precise.

\section{The smallest useful scenario}

A scenario is a named grammar fragment. Every emitted terminal is an observable
message event. Endpoint commands establish the \texttt{from} and \texttt{to}
context for the messages that follow.

\begin{lstlisting}
def requestQuote (customer shop : Actor) : Scenario :=
  scenario "request a quote" do
    let requestId <- declare RequestId "requestId"

    from_ customer
    to_ shop
    emit "quote requested" [field "requestId" requestId]

    let quoteId <- declare QuoteId "quoteId"
    let amount  <- declare Money "amount"

    from_ shop
    to_ customer
    emit "quote offered"
      [ field "requestId" requestId
      , field "quoteId" quoteId
      , field "amount" amount
      ]
\end{lstlisting}

The spelling \texttt{from\_} avoids collision with Lean syntax while remaining
visually explicit. Endpoint commands affect authoring context only; elaboration
copies both endpoints into every event. A scenario with an \texttt{emit} before
both endpoints have been established is rejected.

\subsection{Variables and assignment}

There are two kinds of assignment.

\begin{itemize}
  \item Ordinary \texttt{let x := expression} evaluates a known Lean expression.
  \item \texttt{let x <- declare T "x"} introduces a symbolic value of type
        \texttt{T}. The grammar binds it when generating or matching a trace, and
        later events may reuse it.
\end{itemize}

Variables are immutable. A later \texttt{let attempt := attempt + 1} creates a new
binding rather than mutable hidden state. Information flow is consequently visible
in the grammar's data dependencies. Equality of two occurrences of
\texttt{requestId} means they carry the same value, not merely values with the same
field name.

A value received from the environment is bound by matching an observable event:

\begin{lstlisting}
from_ customer
to_ shop
receive "quote accepted" do
  let quoteId <- take QuoteId "quoteId"
  let payment <- take PaymentToken "paymentToken"

from_ shop
to_ bank
emit "payment authorization requested"
  [field "quoteId" quoteId, field "paymentToken" payment]
\end{lstlisting}

\texttt{receive} and \texttt{emit} both denote grammar terminals; they differ only
in the viewpoint used when projecting a global scenario to executable participant
code.

\section{Vague messages first, typed alphabets later}

\index{alphabet!vague}
Early requirements should not require a finished protobuf schema. A vague message
has a stable semantic name and a list of named, typed fields. It is already precise
enough to express ordering, correlation, and temporal properties.

\begin{lstlisting}
emit "quote offered"
  [field "requestId" requestId, field "amount" amount]
\end{lstlisting}

Later, a refinement maps that terminal to a concrete alphabet:

\begin{lstlisting}
refineMessage "quote offered" with Proto.Shop.QuoteOffered where
  request_id := field "requestId"
  quote_id   := field "quoteId"
  cents      := encodeMoney (field "amount")
\end{lstlisting}

The refinement obligation is language inclusion: every concrete implementation
trace, after erasing representation details, must be admitted by the abstract
grammar. Refinement may decide serialization, retry mechanics, and internal state;
it must not invent externally visible behaviour forbidden by the requirements.

\section{One concern per scenario}

Scenarios should be small enough to read as stories and independent enough to
render separately. The quote protocol can be decomposed as follows.

\begin{lstlisting}
def quoteAccepted (customer shop : Actor) : Scenario :=
  scenario "quote accepted" do
    include (requestQuote customer shop)
    -- bind quoteId from the included scenario's exports
    use quoteId <- exported QuoteId "quoteId"
    from_ customer; to_ shop
    emit "quote accepted" [field "quoteId" quoteId]

def quoteDeclined (customer shop : Actor) : Scenario :=
  scenario "quote declined" do
    include (requestQuote customer shop)
    use quoteId <- exported QuoteId "quoteId"
    from_ customer; to_ shop
    emit "quote declined" [field "quoteId" quoteId]

def quoteOutcome (customer shop : Actor) : Scenario :=
  oneOf "customer decision"
    [ quoteAccepted customer shop
    , quoteDeclined customer shop
    ]
\end{lstlisting}

\texttt{include} is textual only in the rendered book view; semantically it is a
reference to a named nonterminal. The compiler reads all referenced scenarios,
checks exported bindings, detects cycles, and builds one grammar. Tools retain the
scenario boundary for navigation, diagrams, tests, and counterexamples.

\section{Choices and unresolved probability}

\index{probability}
Nondeterminism and probability are different. \texttt{oneOf} says that multiple
behaviours are legal without claiming how often they occur. \texttt{weighted}
attaches a distribution when the abstraction has one.

\begin{lstlisting}
def paymentOutcome : Scenario :=
  oneOf "payment outcome" [paymentApproved, paymentRejected]

def estimatedCustomerDecision : Scenario :=
  weightedOneOf "customer decision"
    [ weighted (95 / 100) customerSubmitsPayment
    , weighted ( 5 / 100) customerAbandonsPayment
    ]
\end{lstlisting}

There is no separate \texttt{choose customer} annotation. The branch is resolved
when its distinguishing terminal becomes bytes: the terminal names its source,
so the trace already shows that the customer emitted the event that selected the
branch. Probabilities belong to branches, not to an extra, potentially conflicting
claim about a chooser. A deterministic service that consumes probabilistic user
input remains part of the induced probabilistic system: its probability-one
transitions carry the incoming path mass forward. An early requirement can use
\texttt{oneOf}, a symbolic weight, or a range such as \texttt{between 0.90 0.99}.
Implementation refinement resolves those claims to a well-defined stochastic
model or to deterministic conditions. Refinement must preserve possibility even
when a current implementation assigns probability zero to a legal abstract branch;
otherwise changing operational policy would silently change the contract.

Two branches may share a prefix. In that case the choice remains unresolved
through the common terminals and resolves only at the first different byte-level
terminal. Branches whose complete terminal byte languages overlap are
observationally ambiguous at that point; the requirement must merge them or add
an observable discriminator if downstream actors need to distinguish them.

\section{Actor specifications and instances}

An actor name in a grammar denotes a reusable specification, not necessarily one
process. A finite population gives that specification concrete identities:

\begin{lstlisting}
actor Client
  |>.instances "client-" 20 (sticky "session")

actor Server
  |>.instances "server-" 2 (shardHash "tenant_id")
\end{lstlisting}

The grammar may say \texttt{Client -> Server}; a generated scenario resolves
those roles to instances such as \texttt{client-7 -> server-2}. Each instance
has its own inbound and outbound queues and its own set of in-flight
\texttt{(session,task)} pairs, while inheriting behavior and resource bounds from
the actor specification. A population is a homogeneous service cluster: every
member must implement that one actor specification. A cluster cannot quietly mix
gateways, databases, and workers merely because they share a deployment boundary.

The cluster also declares how a message selects an instance. \texttt{sticky}
keeps the value of an observable affinity field on the same member;
\texttt{roundRobin} cycles through members in a declared order; and
\texttt{shardHash} hashes an observable shard-key field. This decision changes
the legal per-instance histories and therefore queue pressure, hot spots,
failure impact, and replay. Kafka partition keys, MongoDB shard keys, and
DynamoDB partition keys motivate the shard-hash abstraction, although each
real system adds product-specific replication and routing semantics beyond this
small model. Population size is finite and explicit so queue,
memory, probability, and temporal checks still have a bounded state space.

\section{Non-functional requirements: rates and scalability}

Timing requirements are stated over boundary messages rather than intervals
hidden inside an event. Suppose every client repeatedly creates a fresh server
task. Each completed unit records a start message, an end message that
backpoints to that start, and a nonnegative amount of work. If one moved byte is
one work unit and timestamps are milliseconds, an exhaustive observation list
supports two different rates.

The word \emph{load} is too ambiguous to serve as a variable. Let $N$ be the
declared upper limit on the number of active clients in the study, and let the
parameter $n$ be the active-client population for one observation, with
$1\leq n\leq N$. Separately, let $\lambda_o$ be offered work per unit time,
$\lambda_a$ be work admitted per unit time, and $X$ be work completed per unit
time. Offering work, accepting it into a queue, and completing it are three
different observable boundaries. The client-experienced, properly weighted
rate is

\[
 X_{\mathrm{client}}(n)=
 \frac{\sum_i \mathrm{work}_i}
      {\sum_i(e_i.timeAt-s_i.timeAt)}.
\]

Read this as: ``client throughput at active-client population $n$ equals the sum, over requests
$i$, of work for request $i$, divided by the sum of end time $e_i.timeAt$
minus start time $s_i.timeAt$ for that request.'' Lowercase $n$ is the varying
client population; uppercase $N$ is only its declared upper limit.

This is the duration-weighted mean of the individual observed rates. Long
requests therefore contribute in proportion to how long a client experienced
them. It is not the unweighted mean of per-request ratios.

The aggregate server throughput is instead

\[
 X_{\mathrm{server}}(n)=
 \frac{\sum_i \mathrm{work}_i}
      {\max_i(e_i.timeAt)-\min_i(s_i.timeAt)}.
\]

Read this as: ``server throughput at active-client population $n$ equals total completed work over requests
$i$, divided by the latest request-end time minus the earliest request-start
time.''  The maximum and minimum make the denominator one wall-clock window.

For an observation window of duration $T$, the boundary rates and backlog obey

\[
 \lambda_o=\frac{W_o}{T},\qquad
 \lambda_a=\frac{W_a}{T},\qquad
 X=\frac{W_c}{T},\qquad
 B_1=B_0+W_a-W_c.
\]

Read this as: ``offered rate lambda sub $o$ is offered work $W_o$ divided by
window duration $T$; admitted rate lambda sub $a$ is admitted work $W_a$
divided by $T$; completed throughput $X$ is completed work $W_c$ divided by
$T$; and ending backlog $B_1$ is starting backlog $B_0$ plus admitted work
minus completed work.'' The backlog identity assumes one conserved work unit
and requires cancellations, expiry, and failures to be recorded as explicit
terminal dispositions when they remove work.

Consequently, $\lambda_o>X$ does not mean that the system handled the offered
load. The difference is rejected, remains queued or in flight, or receives
another explicit terminal disposition. Nor does $\lambda_a$ measure handled
work: an implementation can admit requests faster than it completes them while
latency and backlog grow without bound.

Its denominator is one wall-clock observation window, so overlapping client
waits are counted once. The two quantities answer different questions and must
not share a metric name. Plotting either explicitly chosen rate against the
number of active client instances yields observations that can be fitted to the
Universal Scalability Law,

\[
 X(n)=\frac{\gamma n}{1+\alpha(n-1)+\beta n(n-1)},
 \qquad 1\leq n\leq N.
\]

Read this as: ``completed throughput $X$ at active-client population $n$ equals gamma times $n$, divided by
one plus alpha times $n-1$ plus beta times $n$ times $n-1$; $n$ ranges from one
through the upper limit $N$.'' This curve uses population or concurrency as its
independent variable. It is not, without an explicit experimental mapping, a
curve whose horizontal axis is offered work rate $\lambda_o$.

Gunther's \emph{Guerrilla Capacity Planning} gives the practical capacity-planning
setting for this law and develops it as the Universal Law of Computational
Scaling~\citep{gunther2007guerrilla}. The point is operational, not decorative:
a requirements argument should expose contention, coherency, saturation, and
retrograde scaling before the first production deployment supplies those facts
by falling over.

Every USL observation must therefore retain $n$, $\lambda_o$, $\lambda_a$,
$X$, latency, backlog, rejection or other terminal outcomes, server population,
and observation-window boundaries. The event list supplies the observations;
estimating $\gamma$, $\alpha$, and
$\beta$ is a separate statistical step. The list must be exhaustive for the
declared observation window, or omitted work and unfinished tasks bias both
rates.

\subsection{The three USL regimes and capacity}

The scale parameter $\gamma$ is analogous to clock speed: it is the
single-client service-rate scale and multiplies the entire curve vertically.
It is not literally a processor clock, because an observed unit of work may
include networks, storage, and several actors. Changing $\gamma$ does not move
the population at which the dimensionless USL curve peaks.

The two overhead parameters have distinct effects:

\begin{align*}
 \alpha=0,\ \beta=0 &: \quad X(n)=\gamma n,
   &&\text{ideal linear scaling},\\
 \beta=0 &: \quad X(n)=\frac{\gamma n}{1+\alpha(n-1)},
   &&\text{contention-limited saturation},\\
 \beta>0 &: \quad X(n)=
   \frac{\gamma n}{1+\alpha(n-1)+\beta n(n-1)},
   &&\text{coherency-limited retrograde scaling}.
\end{align*}

Read the three lines as follows.  When alpha and beta are both zero,
throughput at load $n$ is gamma times $n$.  When beta is zero, throughput is
gamma times $n$ divided by one plus alpha times $n-1$.  When beta is positive,
the denominator additionally contains beta times $n$ times $n-1$.

For $0\leq\alpha<1$ and $\beta>0$, differentiation gives the finite capacity
population

\[
 n_* = \sqrt{\frac{1-\alpha}{\beta}}.
\]

Read this as: ``the peak load $n$ star equals the square root of one minus
alpha, divided by beta.''  This fitted peak is a load value and need not equal
the study limit $N$.

The observed integer capacity is one of the adjacent integer populations,
whichever has the larger measured or fitted throughput. When $\beta=0$ and
$\alpha<1$, the curve increases toward the asymptote $\gamma/\alpha$ but has no
finite USL peak. When both parameters are zero, the mathematical model has no
internal capacity limit; a real finite system must eventually reveal an omitted
bottleneck or cease to fit that ideal case.

Figure~\ref{fig:usl-regimes} uses normalized throughput $X/\gamma$. The fitted
example uses $\alpha=0.1$ and, in the third panel, $\beta=0.005$, giving
$n_*\simeq13.42$. Throughput to the right of the marked point declines even as
more clients are added.

Population capacity is not the only overload boundary. For a fixed deployment
with sustainable service rate $\mu$, offered load $\lambda$ is at capacity when
$\lambda=\mu$. Below capacity, a simple queueing illustration has response time
proportional to $1/(\mu-\lambda)$ and queued work proportional to
$\lambda/(\mu-\lambda)$. At and above capacity these steady-state quantities
are unbounded: completed throughput is capped by $\mu$, while unfinished work,
latency, queued bytes, and memory pressure accumulate. A finite queue converts
that growth into blocking or rejection; exhausting the memory budget is a fatal
terminal event rather than another slow sample.

For the queueing foundation behind this illustration---including workload
characterization, service demand, utilization, response time, queueing networks,
and cost/performance tradeoffs---see Menasc\'e, Almeida, and Dowdy's
\emph{Performance by Design}~\citep{menasce2004performance}. USL and a
single queue answer different questions and belong together: USL summarizes
scaling across populations, while queueing models explain how offered work waits
for finite service centers. Neither rescues a requirements model whose demand,
service rates, queue bounds, observation window, and overload behavior were
never stated.

This is why performance belongs in requirements rather than in a post-deployment
incident report. Before implementation, the specification should make it
possible to ask whether forecast demand fits below sustainable capacity, whether
latency and queue bounds remain acceptable, what happens to rejected or blocked
work, how many replicas are affordable, and which failure modes are fatal. The
goal is not to predict every scheduler tick. It is to rule out designs that work
only at toy load and collapse the first time real users arrive.

\section{Outages, recovery, and replica populations}

Reliability assumptions belong to actor specifications and are inherited by
their instances. A contract may set an outage probability and an expected mean
time to repair (MTTR):

\begin{lstlisting}
actor Server
  |>.instances "server-" 2 (roundRobin)
  |>.outageProbability (20 / 10000)
  |>.meanTimeToRepair 45.seconds
\end{lstlisting}

These are specified assumptions. A failed actor does not reliably announce its
own failure: there is no ordinary \texttt{Unavailable} message to receive.
Measurements instead come from evidence visible to an observer. Expected
heartbeats stop arriving; an inbound queue ceases to drain; or messages expected
from the actor's outbound side cease to appear. Each detector must declare its
heartbeat or progress expectation, timeout, clock, observer, and attribution
boundary. Silence without such an expectation is not evidence of failure.

The detector may emit derived observations such as
\texttt{AvailabilityLost} and \texttt{AvailabilityRestored}, but these are
observer conclusions, not protocol messages sent by the failed actor. A loss
observation retains the last known healthy time, the deadline that was missed,
the detection time, and the evidence stream. Restoration retains the first new
heartbeat or queue/message progress that justifies it and backpoints to the loss
observation. The true failure time is generally bounded between the last healthy
observation and detection rather than known exactly. If the declared accounting
policy uses derived boundary times $u_i$ and $r_i$, then for $R$ replicas observed
from $t_0$ through $t_1$, the estimated outage fraction and repair duration are

\[
 \widehat O=
 \frac{\sum_i (r_i.timeAt-u_i.timeAt)}{R(t_1-t_0)},
 \qquad
 \widehat{MTTR}=
 \frac{\sum_i (r_i.timeAt-u_i.timeAt)}{\lvert incidents\rvert}.
\]

Read these as follows.  Estimated outage fraction, $\widehat O$, is the sum
over incidents $i$ of restoration time $r_i.timeAt$ minus outage-boundary time
$u_i.timeAt$, divided by replica count $R$ times window duration $t_1-t_0$.
Estimated mean time to repair, $\widehat{MTTR}$, is that same total outage time
divided by the number of incidents.  A hat marks an estimate from observations.

Availability over the same complete window is $1-\widehat O$. The report must
label whether $u_i$ is the last-known-healthy time, missed deadline, or detection
time; otherwise its outage and MTTR numbers are not reproducible. Both values can
be plotted against time, replica count, offered load, or a deployment policy.
This supports Kubernetes-style experiments in which pods are actor instances,
restarts are recovery events, and changing replica populations yields different
reliability and throughput observations. A configured outage probability or
MTTR is not silently replaced by its observed estimate; comparing them is the
check.

Per-instance uptime is only the first reliability result. Services form a
dependency network, and each dependency gate must say whether its members are
required in \emph{series} or provide redundancy in \emph{parallel}. Let
$u_i(t)\in\{0,1\}$ be the derived up/down indicator reconstructed from one
instance's detector observations and declared boundary policy. For a series gate,
every member must be up:

\[
 u_{\mathrm{series}}(t)=\prod_i u_i(t).
\]

Read this as: ``series availability at time $t$ equals the product, over
instances $i$, of instance $i$'s up indicator at time $t$.''

For a parallel gate, at least one member must be up:

\[
 u_{\mathrm{parallel}}(t)=1-\prod_i(1-u_i(t)).
\]

Read this as: ``parallel availability at time $t$ equals one minus the product,
over instances $i$, of one minus instance $i$'s up indicator at time $t$.''

More generally, a replicated service declares a threshold $k$ and is available
when $\sum_i u_i(t)\geq k$. Its measured availability is the fraction of the
observation window for which that predicate is true. These formulas operate on
synchronized observed indicators, so simultaneous and correlated failures are
preserved. Products such as $\prod_i A_i$ or
$1-\prod_i(1-A_i)$ may estimate expected availability from marginal
availabilities only under an explicit independence assumption; they must not
replace the interval calculation when joint outage observations exist.

A dependency edge points from a consumer service or task to the provider gate
it requires. At each outage boundary, failure propagation repeatedly marks a
consumer unavailable when one of its series requirements is unavailable or
when a parallel/threshold requirement has too few surviving providers. The
fixed point is the cascade for that particular set of failed services. The
report must retain the initiating outage set, every derived unavailable
service, the dependency edge that propagated each failure, affected tasks,
client-visible outcomes, and recovery order. This makes questions such as
``what happens if the database and one authorization replica fail together?''
answerable without pretending that all outages are independent.

The standard reliability output therefore includes per-instance uptime,
series/parallel/threshold service uptime, a time-aligned outage chart, and a
dependency graph overlaid with each observed or proposed failure cascade.
Named service-down scenarios should be replayable even when they have not yet
occurred in production; such a replay is a model prediction and must be labeled
separately from measured uptime.

The generated artifact
\texttt{paxos-quorum-shutdown-network.svg} gives a concrete majority-service
example. A Kubernetes-like runtime manages a parallel pool of three stateless
web actors; the one-of-three web pool is in series with a two-of-three
database-replica gate. Each web actor has specified uptime $9999/10000$; each
replica has specified uptime $999/1000$. If replica outages were independent and each replica had
uptime $p$, the quorum's assumed uptime would be

\[
 A_{2\text{-of-}3}=3p^2(1-p)+p^3.
\]

Read this as: ``two-of-three availability equals three times the probability
that exactly two replicas are up, $p$ squared times one minus $p$, plus the
probability that all three replicas are up, $p$ cubed.'' This calculation is
only an independent-marginal baseline. It does not describe an operator who
deliberately stops correlated members.

The named shutdown cascade first stops \texttt{kv-1}. Two voters remain, so the
successful first maintenance action appears to confirm that the cluster is
redundant. Stopping \texttt{kv-2} next leaves \texttt{kv-3} running but destroys
the majority: the quorum gate and the web-plus-quorum series path become
unavailable. This is the operational trap familiar from ZooKeeper-backed Kafka
deployments and Paxos- or Raft-like services. ``A database process is still
up'' is not the service predicate; ``a majority of the configured voting set is
available and mutually communicating'' is. Planned shutdowns, shared power,
network partitions, and common automation are correlated failures and must be
replayed as named sets rather than hidden inside multiplied uptime percentages.
The runtime may create arbitrarily many healthy stateless web instances without
creating another database vote. Autoscaling the parallel web tier therefore
cannot repair the failed serial quorum gate; it may merely increase the number
of requests waiting on that unavailable dependency.

An actor inferred unavailable produces no observed heartbeat or outbound
protocol progress and does not drain its observed inbound queue. Work waiting on
it remains stalled, is rejected, or ends in an explicit timeout/cancellation
outcome according to the requirement. An ordinary send or receive attributed to
that instance after a detector's loss boundary is evidence that either recovery
occurred or the detector/attribution model was wrong; it is not silently discarded
as an invalid trace. Thus an outage commonly falsifies a nominal liveness promise
(for example, ``every accepted request eventually receives a response'') even
when safety remains intact.

The nominal protocol language and its failure extension must therefore be
distinguished. The nominal language describes ordinary successful and rejected
conversations. The failure extension adds heartbeat expectations, queue and
message-progress observations, derived availability boundaries, stalled or
censored work, explicit failure outcomes, and legal resume/retry behavior.
Cascade analysis suppresses modeled progress for every instance inferred
unavailable at the dependency fixed point, then reports which
nominal safety and progress properties remain true, become false, or cannot be
decided before the observation window closes.

The same dependency graph supports denial-of-service analysis. A PageRank-like
centrality calculation, with dependency edges directed toward the consumers
whose operation they enable, highlights nodes whose failure influence is
reinforced by other important services. Edge weights may incorporate observed
message traffic, affected task value, or measured cascade frequency, but the
chosen weighting is part of the requirement and must be shown in the report.
Centrality is a prioritization heuristic, not an availability proof: ordinary
PageRank can miss a low-traffic series dependency, a cut vertex, or the exact
number of replica failures that crosses a quorum threshold. The denial-of-
service report therefore places the centrality ranking beside single-node and
named multi-node cascade simulations, minimal service cut sets, lost task
capacity, and client-visible outcomes. This answers both ``which node looks
important?'' and the stronger question ``what actually stops if an attacker
makes this set unavailable?''

\section{Infrastructure cost and demand-constrained supply}

A running service has at least two distinct time-based costs. Hardware is paid
for while an instance is provisioned, whether or not the service is healthy.
The service may also have a license, managed-service, or operational cost for
each hour it is available. Those are not task-event costs and must not be
multiplied by request count:

\begin{lstlisting}
cost Server
  |>.hardwarePool "general-purpose"
  |>.hardwareCostPerProvisionedHour 12 USD.cent
  |>.serviceCostPerAvailableHour 3 USD.cent
  |>.sustainableCapacityPerHour 3600000 bytes
\end{lstlisting}

For $R$ replicas, provisioned hours $H_r$, available hours $A_r$, hardware rate
$c_h$, and service rate $c_s$, the accounting-period infrastructure cost is

\[
 C(R)=\sum_{r=1}^{R}(H_r c_h + A_r c_s).
\]

Read this as: ``cost at replica count $R$ equals the sum from replica index
$r=1$ through $R$ of provisioned hours $H_r$ times hardware rate $c_h$, plus
available hours $A_r$ times service rate $c_s$.''

Supply planning is a constrained optimization, not merely ``pick the cheapest
server.'' Let one replica sustain $\mu$ completed work units per hour, let $a$
be the required availability fraction, and let $D$ be the work rate that must
complete within the declared latency boundary. A candidate replica count is
feasible for demand $D$ only when

\[
R\mu a \ge D.
\]

Read this as: ``replica count $R$ times per-replica completed-work capacity mu
times required availability fraction $a$ must be at least required completed
demand $D$.'' This inequality is necessary but not sufficient: routing
imbalance, queueing, and latency can still make the observed system infeasible.

For total offered rate $\lambda_o$ routed across $R$ servers, let
$\lambda_{o,r}$ be the rate offered to server $r$:

\[
 \lambda_o=\sum_{r=1}^{R}\lambda_{o,r},
 \qquad
 \lambda_{o,r}=\frac{\lambda_o}{R}\ \text{only under ideal balance}.
\]

Read this as: ``total offered rate lambda sub $o$ equals the sum, from server
index $r=1$ through server count $R$, of the rate offered to server $r$; under
ideal balance only, each server's offered rate is total offered rate divided by
$R$.'' Handled work must still be measured at each completion boundary; neither
formula says that the offered work completed.

With an ideally balanced routing policy, the nominal demand on each server is
therefore $D/R$. Spawning more homogeneous servers lowers nominal average
per-server demand. That statement alone cannot choose a replica count: every added server
also adds provisioned hardware cost and, while healthy, service cost. The useful
graph places $D/R$, observed load for each concrete instance, effective supply,
and total hourly cost on the same replica-count axis.

LeanFM enumerates the declared finite set of permitted replica counts, rejects
infeasible points, and chooses the remaining point with minimum expected hourly
cost $R(c_h+a c_s)$. The derived XY artifact plots demand, effective supply, and
cost against replica count and marks the feasible optimum. It also reports
headroom and rejected demand so an apparently cheap under-supplied plan cannot
win. The average $D/R$ is not a promise of balance. Routing policy matters here:
shard hashing can create a hot shard even when
aggregate supply exceeds demand, while sticky routing and round-robin make
different balance assumptions. Product-specific replication, reserved pricing,
autoscaling delay, and nonlinear volume tiers require additional declared
constraints rather than silent arithmetic.

Server count by itself is not a scalability result. An unbounded thought
experiment can pair unbounded offered work with unbounded servers, backlog,
cost, and latency; it says nothing useful about work completed within a finite
deadline. A valid capacity claim fixes a finite observation window and reports
offered, admitted, completed, rejected, and still-outstanding work together
with latency, server count, utilization or imbalance, and cost. ``Handled''
means completed within the declared outcome and latency boundary, not merely
accepted somewhere in an arbitrarily large system.

\section{Specified dwell time}

A specification may attach a dwell time to an event step or to a named production.
The dwell is a duration on the same monotonic time scale as event clocks:

\begin{lstlisting}
emit "token requested" [field "code" code]
  |>.dwell 3.milliseconds

include exchangeAndFetch
  |>.dwell 12.milliseconds
\end{lstlisting}

Taking a step with dwell $d$ advances the model clock from $t$ to $t+d$ before
timestamping the event that completes the step. A production dwell constrains the
elapsed time between its entry and exit boundary events; it does not assign the
same dwell independently to every contained event. Exact values, bounded ranges,
or weighted dwell outcomes may be used when the corresponding timing information
is available.

Dwell is part of the specification, so it can drive latency, throughput, timeout,
and queue-pressure calculations. It does not create event order:
\texttt{priorIds} supplies the predecessor relation, while the grammar separately
states why a sequence or dependency is legal.

\section{Estimating completion from an event stream}

The same specification can consume observed events. A terminal event of any kind
names its corresponding start event in its backpointer list. The reducer follows
that identity rather than guessing from adjacency or selecting the first open
\texttt{(session, task)} attempt. Each matched pair yields a task attempt:

\begin{lstlisting}
structure TaskAttempt where
  key       : WorkKey
  started   : Event
  completed : Option Event
  outcome     : Option TaskOutcome

def latency (attempt : TaskAttempt) : Option Duration :=
  attempt.completed.map fun completed =>
    completed.timeAt - attempt.started.timeAt
\end{lstlisting}

For an observation window containing $M$ starts, $C$ matched terminal events,
$S$ successful terminals, and completed latencies $L_1,\ldots,L_C$, the basic
estimates are
\[
  \widehat P(\text{complete}) = \frac{C}{M}, \qquad
  \widehat P(\text{success}\mid\text{complete}) = \frac{S}{C}, \qquad
  \widehat E[L\mid\text{complete}] = \frac{\sum_i L_i}{C}.
\]

Read these as follows.  Estimated completion probability is completed count
$C$ divided by started count $M$.  Estimated success probability conditional
on completion is successful count $S$ divided by completed count $C$.
Estimated latency conditional on completion is the sum of completed latencies
$L_i$, over completed attempts $i$, divided by $C$.  The vertical bar is read
``given,'' and each hat marks an estimate from the observation window.

Attempts without a terminal event remain \emph{in flight}. They contribute to the
number started and to queue/load measurements, but not to completed-task latency
or to the conditional success denominator. Calling them failures would bias both
probability and latency whenever the observation window ends before they do.

The reducer can group these sufficient statistics by task, actor, time bucket,
maximum concurrency, or queue occupancy and feed them directly to pie, time-series,
and XY plots. Specified probabilities and dwell times are therefore predictions;
stream-derived estimates provide measurements against which those predictions can
be checked.

In the executable reducer, an entry event opens a \texttt{TaskAttempt}, progress
events leave it open, and a success or failure event closes the open attempt with
the same \texttt{(session, task)} key. The resulting attempts feed the estimates
above.

\section{Composing requirements means intersecting constraints}

\index{composition!requirement intersection}
Scenario composition builds behaviour in familiar language-theoretic ways:

\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
Operator & Language operation & Purpose \\
\midrule
\texttt{then a b} & concatenation & $a$ happens before $b$ \\
\texttt{oneOf [a,b]} & union & either story is legal \\
\texttt{together a b} & shuffle/interleaving & independent concurrent stories \\
\texttt{repeat a} & closure & repeated conversation \\
\texttt{where\_ p a} & trace filtering & context-sensitive legality \\
\bottomrule
\end{tabular}
\end{center}

Combining requirements is subtler. A requirement usually does not add another
message sequence; it removes histories that violate a concern. Therefore
\texttt{requireAll} denotes intersection of accepted trace sets.

\begin{lstlisting}
def quoteSystem : SystemSpec :=
  generatedBy quoteOutcome
  |> requireAll
      [ correlate "offered quote matches request"
          (sameField "requestId")
      , forbid "confirmation without acceptance"
          (event "order confirmed" && notPreviously "quote accepted")
      , ctl "every accepted quote is answered"
          (AG (accepted --> AF (confirmed || rejected)))
      , timing "answer within service objective"
          (accepted --> within 2.seconds (confirmed || rejected))
      ]
\end{lstlisting}

This distinction prevents an important category error: union and concatenation
assemble possible stories; intersection layers independent obligations over those
stories. A system is consistent only if the intersection remains nonempty. When it
is empty, tooling should return a minimal conflicting set of requirements and the
shortest available counterexample prefix.

\section{Charts are declarative trace reductions}

\index{chart specification}
Charts are also specified in the Lean subset. A chart names an observable event
source, a grouping or $x$ expression, and an aggregate or $y$ expression. It does
not contain rendering code.

\begin{lstlisting}
def outcomeShare : ChartSpec :=
  pie "quote outcomes" do
    source events
    where_ (kind == "quote accepted" || kind == "quote declined")
    groupBy kind
    value count

def responseLatency : ChartSpec :=
  line "quote response latency" do
    source (correlate events by "quoteId")
    x clock
    y (elapsed "quote offered" "customer decision")
    series "p50" median

def latencyByConcurrency : ChartSpec :=
  xyplot "latency by concurrent sessions" do
    source completedRuns
    x maxConcurrentSessions
    y (mean (elapsed firstEvent terminalEvent))

def queueByOfferedLoad : ChartSpec :=
  xyplot "queue occupancy by offered load" do
    source completedRuns
    x requestsPerSecond
    y (mean totalQueueOccupancy)

def propagatedGrantProbability : ChartSpec :=
  xyplot "user probability propagated through deterministic servers" do
    source parameterSweep
    x userGrantProbability
    y terminalGrantProbability
\end{lstlisting}

An XY plot preserves two numeric axes. It differs from a time series, whose
$x$-axis is specifically an event clock, and from a categorical chart, whose
$x$ values are labels. The first two examples reduce each completed model run to
one point. The third sweeps a model parameter and checks that deterministic
downstream processing transports the user's probability mass.
