\section{The grammar represented by events}

Bread is not baked in response to an individual order. A predictable schedule
creates batches by bread kind; each batch is baked, shipped before opening, and
stocked at the storefront. Customer orders reserve fresh inventory from those
lots. After the declared two- or three-day freshness window, remaining units
move to a charity rack and produce a donation receipt. An
\texttt{InventoryReserved} event names both the paid order and the stocked batch
lots that supplied it, making FIFO allocation, age, quality, and stockouts
replayable. No event permits a customer to wait for a same-day custom loaf.

The truck is a bounded FIFO queue. \texttt{ShipmentEnqueued} records its queue
position and capacity; \texttt{ShipmentDequeued} backpoints to both the matching
enqueue and the preceding dequeue. The retail interaction begins only after
\texttt{ShipmentDequeued} has added the batch to storefront inventory.

For each calendar-day bucket $d$, the reducer computes

\AccessibleEquation{Gross sales on day d equals the sum of amounts on Sale Completed events. Refunds on day d equals the sum of refund values. Net revenue equals gross sales minus refunds. Ingredient cost equals the sum of ingredient costs on Batch Baked events. Donation value equals the sum of eligible values on Donation Receipt Recorded events. Employee pay equals the sum of pay on Shift Paid events. Profit equals net revenue minus ingredient cost minus employee pay.}{\begin{align*}
\operatorname{grossSales}_d
  &= \sum_{e.kind=\mathrm{SaleCompleted}} e.amount,\\
\operatorname{refunds}_d
  &= \sum_e e.refund,\\
\operatorname{netRevenue}_d
  &= \operatorname{grossSales}_d-\operatorname{refunds}_d,\\
\operatorname{ingredientCost}_d
  &= \sum_{e.kind=\mathrm{BatchBaked}} e.ingredientCost,\\
\operatorname{donationValue}_d
  &= \sum_{e.kind=\mathrm{DonationReceiptRecorded}} e.eligibleValue,\\
\operatorname{employeePay}_d
  &= \sum_{e.kind=\mathrm{ShiftPaid}} e.pay,\\
\operatorname{profit}_d
  &= \operatorname{netRevenue}_d-\operatorname{ingredientCost}_d
     -\operatorname{employeePay}_d.
\end{align*}}

Read every line at day $d$.  Gross sales is the sum of amount on events $e$
whose kind is SaleCompleted; refunds is the sum of each event's refund;
net revenue is gross sales minus refunds; ingredient cost is the sum of
ingredient cost on BatchBaked events; donation value is the sum of eligible
value on DonationReceiptRecorded events; employee pay is the sum of pay on
ShiftPaid events; and profit is net revenue minus ingredient cost minus
employee pay.  The subscript $d$ means that every sum and result is restricted
to the same calendar-day bucket.

Donated bread is already part of batch ingredient cost, so subtracting it again
would double count. Donation value is not revenue and is not itself a tax
saving. The tax effect is calculated only after the applicable rules and rate
are supplied. This modeled profit excludes other costs for which the stream has
no event.

\section{XY plots as questions over scenarios}

The XY chart is not restricted to time on the horizontal axis. The reducer also
generates daily order count against daily profit:

  xlabel={orders placed in day},ylabel={profit (dollars)},grid=major,
  scaled ticks=false]
  \addplot[only marks,color=leanblue,mark=*]
    coordinates {\BakeryOrdersProfitCoordinates};
\end{axis}
\end{tikzpicture}
\caption{Daily order volume against profit. Each point is one day reduced from
the event corpus.}
\label{fig:bakery-orders-profit}
\end{figure}

The same mechanism can measure many scenarios: offered load against latency,
staffing hours against profit, price against cancellation probability, queue
capacity against completed orders, or waste against bake batch size. In each
case the axes are named reductions over event streams. A parameter sweep produces
several streams; observed operation supplies streams from different days. The
chart renderer need not know which kind it received.

The old made-to-order order-lifetime statistic is intentionally absent. Useful
service metrics are payment and inventory-reservation time, storefront
fulfillment time, stockout rate, inventory age at sale, freshness-window
sell-through, and units and eligible value transferred to charity.

\section{A code-generation boundary}

The intended code-generation boundary uses durable files, not the conversation
that produced them. Let $R$ be \texttt{Requirements.lean}, $I$ be
\texttt{Implementation.lean}, $P$ the protobuf schema, and $C_k$ an optional
existing implementation:

\AccessibleEquation{Requirements R and implementation I and protobuf schema P generate initial code C zero. Requirements R and implementation I and protobuf schema P and code revision C sub k generate revision C sub k plus one.}{\[
  (R,I,P) \longrightarrow C_0,
  \qquad
  (R,I,P,C_k) \longrightarrow C_{k+1}.
\]}

Initial generation uses $(R,I,P)$; revision also receives $C_k$ so conforming
code can be retained. Missing decisions must be reported rather than recovered
from chat. This is the intended boundary, not a claim that the bakery sketch
below was generated or that the complete code-generation pipeline is implemented.

The general conformance target is that generated units carry machine-readable
requirement references and justifications, with a manifest linking IDs to
files, symbols, and tests. Current validation checks requirement references in
implementation mappings; symbol-level validation of generated code remains a
separate requirement. The grammar should supply legal-trace tests, reject
mutations outside its language, and pair byte round trips with the mapped
implementation.
