\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

LeanFM is a way of building software by arguing about it first. You describe
what a system should do in ordinary language; an LLM turns that into precise
requirements; and LeanFM checks those requirements and shows you what they
mean---as sequence diagrams, state machines, event traces and counterexamples.
You push back, the requirements change, and the pictures change with them.
Only when you are satisfied does any code get written.

The precise part is Lean. Every requirement is a Lean definition: which actors
exist, which messages they exchange down to the protobuf bytes, which orders of
messages are legal, and what must always or never happen. Because these are
definitions rather than prose, they can be checked, and the diagrams are
generated from them rather than drawn by hand. When two requirements
contradict each other---say $A$ must reference $B$, $B$ needs a $C$, and policy
forbids that $C$---LeanFM finds the contradiction before anyone builds it.

Not everything worth requiring is a message on a wire. Some requirements are
about values and relationships, such as an identifier that must refer to a
real object. LeanFM states those as predicates in the requirements and then
says, in a separate implementation mapping, how the code will enforce them.
Requirements over hidden state that no observer can see are flagged, so they
can be restated in terms of events that can actually be tested.

\section*{Three layers, reviewed in git}

Work proceeds in three layers: first the \emph{requirements}, the observable
behaviour and the views generated from it; then the \emph{implementation
mapping}, how each requirement will be realized and tested; then the code,
written in one pass. Each layer is checked by LeanFM before the next is built
on it. Review is what you already do with git: you read the diff and commit it.
LeanFM has no approval step of its own and never makes you click to continue.
A passing check is evidence for your review; it is not the review.

\section*{Nothing lives only in the chat}

A conversation with an LLM is temporary. Everything that matters is written
into the project: the book, the requirements, the protobuf schema, the
implementation mapping and the source. Each project has one directory that
holds all of its state, so you can delete the conversation, delete a project,
or start a new session and pick up exactly where the files leave off. This
repository is itself such a project; the book you are reading is part of its
specification and is read by the agents that work on it.

\section*{How to read this book}

Chapter~\ref{ch:vision} sets out the method. The chapters that follow build it
up: events and scenarios, a worked bakery example, the grammar that describes
legal message orders, and the authoring language. Chapter~\ref{ch:web-server}
covers the LeanFM server, including the MCP interface that lets an agent
consult LeanFM's logic directly. Later chapters apply temporal and modal logic
to security and legal examples, and Chapter~\ref{ch:bootstrap-contract}
defines exactly how a new project is set up.

LeanFM is a working draft. The method and its tools are still changing, and
the book records what exists today alongside what is planned; where it makes
a claim, the evidence labels in Chapter~\ref{ch:vision} say what kind of
evidence stands behind it---compiled, tested, proposed or planned. The source is public \citep{leanfmrepo}.
