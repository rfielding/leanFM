\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

This book is about \emph{Requirements Logic}: a way to say what a system must do, usually a
piece of software, precisely enough that a machine can check it. Think of it as a
\emph{Temporal Lean}. Lean checks that a proof proves what it claims. Requirements Logic
checks claims about behaviour over time: what may happen next, what must happen eventually,
and what must never happen.

It has two halves, and each has a plain job.
\begin{itemize}
\item A \textbf{protocol} says who sends what to whom, in what order, and where the
  conversation branches. ``The browser asks for an image; the server answers with the image
  or with not-found.'' The textbooks call this a \emph{session type}; it is easy to write and
  easy to draw.
\item A \textbf{claim} says what may or must happen next, from any moment of the
  conversation. ``Every request is eventually answered.'' ``No refund before a charge.''
  The textbooks call this \emph{CTL}, a logic of the future; it is easy to check, combine
  and extend.
\end{itemize}
The claims come down to a handful of everyday words, all made from one function. The
function says ``this holds until that comes'', and it is asked about \emph{every} future or
about \emph{some} future; that one choice, every or some, is all the logic adds to ordinary
and, or and not:
\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
word & meaning \\
\midrule
\textsf{possibly} $p$ & in some future, $p$ happens \\
\textsf{inevitably} $p$ & in every future, $p$ happens \\
\textsf{eventually} $p$ & the same as \textsf{inevitably} $p$ \\
\textsf{always} $p$ & in every future, $p$ holds at every moment \\
\textsf{never} $p$ & in every future, $p$ holds at no moment \\
\textsf{someAlways} $p$ & in some future, $p$ holds at every moment, forever \\
\bottomrule
\end{tabular}
\end{center}
Anything these words can say, Requirements Logic can say and check, and nothing more is
needed: Chapter~\ref{ch:checker} writes the function and builds every word from it on one
page.

\medskip
\noindent\fcolorbox{leanblue}{diagramblue}{\parbox{\dimexpr\linewidth-2\fboxsep-2\fboxrule\relax}{%
\color{foregroundink}\textbf{Features need strong implication. Security guarantees need weak implication.}

\smallskip
A feature is required with \emph{strong} implication:
\begin{center}
\texttt{(stronglyImplies a b)} \;=\; \texttt{(and (possibly a) (always (implies a b)))}
\end{center}
``A request can be made, and every request is answered.'' The trigger \texttt{a} must be able
to happen. A system that never lets anyone make the request fails the requirement, instead of
passing it for free. The usual shape is \texttt{(leadsTo a b)}, the same as
\texttt{(stronglyImplies a (eventually b))}.

\smallskip
A security guarantee is required with \emph{weak} implication:
\begin{center}
\texttt{(weaklyImplies a b)} \;=\; \texttt{(always (ifEver a b))}
\end{center}
Here \texttt{(ifEver a b)} is \texttt{(implies a b)}, marked so that \texttt{a} never
happening is fine. ``Whenever someone logs in, they gave the right password.'' A system in which no one can ever
log in passes, as it should: a door that never opens lets no one in.

\smallskip
The difference is \textsf{possibly}: some future reaches \texttt{a}. That is a claim about
branching futures, and LTL, which speaks only of every path, cannot make it. This is why
requirements need CTL. Plain \texttt{(always (implies a b))} is neither: when \texttt{a} cannot
happen, LeanFM reports it as vacuous, not proved.}}
\medskip

The book's central result joins the halves: a protocol \emph{is} a short list of claims,
one per moment the conversation can be in, and a system obeys the claims exactly when it
behaves as the protocol says. So one language does both jobs. The protocol is what people
write and look at; the claims are what the machine checks; and any rule a diagram cannot
show is added as one more claim in the same language.

This is a different approach from the usual one. Most tools for checking behaviour model
the inside of each process: its variables, its counters, its locks. Requirements Logic
models only what can be observed: the messages, as a log records them. A claim reads the
message just delivered and whether the conversation may stop, and nothing else; no variable
of any implementation appears in it. The state does not disappear: it moves into the
observable protocol. Where the conversation is (what has been said, what may come next) is
the state, and the messages show it, so a log is enough to know it. Observed behaviour is messier than one process's
state, because conversations fork into child conversations that run at once and later join
again, and the logic is built for exactly that (Chapter~\ref{ch:where}). It follows that systems with identical observable behaviour are indistinguishable: a claim
true of one is true of the other, however differently they are built (Chapter~\ref{ch:checker}).
Identical here means the same messages \emph{and} the same choices still open at every
moment, so a system that decides early is told apart from one that decides late, even when
their logs could be the same (Chapter~\ref{ch:deciding}). That is what makes a port
safe. To move a program from Rust to Zig, go through the specification: port from Rust to
the protocol and its claims, checked against the Rust program's logs, then from the
specification to Zig, checked against the same claims. When both pass, nothing observable
can tell the two programs apart, though they share no code. In return, every
claim is a requirement anyone can check against a real log, and how to build the system is
left to whoever builds it.

The parallel with Lean goes further. A requirement is a statement; an implementation is
evidence that it holds, such as a log that follows the protocol, or a test; and a
requirement nobody can state precisely yet is \texttt{sorry}: admitted, counted and shown,
never silently assumed. Every requirement and every implementation choice is an entry in a
list, and every entry becomes claims or says that it does not yet (Chapter~\ref{ch:lists}).

Requirements Logic is meant to be driven by LLMs. A person argues about what the system
should do; an LLM writes the protocols, the claims, the implementation and its code; and
LeanFM, the tool this book describes, checks every step, so nothing the LLM writes has to be
trusted. The LLM reaches LeanFM through the Model Context Protocol (Part~\ref{part:mcp}) and
asks it the questions this book asks.

The book has four parts. Part~\ref{part:language} is the protocol language of
LeanFM: global types, their projection onto each role, and the where clauses that
tie messages to the data that implements them. Part~\ref{part:ctl} turns a
protocol into claims, shows that nothing is lost, takes it construct by construct,
and shows how to check it in time close to linear. Part~\ref{part:lists} puts that to
work: a project's requirements are an actual list, and so is each implementation, and
every entry of both becomes claims or says plainly that it does not yet, the way
\texttt{sorry} does in Lean. Part~\ref{part:mcp} is the
LeanFM server: an agent such as Claude connects to it over the Model Context
Protocol and asks every question in this book, with the answers shown as they
arrive.

Every listing, diagram, table and answer in this book comes from LeanFM, through
the same functions its tools call; the generator, \texttt{CtlBookExample.lean},
names its inputs in a provenance file beside what it writes. Every listing of LeanFM
text passes LeanFM's checker as printed, so every name in it is defined in it; a listing
whose first line is \texttt{-- from} \emph{file} is an excerpt, and the whole file is
checked instead. The proofs are on paper, and LeanFM's tests check the implementation against them: the fast
checker against the plain definitions on every word of the logic, and the faithfulness check
against the claim checker on broken copies of real protocols. The source is public
\citep{leanfmrepo}.
