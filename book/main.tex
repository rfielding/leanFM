\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

LeanFM is a programming language whose programs are protocols. A protocol names
the roles in a conversation, the messages between them and their order, who
decides at each choice, what is assumed about decisions nobody else can see, and
what the system promises. Everything else in a LeanFM project is generated from
the protocol or checked against it: the diagrams people read, the requirements
and implementation mapping reviewed in git, the interfaces, the code each role is
written on, and the verdicts on what the running system logs.

Most LeanFM is written by an LLM. A person says in ordinary words what the
software must do; the model writes the protocol; LeanFM checks it and shows what
it means, as diagrams, obligations, witnesses and counterexamples. The person
pushes back, the protocol changes, the pictures change with it, and only then is
code written. The model learns the language from LeanFM itself: its server speaks
the Model Context Protocol and hands any agent that connects the language
reference and the tools.

The language starts from multiparty session types, one global description of a
conversation from which each role's obligations are derived
\citep{honda2008multiparty}. To that it adds stated assumptions on hidden
decisions, time and value on messages, promises judged over observation periods,
temporal questions answered with paths, and attackers who see every channel.

\section*{How to read this book}

Part~I is the language: what a protocol says (Chapter~\ref{ch:language}), what it
means (Chapter~\ref{ch:meaning}), its assumptions and promises
(Chapter~\ref{ch:assumptions}), the questions you can ask it
(Chapter~\ref{ch:questions}), and executions as event streams
(Chapter~\ref{ch:execution}). Part~II is what a protocol generates and how the
outputs are reviewed. Part~III works examples end to end: a bakery with declared
and measured rates, TFTP and its physics, OAuth, a legal settlement, and security
protocols. The appendices list the MCP tools and the server's own protocol, and
define how a new project is set up.

Every listing, diagram and verdict in Part~I comes from LeanFM, through the same
functions its tools call; the generator is named beside each. What LeanFM does not
yet do is listed in \texttt{CRITIQUE.md}. The source is public \citep{leanfmrepo}.
