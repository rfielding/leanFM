\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}
LeanFM is a software-engineering methodology for arguing requirements into
existence with an LLM. Stakeholders challenge assumptions, add scenarios and
constraints, and inspect generated diagrams, traces and measurements. The
argument produces durable project artifacts rather than relying on chat memory.

The book is the main artifact. Every project begins with \texttt{./book/main.pdf}:
its purpose, vocabulary, boundaries, examples and design argument. It acts as a
maintained, project-specific section of the LLM's system-prompt context, whether
supplied directly or discovered through the agent interface. Final diagrams come from the specification
and are reused in the book, not maintained as separate designs.

The book is itself vibecoded: missing views, checks and editing tools are built
as the argument needs them. Each project owns one directory containing its book,
specifications, schemas, conversations, source, tests and generated artifacts.
Copying that directory preserves the project; deleting it removes its local
state. External deployments require explicit teardown.

This repository is also a LeanFM project. Its book, specifications and source
are the inputs used to develop LeanFM itself. Other projects can be copied into
their own repositories and opened in Codex without reconstructing the conversation.

\texttt{book/main.pdf} remains a central input in Codex; \texttt{book/main-dark.pdf}
is its accessible rendering from the same source. Requirements and implementation
specifications have stable project-relative paths. Each revision identifies one
canonical implementation specification; deliberate alternatives name their targets.

The workflow has two acceptance gates. First accept \texttt{Requirements.lean}:
observable behavior, legal conversations and properties. Then accept
\texttt{Implementation.lean}: runtime, transport, actor, file and test mappings.
These specifications refine the book. Together with the current repository, they
are intended to support one complete, reviewable PR. ``One-shot'' describes this
implementation pass; requirements discovery remains iterative. The integrated
requirements-to-PR workflow is still under development.

This differs from software engineering organized primarily around coordinating
people who debate separate drawings. LeanFM centers the shared, executable account
of the design and records communication between actors down to the bytes represented
by protobuf objects. Parameterized multiparty grammars describe legal message
sequences; generated views let people reason about them; and Lean theorems check
their consistency. Many important requirements, however, are not themselves
observable messages. Security properties, referential integrity, and constraints
between protobuf objects also belong in the theory. Protobuf has no standard
foreign-key mechanism: it can encode an identifier and field presence, but it
neither declares that the identifier resolves to another object nor enforces what
must exist. Those relationships are predicates over decoded objects and reachable
system states, stated and proved as Lean theorems in the requirements specification.
The implementation specification must then identify the storage, transaction, or
validation mechanism that preserves each theorem.

For example, if $A$ carries an identifier for $B$, every reachable $A$ may be
required to resolve to an existing $B$. If $B$ in turn requires a $C$, while policy
disallows every admissible $C$, Lean should expose that the predicates are jointly
unsatisfiable: $A$ cannot consistently exist. The design must change, perhaps by
making the relationship to $C$ optional or by changing the policy. Such
contradictions are requirements discoveries even when no new wire event reveals
them; they are not foreign-key declarations hidden in a \texttt{.proto} file.

Formal methods should therefore be the easy way to build software. This working
book develops that claim into a practical method, while the LeanFM repository
contains the evolving language, tooling, examples, and implementation
\citep{leanfmrepo}.
