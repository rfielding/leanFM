\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}
LeanFM is a software-engineering methodology for arguing requirements into
existence with an LLM. Stakeholders challenge assumptions, add scenarios and
constraints, and inspect generated diagrams, traces and measurements. The
argument produces durable project artifacts rather than relying on chat memory.

The book is the central, project-specific design argument and LLM context;
\texttt{book/main-dark.pdf} is its accessible companion. Generated diagrams
come from the specification and are reused here, not maintained as separate
designs. The Bootstrap chapter defines the project-root inputs and handoff.

A conversation is provisional. The proposed ``Compact and clear conversation''
action checkpoints decisions into the book, grammar, and task constraints, then
clears only the captured message prefix after artifacts and views validate and
the checkpoint is recoverably committed. Failure preserves prior artifacts and
messages; newer messages remain untouched. Compaction accepts neither gate.
Answers attach to their identified questions; the same semantic question is not
repeated unless reopened, though a distinct ambiguity may still be asked.
Ordinary prompts may proceed while a clarification is deferred. The Chat chapter
describes this interaction.

Each project root contains its complete resumable state; this repository is
itself one such project. Example roots live under \texttt{projects/} (the
GoServer book is \texttt{projects/go-server/book/main.pdf}). The Bootstrap
chapter defines stable artifact paths and the two explicit gates: observable
requirements first, then their implementation mapping. Discovery remains
iterative; the intended one-pass implementation is ready only when generated
source passes increasingly realistic in-project tests. That integrated
requirements-to-PR workflow remains under development.

LeanFM centers a shared, executable account of actor communication down to
protobuf bytes. Parameterized multiparty grammars describe legal sequences;
generated views and Lean theorems check the model. Not every requirement is an
observable message: referential integrity and cross-object constraints are
predicates over decoded values and reachable states. Protobuf can encode an ID,
but does not enforce its relationship to another object. Requirements.lean states
and proves such predicates; Implementation.lean maps them to storage, transactions,
or validation. For example, if $A$ must reference $B$ and $B$ requires a $C$ that
policy forbids, the requirements are inconsistent and must change before
implementation.

Chapter~\ref{ch:vision} develops this argument into a practical method; the
remaining chapters present LeanFM's evolving language, tooling, examples, and
implementation \citep{leanfmrepo}.
