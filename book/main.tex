\chapter*{Preface}
\addcontentsline{toc}{chapter}{Preface}

LeanFM is a way of building software by arguing about it first. You describe
what a system should do in ordinary language; an LLM turns that into precise
requirements; and LeanFM checks them and shows what they mean, as sequence
diagrams, state machines, event traces and counterexamples. You push back, the
requirements change, the pictures change with them, and only then is code written.

Its subject is the \emph{behavior} of software at its boundaries: who sends what to
whom, in what order, within what time and with what probability, and what must
always or never happen. The record it keeps is a \emph{multiparty session type},
one global description of a conversation from which each role's obligations are
derived. Session types come from programming-language research, where they
guarantee that no party sends a message the other cannot handle or waits for one
that will never come. LeanFM uses them for messages between network nodes and calls
between APIs alike, and adds what the classic theory leaves out: every queue has a
declared size, and every channel declares how it fails. Messages are lost,
duplicated, reordered and late; timers fire early; a retried request arrives twice.
LeanFM checks the protocol together with those facts.

The precise part is Lean. Every requirement is a Lean definition: the roles, the
messages down to their protobuf bytes, the legal orders, and what must always or
never happen. Definitions can be checked, so diagrams are generated rather than
drawn, and a contradiction (say $A$ must reference $B$, $B$ needs a $C$, and policy
forbids that $C$) is found before anyone builds it. Requirements about values, such
as an identifier that must refer to a real object, are predicates whose enforcement
the implementation mapping describes; requirements over state no observer can see
are flagged, so they can be restated over events that can be tested.

\section*{Three layers, reviewed in git}

Work proceeds in three layers, each checked before the next: the
\emph{requirements} (observable behaviour and its generated views), the
\emph{implementation mapping} (how each requirement is realized and tested), and the
code, written in one pass. Review is what you already do with git: read the diff
and commit it. A passing check is evidence for that review, not the review itself.

\section*{Nothing lives only in the chat}

A conversation with an LLM is temporary. Everything that matters is written into
the project's one directory: the book, requirements, protobuf schema,
implementation mapping and source. Delete the conversation or start a new session
and work resumes from the files. This repository is such a project, and this book
is part of its specification, read by the agents that work on it.

\section*{How to read this book}

Chapter~\ref{ch:vision} sets out the method. Then come events and scenarios as
recorded runs, a worked bakery example, global types as grammars, TFTP (where
declaring the physics turns a perfect session type into a famous bug) and the
authoring language. Chapter~\ref{ch:web-server} covers the server and the MCP
interface through which an agent consults LeanFM's logic. Later chapters apply
temporal and modal logic to security and legal examples, and
Chapter~\ref{ch:bootstrap-contract} defines how a new project is set up.

LeanFM is a working draft. The book records what exists alongside what is planned,
and the evidence labels of Chapter~\ref{ch:vision} say what stands behind each
claim. The source is public \citep{leanfmrepo}.
